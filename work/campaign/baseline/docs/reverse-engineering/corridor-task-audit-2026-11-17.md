**Подтверждённая цепочка задач.**

Автоназначение `evt_autoprod_dig` сохраняет `current_worktask="dig"` и позицию, затем включает `work_auto` (`Z/z_events.tcl:1514–1538`). `work_auto` кладёт `dig_starttask` в очередь (`Z/z_work_states.tcl:125–128`); `work_dispatch` извлекает и выполняет её голову (`:13–21`). Прямое назначение игроком также кладёт `dig_starttask`, через `evt_task_dig` (`Z/z_events.tcl:1039–1054`): это пригодная исходная точка для первого работающего исполнителя без новой системы AI.

`dig_starttask` вызывает `gnome_announce_dig`, `get_digedge`, затем `vector_fixdig`; при подходящей кромке ставит `walk_pos_dig` и `dig_continue` (`Z/z_dignwalk.tcl:136–163`). Продолжение вызывает `dig_next`, проверяет соседей, при необходимости переставляет гнома, выбирает инструмент и `dig_anim` (`:205–289`). В `dig_check` нужны хотя бы две из трёх направленных соседних точек с `h < 13` (`:166–182`). После анимации выполняется вероятностный `dig_execute` → `dig_apply` → следующий цикл; при отсутствии продолжения — `dig_resetid` и `work_idle` (`:284–289,295–382`; `Z/z_procs.tcl:195`). Один callback может сделать несколько попыток/изменений при достаточном опыте (`Z/z_dignwalk.tcl:314–377`), поэтому равенство «одна анимация = ровно одна изменённая точка» также не доказано.

**Подтверждено: центр указателя → начало четырёх samples.** Обработчик ввода передаёт в `0x5680B0` три float из native cursor vector, затем использует возвращённый вектор без дополнительного X/Y-сдвига (`0x530232–0x530266`, `0x5303C7–0x530415`). При внутреннем состоянии `0`:

```text
S4(p) = 4 * floor((p + 0.5) / 4) + 1.5       # отдельно X и Y
A = (S4(px), S4(py))                        # центр начала штриха
O = (trunc(A.x), trunc(A.y)) = A - (0.5, 0.5)
samples = { O, O+(1,0), O+(0,1), O+(1,1) }   # до обрезки/отказа валидатора
```

`S4` доказана в `0x5680C7–0x568175`; `floor` — вызов `0x6F6DA0`, его реализация `0x6F6DE0–0x6F6E9C`. Нативные SSE-операции выполняются в float32; аргумент `floor` расширяется из float32 в double. `0.5`, `0.25`, `4.0`, `1.5` читаются соответственно из `0x73708C`, `0x737058`, `0x7374A0`, `0x7371C0`. Начало сохраняет **тот же** центр в `this+0xE4/E8/EC` и конец в `this+0xF0/F4/F8`, выставляя `this+0xE0=1` (`0x5664F0–0x566538`). При подтверждении `cvttss2si` переводит эти центры в целые координаты, затем предел обхода получает `+2` (`0x56657A–0x5665C0`). Именно отсюда следует `O=A−0.5`; это не подобранный отступ. Для положительных полуцелых центров `trunc = floor`.

| Исходный `p` по одной оси | Центр `S4(p)` | Координаты samples по этой оси |
|---|---:|---|
| `0.01`, `3.49` | `1.5` | `1, 2` |
| `3.5`, `7.49` | `5.5` | `5, 6` |
| `7.5`, `9.2` | `9.5` | `9, 10` |

Например, исходный указатель `(3.5,9.2)` даёт центр `(5.5,9.5)` и **ровно** `{5,6}×{9,10}` до валидации. В общем случае центр `4k+1.5` выбирается при `p ∈ [4k−0.5,4k+3.5)` с оговоркой о float32 на границах. Предварительный `floor(raw_p)` уничтожает эту информацию: `p=3.49` и `p=3.5` попадают в разные штампы, хотя имеют одинаковую целую часть.

**Подтверждено: drag использует начальный anchor, а не предыдущую точку.** В ветке `state != 0` сначала вычисляется `C = S2(raw_p)`, где `S2(p) = 2*floor((p−0.5)/2)+1.5` (`0x5682F0–0x5683AD`). Затем читается исходный `A` из `+0xE4/E8`, а не текущий конец `+0xF0/F4` (`0x568357–0x5683AD`). Ограничение оси точно такое (`0x5683A5–0x5683EF`):

```text
snap_drag(raw_p, A):
    C = S2(raw_p)                         # покомпонентно; native float32
    i = trunc((trunc(A.x) - 1) / 2)
    j = trunc((trunc(A.y) - 1) / 2)
    if ((i | j) & 1) == 0:               # оба индекса чётные
        if abs(C.x-A.x) <= abs(C.y-A.y):
            C.x = A.x                    # вертикаль, включая равенство
        else:
            C.y = A.y                    # горизонталь
    elif (i & 1) == 0:
        C.x = A.x                        # чётный X, нечётный Y: вертикаль
    elif (j & 1) == 0:
        C.y = A.y                        # нечётный X, чётный Y: горизонталь
    return C                             # оба нечётные: здесь без ограничения;
                                         # такой anchor запрещён валидатором
```

После нормального положительного старта через `S4` оба индекса всегда чётные; остальные ветви алгоритма подтверждены кодом, но их достижимость через обычное начало мышью этим не доказана. При чётной паре ось пересчитывается на каждом обновлении относительно `A`; однократной фиксации выбранной оси в этом коде нет. Пример: `A=(5.5,9.5)`, указатель `(10,10)` → конец `(9.5,9.5)`; указатель `(10,14)` → `(5.5,13.5)`, поскольку смещения равны и выбирается вертикаль.

**Подтверждено: фазы штриха и растеризация.** Вызов `snap` предшествует выбору ветви начала/подтверждения/обновления: `0x5303D6` → `0x530415 / 0x53042F / 0x53044E`. Обновление `0x566830–0x56684B` меняет только сохранённый конец `E`. Обычная ветка подтверждения `0x566550` читает сохранённые `A,E`; переданный ей вектор события в этой ветке не участвует.
```text
press(raw):     A = S4(raw); E = A; state = 1
motion(raw):    E = snap_drag(raw, A); rebuild_preview(A, E)
release(raw):   commit(A, E); state = 0  # не подставлять raw как новый E

commit(A, E):                            # native integer, half-open bounds
    L = clamp(min(trunc(A), trunc(E)), native_min, native_max-1)
    U = clamp(max(trunc(A), trunc(E))+2, native_min, native_max-1)
    for y in range(L.y, U.y):
        for x in range(L.x, U.x):
            i = trunc((x-1)/2); j = trunc((y-1)/2)
            if (i & j & 1) == 0:
                try_native_tunnel_mark(x, y, layer)  # nibble 3; все native проверки
```

Минимум/максимум выше покомпонентные; `native_min/max` — поля мира `+0x84/+0x88/+0x8C/+0x90`, не размеры нарисованного QuadMesh. Обрезка доказана в `0x5665C4–0x566651`, обход и чётность — `0x56671D–0x566779`, остальные отказы — внутри `0x5672D0`/`0x566870`. На отпускании прямой горизонтальный штрих с центрами `(5.5,9.5) → (9.5,9.5)` проверяет `{5..10}×{9,10}`: 12 samples, а не интерполированную цепь квадратов между последними mouse-motion событиями.

**Подключение к `_mark_corridor_from`: математика восстановлена; одного изменения шага недостаточно.** В `G2:1266` уже приходит `exact` из `_terrain_point` (`G2:1423`); использовать нужно этот дробный X/Y. Импорт геометрии складывает исходные X/Y с PMP-координатами и меняет знак Y (`G2:889–891`), а `_terrain_point` выполняет обратное чтение `(local_x,−local_y)`. Поэтому внутри уже полученных native/map X/Y нет доказанного основания добавлять `GRID_Y_OFFSET=2`, масштаб `2.5` или ещё одну поправку `±0.5`: все смещения нужной привязки явно перечислены в `S4/S2` и `trunc(center)`.

Точная интеграция требует хранить `A,E,state` и различать `press/motion/release` в `_input` (`G2:1064`). Существующий `corridor_last_cell` обновляется на каждом движении, а `_mark_corridor_from` сразу ставит marks: этих поведения и одного аргумента `exact` недостаточно для нативного подтверждения штриха. Нужны preview без записи terrain marks и отдельный commit по отпусканию. Ранние проверки по `floor(raw_p)`/`open_air` также не являются доказанным нативным валидатором выбранных samples: валидировать следует результат привязки и растеризации.

**Неизвестно:** совпадает ли экранная проекция Godot с исходной во всех ракурсах. У Godot луч пересекает плоскость `DIG_MARK_DEPTH=15.12`; вычисление исходного cursor vector до чтения `[global+0x284..0x28C]` в данном ограниченном исследовании не восстановлено. Это граница доказательства экранного попадания, а не повод подбирать X/Y-сдвиг. Алгебра `native p → center → samples` выше восстановлена полностью для оговорённой области.

**UI-поверхность и heightmap samples — разные данные.** Подтверждённые четыре samples `{O,O+(1,0),O+(0,1),O+(1,1)}` имеют bounding box **1×1 в координатах точек**, хотя их количество — 2×2. Они не задают автоматически размер закрашенного UI-квадрата. Нативный preview проверяет четыре соседних значения (`0x56D402–0x56D481`), вызывает `0x56AE30`, а тот выбирает геометрию через `0x568410` по числу ненулевых углов (`0x568420–0x5684F4`). В полностью заполненном случае четырёх углов записывается единичный quad `(x,y)..(x+1,y+1)` с `z=14.5` (`0x56A9BC–0x56AD23`, `0x41680000`); граничные случаи используют иные вершины, например смещения `0.30/0.49` (`0x568580–0x568699`, константы `0x737060/0x737088`).

**Неизвестно:** полный внешний видимый размер одиночного штампа после всех граничных случаев, колебания и преобразований renderer. В этом аудите не доказано ни равенство этого размера `2`, ни `2.5`. Восстановленная сетка samples не требует менять видимый quad именно на `2×2`; точный preview следует строить отдельным переносом нативного генератора границ. Новый шаг `2` вместе с прежними квадратами и последовательной lerp-разметкой не будет точным переносом ввода.
