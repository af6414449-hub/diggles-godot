## 1. Доказательства и точные условия установки

Обозначения: `world = [0x77241C]`, `C(x,y) = world.cell(x,y)` через `0x592F10`; размер runtime-cell — `0x7C`. `Ls` — переданный слот метки, `La = DigMarkManager+0x11C` — активный слот валидатора; массивы поддерживают 0..7. Обычный корректный вызов должен согласовать `Ls == La`, а не молча смешать их.

| Адрес | Подтверждённое условие / действие |
| --- | --- |
| `0x5672E2–0x56731E` | Для `0x5672D0`: `minX+1 <= x < maxX-1`, `minY+1 <= y < maxY-1`. Границы — signed dword `world+0x84/88/8C/90`. |
| `0x56732D–0x567357` | Читать **байт `C+0x34+Ls`**. Если он нулевой, пропустить следующую проверку материала/высоты; это не универсальный запрет отметки пустого места. |
| `0x567359–0x567369` | При ненулевом байте отклонить `M = u16(C+0x18)&3`, если `M==0 || M==3`. Старший бит `0x80` здесь не проверяется. |
| `0x56736F–0x567390` | В той же ненулевой ветке получить `Hnext = 0x5968B0({x,y})`; отклонить при **`Hnext < 0x597430(3)`**, то есть `<11`. Сравнение signed, `-1` тоже отклоняется. |
| `0x567395–0x5673AB` | Затем обязательно вызвать `0x566870(x,y,1)`; при `AL==0` ничего не записывать. |
| `0x5673AD–0x5673FE` | Заменить nibble `Ls` слова `C+8` на **3**, сохранив остальные слоты. В `C+0xC` заменить тот же nibble на `manager[0xB4+4*Ls]&15` — номер группы. Функция возвращает `void`, не доказанный bool успеха. |

`0x566870(x,y,strict)` добавляет следующие проверки:

1. `strict==0` немедленно возвращает true (`0x566874–0x566882`). `0x5672D0` всегда передаёт **1**.
2. Повторить interior bounds (`0x566891–0x5668CA`). Затем отклонить, если `((trunc0((x-1)/2) & trunc0((y-1)/2)) & 1) != 0` (`0x5668D0–0x5668E7`). `trunc0` — деление с усечением к нулю, включая отрицательные координаты. Это **не** общий тест «оба индекса нечётные»; например, (3,3) отклоняется, (9,3) проходит.
3. Отклонить, если nibble **активного La** в `C(x,y)+8` содержит бит `8` (`0x5668F6–0x56690D`). Проверяется признак cave-mark, а не любое ненулевое значение.
4. Прочитать `M=u16(C+0x18)&3` и байт **`C+0x34+La`** через `0x423700`. Если `M` равен 0 или 3 **и** байт ненулевой — отказ (`0x566913–0x566930`). Семантика этого байта игрока этим аудитом не установлена; называть его физической высотой нельзя.
5. Если `y+1 < maxY` (при interior bounds это выполняется), проверить cave-bit активного La у `C(x,y+1)` (`0x566936–0x566966`).
6. Через `0x4093B0` получить metadata по block-ref и потребовать `metadata[0] >= 2` у **пяти различных соседей**: `(x,y+1)`, `(x+1,y)`, `(x-1,y)`, `(x+1,y+1)`, `(x-1,y+1)`. Нижний центральный сосед фактически проверяется дважды. Отказ — unsigned `JB` после сравнения байта с 2 (`0x56696C–0x566A46`). Это не `cell_attribute` и не material word.

**Подтверждено:** постановка через UI commit `0x566550` отдельно повторяет тот же half-grid parity перед вызовом `0x5672D0` (`0x56672B–0x56675A`). Переносить только nibble 3 без перечисленных gates — неполный нативный контракт.

## 2. PMP → runtime: исправленная цепочка

`W/tools/export_pmp_terrain.py:22–37` правильно читает W/H, `flags[N]`, `refs[N]`, пропускает counted U16 и возвращает trailing `cell_attribute[N]`. Однако его комментарий `:92–96,127–128` и прежний `ground-material-evidence.md:15–18` рассматривают только **второй** проход загрузчика. Для сырого PMP это неполная цепочка.

| Исходное поле | Подтверждённый путь |
| --- | --- |
| `flags[i]` | Первый проход `0x5995F4–0x599782`, jump table `0x599FA8`: `high=raw&0x80`; low 0→0, 1→`(старый material&3)+1`, **2→3, 3→2, 4→1, 5→4**. High сохраняется. Значения 0/2/4/132/133 фактического `multi_start_010.pmp` не требуют ветки наследования low=1. |
| Преобразованные flags | Второй проход `0x599805–0x59991C` берёт первый ненулевой low-код из `[текущий, снизу, справа, снизу-справа]`. Если все нули, импорт runtime-cell **пропускается**, а не записывает «пустую клетку». |
| Material word | Если выбран low-код 4, записывается `(raw[i]&0x80) | 3` (`0x599947–0x5999EA`). Иначе — `(выбранный low-1) | (raw[i]&0x80) | ((rand()%6)<<8)` в `u16(C+0x18)` (`0x5999F3–0x599A8E`). Неизвестный RNG меняет старший байт, но не проверяемые два младших бита. |
| `refs[i]` U32 | Напрямую в **`u32(C+0)`**, без индексации counted U16 (`0x599A92–0x599B3E`). Это индекс metadata BlockDB, доступ `base + 0x59*ref` (`0x4093B0–0x4093C9`). |
| trailing `cell_attribute[i]` | Напрямую в **`u8(C+7)`**, `0x599B40–0x599BEC`. Не `C+0x18`, не `C+0x34`, не высота. |
| counted U16 | **RLE**, не координатные пары: `value=u16&3`, `run=u16>>2`, нулевая длина означает `0x4000`. Временный буфер заполняется этим байтом (`0x599D80–0x599DBE`). Затем `0x596550` распределяет 8×8 байт на cell в **`C+0x3C .. C+0x7B`** (`0x59669A–0x596709`, полный tile `0x596731–0x59686D`). Это не массив высот и не массив `C+0x34+slot`; более полная игровая семантика этих 8×8 значений здесь неизвестна. |

Следовательно, **для записанной точки с raw flags=2 собственный первый код ненулевой: material&3=2**, не 1. Для raw 4/132 получается 0; для raw 133 — 3 с битом 0x80. Это вывод о ветках загрузчика, а не предложение менять текстуры/renderer в этой задаче. Старое предположение «raw 2 → material 1» пропускает преобразование `2→3` в `0x5996C4`.

**Подтверждение буквы C:** для четырёх одинаковых material index=2 функция `0x4CD020` получает bitset `4` и переходит через `0x4CD0C3–0x4CD0C6 → 0x4CD9AC` в одноцветную ветку. Там **`0x4CDA96: mov eax,[ebp+8]`; `0x4CDA9B: add eax,0x41`** даёт ASCII `C`. В `0x4CDAC3–0x4CDAD5` буква передаётся форматтеру со строкой по `0x7248B4`: **`ground/Gnd_%c%c%c.tga`**. Поэтому uniform material 2 выбирает семейство `Gnd_Cxx`, не B. Смешанная ветка имеет отдельную обработку (`0x4CD067–0x4CD0A1`); это не утверждение о каждой смешанной поверхности. Прежнее доказательство B для сырого PMP-кода 2 требует пересмотра с учётом первого прохода.

## 3. Высота: не путать текущий угол и следующий удар

**Подтверждено:** `0x5968B0` не возвращает просто байт текущей высоты. Для четырёх runtime-cells вокруг точки берутся следующие metadata-поля:

| Cell | Ссылка следующего состояния | Высотный байт выбранной metadata |
| --- | --- | --- |
| `(x-1,y-1)` | `i32(meta+0x4C)` | `u8(meta+0x53)` |
| `(x,y-1)` | `i32(meta+0x48)` | `u8(meta+0x52)` |
| `(x-1,y)` | `i32(meta+0x44)` | `u8(meta+0x51)` |
| `(x,y)` | `i32(meta+0x40)` | `u8(meta+0x50)` |

Если next-ref отличен от `-1` и текущего ref, используется следующая metadata, иначе текущая. Если ни один угол не может перейти, результат `-1`; иначе результат — **максимум четырёх выбранных байтов**. Доказательства: `0x5968D0–0x596962`, `0x596977–0x596A0B`, `0x596A18–0x596AAA`, `0x596AB5–0x596B71`. Для валидных ссылок это реализуемая чистая функция. При повреждённом ref оригинал вызывает exception-path; подставлять block 0 как нормальный fallback нельзя.

Исходные metadata находятся в BDB после `<7I>` и `18*block_count` байт каталога; stride 89. Соответствие runtime-памяти подтверждает загрузчик `0x565E26–0x565E38`; layout также читает `W/tools/inspect_bdb.py:108–120`. Для BlockDB2: `block_count=118688`, metadata offset `2136412`.

Контроль: у block 0 текущие bytes `+0x50..53 = [15,15,15,15]`, links `+0x40..4C = [54,44,32,22]`; соответствующие углы следующих блоков равны 11. Поэтому четыре соседних block 0 дают **Hnext=11, текущие углы=15**. Четыре block 80 дают Hnext=7 при текущих 11; четыре block 1225 — Hnext=0 при текущих 3.

В `0x596B80` перед ударом вызывается дополнительная политика `0x5976B0` (`0x596C03`): она проверяет material, Hnext и далее объекты мира; полный объектный фильтр **не восстановлен**. Целевой уровень декодируется из nibble (`0x596C22–0x596C5C`): 0→15; ненулевой без bit8→11; cave→`max(4*(nibble&3)-1,0)`. При `target > Hnext` метка очищается и удара нет (`0x596C6F–0x596C8E`). Иначе выбираются изменения четырёх соседних block-ref, начиная `0x596CAD`; равенство кандидатного угла Hnext видно в `0x596D09–0x596D14` и `0x596D6F–0x596D7D`. Успешная постановка метки ещё не доказывает разрешение удара исполнителя.

## 4. Границы и положительный начальный пример

**Подтверждено:** конструктор мира `0x594160` принимает размеры и origin; `0x594481–0x5944BC` сохраняет width/height в `+0x44/48`, origin в `+0x74/78`; `0x594542–0x594580` формирует `(minX,minY,maxX,maxY)=(originX,originY,originX+width,originY+height)` в `+0x84..90`. Материалы и refs PMP записываются по координатам `offset+(col,row)`; offset берётся из аргументов загрузчика (`0x59937F–0x599388`, `0x5997A4–0x5997DA`).

`O/Templates/multi_start_010.pmp`: **44×24 = 1056 исходных samples**, 7176 байт, SHA-256 `b6fc5ef7b1800dce9fb0dd4a42de879b8198f25ac84eb82b524266378ddb7807`. Counted U16: 414 элементов, RLE раскрывается в **67584 = 44*24*64** байт. Flags counts: `{0:156, 2:324, 4:207, 132:262, 133:107}`. Применяемых по four-corner test точек — 943; 113 полностью нулевых окрестностей оставляют прежнее состояние мира. Экспортёр фильтрует такие точки в `:69–77`; его 943 клетки нельзя использовать как полный набор адресуемых world-samples.

**Граница знания:** PMP содержит размеры **шаблона**, не глобальные min/max мира. `O/Templates/multi_urw_start_010_a_0.tcl:1–4` передаёт `xoffset/yoffset` в `map_template`. Обычная multiplayer-генерация сначала делает `map create $MapW $MapH` (`O/GameScripts/multiplayer.tcl:259–284`). Фактические размеры/offset конкретного запущенного мира отсюда не следуют. Editor-ветка может отдельно создать мир размеров `PMP_W+2*xoffset`, `PMP_H+2*yoffset` (`0x599328–0x599378`).

Поэтому **1..42 × 1..22 — доказанный interior только для явно созданного отдельного мира `(width,height,origin)=(44,24,(0,0))`**. Для обычной вставки этого шаблона в больший мир — неизвестно; `1..width-2` из PMP нельзя выдавать за нативные границы. Чётность считается в мировых координатах, после offset.

**Положительный воспроизводимый sample:** offset `(0,0)`, мир покрывает interior точки, `Ls=La`, в текущей точке и снизу нет активного cave-bit. Тогда `(x,y)=(9,3)` проходит все gates постановки **при любом значении layer-byte `C+0x34+slot`**:

- Индекс PMP `i=141`; raw flags=2 по file offset `0x95`; ref=0 по `0x65C`; trailing attribute=4 по `0x1875`. После загрузчика `material&3=2`, а `C+7=4`.
- `(trunc0(8/2)&trunc0(2/2))&1 = 0`.
- Четыре refs вокруг точки: `(8,2),(9,2),(8,3),(9,3)` — все 0; все эти cells реально затронуты импортом. Угловые next-refs соответственно `22,32,44,54`; выбранные bytes все 11, Hnext=11. Сравнение `<11` не срабатывает.
- Пять различных соседей `(9,4),(10,3),(8,3),(10,4),(8,4)` имеют ref=0 и `metadata[0]=15 >=2`; нижний cave-bit проверяется отдельно. Запись результата — nibble 3 только выбранного слота.

Второй подтверждённый исходный sample `(5,17)` при тех же предпосылках также имеет raw 2/ref 0/attribute 4, four-corner Hnext=11 и пять соседних `metadata[0]=15`; parity проходит. Это контрольные данные начального файла, а не наблюдение live-runtime. Наоборот, (3,3) отклоняет parity независимо от материала. Raw 4 в (13,5) даёт material 0, но **не является безусловным отрицательным примером**: при нулевом layer-byte эта material-проверка пропускается.

**Реализуемо сейчас:** полный raw-grid, флаг «импорт действительно записал cell», low material из двух проходов, metadata/next-height из BDB, пять соседних byte-проверок, parity, явные world-bounds и текущие mark nibbles. Состояние пропущенных cells, реальные world-bounds/offset и player-byte нельзя заполнять догадками. Для них возвращать «неизвестно» либо явно называть ограничение адаптера; не считать отсутствие mesh доказательством native-отказа.

**Fixture интегратора `x=5..10, y=5..6`:** если это скопированный solid-патч (raw flags=2, четыре угловых ref=0 для каждой проверяемой точки, соседние metadata[0]>=2, cave-bits отсутствуют), ожидаются **12 записей nibble 3**. У всех точек `trunc0((y-1)/2)=2`, parity не отклоняет ни одну. Material=2 и Hnext=11 проходят и при нулевом, и при ненулевом player-byte. Проверять нужно также окружение патча, а не только его 12 центральных samples; копирование одного flag без refs/окружения не доказывает положительный результат. Это специально подготовленный fixture, не утверждение, что все эти координаты в неизменённом исходном PMP имеют одинаковый flag. Принятый интегратором полный point-domain 44×24 допустим как **явный адаптер**; он не становится доказанными min/max исходного multiplayer-мира и не должен зависеть от наличия mesh.

## 5. Стирание: commit mode 2 не равен постановке

**Подтверждено:** `0x566550:0x566809–0x566813` при `manager+0xE0==2` вызывает **`0x567410(cursor)`**, а не проход постановки. Обновление drag `0x566830:0x566851–0x56685B` тоже вызывает эту функцию в режиме 2.

1. Seed = `cvttss2si(cursor.x/y)`. Cave-seed проверяется только в полных bounds **`min <= seed < max`**, без interior-отступа (`0x56744E–0x56749D`). Если seed снаружи, переход идёт в обычную интерполированную ветку `0x567918`, а не в немедленный отказ всего stroke. Здесь нет half-grid parity, `0x566870` не вызывается.
2. Если у seed в активном nibble есть **bit8** (`0x5674A5–0x5674B5`), вызвать `0x58A820 → 0x58EC00(x,y)` (`0x5674BB–0x5674C7`). Это тот же remover, который вызывает Tcl `cave_skin rem` (`0x66AE53–0x66AE5E`). Он удаляет **первую целую pending-запись**, чей прямоугольник содержит точку, с включёнными обеими границами (`0x58EC3A–0x58ECB7`); `0x58F2A0` перемещает последний 20-байтовый record на её место и уменьшает count. Это не удаление одного sample из record и не автоматическое удаление всех перекрывающихся records.
3. В этой cave-ветке очищение marks — **BFS по четырём соседям**: только bit8 и тот же nibble группы из `C+0xC`; world-bounds полные, parity отсутствует (`0x5675AF–0x567733`). Очищается nibble в `C+8`; группа в `C+0xC` остаётся. Следовательно, удаляется record целиком, но samples очищаются по связности/группе, не слепой заливкой всего прямоугольника. Для искусственно разорванной группы нельзя обещать очистку всех её островков.
4. Если seed не cave, идёт отдельный интерполированный erase-stroke (`0x567918–0x567A37`). На каждом шаге обходится **весь 2×2 прямоугольник целочисленных samples**, от truncate-позиции до `+2` exclusive, с clipping; каждый индекс увеличивается на 1 (`0x567ABC–0x567C18`). **Той же parity-фильтрации, что у постановки, нет.** Начало и exclusive-конец clamp-ятся в `[min,max-1]` (`0x567A3A–0x567AB6`).
5. В обычной erase-ветке sample с bit8 **пропускается**, остальные теряют только выбранный nibble `C+8` (`0x567B53–0x567BF6`). Стирание соседней обычной отметки не является неявной отменой всех попавших под кисть cave-records. Cave-отмена запускается именно от cave-seed.

**Не смешивать API:** Tcl `dig_mark … mode=2` в `0x658AFD–0x658B36` отдельно очищает один nibble `C+8` после своих bounds; оно не проходит ни UI-stroke, ни `cave_skin rem`, ни BFS. Совпадение числа 2 не означает одинаковую транзакцию. `C+0xC` и в этой ветке не очищается.

### Вход erase и ограниченный псевдокод для интегратора

**`0x5680B0` не содержит passthrough для mode 2.** `0x5680C7–0x5680CE` различает только `mode==0` и `mode!=0`. Если функция вызвана в mode 2, она идёт в ту же S2/axis-ветку, что и mode 1 (`0x5682F0–0x5683EF`): исходная S2-кандидатура для каждой оси — `2*floor(f32(f32(raw-0.5)*0.5))+1.5`, затем применяется ограничение оси от anchor `+0xE4/E8`. Mode 0 использует исходный S4 с его fallback. Значение Z копируется без снапа (`0x5683F2–0x568403`).

**Есть две разные frontend-ветки.** В ветке инструмента 0 вход проходит через `0x5680B0` **до** begin/update/commit (`0x5303C7–0x53044E`; также commit `0x5301B0–0x5301F5`). Поэтому press при старом mode=0 получает S4, а motion/release при mode=2 — S2 с axis-ограничением. Отдельный инструмент 5 в `0x530693–0x5306E6` **обходит `0x5680B0`** и передаёт текущий cursor напрямую, начиная erase через `begin(cursor,true)`. «Raw erase» подтверждён для этой отдельной ветки, а не как поведение самой snap-функции. Отождествление инструмента UI интегратора с одной из этих веток — явный выбор адаптера.

Далее `P` — уже полученный этим путём `float32 Vector3`; это не экранные координаты. Нативные begin/update/commit подтверждены в `0x5664F0–0x56654B`, `0x566830–0x566862`, `0x566809–0x566818`:

```text
press(P, erase):
    anchor = endpoint = P                    # +E4..EC, +F0..F8
    mode = 2 if erase else 1
    if erase: erase_at(P)                     # немедленно, не ждать release
motion(P):
    endpoint = P
    if mode == 2: erase_at(P)
release(P):
    if mode == 2: erase_at(P)                 # release использует переданный P
    mode = 0

erase_at(P):
    seed = trunc0(P.xy)
    if seed in [world_min, world_max) and cave_bit(mark(seed, La)):
        remove_first_pending_record_containing(seed)
        clear_4_connected_cave_marks_of_same_group(seed, La)
        return                               # previous/counter здесь не обновляются

    if last_erase_counter + 2 < current_counter:
        previous = P                         # +A8..B0
    N = 1 + trunc0(length3D_f32(P - previous))
    for i in 0..N inclusive:                  # N+1, не N итераций
        t = f32(f32(i) / f32(N))
        u = f32(1.0 - t)
        Qx = f32(f32(previous.x*u) + f32(P.x*t))
        Qy = f32(f32(previous.y*u) + f32(P.y*t))
        A = trunc0(Qx, Qy)
        lo = clamp(A,     world_min, world_max - 1)
        hi = clamp(A + 2, world_min, world_max - 1)
        for y in [lo.y, hi.y):
            for x in [lo.x, hi.x):            # каждый индекс, БЕЗ parity
                if not cave_bit(mark(x,y,La)):
                    clear_only_mark_nibble(x,y,La)
    previous = P
    last_erase_counter = current_counter
```

Точные свидетельства: reset previous — `0x567918–0x56793D`; `N=trunc(length)+1` — `0x567943–0x567999`; интерполяция — `0x5679D9–0x567A31`; clipping — `0x567A3A–0x567AB6`; inclusive-конец по i — `0x567C3C–0x567C56`; сохранение previous/counter — `0x567C6C–0x567C8F`. В длине используется **XYZ**, хотя footprint только XY. Квадраты считаются float32, сумма `(dy²+dx²)+dz²`; `0x40B7E0` переводит эту сумму в double для sqrt и возвращает float32. При совпадающих P/previous получается N=1 и две одинаковые обработки footprint.

`current_counter`/`last_erase_counter` — dword `+0xA0/+0xA4`; конструктор задаёт **0 / -100** (`0x5662A4/0x5662AE`), previous=(0,0,0) (`0x566208–0x56621C`), поэтому первый erase сбрасывает previous на P. `press` сам по себе эти поля не сбрасывает. **Неизвестно:** единица и внешний источник изменения current_counter; подменять условие «+2» двумя миллисекундами нельзя. Псевдокод сохраняет именно установленную логику состояния.

## 6. Что остаётся динамическим / неизвестным

- **Подтверждено отдельно:** сам mark-writer не проверяет занятость гномом/предметом. Дополнительный predicate `0x5976B0`, вызываемый core `0x596B80`, выполняется при ударе; его полный объектный фильтр в этот ограниченный аудит не вошёл.
- **Неизвестно:** значение player/layer-byte `C+0x34+slot` после загрузки, раскрытия карты и обновлений мира. Из PMP `cell_attribute` или counted U16 оно не следует. Положительные samples выше специально выбраны так, чтобы эта неизвестная ветка не меняла ответ.
- **Неизвестно:** фактические `min/max`, offset, активный слот и уже поставленные cave/группы конкретного live-запуска. Данные текущего Godot-контроллера не читались и не изменялись; нативный процесс не запускался.
- **Не подтверждено:** что все 1056 исходных samples были явно записаны загрузчиком или что все cells можно инициализировать высотой 15. Для пропущенных областей нужно основание из создания/генерации мира.

Для приёмки интеграции достаточно сначала использовать два положительных sample при явно заданных bounds/offset и mark-состоянии; сравнить записанный nibble/сохранение других слотов, parity-отказ (3,3), erase без parity и отдельную cave-отмену record+BFS. Это будущая проверка интеграции: здесь выполнены статическое чтение EXE, декодирование исходных файлов и расчёт значений, а не игровой smoke-test.
