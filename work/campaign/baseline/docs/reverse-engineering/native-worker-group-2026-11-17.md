# Worker group: происхождение, reset и reservations

17.11.2026. **Ответ для интеграции:** да, **свежему или явно сброшенному** worker доказанно соответствует `group=-1`; после принятого terrain core следует присвоить **`u32(cell.groups) >> (4*slot)` без `&15`**. До следующего принятого удара или reset значение сохраняется. Это не универсальное правило «первый удар любого нового задания»: `dig_starttask` сам reset не вызывает, а поле участвует в загрузке/сохранении состояния объекта. Announce не заменяет присвоение после удара и не сбрасывает группу.

## 1. Кто пишет worker+0x250

| Событие | Точный источник | Подтверждённое действие |
| --- | --- | --- |
| Конструирование объекта | `0x5C83F0`; `0x5C8417` сохраняет this в EDI; **`0x5C8D80`** | `mov dword [edi+0x250],0xFFFFFFFF`. Реальный путь создания объекта вызывает конструктор в `0x5C7BD1–0x5C7BD8`; это не только инструкция в неиспользуемом конструкторе. |
| `dig_resetid worker` | Регистрация `0x6718BA–0x6718E0` → wrapper `0x67BB90`; resolve worker `0x67BC45`, запись **`0x67BC56`** | Только `worker+0x250=-1` в интересующих нас полях. Packed groups/marks клетки не очищаются. Отсутствующий worker не получает запись (`0x67BC4D–0x67BC54`). |
| Принятый `dig_apply` | Tcl-wrapper `0x6347A0`, вызов core **`0x634A13` → `0x596B80`**; **`0x597304–0x59731C`** | После четырёх refs и очистки завершённых marks: `eax=u32(C(target)+0xC); eax >>= shift; worker+0x250=eax`. **SHR**, не SAR; следующей `AND 15` нет. `shift=4*slot` сохранён в `0x596C0B–0x596C14`; слот — worker+0x36C. |
| Отклонённый core | `0x596C20`, `0x596C6F–0x596CAA` | Ветви policy=false/target>Hnext очищают mark выбранного слота и возвращают false раньше присвоения group. Прежний worker group и packed groups сохраняются. Bounds-failure также не достигает присвоения. |
| Перенос состояния объекта через stream | `0x5D0CE0`; **`0x5D1649–0x5D1652`** → `0x406F60` | Адрес worker+0x250 передан 4-байтному transfer. Режимы 1/2 обрабатываются в `0x406F66–0x406FC4`. Поэтому произвольный загруженный объект нельзя считать свежим только по конструктору. Точный payload конкретного save здесь не исследовался. |

Точный фрагмент принятого core:

```text
597314: 8B400C        mov eax,[eax+0xC]
597317: D3E8          shr eax,cl
597319: 8B4D0C        mov ecx,[ebp+0xC]       ; worker
59731C: 898150020000  mov [ecx+0x250],eax
```

**Подтверждено:** core читает groups уже после удаления завершённых marks, но само слово groups принятым ударом не переписывается. Завершение mark не обнуляет его group. Локальная копия packed groups в snapshot должна переживать очистку marks; иначе stamp после удара окажется выдуманным.

## 2. Кто пишет packed groups C+0xC

Это восемь четырёхбитных групп по слотам, отдельно от восьми mark-nibbles `C+8`. Номер — **группа постановки**, не ID работника и не reservation. `D` — менеджер разметки, `counter[L]=u32(D+0xB4+4*L)`.

| Источник | Действие |
| --- | --- |
| Конструктор `D`, `0x5661C0`, цикл **`0x56631C–0x56634B`** | Все восемь counters начинают с 0. Это доказательство свежего менеджера; восстановление его произвольного сохранённого состояния отдельно не доказано. |
| Принятая коридорная постановка `0x5672D0`, **`0x5673AD–0x5673FE`** | После gates записывает mark3 и `groups=(old_groups & ~(15<<s)) | ((counter[L]&15)<<s)`, `s=4*L`. Другие слоты сохраняются. Ни worker, ни его stamp в аргументах этого point-writer нет. Отказ до `0x5673AD` groups не меняет. |
| Прямоугольный коридорный commit `0x566550`, mode1 | Вызывает point-writer для всех прошедших parity точек (`0x56675A`), затем **один** `counter[L]++` (`0x566783–0x5667AA`). Значит принятые точки одного commit получают одну группу; следующий commit — следующую. Вызов одного point-writer счётчик не увеличивает. |
| Пустой/полностью отклонённый mode1 commit | Внешний цикл может сразу перейти в `0x56677F` (`0x566721–0x566723`); rejected points также доходят до общего хвоста. Инкремент не обусловлен числом успешно записанных points. |
| Другой point-writer `0x5671A0`, **`0x56728C–0x5672C4`** | Тот же replace-nibble из `counter[L]&15`. Commit `0x567CB0` имеет инкремент в `0x56806D–0x56808A`. Полная cave-логика вне этой задачи. |
| Явная инициализация/очистка клеток мира `0x593EC0` | `world=[0x77241C]` (`0x593EEE`), массив `world+0x14` (`0x593F8C`), цикл width*height. **`0x594077–0x59407F`** вызывает memset(C+8,0,0x74), stride0x7C (`0x59408E`), включая groups. `0x6D0560` подтверждён как memset. Это reset клеток, не обещание о любом loaded snapshot. |

Счётчик — dword; **только записанный group nibble** циклически повторяется через 16 commits. Не закреплять группу навсегда за worker или отдельной точкой. PMP не содержит эти counters или группы работника; для standalone они должны принадлежать явной модели текущих marks. Нулевое слово групп допустимо для явно очищенного мира, но не выводится из наличия/отсутствия mesh-cell.

## 3. Где нужен nibble-mask

**Два различных чтения подтверждены одновременно:**

```text
accepted_core: worker_stamp = u32(groups_at_struck_point) >> (4*L)    # БЕЗ &15
dig_next:      candidate_g  = (u32(candidate.groups) >> (4*L)) & 15
               compare candidate_g with RAW worker_stamp
```

В `dig_next/0x597B20` raw worker stamp читается `0x597CBF`; `SHR`+`AND 15` кандидата — **`0x597D69–0x597D6E`**. Strict=true пропускает несовпадение (`0x597D71–0x597D7A`); ordinary добавляет float32 **+8** (`0x597E01–0x597E0E`). Следствия:

- При stamp=−1 любой candidate nibble 0..15 получает +8; strict-вариант не найдёт совпадений.
- При groups=0x000000A3 и L=0 accepted stamp имеет bits0xA3, **не 3**. Кандидат с nibble3 всё ещё чужой; все nibble 0..15 чужие. Для faithful-переноса нельзя «исправлять» stamp маской.
- При L=7 сдвиг сам оставляет один nibble; при нулевых старших группах результат также совпадает с nibble. Эти частные случаи не доказывают общий `&15`.
- В GDScript перед SHR очистить расширение до 64 бит: `(int(groups) & 0xFFFFFFFF) >> (4*slot)`. Полученный u32 можно хранить неотрицательным; reset хранить −1. Сравнение с candidate 0..15 сохраняет результат native CMP. `groups >> shift` над отрицательным 64-битным int без приведения u32 — другой алгоритм.

Назначение необычного немаскированного присвоения **неизвестно**; называть его намеренной механикой либо исправляемой ошибкой оснований нет. Instructions и результат сравнения известны.

## 4. Announce и reservations

**Подтверждено:** `gnome_announce_dig` зарегистрирован `0x66F1FE–0x66F22C` → `0x67A450`. Успешная ветка начинается `0x67A57E`; в интересующих нас данных она не пишет ни worker+0x250, ни C+0xC. Восстановлены следующие побочные записи, их нельзя выдавать за group stamp:

1. `0x67A795–0x67A7BD` передаёт worker и P в **`0x43BC90`** при `[0x772400]+0x590==0`, `[0x76837A]==0`, slot!=-1. `0x43BC9D–0x43BCA7` берёт **record=[worker+0x3E4]** и вызывает `0x5EC3A0(record,&P)`. Последний сбрасывает поля этой отдельной записи, устанавливает `record+0xC=14` и XYZ в `record+0x1C/20/24` (`0x5EC3A8–0x5EC40A`). Это изменение объявленной цели, не worker group.
2. В той же `0x43BC90` список по base+0x3074 с count+0x3078 обходится stride16. Записям с Manhattan XY distance<20 до округлённой цели записывается **float10** по entry+8 (`0x43BD58–0x43BDA7`). Список и запись цели — разные данные от packed groups. Нет записи worker stamp или обращения к клеткам мира в этом callee.
3. Отдельная ветка при `[0x76837A]!=0` и slot>=0 добавляет 12-байтную запись `(rounded_x,rounded_y,50)` в массив per-slot state+0x28 (`0x67A621–0x67A6FB`, slot stride0x70). Getters `0x5EE9D0` и `0x432390` возвращают отдельные singleton states; это не возврат worker+0x250. Трактовка глобальных режимных флагов здесь не установлена.

**Предел:** это не перенос всего reservation/AI протокола и не доказательство отсутствия влияния объявлений на назначение задач другим гномам. Для уже полученного полного snapshot входов `dig_next` его стоимость не читает эти списки: только raw stamp, candidate groups и остальные известные terrain gates. Поэтому isolated selector не требует поддельного reservation ID вместо группы. Согласованное распределение задач нескольким native workers остаётся отдельной подсистемой.

Tcl: `O/Scripts/classes/zwerg/z_dignwalk.tcl:143` announce перед стартом; `:236` после выбора next; `:313` перед ударами. **В `dig_starttask:136–163` нет dig_resetid.** Reset вызывается в `dig_continue:209` при try>6, `:288` при завершении; laser-вызовы `:224/231` отдельно. Общий `stop_prod` из `z_procs.tcl:1213` вызывает reset в **`:1243`**. Следовательно, announce перед назначенной первой точкой не доказывает stamp=−1 у существующего worker.

## 5. Контракт standalone и проверка

```text
new_worker / explicit_native_reset: G = -1
place_accepted_point: replace only slot group nibble from commit counter
finish_mode1_commit: counter[slot] = u32(counter[slot] + 1)
announce(P): G unchanged; packed groups unchanged
accepted_step(target): G = (groups[target] & 0xFFFFFFFF) >> (4*slot)
rejected_step(target): G unchanged
next_selection: pass G unchanged to the existing native_dig_next helper
```

Для новой standalone-модели с явно назначенной первой точкой это доказанный локальный контракт. Не сбрасывать G перед каждым next и не выводить его из текущей цели/последнего пути; обновлять только после принятого core. Если задача/worker продолжены из snapshot, сохранять G либо явно моделировать reset. Счётчик постановки и reservation state не являются этим G.

В соседнем JSON сохранены instruction bytes и независимые числовые fixtures: первые/повторные commits, wrap nibble, сохранение других слотов, пустой commit, accepted/rejected/reset/announce и SHR с ненулевыми старшими группами. Проверены непосредственно по установленному EXE и 32-битной арифметикой; это не тест runtime интегратора и не live-трасса. Неизвестными остаются конкретные loaded counters/stamps и полный эффект reservation AI; full get_digedge, player-byte producer и vector_fixdig не исследовались в этом приращении.
