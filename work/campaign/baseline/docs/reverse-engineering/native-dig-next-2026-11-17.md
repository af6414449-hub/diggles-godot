# Выбор следующей точки копания: dig_next и get_digedge

17.11.2026. **Подтверждено статическим разбором:** `dig_next` ранжирует точки в окне, а `get_digedge` обходит связную разметку с внешним кольцом и выбирает доступного кандидата по квадрату расстояния до работника. Это разные алгоритмы. Реализован один законченный результат — чистое ранжирование `dig_next`; входы, ещё не полученные из исходного состояния, возвращают `unknown`. Контроллер, terrain state, экспорт, STATUS и APK не изменены.

## 1. Точный dig_next

**Подтверждено.** Tcl-wrapper `0x634B50`, core `0x597B20`. Пусть `P` — переданный native logical XYZ; `L=u32(worker+0x36C)` — слот 0..7; `G=i32(worker+0x250)` — сырое поле группы. World bounds читаются из `world+0x84/88/8C/90`; max исключён. `C(x,y)` — runtime-cell stride `0x7C`.

| VA | Операция |
| --- | --- |
| `0x634CC6–0x634CFD` | Форма `dig_next P worker try`: `K=max(try,0)+1`, strict=false. `K` — порядковый номер с единицы. |
| `0x634CFF–0x634D42` | Без try: K=1. **Форма `dig_next P worker ignored bool`: K=1; argv[3] вообще не читается**, argv[4] задаёт strict. Поэтому Tcl `:375`, `dig_next $thispos this 1 1`, ищет первого в своей группе, а не второго. |
| `0x634C82–0x634C99` | Если worker не разрешён, core не вызывается; wrapper уходит с пустым Tcl-результатом. Это отдельный случай, не sentinel core. |
| `0x597B9F–0x597BF5` | `cx=trunc0(P.x), cy=trunc0(P.y)` через CVTTSS2SI. `x∈[max(minX+2,cx−16), min(maxX−2,cx+16))`; `y∈[max(minY+2,cy−17), min(maxY−2,cy+15))`. |
| `0x597C30–0x597CB8` | K слотов с point `(-1,-1,-1)` и cost=**10000000.0f**, bits `0x4B189680`. |
| `0x597CC8–0x597D10` | Маска работы **`0xB << (4*L)`**, не 0xF: scratch-bit 4 игнорируется. Требуется `(u32(C+8)&mask)!=0`. |
| `0x597D20–0x597D3B` | `u8(C+0x18)&3` должен быть 1 или 2. Старшие биты слова не фильтруются. |
| `0x597D41–0x597D56` | `H=world.0x5968B0(x,y)`; H=−1 пропускается. Это **следующая**, не текущая высота. |
| `0x597D66–0x597D7A` | `g=(u32(C+0xC)>>(4*L))&15`. Если strict и g!=G — пропуск. G **не маскируется** до nibble. |
| `0x597CEB–0x597CF9`, `0x5980C0–0x5980D8` | Полный проход по окну: Y возрастает снаружи, X внутри. Отсутствует остановка на первом кандидате или нулевой стоимости. |

**Подтверждённая стоимость**, `0x597D95–0x597E0E`:

```text
dx = x − P.x
dy = y − (P.y − 0.75)
dz = (H + 4) − (P.z + 6)
cost = sqrt(dx² + dy² + 0.25*dz²) + (8 if g != G else 0)
```

Каждые сложение/вычитание/умножение округляются в float32 в указанном порядке: сначала `dx²+dy²`, затем `+0.25*dz²`. `0x40B7E6–0x40B7F7` делает `f32(sqrt(double(f32_sum)))`. Константы прочитаны непосредственно: `0x7370C0=.75`, `0x7374E0=6`, `0x737058=.25`, `0x73752C=8`. Это геометрическая стоимость со штрафом группы; препятствия и стоимость пути здесь не участвуют.

`0x597E4A–0x597E8C`: новый cost должен быть **строго меньше** последнего cost в K-списке; вставка перед первым строго большим. Равные стоимости сохраняют Y/X-порядок сканирования. В конце возвращается **K-й** элемент, не первый элемент списка K лучших. Отсечение cost>=10000000 также действительно; helper сохраняет его.

`0x5980E1–0x59817B`: сохранённый Z=H+4 получает ещё +2 и clamp **[1,14]**; константа `0x737550=14`, не 15. Результат валидной точки `(x,y,clamp(H+6,1,14))`. Если K больше числа кандидатов, sentinel проходит этот же epilogue и становится **`(-1,-1,1)`**. Только недостижимая через обычный Tcl-wrapper ветка K=0 (`0x597B48–0x597B7F`) возвращает `(-1,-1,-1)` без clamp; helper K=0 не моделирует.

Здесь **нет** target(mark)<=Hnext, parity, player-byte, объектной политики `0x5976B0` или проверки пути. Например, mark=3/Hnext=7 ещё может быть выбран; последующий strike отклонит target11>7 и очистит метку. Подменять этим селектором разрешение удара нельзя.

## 2. Точный get_digedge, отдельно от ранжирования

**Подтверждено.** Wrapper `0x635180`, integer core `0x5981D0(out, seed, worker_reference, slot)`.

`0x63544D–0x63549A`: worker_reference XY получаются из worker+0xC/+0x10 после float32 `+0.5` и x87 FISTP. `0x63549D–0x6354C6`: seed XY получаются FISTP из переданной позиции **без +0.5**. Это не CVTTSS2SI. Константа `0x73708C=.5`. **Неизвестно:** действующий x87 rounding mode в нужном live-вызове; не выдавать `int()` или Godot `round()` за доказанный wrapper. Integer-core ниже от этого не зависит.

```text
I = [minX+1,maxX−1) × [minY+1,maxY−1)
if seed outside I: return (-1,-1)
best=(-1,-1); best_d2=INT_MAX
work_mask=0xB<<(4*slot); visited_mask=4<<(4*slot)
queue=[seed]; C(seed).marks |= visited_mask
for q in queue, FIFO (queue растёт в ходе прохода):
    if q outside I: continue
    if metadata[C(q).block_ref].byte0 < 12 AND C(q).byte[0x34+slot] != 0:
        d2 = (q.x-worker_reference.x)^2 + (q.y-worker_reference.y)^2
        if d2 < best_d2: best=q; best_d2=d2
    if C(q).marks & work_mask:
        for n in [q+(1,0), q+(-1,0), q+(0,1), q+(0,-1)]:
            if !(C(n).marks & visited_mask):
                queue.append(n); C(n).marks |= visited_mask
for q in queue: C(q).marks &= ~visited_mask
return best
```

| VA | Доказательство |
| --- | --- |
| `0x598222–0x598258`, `0x598310–0x59834C` | Одинаковый interior gate для seed и каждой извлечённой точки. Пограничные элементы очереди не оцениваются и не расширяются. |
| `0x59825E–0x5982DB` | Маски, очередь, безусловный visited seed. |
| `0x598300–0x59830C`, `0x5985A9–0x5985AE` | Растущий FIFO по индексу, до исчерпания очереди. |
| `0x59836A–0x5983DC` | Ref через `C+0`, metadata stride `0x59`, unsigned byte0<12, затем ненулевой byte `C+0x34+slot`. Повреждённый ref идёт в exception-path, а не считается пустотой. |
| `0x5983E1–0x598405` | Только квадрат XY-расстояния до worker_reference; signed i32 MUL/ADD/CMP, строгое улучшение. При равенстве сохраняется первый FIFO-кандидат. Для обычных небольших координат переполнения нет; перенос на произвольные большие координаты требует сохранения i32-арифметики. |
| `0x59840D–0x59841E` | Проверка work-mask **после** оценки кандидата. Поэтому немеченый seed и немеченое внешнее кольцо могут выиграть. |
| `0x598424–0x598482`, `0x598485–0x5984E3`, `0x5984E6–0x598542`, `0x598545–0x5985A1` | Соседи строго +X, −X, +Y, −Y; visited ставится при добавлении. Уже выставленный scratch-bit блокирует добавление соседа. Нельзя незаметно предположить чистые scratch-bits для произвольного повреждённого snapshot. |
| `0x5985EB–0x598618` | Очистка scratch-bit у **всей очереди**, возврат best. Остальные mark-bits остаются. Нет ограничения радиуса или ранней остановки после найденного края. |
| `0x6354EA–0x635512` | Wrapper возвращает `(best.x,best.y,14)` даже для invalid `(-1,-1,14)`. |

Это доказанный обход связной работы + одно немеченое кольцо; он не перескакивает через немеченую точку к другой компоненте. Нет группы, material-word или Hnext gate. Название «край» не даёт права заменить алгоритм поиском ближайшей отмеченной точки.

Воспроизводимые integer-core примеры, выведенные из веток (не live-captures): мир `[0,10)²`, seed/reference `(5,5)`, у seed mark3/meta0=15. Если только немеченый `(6,5)` имеет meta0=11 и byte34=1, результат `(6,5)`; первая очередь `(5,5),(6,5),(4,5),(5,6),(5,4)`. Если оба `(6,5)` и `(4,5)` допустимы, выигрывает +X при равной d2=1. Если seed немеченый и сам допустим, оценивается только seed; соседняя компонента не ищется. Seed `(0,5)` сразу invalid. Все эти примеры предполагают исходный scratch-bit=0.

**Неизвестно:** полная игровая семантика/производитель `C+0x34+slot`. PMP `cell_attribute` идёт в `C+7`, counted U16/RLE — в `C+0x3C..0x7B`; ни то, ни другое нельзя подставлять вместо этого байта. Поэтому helper get_digedge с выдуманной доступностью не добавлен. Известные byte0 легко брать из BlockDB; для начального block0 byte0=15 и candidate-gate false, хотя очередь через такую отмеченную точку проходит.

## 3. Продолжение и остановка обычного наземного задания

**Подтверждено Tcl, без laser-ветки.** `dig_starttask:138–144` выбирает startpos, объявляет работу и вызывает get_digedge. При Y>0 ставит walk_pos_dig и dig_continue (`:147–160`); иначе возвращает false (`:162`). `vector_fixdig` и ходьба остаются отдельными подсистемами.

В `dig_continue:208` условие буквально `remaining_sparetime==0.0 || current_worktask!="dig"`; эта запись не исправлялась по догадке. Внутри ветки:

1. При try>6 вызывается dig_resetid (`:209`). Регистрация `0x6718BA–0x6718E0` связывает его с `0x67BB90`; **`0x67BC56` записывает worker+0x250=−1**. В обычном ранжировании все группы после этого получают одинаковые +8; это не жёсткий фильтр.
2. `:211–212`: `digpoint = dig_next(current_position,worker,try) + (0,0,−1)`. Для Hnext11 получаем Z13; sentinel становится `(-1,-1,0)`.
3. `:237–239`: требуется Y>0 и try<9; затем dig_check. Он берёт `get_angle_num4` относительно worker+(0,−0.8,0), проверяет три соседние точки в выбранном направлении; больше одного `get_hmap<13` означает успех (`:169–182`). При отказе рекурсивно try+1, то есть следующий **ранг**, а не следующий FIFO-сосед. Нельзя считать get_hmap здесь Hnext по совпадению названия.
4. При необходимости подхода try увеличивается: для нового try<8 walk-failure очищает очередь и вызывает dig_continue try; при try==8 вызывает dig_starttask 0; при большем try fallback пуст (`:245–259`). Путь здесь не ранжируется селектором.
5. Если Y<=0 либо try>=9: dig_endanim, dig_resetid, work_idle, return true (`:284–290`). Таким образом, один invalid выбор сам не стирает terrain marks. После локальной серии ударов `:375–376` отдельно ищется K=1 со strict=true и снова применяется dig_check; при отказе серия прерывается.

## 4. Проверенный helper и входы интегратора

`godot/scripts/native_dig_next.gd` предоставляет `select_next(P, world_bounds:Rect2i, slot, worker_group, samples, rank_index=0, require_same_group=false)`. Это core-ranking API с индексом ранга от нуля. Для обычного Tcl try передать `max(try,0)`; для пятиаргументного Tcl-вызова передать **0** и bool. XYZ — native logical coordinates, до Godot/render-преобразований. Rect2i содержит origin+size и исключённый end; размеры PMP не объявлены автоматически глобальными world bounds.

`samples[Vector2i(x,y)]` обязан иметь packed `marks` для **каждой** точки scan_rect. Для реально отмеченных кандидатов нужны `material_word`, `next_height`, `groups`, в порядке native gates. Hnext должен поступить из четырёх refs/BlockDB по `0x5968B0`, см. [native-terrain-strike-2026-11-17.md](native-terrain-strike-2026-11-17.md); material — из импортированного runtime word+0x18, см. [native-tunnel-validator-2026-11-17.md](native-tunnel-validator-2026-11-17.md). Полнота mesh-списка 943 не заменяет полноту source grid 1056. Нельзя считать отсутствующую клетку немеченой.

Выходы: `ok` + point/cost/scan_rect; `no_candidate` + native sentinel/cost=10000000/scan_rect; `unknown` + at/missing; `invalid_input` для недопустимого слота/bounds/нечислового P. Последние два статуса — явный контракт адаптера, не дополнительные ветки оригинала. Входной snapshot не изменяется; helper не реализует Tcl retry-loop, dig_check, walk, strike policy или get_digedge.

**Исходный положительный fixture:** `multi_start_010.pmp` SHA-256 `b6fc5ef7b1800dce9fb0dd4a42de879b8198f25ac84eb82b524266378ddb7807`, 44×24. В (9,3) flag2→material2; refs `(8,2),(9,2),(8,3),(9,3)` равны 0. BlockDB2 (`SHA-256 13d06172ae42a42657c10fe6007c8213fc525a7fde8132fe0041f48c9507b856`): metadata base2136412/stride89, соответствующие next-refs `[22,32,44,54]`, высоты `[11,11,11,11]` ⇒ Hnext11. При **явно добавленных** mark3/group0/workerG0/P=(9,3.75,9) и bounds адаптера `(0,0,44,24)` результат `(9,3,14)`, cost0. Marks, P и bounds fixture заданы тестом, не извлечены из PMP. Проверка four-ref мутации принадлежит предыдущему результату.

**Проверено:** Godot 4.7.2 headless, `--path godot --script res://tools/native_dig_next_self_test.gd`; 22 fixtures и 101 assertion. Ожидаемые XYZ и float32 bits в соседнем JSON заданы независимо от helper: равенства, штраф/strict/raw group, slots, height, Z clamp, исчерпание ранга, неполные входы и границы. Lint проекта — 0 errors/0 warnings. Это подтверждает перенос указанной арифметики и контракта; поведение оригинального процесса и полный task lifecycle пока не проверены. Недоказанные интеграционные зависимости: реальные world bounds/offset, актуальный worker group stamp, player-byte для get_digedge, x87 wrapper rounding и отдельные movement/policy gates. Гипотезы для закрытия этих пробелов в код не внесены.
