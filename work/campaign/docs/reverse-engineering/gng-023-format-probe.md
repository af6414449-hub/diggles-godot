# Форматный зонд `gng_023`

Дата: 2026-11-14

## Связка из оригинального Tcl

```tcl
map_template data/templates/gng_023.pmp $xoffset $yoffset
map_setlayer2 $xoffset $yoffset data/templates/kris_gng_023_a.l2m
```

## `.pmp`

- размер: 174 байта;
- первые два little-endian `uint32`: `4`, `4`;
- далее 16 одинаковых байтовых значений `02`, что похоже на блок 4×4;
- после этого идут little-endian поля с последовательностью `192, 80, 193, 0, 194, 195, 196`;
- в хвосте присутствуют повторяющиеся крупные значения, вероятно ссылки/координатные или packed-поля.

## `.l2m`

- размер: 44 байта;
- сигнатура `M2L\0`;
- после сигнатуры наблюдаются значения `4`, `4`, затем packed-последовательность с `0x40`, `0xC0`, `0x11`, `0x45`, `0x55`;
- формат не является простой прямоугольной bitmap-картой.

## Вывод

Диагностическая визуализация 29×6 для `.pmp` была неверной: первые поля прямо указывают на блок 4×4, а оставшиеся данные являются структурированными записями. Следующий renderer должен сначала разобрать заголовок и записи, а не отображать весь файл линейно.

Для следующей итерации нужно:

1. трактовать первые два `uint32` как размеры/параметры блока;
2. отделить 4×4 байтовую матрицу от последующих записей;
3. сравнить `gng_023.pmp` с `gng_022.pmp` и `caves_1.pmp`;
4. сопоставить числовые записи с `.3db`/текстурами;
5. восстановить tile/mesh placement до визуализации.
