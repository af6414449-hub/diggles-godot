# Аудит оснований плана — 2026-11-15

Этот документ фиксирует прочитанные файлы и проверенные сведения. В этой работе не запускались игра, захват кадра, сборка APK или тесты реализации. Изменены только документы планирования.

## Факты текущего конвейера

- android/app/src/main/java/com/diggles/port/GameView.java загружает saved_scene.jpg и рисует его Canvas.drawBitmap. Жесты изменяют растр, геометрия 3D в приложении не рендерится.
- tools/render_saved_scene.py использует saved_runtime_placements/saved_template_objects из map.json. demo_start_scene.json — другой манифест с ключом objects; текущий JPEG не является рендером этого эталонного файла.
- В офлайн-рендере terrain-detail кладётся на плоскость; вершины модели после X→Y→Z вращений проецируются в XY. Z используется для сортировки треугольников по среднему, полноценного буфера глубины нет (render_saved_scene.py, строки 122–135).
- Парсер 3DB читает bounds, но офлайн-рендер использует для точек (v−0.5)×100, не применяя bounds или инициализацию класса. Это не доказывает ошибку масштаба; требует проверки на исходной модели.
- extract_template_objects.py сохраняет detail_tier, офлайн-рендер его не фильтрует. export_editor_template.py индексирует new и исходные трансформации без исполнения Tcl и свойств класса.
- В data/Templates/tcl/demo_start.tcl строки 251, 257, 263, 269, 275 и 281 создают шесть Grillpilz с одинаковыми координатами (16.4004, 10.4015, 5.8). На строке 245 рядом создаётся Schatztonne. Назначение совпадений не установлено; предметы внутри контейнера, физика, скрытие — гипотезы, а не основание автоматически удалить дубликаты.
- В data/Scripts/classes/items/emitter.tcl существуют class_defaultanim под условием get_mapedit. Следовательно, режим редактора может добавлять служебные изображения, которые нельзя принимать за обязательные игровые модели.
- demo_start_scene.json: 76 статических объявлений, 59 связей с модельными пакетами, 17 без привязки. Среди последних свет, Info_Coll, Feuerstelle, Bier, Zelt и Zwerg. Это не 17 доказанно отсутствующих мешей.

## BlockDB — проверенная новая зацепка

Установленная игра: C:/Program Files (x86)/Steam/steamapps/common/Diggles The Myth of Fenris.

| Файл в data/ | Размер, байт | Первые 16 байт |
|---|---:|---|
| BlockDB0.BDB | 20 751 437 | 0b00000000000000a0cf010000000000 |
| BlockDB1.BDB | 26 067 491 | 0b00000000000000a0cf010000000000 |
| BlockDB2.BDB | 37 045 082 | 0b00000000000000a0cf010000000000 |

В Diggles.exe найдены ASCII-строки со следующими файловыми смещениями:

| Смещение | Строка |
|---|---|
| 0x3290cc | void CBlockDB::LoadDB(const KStr& sFileName) |
| 0x32910c | BlockDB mesh alloc %d |
| 0x329154 | BlockDB mesh load %d Blocks |
| 0x329170 | BlockDB ILT load |
| 0x329184 | data\\BlockDB2.BDB |
| 0x329198 | data\\BlockDB0.BDB |
| 0x3291ac | data\\BlockDB1.BDB |

В бинарнике также есть строка пути к Map/BlockDB.cpp. Это диагностическая строка; наличие исходного C++-файла на компьютере не установлено.

Подтверждено: EXE связывает BDB с загрузкой mesh-блоков. Гипотеза: часть PMP-полей ссылается на эту базу. Неизвестны формат записей, схема адресации, назначение трёх баз и преобразование блоков. Следующий полезный результат — проследить загрузчик, извлечь один меш и сопоставить с hol_024, а не соединять соседние u16 на глаз.

Повтор проверки: прочитать первые байты BDB без изменения файлов; найти перечисленные ASCII-последовательности через bytes.find в Diggles.exe. Смещения относятся к локальной версии EXE из прежнего PE-аудита; при смене файла их нужно перепроверить.

## Внешние инструменты: возможность, а не выполненная интеграция

- [Diggles3db](https://github.com/djunkles/Diggles3db): README описывает экспорт в glTF. Это независимая точка сравнения нашего парсера.
- [Diggles3db-Converter](https://github.com/Zimennik/Diggles3db-Converter): автор заявляет сохранение геометрии, материалов, анимаций и иерархии, экспорт в FBX через Blender. Совместимость с нашими конкретными образцами не проверялась.
- [Godot — доступные 3D-форматы](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html): рекомендован glTF 2.0, поддерживаются .gltf и .glb. Поэтому сначала оценивать этот промежуточный путь.
- [RenderDoc](https://github.com/baldurk/renderdoc): поддерживает D3D11; Windows x64-версия поддерживает захват 32-битных программ. Предыдущий локальный PE-аудит нашёл D3D11/DXGI у DigglesPort.dll. Это основание для пробы; успешный захват Diggles ещё не доказан.
- [RenderDoc Mesh Viewer](https://github.com/baldurk/renderdoc/blob/v1.x/docs/window/mesh_viewer.rst): показывает входные/выходные данные вершин и представление меша. Автоматически угаданная обратная проекция может быть неверной; матрицы и координаты нужно проверять.

Захват кадра не восстанавливает всю невидимую сцену, игровую логику, коллизии или изменяемый грунт. Он полезен как источник геометрии и эталон для импорта.
