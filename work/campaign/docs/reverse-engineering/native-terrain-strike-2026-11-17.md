# Один удар по грунту: четыре block-ref и завершение меток

Дата: 17.11.2026. **Подтверждено статическим чтением EXE и исходных данных:** один принятый удар выбирает не более одного next-ref для каждого из четырёх углов; заменяются только кандидаты, чья угловая высота равна общему Hnext. После записи всех четырёх refs Hnext вычисляется заново и в этой же операции очищаются завершённые метки **всех восьми слотов целевой точки**. Для исходного `(9,3)` коридорная метка 3 завершается за один принятый вызов.

**Граница:** ниже специфицирована мутация после положительной политики `0x5976B0`. Её объектные запреты, работа гнома, сетевой протокол и эффекты — отдельные зависимости. Оригинальный процесс не запускался; live-исполнение не выдаётся за проверенное. Изменены только этот отчёт и соседний JSON с fixtures; код, контроллеры, экспорт, статус и существующие исследования не изменялись.

## 1. Источники и точные ветки

Все адреса — preferred VA `Diggles.exe`, image base `0x400000`. EXE: `C:/Program Files (x86)/Steam/steamapps/common/Diggles The Myth of Fenris/Diggles.exe`, SHA-256 `58a01d3d80670a6042c66a82684397c98e39c503e00a6e2c2c511f338a30ed74`. `O/` далее означает его каталог `data/`. Код прочитан через pefile/Capstone; `tools/.cache/diggles-text-disassembly.txt` служил указателем адресов.

| VA | Подтверждённое действие |
| --- | --- |
| `0x596BB2–0x596BED` | Interior bounds: `minX+1 <= x < maxX-1`, аналогично Y. За границей — AL=false без очистки метки. Глобальные bounds не выводятся из размеров PMP; см. предыдущий `native-tunnel-validator-2026-11-17.md`. |
| `0x596BFA–0x596C20` | Слот `L = u32(worker+0x36C)`; вызов политики `0x5976B0(x,y)`. При false перейти к очистке **только L** в целевой точке и вернуть false (`0x596C78–0x596CAA`). |
| `0x596C22–0x596C62` | Прочитать nibble L из `C(x,y)+8`, декодировать target, вызвать `0x5968B0` для Hnext. |
| `0x596C6F–0x596C8E` | **Если target > Hnext:** очистить только nibble L, вернуть false; refs и dirty-регионы этой веткой не меняются. Равенство разрешает удар. |
| `0x596CAD–0x596E4E` | Из старых refs вычислить четыре результата, по одному кандидату на угол. Никакого перехода по цепочке здесь нет. |

| `0x596EF0–0x596F6A` | На новых refs пересчитать Hnext и проверить все восемь nibble целевой точки: очистить каждый, у которого **target(nibble) > post_Hnext**. |
| `0x596FD4–0x596FE2` | Целевой cell `(x,y)` дополнительно получает `C+0x13 |= 2`. |
| `0x597284–0x5972FF` | Два запроса invalidation: flags `0x10040` и `0x200`, прямоугольники ниже. |
| `0x597304–0x59731C` | `worker+0x250 = u32(C(x,y)+0xC) >> (4*L)` — в этой записи **нет** дополнительного `&15`. Само слово групп `C+0xC` не меняется. |
| `0x597423–0x597425` | После последующих эффектов/сообщения вернуть AL=true. |

**Подтверждено:** в самом core нет отдельной проверки parity и нет отдельного `if mark==0: return false`. Нулевой nibble проходит через target=15 и обычное сравнение. Восстановленный слот берётся из worker, а не из текущего UI-selection.

## 2. Формула одного принятого шага

`C` — runtime-cell stride `0x7C`; `C+0` — block-ref, `C+8` — восемь mark-nibbles, `C+0xC` — группы. `M[b]` — metadata BlockDB, stride `0x59` (89 байт). Высоты — bytes metadata, не PMP trailing `cell_attribute` и не player-byte `C+0x34+L`.

| Порядок | Cell | Corner k | next-ref из старой metadata | Кандидатный высотный byte | Выбор / запись |
| --- | --- | ---: | --- | --- | --- |
| NW | `(x-1,y-1)` | 3 | `i32(M[old]+0x4C)` | `u8(M[next]+0x53)` | `0x596CF2–0x596D14` / `0x596E64` |
| NE | `(x,y-1)` | 2 | `i32(M[old]+0x48)` | `u8(M[next]+0x52)` | `0x596D5B–0x596D7D` / `0x596E8B` |
| SW | `(x-1,y)` | 1 | `i32(M[old]+0x44)` | `u8(M[next]+0x51)` | `0x596DC4–0x596DE6` / `0x596EB0` |
| SE | `(x,y)` | 0 | `i32(M[old]+0x40)` | `u8(M[next]+0x50)` | `0x596E29–0x596E4E` / `0x596ED3` |

Hnext — значение уже разобранной функции `0x5968B0`, а не просто текущая высота:

```text
target(n):
    if n == 0: return 15
    if (n & 8) == 0: return 11
    return max(4*(n & 3) - 1, 0)

next_height(point, refs):
    for each (cell, k) in [NW/3, NE/2, SW/1, SE/0]:
        old = refs[cell]
        next = M[old].i32[0x40 + 4*k]
        can_change = next != -1 and next != old
        chosen = next if can_change else old
        h[k] = M[chosen].u8[0x50 + k]
    if no corner can_change: return -1
    return max(h)

pure_core(point, worker_slot, policy_passed):
    if not native_interior_bounds(point):
        return false                         # marks и refs не трогать
    if not policy_passed:
        clear_mark_nibble(point, worker_slot)
        return false

    T = target(mark(point, worker_slot))
    H = next_height(point, refs)
    if T > H:
        clear_mark_nibble(point, worker_slot)
        return false

    old_refs = snapshot(refs[NW], refs[NE], refs[SW], refs[SE])
    for each (cell, k, old) in this snapshot:
        next = M[old].i32[0x40 + 4*k]
        result[cell] = old
        if next != -1 and M[next].u8[0x50 + k] == H:
            result[cell] = next               # один кандидат, НЕ while
    for each cell in [NW, NE, SW, SE]:
        refs[cell] = result[cell]
        dirty_byte_13[cell] |= 1

    post_H = next_height(point, refs)          # после всех четырёх записей
    for L in 0..7:
        if target(mark(point, L)) > post_H:
            clear_mark_nibble(point, L)       # другие точки не обходятся
    dirty_byte_13[SE] |= 2
    emit_invalidation_requests(point)
    return true                              # эффекты описаны отдельно
```

Предпосылки: все нужные refs/next-refs валидны и metadata доступны. Нативные исключения по повреждённым индексам не являются обычной веткой «подставить block 0». Условие выбора кандидата — **равенство общему H**, не `candidate_h >= target`, не `candidate_h < current`, не безусловная замена всех четырёх на next. Все результаты читаются из старого снимка до первой записи. Core не проверяет `changed_count>0`; добавлять такой gate как «найденный нативный» нельзя.

Post-pass в оригинале вызывает `0x5968B0` заново для каждого L, но между вызовами меняются только marks. В чистой функции один post_H эквивалентен. Если post_H=-1, очищаются даже cave-nibbles с target=0, поскольку `0 > -1`. Строгое `>` существенно: target=post_H **сохраняет** метку, позволяя следующий удар до этого уровня.

## 3. Независимые fixtures из PMP/BlockDB2

Fixtures находятся в соседнем JSON. Это непосредственно декодированные bytes исходных файлов, независимо от нового TerrainState/контроллера/экспортёра интегратора. Ожидаемые ветки сопоставлены с инструкциями выше; нативный код не исполнялся. В каждой принятой операции явно предполагаются native-interior bounds и `policy_passed=true`; это не утверждение, что неизвестные объектные gates оригинального запуска обязательно пропустят точку.

Исходники:

- `O/Templates/multi_start_010.pmp`: 44×24, SHA-256 `b6fc5ef7b1800dce9fb0dd4a42de879b8198f25ac84eb82b524266378ddb7807`.
- `O/BlockDB2.BDB`: 37045082 байта, SHA-256 `13d06172ae42a42657c10fe6007c8213fc525a7fde8132fe0041f48c9507b856`. 118688 metadata-records, начало `2136412 = 28 + 18*118688`; поля читаются `offset + 89*id + field`. Соответствие layout runtime: `0x565E26–0x565E38`; доступ metadata — `0x4093B0`.

### A. Начальный (9,3), коридор

В PMP четыре refs `(8,2),(9,2),(8,3),(9,3)` равны 0. Эти cells действительно записываются загрузчиком через непустую four-corner окрестность; сырой flags целевой точки=2, attribute=4. Последние два числа не подменяют высоту.

| Cell | Старый ref | next-ref | Кандидатная h | Новый ref | Новые bytes `+0x50..53` |
| --- | ---: | ---: | ---: | ---: | --- |
| (8,2), NW | 0 | 22 | 11 | 22 | 15,15,15,11 |
| (9,2), NE | 0 | 32 | 11 | 32 | 15,15,11,15 |
| (8,3), SW | 0 | 44 | 11 | 44 | 15,11,15,15 |
| (9,3), SE | 0 | 54 | 11 | 54 | 11,15,15,15 |

Pre-Hnext=11; target(3)=11: шаг принят. Следующие кандидаты **уже новых** refs: `[34503,34505,34510,34511]`, углы `[7,7,7,7]`, поэтому post-Hnext=7. **Метка 3 очищена в этом же ударе.** Повторный вызов с заново выставленным nibble 3: `11>7`, false, только очистка выбранного nibble; refs остаются `[22,32,44,54]`.

Та же точка, но cave-nibble 10 (target=7): первый принятый шаг всё ещё 15→11, метка остаётся (`7==post_Hnext`). Второй принятый шаг меняет refs на `[34503,34505,34510,34511]`, высоту на 7; post-Hnext=3 и метка очищается. Весь источник next-chain здесь: `0 → [22,32,44,54] → [34503,34505,34510,34511] → [39250,39253,39258,39259] → [55,57,47448,47449]`; угловые уровни 15→11→7→3→0, после последнего шага Hnext=-1. Это **несколько вызовов**, не один обход до target.

### B. Соседний (10,3) после только A

Его cells `(9,2),(10,2),(9,3),(10,3)` теперь имеют старые refs `[32,0,54,0]`. Их next-кандидаты по соответствующим углам — `[207,32,81,54]`, каждый даёт h=11. Результат одного corridor-удара — **`[207,32,81,54]`**, post-Hnext=7, mark 3 очищен. Это проверка общей границы соседних операций: заново инициализировать все четыре cells из PMP перед вторым ударом нельзя.

Для соседнего `(9,4)` после только A аналогично: старые `[44,54,0,0]`, результат `[33,43,44,54]`, pre/post-Hnext 11/7. Незатронутые refs мира сохраняются; общий угол не означает удаления всего блока из сцены.

### C. Частичная замена, начальный (21,2)

Старые refs из PMP — `[11197,80,11683,80]`; кандидатные refs — `[33,34524,37200,34522]`, кандидатные h — **`[11,7,11,7]`**. Hnext=11, результат — **`[33,80,37200,80]`**: NE и SE обязаны остаться 80, хотя их next существует и имеет меньшую высоту. Post-Hnext=7; corridor-mark очищается.

Все четыре **текущих** общих угловых byte в этом fixture до и после равны 11. Значит, принятый вызов может менять refs без уменьшения этих угловых byte; проверка «высота обязательно уменьшилась» не эквивалентна core. Намерение таких геометрических переходов — **неизвестно**, сами переходы подтверждены данными и сравнением `==H`.

### D. Очистка нескольких игроков и сохранность групп

На свежем A задать `L=0`, packed marks `0x20F89BA3`, то есть slots 0..7 = `[3,10,11,9,8,15,0,2]`. После принятого шага post-Hnext=7 и marks должны быть **`0x000890A0`**, slots `[0,10,0,9,8,0,0,0]`. Группы `C+0xC`, например `0x76543210`, остаются прежними. Dirty-byte 13 исходно `[0x40,0x80,0x20,0x10]` в NW/NE/SW/SE станет `[0x41,0x81,0x21,0x13]`: сохраняются старые биты.

В ранней ветке отказа нет прохода по всем слотам: например, при target 11 и pre-Hnext=7 очищается только выбранный L, остальные pending-nibbles сохраняются. Это отличается от post-pass принятого шага.

## 4. Dirty-bounds и другие изменяемые поля

**Прямые terrain-записи core:** четыре `u32(C+0)` refs; bit0 byte `C+0x13` у всех четырёх; bit1 byte `C(x,y)+0x13`; mark-word `C(x,y)+8` по условиям выше. На этом участке нет прямой записи material-word `C+0x18`, attribute `C+7`, групп `C+0xC`, player-bytes `C+0x34..3B` или 8×8 данных `C+0x3C..7B`. Это утверждение о прямых записях core, а не о будущих последствиях вызываемых подсистем. Отдельного словаря «новая высота точки» оригинал здесь не пишет: высоты выводятся из новых BDB refs.

Core передаёт в `0x5A3FD0` следующие rectangles **в координатах 8× на sample**, с exclusive-концом:

| Request | Flags | Rectangle `(left,top,right,bottom)` | Для (9,3) |
| --- | --- | --- | --- |
| `0x59728F–0x5972BF` | `0x10040` | `(8x-8,8y-8,8x+8,8y+8)` | `(64,16,80,32)` |
| `0x5972CF–0x5972FF` | `0x200` | `(8x-4,8y-4,8x+4,8y+4)` | `(68,20,76,28)` |

Это не размеры в единицах Godot и не обещание, что всех consumer-обновлений достаточно ограничить четырьмя meshes. Диспетчер сначала clips к world `+0x94..A0` (`0x5A3FE9–0x5A4032`), а flag `0x10000` порождает дополнительные запросы, включая расширение на 16 по всем сторонам (`0x5A4093–0x5A4166`). Точные назначения всех его flags/очередей — **неизвестны**; список четырёх клеток, в чьи ref-поля core выполняет запись, доказан. Для мешей с совпавшими old/new можно избежать пересборки как оптимизации адаптера, сохранив нативный dirty-контракт отдельно.

Дополнительные записи/вызовы после смены refs:

- `0x596F6C–0x596FD2`: при `world[0x50+4*L]==-1` создать handle через manager `0x492250 → 0x495070` и сохранить его; `0x59704E–0x597087` может записать `5` в record этого handle `+0x5C`. Назначение полей — **неизвестно**, не material/height.
- `0x596FE6–0x59700E`: читать новый byte высоты через `0x4093F0(8x,8y)` и прибавить `2.0` для позиции эффекта. Сам `0x4093F0:0x4093FE–0x409444` выбирает metadata и byte локальной 8×8 позиции; при целых `(8x,8y)` это **`M[SE.new][0]`**. Это уже текущая высотная выборка, в отличие от Hnext. Для A она 11, эффект получает z=13.
- Вызовы `0x495940`, `0x4964C0` и условная ветка RNG/`0x495CA0` (`0x597102–0x59727F`) вынесены за чистый terrain-step. Наличие этих вызовов не устанавливает выдачу ресурса в инвентарь, его тип или количество.
- `0x597304–0x59731C` копирует shifted group-word в `worker+0x250` без маски. `0x597373–0x5973A0` формирует событие по строке `0x72B168 = "digmessage %i %i %i %i"` с аргументами x, y, `worker+0xDC`, текущий высотный byte; сетевое отправление дополнительно условно. Полный смысл обработчика здесь не установлен.

## 5. Граница политики и завершения пещеры

**Подтверждено:** `0x5976B0` начинается проверкой low material против 0/3 и Hnext против -1 (`0x5976EA–0x59771E`), затем строит запрос объектов. Полный запрос и последующие запреты в этот ограниченный аудит не вошли. Поэтому pure-step должен принимать уже проверенный `policy_passed`, а не выдавать свой упрощённый мир за полную нативную политику. При false core всё равно снимает выбранную метку: это не нейтральная «попробовать позже» ветка.

Core не удаляет pending cave-record непосредственно. Внешний Tcl wrapper вызывает core в `0x634A13`, сохраняет AL в BL (`0x634A18`), затем при отдельном host/context-условии вызывает `0x58BA00` (`0x634A2F–0x634A4C`). **В этой ветке нет проверки BL перед вызовом completion-manager**; старое описание «только при true» не подтверждается инструкциями. Проверка/создание облицовки и удаление cave-record — за пределами четырёх refs; их нельзя отождествлять с очисткой nibble в core.

## 6. Достаточная проверка интеграции

1. На A получить четыре исходных меша BDB refs `22/32/44/54` на прежних cell-координатах и убедиться, что mark 3 снят уже после одного разрешённого удара; другие клетки не удалены.
2. На B использовать изменённые общие refs, получить `207/32/81/54`; метаданные для post-Hnext нужны и для следующих refs, чьи meshes пока не рисуются.
3. На C получить ровно две замены; не принимать меньший кандидат 7, пока общий Hnext равен 11.
4. Проверить target=post-Hnext (метка остаётся), terminal Hnext=-1 (завершённые marks снимаются), отказ до мутации (очистка только выбранного слота), packed multi-slot D и сохранность group-word/старых dirty-битов.

Это критерии для будущего mutable TerrainState. Здесь проверены bytes PMP/BDB и инструкции EXE; импорт/рендер новых мешей, действия гнома, объекты-препятствия и запуск игры не выполнялись.
