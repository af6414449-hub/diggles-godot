## З24.11 — Camera-set, `camera+0x130` и «плоскость мира 14.4»: три поправки к прежним записям

*(2026-11-22; разбор субагента Explore по декомпиляции + мои проверки дизасмом и по численным константам)*

### ФАКТ (Diggles.exe + скрипты игры)

1. **УТОЧНЕНИЕ (без противоречия прежним записям): объект камеры — это НЕ `DAT_00772400`, а `*(int *)(DAT_00772400 + 0x5a4)`.**
   `DAT_00772400` — глобальный игровой объект; поле `+0x5A4` = указатель на камеру
   (`FUN_006ae6b0_006ae6b0.c:34, 40`). Все смещения `+0x134…+0x164`, о которых шла речь в З24.1,
   принадлежат объекту по `+0x5A4` (в З24.1 это уже было записано верно — здесь подтверждается
   и добавляется ссылка на конструктор глобального игрового объекта).
   Evidence: `FUN_006ae6b0_006ae6b0.c:34, 40`; дизасм `CTclGlobalMethods__CameraSets`: `0x629034 mov ebx, dword ptr [eax+0x5a4]`;
   `FUN_005716e0_005716e0.c:662` `iVar13 = *(int *)(DAT_00772400 + 0x5a4);`.


2. **ПОПРАВКА к З24.1: «плоскость мира z = 14.4» — это НЕ плоскость мира, а ВЫСОТА ПОВЕРХНОСТИ ЖИДКОСТИ.**
   * `14.4f` = `0x41666666`, зашит **непосредственно в код** (`mov dword ptr [esi+8], 0x41666666`),
     а не берётся из настроек и не вычисляется;
   * встречается **только в трёх функциях**: `FUN_005716e0`, `FUN_00573250`, `FUN_00574c60`;
   * эти три функции вызываются **исключительно** из рендерера жидкости:
     `CFluid__Draw_00576c60.c:580` (`case 1`), `:585` (`case 2`), `:591` (`case 3/4`);
   * `pfVar6[2] = 14.4` — это **Z-координата вершины квада ячейки воды** (`FUN_005716e0:676, 688`);
     второе применение — стартовая высота при переборе столбцов: `local_30 = 14.4 − local_40` (`:201`).
   ⇒ **Другой константы «плоскости земли» в exe нет** (полный grep `14.4` по 11 373 файлам — только эти три файла).
   ⇒ **Вывод З24.1 «камера ведётся при постоянной высоте плоскости z = 14.4» НЕВЕРЕН в этой части.**
   Что в З24.1 остаётся верным и подтверждается здесь: **`+0x14C/+0x150` (rx/ry) не читаются никем**
   (ни `FUN_005716e0`, ни `FUN_00573250`, ни `FUN_0052c510`, ни `FUN_00529570` к ним не обращаются —
   читаются только `+0x154`, `+0x158`, `+0x15C`, `+0x160`, `+0x164`).
   Evidence: `FUN_005716e0:662-690`; `FUN_00573250:605-619`; `CFluid__Draw:578-593`;
   `FUN_00529570:29-32`; `FUN_0052c510:171-191`.

3. **Подтверждено З24.1: «глаз = фокус + 3·(offX, offY)».**
   `FUN_005716e0:662-668`:
   ```
   camera = *(int *)(DAT_00772400 + 0x5a4)
   eyeX = *(float *)(camera + 0x164) * 3.0 − *(float *)(camera + 0x158) * 0.125 * 0.5
   eyeY = *(float *)(camera + 0x160) * 3.0 − *(float *)(camera + 0x154) * 0.125 * 0.5
   ```
   Evidence: `FUN_005716e0_005716e0.c:662-668`; аналогично `FUN_00573250:605-611`.

4. **`camera+0x130` — это НЕ угол наклона, а float-метка игрового времени; и она нигде не читается.**
   * `DAT_00772400 + 0xA088` = **глобальный игровой таймер (double)**: сброс — `CTclGlobalMethods__GameTime_0061ece0.c:110`
     (команда `gametime reset`), обновление — `FUN_00556570_00556570.c:111`
     `*(undefined8 *)(DAT_00772400 + 0xa088) = local_30;`, шкала времени — `/150.0`
     (`CTclGlobalMethods__TimeSchedule_00645410.c:252`, `CTclObjMethods__GetWorkTime_0068b790.c:107`);
   * `camera+0x130` пишется ровно в двух местах, оба — как float-копия этого double:
     `CTclGlobalMethods__SetView_006284e0.c:390` и `CTclGlobalMethods__SetViewPos_00629fe0.c:518`
     (дизасм `0x628CAD movsd xmm0, qword ptr [eax+0xa088]` + `cvtpd2ps`);
   * **читателей нет**: полный grep по `0x130` по всей декомпиляции даёт 34 вхождения в 23 файлах,
     и в объекте камеры — только эти две записи; остальные — чужие объекты.
   ⇒ **поле мёртвое**, ровно как `+0x14C/+0x150` и `+0x118/+0x11C` (З24.1).
   Побочно: `DAT_00772400 + 0xA0B8` = копия времени на **начало кадра** (`CGameThread__Draw_006b5d90.c:75`).

5. **Camera-set — это НЕ пресет камеры, а СПЛАЙН-ТРАЕКТОРИЯ ДВИЖЕНИЯ.**
   * Tcl-команда **`camera_set`** (ровно одна, `work\campaign\ref\tcl_command_table.tsv:38`),
     арность **2** (`CTclGlobalMethods__CameraSets_00628f50.c:87` `if (param_3 == 3)`);
   * arg0 → `Tcl_GetDoubleFromObj` → float в `camera+0x124` («скорость» сета);
     arg1 → Tcl-список, каждый элемент — тройка `{tag float float}` (`:147-293`);
   * хранилище: `camera+0x124` (float), `camera+0x128` (буфер `DSFastArray`), `camera+0x12C` (счётчик);
     элемент = **12 Б**: `{uint type@0, float a@4, float b@8}` (дизасм `0x6293B9 lea ebx,[esi+esi*2]` + `0x6293C1 mov [eax+ebx*4],ecx`);
   * **`DAT_0072b3d8` = литерал `"s"` в `.rdata`** (VA 0x72B3D8, байты `73 00`), сравнивается
     **побайтово после `__strlwr`** с тегом тройки (`0x62924A mov ecx, 0x72b3d8`);
     ссылка на этот адрес в декомпиляции ровно одна (`CTclGlobalMethods__CameraSets_00628f50.c:200`);
     ⇒ **это не «имя camera-set»** — имя сета существует только на стороне Tcl (`camsetlist`);
   * `type = 1`, если тег == `"s"`, иначе 0; любое другое значение type → Tcl-ошибка `"Invalid cameraset"`
     (`CTclGlobalMethods__SetView_006284e0.c:393-396`);
   * построение траектории — `FUN_00463930` (вызывается из `SetView`/`SetViewPos` с `this = camera+0xEC`):
     массив траектории = DSFastArray (`camera+0xEC` — указатель, `camera+0xF0` — счётчик),
     элемент `{float x@0, float y@4, float tangent@8}` (шаг 12 Б);
     `type==1` → `FUN_00463500` — касательная Катмулла-Рома
     `t[i] = 2·(y[i]−y[i−1])/(x[i−1]+x[i]) + t[i−1]` (`FUN_00463500:66-67`);
     `type==0` → `FUN_00463310` — касательная задана явно, вычисляется x
     `x[i] = 2·(y[i]−y[i−1])/(t[i]−t[i−1]) − x[i−1]` (`FUN_00463310:42-66`);
   * если camset-флаг = 0, `SetView` строит **дефолтную** траекторию: точка `(1.0, 0.0)` +
     точки `(0.3, 0.5)` и `(0.0, 1.0)` (дизасм `0x628BBE-0x628BEF`, константы `1.0`@`0x737138`,
     `0.5`@`0x73708c`, `0.3`@`0x737060`);
   * флаг camset — это **10-й аргумент `set_view`**: `set_view x y zoom dx dy move freeze speed camset`
     (`CTclGlobalMethods__SetView_006284e0.c:330-350`);
   * `set_view_begin <float>` → `camera+0x188` (`CTclGlobalMethods__SetLightBegin_0064ba50.c:71, 80`).

6. **Где camera-set реально используется.**
   * `camera_set` вызывается в скриптах **ровно в одном месте**: `classes/story/sequencer.tcl:1291`
     (`camera_set [lindex $actcameraset 0] [lindex $actcameraset 1]` внутри `proc sq_camera`);
   * пресеты: `init_camsets` (`sequencer.tcl:1214-1219`) —
     `{standard {1.0 {{s 0.5 0.3} {s 1.0 0.0}}}}`, `{inout {0 {{s 0.3 0.7} {s 1.0 0.0}}}}`;
   * выбор: `sel_camset <name>` (`sequencer.tcl:1227-1237`); добавление: `add_camset <name> <ispeed> <cset>`
     (`1221-1225`), пример `sequences/Urwald/wusch.tcl:17-18`;
   * `init_camsets` зовётся из `sequencer_activate` (`sequencer.tcl:393`) — **при активации секвенсера,
     не при старте главы**;
   * **на старте главы camera_set НЕ используется**: `gameplay/Campaign.tcl:9-10` =
     `set_view_begin 23` + `set_view 246.7 28.8 1.478 -0.29 0.05` (camset = 0 ⇒ дефолтная траектория).
     То же — `Campaign6000.tcl`, `SandboxUrw.tcl`, `classes/story/story.tcl:925`, `Skirmish.tcl:91`.

### Что это меняет для порта

* **Поправка З24.1 (важно):** «плоскость мира 14.4» в exe отсутствует как таковая — **14.4 уместно только
  для поверхности жидкости**. Всё, что порт считал «камерой при z = 14.4», надо перепроверить:
  в exe камера вообще не привязана к постоянной высоте — она задаёт **фокус** (`+0x154/+0x158`),
  **zoom** (`+0x15C`) и **2D-смещение** (`+0x160/+0x164`, |v| ≤ 0.7), а глаз = фокус + 3·смещение.
  Высота рельефа в exe задаётся **данными** (сетка высот блока, З8 п.6), а не формулой.
* **rx/ry из `set_view` — мёртвые и в этом смысле:** они не читаются ни рендером, ни логикой;
  единственное, что из них выводится, — промежуточная пара с длиной ≤ 1.8, которая тоже никуда не идёт.
  ⇒ **Модель порта `tilt = -rx, yaw = ry` (`godot/scripts/native_campaign_camera.gd`) опирается на данные,
  которые в оригинале не имеют эффекта.** Это не «второй интерпретационный слой», а заимствование
  из мёртвого параметра. Порт должен выводить наклон из своего собственного правила (или принять
  фиксированный), а не из `rx/ry` оригинала.
* **Если порт когда-нибудь будет повторять движение камеры в катсценах**, ему нужна сплайн-траектория
  `{x, y, tangent}` с правилом Катмулла-Рома (а не «пресет камеры»). Для статичных скриншотов главы
  это не нужно: camset = 0 ⇒ дефолтная траектория `(1.0,0) → (0.3,0.5) → (0.0,1.0)`.
* **`set_view` в оригинале имеет 10 аргументов**, а порт читает их как 5 (`x y zoom rx ry`).
  Полный порядок: `set_view x y zoom dx dy move freeze speed camset`
  (`dx→+0x14C`, `dy→+0x150`, `move→+0x140`, `freeze→+0x148`, `speed→+0x144`).

### Что осталось неизвестным

* **Кто читает массив траектории `camera+0xEC/+0xF0`** при рендере и что делает `FUN_00463a40`
  («текущий индекс» по траектории) — не найдено. Проверка: grep по чтениям `camera+0xEC`/`+0xF0`
  вне диапазона `0x463220-0x463930` + вызовы `FUN_00463a40`.
* **Точная семантика чисел внутри `{s a b}`** — гипотеза: `a` = значение узла, `b` = касательная/время
  (в `inspeed` задано `{s 1.0 1.0}`, в `inout` — `{s 0.3 0.7}`/`{s 1.0 0.0}`).
  Проверка: breakpoints на `FUN_00463500`/`FUN_00463310` и наблюдение фактических x/y/tangent.
* **`camera+0x130` может использоваться в более ранних билдах** — статически в этой сборке читателей нет.
* **Множители `0.125 / 0.032 / 0.04`** в `FUN_005716e0` (масштаб world→screen для квадов жидкости)
  не разобраны.
