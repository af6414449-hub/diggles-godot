**ФАКТ (Diggles.exe):** в exe есть **глобальный объект-реестр** (`this` = `in_ECX` во всех функциях ниже). Его раскладка восстановлена полностью:

**ФАКТ (Diggles.exe):** хеш-карта — открытая адресация с бинарным поиском внутри корзины; корзины отсортированы по имени, вход — по хешу `h = h*9 + c` по всем символам строки, корзина = `h & 0xFF` (`FUN_00444990.c:19-29,31-52`). Запись корзины: 8 байт — `[указатель на массив пар, счётчик]`; пара: 8 байт — `[указатель на ключ-строку, значение]`.

**ФАКТ (Diggles.exe):** **id = порядок первой регистрации.** Регистрация текстурной стадии — `FUN_0045a7b0.c:13-34`: если имени ещё нет, берётся `id = count-1` (после предварительного роста массива), имя пишется в хеш-карту через `FUN_00440680`, а сама запись создаётся по адресу `base + id*0x50`. Регистрация техники — `FUN_0045aa00.c:13-34`, запись `base + id*0x6C`. Повторная регистрация того же имени возвращает уже существующий id (строка 34 обоих файлов), то есть **id стабилен и детерминирован**.

**ФАКТ (Diggles.exe):** обратный переход id → имя для текстурных стадий — `FUN_0045a850` (`in_ECX+0x50`), для шейдеров — `FUN_0045aab0` (`in_ECX+0x858`); оба возвращают строку `"invalid"` (0x61766e69/0x64696c), если id не найден (`FUN_0045a850.c:99-105`). Имя стадии по id — `FUN_0045b080` (вызывается из `FUN_0045d480.c:138`).

### 7. Что это меняет для порта

1. **Порт может брать готовую таблицу 37 техник и 24 текстурных стадий из оригинала** — это ровно тот контент, который сейчас приходится угадывать. Таблицы приложены (`z38_tables.txt`), их можно перенести в порт как данные.
2. **id техник — фиксированные числа 0..36**, значит «подстановки 7→6, 18→19, 33→7» из З37 надо понимать как подстановки **id техник**: `7` = `model_solid`, `6` = `model_blend`, `18` = `scape_solid`, `19` = `scape_blend`, `33` = `alpha_light`. Это снимает вопрос «что означают эти числа».
3. **Пары (X, X+1) из З36 расшифрованы**: это TS0/TS1 техник `scape_multi_urw`(4,5 = `scape_urw_mt0/1`), `scape_multi_lav`(6,7 = `scape_lav_mt0/1`), `scape_multi_lav_fow`(6,7), `sky_blend_multi`(9,10 = `sky_mt0/1`), `alpha_light`(15,16 = `alpha_light0/1`), `water_blend`(17,18), `sulfur_blend`(19,20), `lava_blend`(21,22). Двухслойная земля Урвальда = `scape_urw_mt0` + `scape_urw_mt1`.
4. **Реестр enum’ов движка нельзя заменять на D3D7-константы «по памяти»**: D3DTOP и D3DBLEND совпадают с D3D9/D3D11 (порту можно класть числа прямо в состояния), а **D3DTEXTUREARG — своя нумерация**, и «инвертированный» аргумент = база | 0x10 (порт это уже учитывает маской `& D3DTA_SELECTMASK`, но сам бит 0x10 при выборе аргумента **игнорируется** — расхождение с оригиналом, если оригинал его учитывал).
5. **Значения фильтров/адресации движка** (MAGFILTER `point=1…anisotropic=5`; MINFILTER `none=1, point=2, linear=3`; MIPFILTER `point=1, linear=2, anisotropic=3`; ADDRESS `wrap=1, mirror=2, clamp=3, border=4`) в портовом `Common.fxh` **не определены вообще** — их надо добавить, иначе `WRAPPED_D3DTSS_MAGFILTER`/`MINFILTER`/`MIPFILTER`/`ADDRESS*` придётся заполнять «на глаз».
6. **Наследование техник** («родитель») — это реальный механизм оригинала: 22 из 37 техник не задают часть полей и берут их от родителя. Порт, если у него есть своя система материалов, обязан воспроизвести цепочку или развернуть её в плоские значения.

### 8. Что осталось неизвестным (и как проверить)

1. **Кто читает `TextStage1..7`** (id > 0) и как ставится вторая текстура в шейдер. В exe видно только заполнение TS0/TS1 у восьми техник. **Проверка:** найти применение техники к отрисовке (вызов `FUN_00483d80` и далее) и посмотреть, читаются ли `+0x48..+0x60` записи техники.
2. **Куда уходят значения enum’ов при отрисовке**: exe нигде не содержит строк `SetTextureStageState`/`D3DTSS_` (grep по `out/decomp` — 0 совпадений), т. е. вызовы идут через vtable DirectDraw/D3D в отдельном слое. **Проверка:** разобрать `DirectDraw7Port`/`IDirectDrawSurface7Port` (осталось несоставленной) и посмотреть, транслируются ли номера движка в D3D-константы или кладутся как есть.
3. **Три зарегистрированных шейдера** (`default`, `additiveonly`, `modelnozwrite`, шаг 0x48, `FUN_0045a130.c`) — их 12 dword расшифрованы лишь частично (значения 1,7,9,6,11,13,10,14,33,34,35,−1). **Проверка:** найти потребителя шейдеров (используется `FUN_0045bff0` — экспорт `shader%d %s`) и сопоставить с рендером порта.
4. **Реестр имён в `.rdata` (VA `0x722A80`–`0x72313C`)** содержит 74 имени; 20 из 24 текстурных стадий и 37 техник совпадают с порядком регистрации, но 4 имени (`disable`, `default`, `sky_mt0`, `sky_mt1`) в пуле отсутствуют — они собираются литералами в коде. **Проверка:** при желании — сверить адреса из пула с `z38_tables.txt` (совпадение построчное).
5. **Ни один вывод не сверен с живой игрой** — всё статическое. В частности, неизвестно, отображаются ли в игре техники из id > 0 как «материалы» объектов, или id техники выбираются из слота группы (З37: подстановки 7→6, 18→19, 33→7).
