# З15. Формат `.3db` полностью восстановлен; ридер порта байт в байт совпадает

Дата: 2026-11-21. Инициатор: `mvs_785ae066116d4a819552d6b624e53aef`.
Источник: оригинальный загрузчик `C3DDB__Persist_00402ff0.c` (VA 0x402FF0) в декомпиляции Ghidra + 43 пакета `data/3db/*.3db` + `tools/inspect_3db.py` порта (read-only).

---

## 1. Загрузчик и секции

Файл читается как memory-mapped (`C3DDB__Persist_00402ff0.c:102-104`), секции идут строго последовательно, их имена зашиты в строки движка (`:53, 77, 125, 187, 235, 318, 475, 569, 661, 748, 916, 984, 1053, 1113, 1179`).

| # | Секция | Содержимое |
|---|---|---|
| 0 | Header | 2 строки с префиксом u32: версия `"3DDB 1.0"`, имя пакета |
| 1 | Materials | u16 count; запись = строка name + строка path + u32 (всегда 1) |
| 2 | Meshes | u32 count; запись описана ниже |
| 3 | Objects | u16 count; запись = строка name + u16 n + n×u32 (**индексы анимаций**) |
| 4 | Anims | u16 count; запись = строка name + u16 frames + frames×u32 (**индексы мешей**) + u16 + 4 Б + строка пути `.sex` + 3f + 3f |
| 5 | Shadows | u16 count; на каждый — блоб **0x400 байт** (`:623`) |
| 6 | CMaps | u16 count; запись = 4×u16 (w,h,?,?) + w×h байт (`:714-728`) |
| 7 | Lst Count&Init | 4×u16 counts + u32 (followmesh count) + 4 массива u16: IdxLst, UVLst, VLst, NLst |
| 8 | FollowMesh | followmesh_count × **20 байт** |
| 9 | IdxLst map | count1 списков × u16 (2 Б/эл.) — данные **вперемешку**, без заголовков |
| 10 | UVLst map | count2 списков × 8 Б (2×f32) |
| 11 | VLst map | count3 списков × 6 Б (3×u16) |
| 12 | NLst map | count4 списков × 1 Б |

Секции 9-12 не читаются, а «сканируются»: ftell → запись указателя → fseek на длину (`:949-977, 1020-1046, 1094-1106, 1146-1172`).

### Запись меша (в файле 232 Б, stride 0xe8)

1. u16 N (число link-записей) → `mesh+0x38`
2. N × 12 Б (6×u16) → link-массив
3. 12 Б → `mesh+0x44`
4. 12 Б → `mesh+0x50`
5. **128 Б** → `mesh+0x5C` = 32×u32 (индекс follow-записи по link-id 0..31)
6. u16 → `mesh+0x04`
7. 48 Б → `mesh+0x08` (12 float)
8. u16 → `mesh+0x00`

### Link-запись

6×u16, но в память кладутся в слоты **24 Б в переставленном порядке**: файл[0]→слот4, [1]→слот0, [2]→слот16, [3]→слот20, [4]→слот8, [5]→слот12 (`FUN_004023a0_004023a0.c:27-53`); слоты 16/20/8/12 — unsigned (отрицательное → +0x10000).

### Follow-запись (20 Б)

`+0` u16 X, `+2` u16 Y, `+4` u16 Z, `+6` u16, `+8/+12/+16` f32 — позиция + поворот (`FUN_00408920_00408920.c:8` → `base + idx*0x14`; `FUN_00408a10_00408a10.c:9-16`; `CTclObjMethods__GetLinkRot_00687170.c:125-128`).

**Связь модель↔анимация:** Object → индексы Anims; Anims → индексы Meshes (кадры). Отдельного «костного» типа нет: кости = link-id + follow-запись.

## 2. Гипотеза «уровень объекта хранится в `.3db`» — ОПРОВЕРГНУТА

В `.3db` **нет** мировой позиции/масштаба объекта. Размещение задаётся из Tcl:
`data/Scripts/sequences/Oberwelt/tourn_2100.tcl:149` → `sel /obj;new Dummy_Obw_absperrung_c "" {179.12 30.5 2.99} {0 0 0}` (позиция + поворот в скобках).

Что в `.3db` **есть** (локальное, модельное):
* **AABB меша** — 6 float в `mesh+0x44/+0x50`. Проверено численно: для `obw_baum_a` bbox = (−1332.36, −4187.97, −1416.29)…(1648.42, 44.0, 1543.56); точки меша дают z ∈ [−1416.28, 1543.56], y_min ≈ −4187.94 — совпадает.
* **Прямоугольник-«след» объекта в XZ** — 12 float в `mesh+0x08` (4 угла, y=0 всегда). Для `obw_baum_a`: x ∈ [−1704.96, 2021.01], z ∈ [−1475.45, 5539.0]; для `obw_boden_a` — нули. Смысл не установлен (гипотеза: опорная площадка/пол).
* **Follow-записи** — локальные смещения костей/линков (`mann.3db` — 62 543 записи, 62 542 ненулевых; `oberwelt.3db` — 1 запись).
* **Смещение анимации** `anim+0x24` (3 float): в `mann.3db` для `gehen_start`/`gehen_loop` = (0, **−16.2218**, 0) — вертикальный сдвиг клипа.

Отрицательные значения в AABB (`obw_baum_a` y_min = −4187.97; `obw_boden_a` — плоскость на локальном y = −10) — это **локальная геометрия модели**, а не уровень размещения.

**Отдельных записей «уровень» в `.3db` нет.** `Dummy_*` — исключительно Tcl-классы: `def_class Dummy_$classname none dummy 0 {}` + `class_defaultanim <name>.standard` (`animinit.tcl:59-81, 335-356`); модель лежит в пакете под именем без префикса (`obw_absperrung_c`, `urw_wasserfall_a` в `flusslandschaft.3db`, `urw_caves_1_a_a` в `auskleidung.3db`). Исключения: `Multi_Dummy_Lava_gng_001` в `JoinedObjs.3db`, `fenris_dummy` в `kampf.3db`.

## 3. Сверка с портом

**Совпало (подтверждено по оригиналу):**
* порядок и размер всех секций; `consumed_bytes == file_bytes` на 43/43 файлах;
* `r.string()` = u32 len + байты (`FUN_006ba590_006ba590.c:27-33`); `r.skip` = чтение N байт (`FUN_006ba670_006ba670.c:29-30`);
* `points` = 3×u16 на элемент, `uvs` = 2×f32, `triangles` = u16, `brightness` = 1 Б — совпадает с VLst/UVLst/IdxLst/NLst;
* `position_native = (u16−32768)/4` — **точно** формула оригинала;
* «attachment_indices» (32×u32) = `mesh+0x5C` — это **индексы follow-записей по link-id**;
* «bounds» = AABB меша; «attachment_records» = FollowMesh 20 Б (совпадает с `FUN_00408920`).

**Расходится / порт теряет:**
1. `extra.f32` анимации — 4 байта, которые оригинал **читает и тут же затирает нулём** (`FUN_004029a0_004029a0.c:51-52`). Значения — мусор (в `transport.3db` 1.76e+22). Порт хранит их как «f32».
2. `auxiliary_vecs` (12 float, `mesh+0x08`) — реально 4 угла прямоугольника XZ с y=0, **не** «auxiliary»; имя вводит в заблуждение.
3. `auxiliary_u16_a/b` (`mesh+0x04`, `mesh+0x00`) — смысл не установлен.
4. **Теряются CMaps** — это **collision-маски** (`animinit.tcl:327`: `has_cmap $firstanim.standard` → `class_collision`). Порт пропускает их целиком.
5. Теряются Shadows (0x400 Б на штуку) — содержимое не разобрано.
6. Имена списков: порт `triangle/uv/point/brightness` ↔ оригинал `IdxLst/UVLst/VLst/NLst`.
7. Семантика 6 полей link-записи в порте не подтверждена: оригинал хранит их в переставленных 24-Б слотах.
8. `extra.vec_a` (анимационное смещение, ненулевое у персонажей) порт не интерпретирует.

## Что это меняет для порта

* **Гипотеза «отрицательные уровни объектов приходят из `.3db`» — неверна.** Уровень размещения задаётся только Tcl-скриптом (`new Dummy_... "" {x y z} {rx ry rz}`). Значит правки по отрицательным уровням надо делать в разборе скриптов и в шкале z (З2), а не в ридере `.3db`.
* **Ридер порта байт-в-байт корректен** — переписывать разбор `.3db` не нужно; расходятся только названия полей.
* **Порт теряет CMaps (collision-маски)** — это влияет на поведение, а не на картинку: если движок строит коллизии по CMaps, порту их тоже нужно читать (секция 6, запись = 4×u16 + w×h байт).
* **`mesh+0x08` — не «auxiliary», а прямоугольник-«след» в XZ**: возможно, это опорная площадка объекта (кандидат на «пятку», к которой садится декор). Стоит сверить с `native_campaign_models.json` (там есть `bounds` и `native_model_transform`).
* **Смещение анимации `anim+0x24`** (у персонажей — по вертикали до −16.2) порт не учитывает — это сдвиг клипа, а не объекта.

## Что осталось неизвестным

* Назначение `mesh+0x00`, `mesh+0x04`, 12-флоатного блока `mesh+0x08` (след в XZ?) и u16 по `+6` в follow-записи.
* Содержимое Shadows (0x400 Б) и CMaps (маска: 1 Б/пиксель).
* Семантика `extra.vec_a`/`vec_b` анимации и `extra.u16`.
* Семантика 6 полей link-записи (какое из них material/tri/uv/point).
* Как из `mesh+0x08`/AABB формируется «уровень» объекта при расстановке — если это вообще он.
