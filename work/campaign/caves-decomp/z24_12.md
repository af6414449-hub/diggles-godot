## З24.12 — Семантика `cell+0x34…0x3B`, `cell+0x07` и `cell+0x12`: уточнение трёх полей клетки

*(2026-11-22; разбор субагента Explore по декомпиляции (11 373 файла) + проверки дизассемблером.
Частично дублирует З10–З11; здесь — только то, что в З10–З11 не записано или там записано иначе)*

### ФАКТ (Diggles.exe)

1. **`cell+0x07` — это НЕ «extra», а БАЗОВЫЙ СВЕТ КЛЕТКИ.** (З8 «неизвестно»: «Что означает extra (cell+0x07,
   значения 0..8)» — закрыто.)

2. **`cell+0x34…0x3B` — 8 байт, per-player туман войны.** (Подтверждает З10–З11 п.1; здесь уточнение —
   **у писателей и читателей ровно 4 / много, и ни один из них не имеет отношения к копанию**.)
   * **индексация (дизасм)**: `FUN_004ca830`, `0x004CA946`:

     Идентично в `FUN_00485370` (`0x004853FA cmp ecx,7 / ja`, `0x00485417 movzx ecx,byte [eax+0x34]`).
   * **писатели (полный список — 4, все в модуле `CFogOfWar`)**:
     1. `CFogOfWar__RemoveFogBoxNoCollision_0057f170.c:203` → `*pbVar14 = 0xff;`
     2. `CFogOfWar__RemoveFogLine_0057ea10.c:217, 326` → `*pbVar16 = 0xff;`
     3. `FUN_0057e710_0057e710.c` = **«void CFogOfWar::FadeBlocks(int iPlayer)»** (строка-имя `:36`):
        затухание −4 за тик, нижняя граница 1 (`:95-97`), запись `pbVar7[param_1] = (byte)local_20` (`:113`);
     4. `FUN_0057f5c0_0057f5c0.c` = **«void CFogOfWar::UpdateFoW()»** (`:47`) → `*puVar16 = 0xff;` для всех 8 игроков.
   * **обнуление**: `CMap__Clear_00593ec0.c:92` `_memset((void *)(cell + 8), 0, 0x74);`
     (гасит `0x08…0x7B`, включая `0x34…0x3B`); `CMap__Init_00594160.c:241-247` — memset массива клеток.
   * **кодирование значения (одинаковая формула в `0x004853ED…0x00485485` и `0x004CA957…0x004CA9B1`):**
     ```
     v = cell[0x34 + player]
     если v == 0 или v >= 0x80:  amount = v − 0x80 (знаковое);
                                   если amount > 0: amount = min((int)(amount * 1.3), 0x80);

     ```
     ⇒ `v = 0` = полностью темно; `v = 1…0x7F` = полностью светло; `v = 0x80` = светло;
     `v = 0x81…0xFF` = пропорциональное затемнение; `0xFF` = «только что задымлено».
   * **Копание (`FUN_00596b80`) пишет только `cell+0x00`, `cell+0x08`, `cell+0x13` — байт `0x34` НЕ трогает.**
   Evidence: `CFogOfWar__RemoveFogBoxNoCollision_0057f170.c:152, 154, 203`;
   `CFogOfWar__RemoveFogLine_0057ea10.c:217, 326`; `FUN_0057e710:95-97, 113`; `FUN_0057f5c0:270`;

3. **`cell+0x12` — ПРОИЗВОДНОЕ поле «в какой субклетке клетки находится пик/обрыв».**
   * **писатель ровно ОДИН**: `FUN_005a6350_005a6350.c:273` (`*(byte *)(iVar8 + 0x12) = bVar17;`)
     и `:281` (`*(byte *)(iVar8 + 0x12) = (byte)((int)uVar25 >> 2) & 0x40 | local_5;`).
     Исчерпывающий grep `\+ 0x12\)\s*=` по всем 11 373 файлам даёт ровно эти два совпадения;
     широких записей, затирающих `0x12`, в коде клеток нет. Вызывается из
     `FUN_005a46d0_005a46d0.c:263` (драйвер перестроения карты).
   * **алгоритм** (`FUN_005a6350:94-124`, дизасм `0x5A6700…0x5A6850`): сканируются 64 байта карты
     поверхности `cell+0x3C`; для субклеток с битом 0 метрика
     `= 8 − |4−sy| − |4−sx| + (бит 1 ? 128 : 0)`, берётся **максимум** и запоминается индекс;
     бит 3 (значение `0x08`) субклетки ставит флаг `bVar3`.
   * **формула значения (дизасм `0x5A67F3…0x5A6835`):**
     ```
     uVar25 = local_24 | 0x100          ; бит 8 = bVar3
     общий случай:            cell[0x12] = ((uVar25 >> 2) & 0x40) | local_5
     все твёрдые, без маркера: cell[0x12] = ((uVar25 >> 2) & 0x40) | 0x24     ; subX=4, subY=4 (центр)
     все твёрдые, с маркером:  cell[0x12] = ((uVar25 >> 2) & 0x40) | dh       ; уточнённый индекс 0..63
     ```
     `local_5`/`dh` — **линейный** индекс субклетки 0..63 ⇒ `sx = биты 0..2`, `sy = биты 3..5`.
   * ⇒ **бит 6 (0x40) — НЕ «есть точная позиция»** (точная позиция есть всегда, в битах 0..5),
     а «в клетке есть хотя бы одна субклетка с флагом поверхности 0x08».
     **Биты 7+ не используются**: максимум `0x7F`.
   * **пустая клетка** (ни одной субклетки с битом 0) ⇒ `cell+0x06 = −1`, и **`cell+0x12` в этой ветке
     НЕ пишется** (дизасм `0x5A6848` идёт в обход стора) ⇒ поле устаревает.
   * **побочно там же**: `cell+0x06` = `50 − 30·(uVar25 >> 8)` (дизасм `0x5A6810/0x5A6826 mov cl,0x32`)
     ⇒ **50** обычно, **20** если есть маркер, **−1** для пустой клетки.
   * **потребители ведут себя по-разному** (важно для воспроизведения):
     - `CPlaceFinder__FindPlaceLongRange_005aa310.c:87-91, 202, 206-209` — **с проверкой** бита 6;
     - `FUN_005a22f0_005a22f0.c:248, 255, 912, 918, 1045, 1051` — декодирует биты 0..5 **без** проверки бита 6;
     - патфиндер (`FUN_0059a740`, `FUN_0059a8b0`, `FUN_0059ab90`, `FUN_0059bf90`, `FUN_0059d640`,
       `FUN_0059fda0`, `FUN_005a0f00`, `FUN_005a1920`) — `(*(byte *)(cell + 0x12) & 0x40) != 0` как доп. условие
       (в `FUN_0059a740/0059a8b0` бит 6 меняет формулу «шага по высоте»: `0x114` против `0x10A`).
   Evidence: `FUN_005a6350:94-124, 273, 281, 285`; дизасм `0x5A6700-0x5A6850`;
   `FUN_005a46d0:263, 318`.

4. **Ноль клетки — полный снимок из `CMap__Clear_00593ec0.c`:**
   `+0x00` = ID блока (`:67, 84`); `+0x04` = `0xFFFF` (`:59, 78`); `+0x06` = `0xFF` (−1, «пусто», `:63, 81`);
   **`+0x07` = 4** (`:71, 87`); `+0x08…0x7B` = 0 (memset `:92`).
   `CMap__Init_00594160.c:241-244`: массив клеток = `*(int *)(map + 0x4C) * 0x7C` байт,
   `map+0x18` = число клеток, `map+0x14` = база.

### Что это меняет для порта

* **`cell+0x07` — свет, а не «extra».** Порт, если он хранит это поле, должен трактовать его как
  яркость (по умолчанию 4, при пересчёте до 20) и **упаковывать в старший байт uint'а** при сборке
  углов вершин — иначе поплывёт яркость граней.
* **Свет можно либо воспроизвести по формуле `FUN_005906a0`, либо хранить байтом в своём формате карты**
  (оригинал умеет и то, и другое: `FUN_005992b0` читает его из файла).
* **`cell+0x12` пересчитываемо** из карты поверхности `cell+0x3C` ⇒ в порту его можно не хранить,
  а вычислять. Но тогда нужно точно повторить `FUN_005a6350`, включая выбор «пиковой» субклетки
  по метрике `8 − |4−sy| − |4−sx| + 128·(ступенька)`.
* **Туман войны — массив 8 байт на клетку (по игрокам)**, и его значения участвуют сразу
  в проходимости патфиндера, выборе места спавна, видимости иконок карты, геометрии стен и затенении
  вершин. Порт рисует всё всегда ⇒ в неисследованной области показывает больше геометрии, чем оригинал
  (это уже записано в З10–З11, здесь подтверждается полным списком писателей).
* **`cell+0x06` = 50 / 20 / −1** — ещё один масштаб, который участвует в формуле высоты
  (`FUN_0059a740:39, 63`: `cell[6] + levelΔ·(−16) + 0x114`). Расхождение шкал с уровнем блока
  (`block+0x24`) остаётся открытым.

   маска `0xF3F3F3F3`), т.е. бит 3 может означать «тень ≥ 2» — но это гипотеза.
   Проверка: найти писателя/читателя бита 3 (`& 8`, `| 8`, `& ~8`) по `+ 0x3C` в `FUN_00596b80`,
   `FUN_005a6b40`, `CMapBeautifier__ScanAtPos_0058b130` и в рендере `0x4C*`.
2. **Точная формула света `FUN_005906a0`** (какие соседи, направление «света», связь с `block+0x24`).
   Проверка: дизасм `0x005906a0` (~0x1200 Б); сверка со шкалой `7.0 + 0.5·v` из `FUN_004c6b20:173`.
3. **Кто и как часто вызывает `CFogOfWar::FadeBlocks`** (скорость затухания дымки) — callgraph по `FUN_0057e710`.
4. **Устаревание `cell+0x12` в пустых клетках** — надо решить, обнулять ли поле в порту.
5. **Поля `cell+0x04 / 0x10 / 0x11 / 0x14 / 0x16 / 0x1C…0x33`** — вне рамок разбора, тоже обнуляются.
   (`cell+0x14` — поле жидкости: из `.l2m` пишется u16 целиком, `CFluid__Tick_005987c0.c:36-39`.)

5. **З24.13 (бонус) — `cell+0x14`: упакованный дескриптор жидкости; идентификаторы `0x60/0x61` подтверждены.**
   * **писатель ровно один** — `CFluid__Tick_005987c0.c:36-39`:
     `_fread(local_34, 1, 2, file)` → `*(undefined2 *)(cell + 0x14) = local_34[0];`
     ⇒ в клетку пишется **u16 целиком** из файла `.l2m` (по 2 байта на клетку, сетка W×H из заголовка).
   * **корпус измерен (свой скрипт, 2252 файла `.l2m` в `data/Templates/l2m`):**
     - младший байт: `0x00` — 542 573 раза, `0x20` — 27 510, **`0x60` — 23 263**, `0x40` — 18 752,
       `0xC0` — 8 108, и далее `0x01…0x06`, `0x21…0x26`, `0x41…0x46`, **`0x61…0x66`**, `0xC1…0xC2`;
     - старший байт: `0` — 497 833, далее `1, 4, 5, 16, 17, 20, 21, 64, 65, 68, 69, 80, 81, 84, 85, 86, 89, 101, 149`.
   * ⇒ **оба байта — упакованные битовые поля**, а не числа: младший байт использует биты 5/6/7
     (`0x20/0x40/0x60/0xC0`) плюс младшие 3 бита (0…6 — по всей видимости, уровень/высота);
     старший байт использует биты 0/2/4/6 (`0x01/0x04/0x10/0x40`) плюс бит 0 (как «+1»).
     **Идентификаторы `0x60` и `0x61` присутствуют в корпусе** ⇒ запись З8 про «идентификаторы жидкостей

     в смысле «вода/лава»: значения `0x60…0x66` идут подряд, что更像 набора флагов, чем идентификаторов.
   * **Потребитель**: `CFluid__Draw_00576c60.c` строит квады жидкости по `switch(*(byte *)(fluidCell + 8) & 7)`
     (`:578-593`) — четыре варианта формы ячейки воды; `FUN_005716e0 / 00573250 / 00574c60` строят квад,
     `FUN_0056dec0` запрашивает высоту/тип жидкости по уровню.
   Evidence: `CFluid__Tick_005987c0.c:25-39`; `CFluid__Draw_00576c60.c:544-593`;
   `FUN_005716e0:201, 676`; `FUN_00573250:186, 619`; `FUN_00574c60:195`.

### Что это меняет для порта (к З24.13)

* **Порт, импортирующий `.l2m`, должен читать u16 на клетку и раскладывать его побитно**, а не
  интерпретировать как «тип жидкости»: 0x60/0x61 — это **флаги**, а не идентификаторы.
* Если порт рисует воду/лаву в пещерах, ему нужен этот разбор: в оригинале форма квада жидкости
  зависит от 4 битовых комбинаций (`:578-593`), а высота поверхности — константа `14.4` (З24.11 п.2).
