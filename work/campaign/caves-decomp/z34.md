# З34. Порядок отрисовки: точная формула ключа сортировки задач

*(2026-11-22; закрывает D12 — «ключ сортировки задач отрисовки»)*

З33 показал, что порядок отрисовки **не** определяется «типом объекта».
Теперь формула восстановлена по дизассемблеру — её можно перенести в порт
дословно.

## 1. ФАКТ (Diggles.exe): задачи отрисовки сортируются по 32-битному ключу

Функция `FUN_00450850` формирует ключи, `_qsort` с компаратором
`RenderJob__Validate` сортирует массив.

Дизасм. `0x4508B1–0x4508C4` — ветка «объект без шейдера»:

```
mov  eax, dword ptr [edi + 8]     ; «проход» объекта
shl  eax, 0x11                    ; проход << 17
or   eax, 0x1ffff                 ; младшие 17 бит = максимум
mov  dword ptr [edi + 0x48], eax  ; первичный ключ
```

Дизасм. `0x450911–0x45099C` — общая часть:

```
movss xmm0, dword ptr [edi + 0x1c]      ; центр bbox, Y
addss xmm0, dword ptr [edi + 0x18]      ; + центр bbox, X
movss dword ptr [ebp - 0x10], xmm0      ; (X + Y)
movss xmm0, dword ptr [edi + 0x20]      ; центр bbox, Z
movzx eax, byte ptr [0x772dd8]          ; = ROUND(центр.Z * 4) & 0xFF
...
mov  eax, dword ptr [0x772dd8]
add  eax, 0x40
movzx eax, al                         ; (ROUND(центр.Z*4) + 0x40) & 0xFF
mov  edx, dword ptr [edi + 0x10]        ; id техники
imul ecx, edx, 0x6c
cmp  dword ptr [eax + ecx + 0xc], 0    ; запись техники, поле +0x0C
```

Итоговый первичный ключ (`объект + 0x48`), 32 бита, от младших к старшим:

| биты | значение |
|---|---|
| 0..7 | `ROUND((центр.X + центр.Y) * 40) & 0xFF` — «пространственный» байт |
| 8..15 | `(ROUND(центр.Z * 4) + 0x40) & 0xFF` — байт высоты; **инвертируется** (`0xFF − значение`), если у объекта нет настоящего шейдера |
| 16 | `проход * 2` |
| 17 | признак «есть настоящий шейдер» (запись техники `+0x0C != 0`, либо `+0x20 != 1`) |

Вторичный ключ (`объект + 0x4C`) = `объект+0x40 + объект+0x3C` (сумма двух int).

Компаратор `RenderJob__Validate_00450a50.c:8-23`: сравнивает первичные ключи
по возрастанию; при равенстве — вторичные по возрастанию; при равенстве и их —
0 (порядок сохраняется).

## 2. ФАКТ (Diggles.exe): «проход» и «настоящий шейдер»

* «проход» = `объект + 8` (dword). В `FUN_004899b0:280` рядом ставятся
  `param_1[2] = 0x14` (значение «прохода/состояния») и `param_1[3] = 4`.
* «настоящий шейдер» вычисляется в `FUN_00450850:61-77`:
  * если запись техники `+0x0C == 0` → **нет** шейдера;
  * иначе, если `объект + 0x14 < 0xFA` → **есть**;
  * иначе → «есть», если запись техники `+0x20 != 1`.
* Ветка «объект без шейдера» (`объект + 0x55 != 0`) ⇒ ключ = `проход<<17 | 0x1FFFF`,
  т.е. **такие объекты уходят в самый конец очереди** (рисуются поверх).

## 3. ФАКТ (Diggles.exe): раскладка «объекта отрисовки»

Конструктор `FUN_00402510_00402510.c:7-22`:

| смещение | содержимое |
|---|---|
| +0x00 | −1 (используется как id объекта) |
| +0x04 | −1 (счётчик ссылок) |
| +0x08 | «проход» |
| +0x0C..+0x14 | указатель на вершины / указатели (+0x10 = id техники, +0x14 = флаг) |
| +0x18, +0x1C, +0x20 | центр bbox: X, Y, Z |
| +0x24..+0x2C | максимумы bbox X, Y, Z |
| +0x30..+0x3C | минимумы bbox X, Y, Z |
| +0x3C, +0x40 | два int-поля (см. ниже) |
| +0x44 | указатель на объект-источник |
| +0x48 | первичный ключ сортировки |
| +0x4C | вторичный ключ сортировки |
| +0x55 | флаг «объект без шейдера» |

## 4. ФАКТ (Diggles.exe): поля +0x3C и +0x40 — уровни освещения

* `CTclObjMethods__ChangeLight_00614990.c:186` и `:203` пишут в **оба**
  поля одно и то же: `*(int *)(*(int *)(local_14 + 4) + 0x3C) = (int)(fVar9 * 31.0)`
  и то же в `+0x40`. Масштаб 31 даёт диапазон 0…255 при `fVar9 ∈ [0, 8.2]`.
* В `FUN_004899b0_004899b0.c:294-295` оба поля получают одно и то же значение
  из стека вызова (`in_stack_00000020`).

⇒ Вторичный ключ = сумма двух уровней освещения объекта. Он используется
**только** как тай-брейкер при равенстве первичного ключа.

## 5. Что это меняет для порта

1. **Порядок отрисовки переносится формулой, а не «на глаз».** Для Godot:
   отсортировать задачи отрисовки по `(проход, признак шейдера, байт высоты,
   байт (X+Y), сумма освещения)`. Это особенно важно для прозрачных объектов:
   в оригинале они накладываются в строго определённом порядке.
2. **Прозрачные объекты рисуются последними** — отдельной веткой ключа
   (`0x1FFFF`), а не «альфа-тестом». Значит, в порте нужен отдельный
   «transparent pass» с сортировкой по глубине, а не только по альфе.
3. **Байт высоты инвертируется для объектов без шейдера** — из-за этого
   объекты с «пустым» шейдером оказываются поверх. Тонкость, которую легко
   потерять при переносе.
4. **Свет влияет на порядок** (через вторичный ключ) — то есть «освещение
   запечено в вершинах» (З27) и «свет влияет на порядок отрисовки» — это
   два разных механизма, и второй тоже нужно перенести.

## 6. Что осталось неизвестным (и как проверить)

* **Почему в «пространственном» байте именно `X + Y`, а не `Y` или `Y − X`.**
  Формула установлена точно, смысл — нет: возможно, камера в Diggles
  смотрит по диагонали, либо это стабильный хеш для разбиения.
  **Как проверить:** поставить в сцену два объекта с известными X, Y и
  посмотреть их взаимный порядок отрисовки (в оригинале — через отладчик
  или перехват `DrawPrimitive`).
* **Семантика `объект + 0x14`** (участвует в решении «есть настоящий шейдер»:
  порог 0xFA). В `FUN_004899b0` это `param_1[5]`. Не установлено.
  **Как проверить:** найти, кто пишет `+0x14` у объекта отрисовки.
* **D25 — есть ли отсечение по видимости.** Поимённого отсечения в exe нет
  (поиск `cull|frustum|ClipPlane` → 2 попадания в парсере шейдеров), тайловой
  сетки нет (З33) ⇒, вероятно, объекты фильтруются иначе (по видимым
  объектам сцены или по списку задач).
  **Как проверить:** поставить камеру так, чтобы часть сцены была за спиной,
  и сверить число задач отрисовки (движок сам считает объекты и кадры в
  `DAT_0076a2f0`, `DAT_0076a338 + 0x281C/0x2820`).
* **`FUN_0045e120(0)`** (вызов из `CDXExecBuf__Render:101`) — по коду
  `FUN_004559a0(param_1 * 0x6c + base)` ⇒ сброс/инициализация записи шейдера;
  назначение не установлено.
  **Как проверить:** прочитать `FUN_0045e120` целиком.

## 7. Оговорка

Всё — статический анализ (Ghidra + дизассемблер). Формулы ключей и
компаратор взяты из машинного кода, поэтому переносить их можно дословно;
интерпретация отдельных полей — нет. Сверка с живой игрой не выполнялась.
