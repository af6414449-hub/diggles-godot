## З24.9 — Внутренности LG: запись шаблона, «запретные круги», скоринг и выбор позиции пещеры

*(2026-11-22; закрывает «неизвестно» из З21: «Как LG выбирает именно шаблон Hol … и ставит ли он пещеру
рядом с цепочкой туннелей или в своём прямоугольнике (`FUN_00587480`, `FUN_00589790`)»)*

### ФАКТ (Diggles.exe)

2. **`LG+0x68` — массив ограничений по уровням (шаг 0xC = 12 Б), счётчик `LG+0x6C`.**
   Запись: `[+0]` int, `[+4]` float = **верхняя граница** (строгое «<»), `[+8]` float = **вес**.
   Назначение: для каждого уровня `l` (их число — `LG+0x98`) значение уровня шаблона
   `templateLevel[l] + LG+0x94[l]` должно быть **меньше** `restriction[l].max`;
   иначе шаблон исключается (`score = 0x7FFFFFFF`).
   Evidence: `FUN_00586710:31-55` (проверка границы; `:46-50` — сравнение),
   `:143-203` (использование веса `restriction[l].weight`).

3. **`LG+0x94 / LG+0x98`** — float-массив «кривой уровня» (значение LG на каждом уровне) и число уровней.
   `LG+0x9C / LG+0xA0 / LG+0x74` — знаменатель, числитель и масштаб нормировки уровня
   (`local_2c = (LG+0xA0 / LG+0x9C) / LG+0x74`, `local_28 = LG+0x74`).
   Evidence: `FUN_00586710:90-96, 113-117, 175-190`.

4. **`local_18` в скоринге РАЗОБРАН — это «фактор соответствия уровню».**
   ```
   local_18 = 1.0                                   ; если уровней нет (LG+0x98 < 1)
   иначе для каждого уровня l:
       f = restriction[l].weight                    ; float, LG+0x68[+8]
       если f != -1.0:
           если f == 0.0:  прибавить 1.3
           иначе:  Δ = | f − (templateLevel[l] + LG+0x94[l]) / local_28 |
                         − | f − LG+0x94[l] / local_2c |
                  прибавить Δ / f
   local_18 = | среднее(прибавок) + 1.0 |           ; если ни одного ограничения — 1.0
   ```
   Итог: **local_18 ≥ 0 и тем больше, чем хуже уровень шаблона совпадает с кривой уровней LG.**
   Множитель стоит в самом конце формулы score ⇒ чем больше local_18, тем позже шаблон в сортировке.
   Evidence: `FUN_00586710:139-206` (в частности `:155` — чтение веса, `:188-191` — формула Δ,
   `:197` — `Δ/f + local_18`, `:205` — `|сумма/счётчик + 1|`).

5. **ПОЛНАЯ ФОРМУЛА SCORE (подтверждена дизасмом).**
   ```
   score = trunc( ( 2·fVar13
                    + 100·local_24
                    + 200·iVar4
                    + 250·iVar7
                    + rand·3.0517578e-05·(1 − local_2c)
                    + 0.5 )
                  · (record+0x3C)          // вес группы
                  · 100
                  · local_18 )
   ```
   где `fVar13 = |(0x14 − record+0x0C) − iVar4′| · (2 − local_2c)`,
   `local_24` = `ABS(3 − record+0x14)` / `ABS(2.5 − …)` / `ABS(2 − …)` / `ABS(1 − …)·10`
   в зависимости от диапазона `local_2c` (0…0.3 / 0.3…0.6 / 0.6…0.8 / ≥0.8),
   `iVar7 = record+0x24`, **`iVar4` = 5 для обычных шаблонов и `min(record+0x1C, 5)` для ПЕЩЕР**
   (ограничение `if (5 < iVar4) iVar4 = 5` действует для всех — переполнения нет),
   `rand = rand() & 0x7FFF`.
   **Итоговое приведение — `fistp` (усечение к нулю), а не округление.**
   Evidence: `FUN_00586710:260-266`; дизасм `0x586EA2-0x586F1B`:
   `mulss xmm2,[0x73760c]` (=100.0), `mulss xmm0,[0x736f94]` (=3.0517578e-05),
   `mulss xmm0,[ebp-0x1c]` (=1−local_2c), `movss xmm0,[esi+0x3c]` (вес группы),
   `mulss xmm0,[0x73760c]` (×100), `mulss xmm0,[ebp-8]` (×local_18),
   `mulss xmm3,xmm0`, `fld xmm3; fistp dword ptr [0x772DD8]`.

   **Точные инструкции для `iVar4` (дизасм `0x586CF8-0x586D36`):**
   ```
   0x586CF8  mov  eax, 0x7FFFFFFF          ; iVar4 = 0x7FFFFFFF по умолчанию
   0x586CFD  cmp  byte ptr [esi+0x41], 0   ; record+0x41 — признак «пещера»
   0x586D01  je   0x586D06                 ; не пещера — оставить 0x7FFFFFFF
   0x586D03  mov  eax, dword ptr [esi+0x1C]; пещера — iVar4 = record+0x1C (вес пещеры)
   0x586D0B  mov  ecx, 5
   0x586D13  cmp  eax, ecx
   0x586D18  cmovg eax, ecx                ; КЛАМП ДЛЯ ВСЕХ: iVar4 = min(iVar4, 5)
   0x586D1A  movd xmm1, eax                ; iVar4 → float
   0x586D2A  mulss xmm1, [0x737644]        ; iVar4 * 200.0
   0x586D1F  mulss xmm0, [0x737650]        ; record+0x24 * 250.0
   0x586D32  addss xmm1, xmm0
   0x586D36  movss [ebp-0x2C], xmm1         ; готовый вклад в score
   ```
   ⇒ **переполнения нет** (`cmovg` действует и для не-пещер): обычный шаблон даёт вклад **1000**,
   пещера — от **0** до **1000**.


6. **Следствие 1 (уточнение З24.5): пещеры ставятся РАНЬШЕ обычных шаблонов.**
   Вклад `200·iVar4` для обычного шаблона = 1000, для пещеры — от 0 до 1000 (у Hol вес `record+0x1C`
   обычно мал ⇒ вклад ≈ 0). Сортировка кандидатов — **по возрастанию score**
   (`FUN_00586540`, вызов из `FUN_00586f40:28`) ⇒ **сначала пробуются пещеры**.
   Плюс: шаблон 4×4 (базовый) получает score = `record+0x14 − 7` (`FUN_00586710:97-99`) ⇒ всегда почти первый.

7. **Следствие 2: «запретные круги» — механизм не-налёгания пещер друг на друга.**
   * При **постановке** шаблона-пещеры (`record+0x41 != 0`) LG добавляет круг
     `{x = param_2, y = param_3, r = record+0x08 · record+0x0C}` (т.е. r = ширина × высота пещеры)
     в массив `LG+0x18C` (шаг 0xC = 12 Б), счётчик `LG+0x190`.
     Evidence: `FUN_005842c0_005842c0.c:213-225`.
   * При **скоринге** шаблон-пещера исключается, если для любого круга
     `|dx| · |dy| < 1.5 · r` (произведение, не сумма квадратов).
     Evidence: `FUN_00586710:56-88` (`:68-83` — расчёт и сравнение).
   * Важно: **круги добавляют и проверяют ТОЛЬКО для пещер** (`record+0x41`). Обычные шаблоны
     (переходы `gng_*`, галереи) на круги не смотрят.
   * Инициализация: `LG+0x18C = 0`, `LG+0x190 = 0` (`FUN_00581470:59-60`); освобождение — `FUN_00581740:38-47`.

8. **Позиция пещеры — СЛУЧАЙНАЯ, кратная 4 клеткам; прямой привязки к туннелю игрока в позиции НЕТ.**
   `FUN_005862c0` (0x5862c0):
   * выбирает «базовый» шаблон: первый в активном списке `LG+0x40` с `record+0x08 == 4` **и**
     `record+0x0C == 4` **и** `record+0x14 == 2` (`:29-49`);
   * диапазоны: `rangeX = (LG+0x58 − LG+0x50) − record+0x08 − 4`,
     `rangeY = (LG+0x5C − LG+0x54) − record+0x0C − 4` (`:72-74`);
   * **до 16 попыток** (`:81-84`): `x = (rand % rangeX) & ~3) + 4`, `y = (rand % rangeY) & ~3) + 4`,
     затем `FUN_005842c0(template, x, y, LG+0x80, 0, 0)` (`:85-91`);
   * в записи о постановке координаты сдвигаются на начало области LG: `x_world = LG+0x50 + x`,
     `y_world = LG+0x54 + y` (`FUN_005842c0:204, 208`).
   ⇒ **Пещера ставится в случайную клетку, кратную 4, внутри области LG.**
   **Почему же пещеры «попадались игроку, который копал вниз»?**
   Потому что **область LG и её начало — производные от якоря** (З21 п.3): `dig_apply` → `FUN_005fd060`
   → «карта сюжета» получает стартовую точку и направление (`FUN_005fcfb0:22-28`:
   `+0x88 = направление`, `+0x8C/+0x90 = старт X/Y`, `+0x94 = флаг`, `+0x98/+0x9C = счётчик приоритета`)
   → `lg_set_starttemplatepro` → LG строит уровень **от этой точки**.
   То есть привязка пещер к туннелю игрока — **не через координату пещеры, а через то, откуда
   строится уровень**: пещера оказывается в цепочке уровня, начатого в выкопанной игроком клетке.

9. **`FUN_00587480` (0x587480) — это НЕ «раскрытие группы шаблонов», а проверка/прорубка СВЯЗИ между двумя уровнями LG.**
   Разбор (941 строка декомпиляции):
   * аргументы: `param_1` и `param_3` — **индексы в массиве уровней LG** `LG+0x194` (шаг 0x10, счётчик `LG+0x198`),
     `param_2` и `param_4` — **номера уровней** внутри них;
   * `FUN_0058ef30(i)` = `i·0x10 + base` (доступ к записи уровня), `FUN_0058f160(id)` = `id·0x54 + base`
     (**доступ к записи шаблона**), `FUN_00441fe0(l)` = `base + l·0xC` (**описание уровня**: `{x, y, направление}`);
   * `:306-320` — отбраковка: `param_2 == -1` или `param_4 == -1` ⇒ «связь не задана» (успех);
     индексы вне `LG+0x198` ⇒ отказ;
   * `:328-348` — проверка «уровень не достигнут» (`item[+4] + level->+0x14 <= param_2`) ⇒ отказ;
   * `:360-387` — вычисление прямоугольника-коридора между двумя уровнями: координаты уровня,
     затем **сдвиг на ±2 клетки в зависимости от направления 0..3** (`:455-478` и `:516-539`),
     с проверками попадания в область LG (`:486-574`);
   * `:389-429` — поиск набора шаблонов `LG+0x8C` (записи по 12 Б), покрывающего полученный коридор;
     не найдено ⇒ отказ;
   * `:735-915` — **прорубка коридора** в сетке LG `LG+0x84` (по 4 байта на клетку):
     маска `| 0xFFFF0000` в старших битах, обход «по границе» (`:757-893`), обнуление счётчиков (`:899-931`);
   * `:589-734` — выбор шаблона **связи**: из массивов `LG+0xAC` (16 записей), `LG+0x154`/`LG+0x158` (5 записей),
     `LG+0x12C`/`LG+0x130` (5 записей) — в зависимости от id связи (**1**, **5**, **10**), случайно;
   * `:439-446` — частный случай «уровни совпадают»: результат = `(направление2 + 4 − направление1) & 3 == 2`.

10. **Запретные прямоугольники LG (`LG+0x17C` / `LG+0x180`).** Массив прямоугольников по 16 Б
    (`{x0, y0, x1, y1}`), каждый из которых **помечается единицей в битмапе занятости `LG+0x84`**
    ⇒ по этим прямоугольникам шаблоны не ставятся.
    Evidence: `FUN_00589790:113-167`.

11. **Группы шаблонов (`LG+0xA4` / `LG+0xA8`) — записи по 0x18 (24 Б):**
    `{+0x00 уровень1, +0x04 уровень2, +0x08 уровень3, +0x0C уровень4, +0x10 …, +0x14 ptr}` —
    и каждая группа проверяется функцией `FUN_00587480` (п.9). То есть «группа» = набор связей уровней,
    а **не** набор шаблонов.
    Evidence: `FUN_00589790:65-112`.

### Что это меняет для порта

* **Порту не нужно воспроизводить LG целиком**, но нужно понимать, что он делает, чтобы не спорить с оригиналом:
  1. **Пещера (Hol) ставится в случайную клетку, кратную 4**, внутри области уровня — **привязки к
     координате туннеля нет**. Если в порте пещера «привязана к туннелю» напрямую — это расхождение
     с оригиналом; правильная привязка — **уровень начинается в точке, где игрок пометил вход в пещеру**
     (З21 п.3), и пещера просто оказывается внутри этого уровня.
  2. **Пещеры не наезжают друг на друга**: после постановки пещеры её «запретный круг» = (ширина × высота)
     исключает другие пещеры при `|dx|·|dy| < 1.5·r`. Порт, ставящий несколько пещер, должен
     иметь эквивалентное правило (у порта 5 пещер в первой главе по статической раскладке — там
     размещение фиксировано скриптом, см. З21 п.2, и правило не применяется).
  3. **Порядок: сначала пробуются пещеры, потом переходы** (вклад `200·iVar4`: 1000 у обычных,
     ≈0 у Hol) ⇒ **в оригинале пещера — первое, что ставится на уровень**. Порт, ставящий сначала
     «коридоры», получает другую картину.
  4. **Вес пещеры `record+0x1C` (0…5) — отдельная величина от веса группы `record+0x3C` (0.287)**.
     Перепутать их = получить неверный порядок постановки.
  5. **Шаблон 4×4 с `record+0x14 == 2` — «базовый»**: он всегда ставится первым и служит точкой отсчёта
     для остальных уровней.

### Что осталось неизвестным

* **Кто и когда заполняет `LG+0x50/+0x54` (начало области LG)** — от этого зависит абсолютная позиция
  пещеры; связать с якорем `FUN_005fd060` удалось на уровне «карты сюжета» (`FUN_005fcfb0`),
  но не с самим LG.
* **Откуда берётся `record+0x1C` (вес пещеры 0…5)** — есть ли Tcl-команда; в `story.tcl`/`lginit.tcl`
  не найдено (нужно проверить `lg_set_templatevalue` / `lg_set_templategroupprops`).
* **Смысл массива `LG+0x8C` (наборы шаблонов по 12 Б) и `LG+0x180` (запретные прямоугольники)** —
  кто их заполняет из Tcl; вероятно, есть команды `lg_set_*area*`, но это не проверено.
* **Три «рамочные» операции** `FUN_005a3dd0`/`FUN_005a3fd0` (маски 0x40000/0x400/8) — не разобраны.
* **Ни один вывод З24.9 не сверен с живой игрой** — все формулы получены статическим анализом.
