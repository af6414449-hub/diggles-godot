## Д.1 Где в клетке лежит сетка высот 8×8

> **ПОПРАВКА (2026-11-21, разбор З8).** Первая редакция этого раздела утверждала, что «сетка высот внутри клетки — это 32 байта по 4 бита (64 ниббла), лежащие в клетке с `cell+0x08` по `cell+0x27`». **Это неверно.** Образцы копания занимают **один uint32 в `cell+0x08`** (8 ниблов). Сетка высот 8×8 лежит **по другому адресу — `cell+0x3c..+0x7b`** (см. З8). Ниже раздел приведён к фактическому состоянию.

**ФАКТ (Diggles.exe): образцы копания клетки — это один 32-битный слой в `cell+0x08`, содержащий 8 нибблов (по 4 бита).** Каждый ниббл — метка рытья (DigMark) **одного игрока** (индекс 0..7); класс твёрдости выводится через `FUN_00597430` (`v==0→15; v&8==0→11; v&8→(v&3)*4−1`). См. З14 отчёта.

Evidence: `FUN_00596b80_00596b80.c:133` — 0x596b80 — чтение одного образца:
```c
          uVar12 = *(uint *)(iVar5 + 8) >> ((byte)local_1c & 0x1f);
```
Evidence: `FUN_00596b80_00596b80.c:149` и `:276` — затирание ниббла при выемке:
```c
            *(uint *)(iVar5 + 8) = *(uint *)(iVar5 + 8) & ~(0xf << ((byte)local_1c & 0x1f));
...
    *(uint *)(iVar5 + 8) = *(uint *)(iVar5 + 8) & ~(0xf << (bVar10 & 0x1f));
```
Evidence: `FUN_00596b80_00596b80.c:131-152` — обход всех 8 нибблов **одного** 32-битного слова (сдвиг `local_1c` = 0,4,8,…,28 ⇒ 8 нибблов; слово всегда `*(uint *)(iVar5 + 8)`, других слов нет).

Почему это важно: `cell+0x14` — поле **жидкости** (uint16), и при прежней формулировке оно оказывалось «внутри сетки образцов». Теперь ясно, что это разные поля (см. З8, раздел A).

Отдельная сетка высот 8×8 (по байту на субклетку, построчно: строка = Y, столбец = X) лежит в **`cell+0x3c..0x7b`**; её пишет `FUN_00596550` (из `.pmp` и из штампов объектов) и читает `FUN_005961c0`. Evidence: `FUN_00596550_00596550.c:67-101`, `FUN_005961c0_005961c0.c:70-101`.

«Тест ямы» (`FUN_004ca830:403-427`, |Δ| ≥ 4 уровней) сравнивает центральный отсчёт с угловым **в 8×8-сетке блока BlockDB** (`block+0x24` против `block+0x00/+0x07/+0x38/+0x3f`), а не в `cell+0x08` — см. З8, раздел B.

## Д.2 Код образца: что означают 4 бита

**ФАКТ (Diggles.exe): 4-битный код образца переводится в «тип/материал» по правилу: 0 ⇒ 15; (код & 8) == 0 ⇒ 11; иначе 0, а если (код & 3) ≠ 0, то (код & 3)*4 − 1.**

Evidence: `FUN_00596b80_00596b80.c:43-55` и повторно `:134-145`:
```c
      if ((uVar12 & 0xf) == 0) {        local_20 = 0xf; }
      else if ((uVar12 & 8) == 0) {      local_20 = 0xb; }
      else {
        local_20 = 0;
        if ((uVar12 & 3) != 0) { local_20 = (uVar12 & 3) * 4 + -1; }
      }
```
То есть код — это не «уровень», а **тип материала**: 0 — «пусто/нет породы» (значение 15), значения 1..3 — «тип × 4 − 1» (типы 1, 7, 11), значения 8..15 — камень (значение 11 = 0xb).

## Д.3 Раскладка блока высот (шаг 0x59 = 89 байт)

**ФАКТ (Diggles.exe): блок высот — запись с шагом 0x59. В нём: `+0x00..0x3F` (64 байта) — **8×8 сетка высот блока** (байт на субклетку, построчно: строка = Y, столбец = X; значения — уровни 0..15, то есть `world-Z = 7.0 + 0.5 * level`), `+0x40/+0x44/+0x48/+0x4c` — четыре «дочерних» блока (варианты следующего состояния), `+0x50..+0x53` — байты «материал-id» этих четырёх вариантов, `+0x54` — уровни углов (младший ниббл используется рендером как базовый уровень угла, `FUN_004ca830_004ca830.c:333`).**

Evidence: `FUN_004093b0_004093b0.c:7-8` — 0x4093b0 — доступ к блоку:
```c

    return param_1 * 0x59 + *in_ECX;
  }
```
Evidence: `FUN_00596b80_00596b80.c:68-69`, `:82-83`, `:96-97`, `:110-111` — отбор кандидата по его же material-id:
```c
          iVar5 = *(int *)(iVar5 + 0x4c);                 // индекс кандидата A

          ...  (аналогично +0x48/+0x53, +0x44/+0x52, +0x40/+0x51)
```
Evidence: `FUN_00596b80_00596b80.c:114-130` — запись выбранного блока в клетку и флаг изменения:
```c
          piVar6 = (int *)FUN_00592f10();
          *piVar6 = local_20;                             // cell[0x00] = новый блок высот
          iVar5 = FUN_00592f10();
```

**Следствие: высота клетки в оригинале НЕ хранится числом «глубина выемки».** Углубление = переход по графу блоков: клетка переключается на дочерний блок, у которого material-id совпадает с типом образца; у дочернего блока свои уровни углов (`+0x54`) и своя сетка. Порт, который режет пещеру, меняя число уровней, получает иную геометрию, чем оригинал.

## Д.4 Что делает выемка (пошагово)


**ФАКТ (Diggles.exe): `FUN_00596b80` (0x596b80) — выемка одной клетки. Порядок действий:**

## Д.5 Что это меняет для порта

* **Правило выемки в оригинале — по материалу образца, а не по уровню.** Образец (ниббл сетки `cell+0x08`) переводится в тип (Д.2); тип сравнивается с порогом инструмента (`FUN_005968b0`); если «мягче» — образец затирается, и клетка переключается на другой **блок высот** (то есть на другой вариант меша ямы/блока), а не «на N уровней ниже».
  ⇒ Порт, который режет пещеру по уровням (по `sub-block+0x54`), получает другую геометрию, чем оригинал. Правило оригинала: **клетка меняет индекс блока высот (`cell[0x00]`) на вариант, у которого «материал-id» совпадает с типом образца; при этом затирается соответствующий ниббл в `cell+0x08`.**
* **Инвалидация рендера — та же, что в З1.4:** «грязный прямоугольник» в слоях, а не пересборка меша на месте.
* Место правки в порту: `godot/scripts/native_dig_rules.gd` (правила выемки) и, вероятно, `godot/scripts/native_tunnel_rules.gd`/`native_corridor_stroke.gd` — если они моделируют выемку по уровням, а не по материалу образца.

## Что осталось неизвестным

* **ПОПРАВКА (З14 отчёта):** позиции 8 нибблов внутри `cell+0x08` — это **8 игроков**, а не 8 углов/рёбер клетки и не 8 инструментов. Нибловый сдвиг = `player*4`; `*(uint *)(param_2 + 0x36c)` — номер игрока. Прежняя формулировка отброшена.
* **Таблица «материал-id» `FUN_004093b0` (0x4093b0)** не разобрана (что означают `+0x50..+0x53` и как они соотносится с `uVar12`).
* **`FUN_005968b0` (0x5968b0)** — «порог инструмента»: не разобрано, что он возвращает и от чего зависит.
* **`FUN_005976b0` (0x5976b0)** — вызывается в начале (`cVar2`), вероятно «можно ли копать этот материал».
* **Не проверено, где именно в игре вызывается `FUN_00596b80`** (инструмент копателя, «кирка»?) — вероятно, обработчик действия `CAct`/Tcl-команды. **Проверка:** grep по call-графу 0x596b80.
