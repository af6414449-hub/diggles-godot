# З2 — привязка декора к поверхности: что такое z объекта из шаблона

Дата: 2026-11-21. Источник: декомпиляция `Diggles.exe` (Ghidra, `C:\diggles-ghidra\out\decomp`), дизассемблер `work/campaign/ref/disasm.py`, оригинальные данные игры (`C:\Program Files (x86)\Steam\steamapps\common\Diggles The Myth of Fenris\data`), экспорт порта `godot/models/native_campaign_chapter.json`, собственные измерения (`work/campaign/caves-decomp/z2_*.py`).

**Короткий ответ:** z объекта в шаблоне — это **абсолютный уровень в шкале высот движка**, а не мировая высота. Движок читает его буквально и сам переводит в world-Z по формуле `world-Z = 7.0 + 0.5 * z` — той же, что и для высот клеток. Штампование шаблона **не** вносит смещения по z. Движок **не** сажает объект на поверхность автоматически (есть только явная команда `set_pos_bottom`). Объекты с отрицательным z — это **надземный (Oberwelt) декор**, у которого своя система координат; в оригинале они тоже оказываются ниже карты и потому не видны.

## З2.1 Шкала z объекта: факт

**ФАКТ (Diggles.exe): движок хранит z объекта как «уровень» и переводит его в world-Z при каждом использовании множителем `* 0.5 + 7.0` — это буквально та же формула, что и для высот клеток.**

Evidence: `CDisplay__DrawObjects_00473cc0.c:429,435` — 0x473cc0 — позиция объекта при отрисовке:
```c

                          local_64 = *(float *)(iVar11 + 0x44);   // y
                          fVar25 = *(float *)(iVar11 + 0x48);     // z
                          ...

```
Evidence: `FUN_00496300_00496300.c:46-50` — 0x496300 — проекция объекта (пикинг), **читает то самое поле `+0x14`, куда `SetPos` кладёт z из шаблона**:
```c

  fVar3 = *(float *)(local_8 + 0x10);     // y
  fVar8 = *(float *)(uVar6 + 0x14) * 0.5 + 7.0;   // z  ← world-Z
  fVar7 = *(float *)(DAT_0076a338 + 0x2770) * fVar3 + ... + *(float *)(DAT_0076a338 + 0x2780) * fVar8 + ...;
```

Evidence: `FUN_0052d170_0052d170.c:613` — 0x52d170 — выбор объекта под курсором, то же поле `+0x14`:

Тот же множитель применяется к высотам клеток — `FUN_004c8220_004c8220.c:33,44` (0x4c8220), `FUN_004c6b20_004c6b20.c:173` (0x4c6b20), `FUN_004ca830_004ca830.c:333` (0x4ca830).

```c
    DAT_00772dd8 = (int)ROUND(fVar9 * 8.0);      // x и y — в клетках, берутся в сетке 1/8 клетки
    ...

```
То есть `get_hmap` возвращает `0..15` (уровень), и движок сам переводит его в world-Z формулой `*0.5+7.0` при отрисовке (см. `FUN_004c8220:33,44`). Литерал z из шаблона — тот же уровень ⇒ **конвертация объектов обязательна**, иначе объект окажется в координатах, которых в карте нет.

### Как z из шаблона попадает в объект

**ФАКТ (Diggles.exe): команда `new` разбирает позицию как список из трёх float и кладёт их в объект как есть; никакой привязки к клетке при этом нет.**

Evidence: `CTclGlobalMethods__New_00623ea0.c` (0x623ea0) → `FUN_006bafe0_006bafe0.c` (0x6bafe0 — разбор списка из 3 float) → `FUN_00601df0_00601df0.c` (0x601df0) → `FUN_005d7450`/`FUN_005d7290_005d7290.c:14-16` (0x5d7290 — конструктор, `in_ECX[1..3]` = позиция) → `FUN_005cd7e0`/`FUN_005cd8e0_005cd8e0.c:19-21` (0x5cd8e0 — SetPos):
```c
  *(float *)(in_ECX + 0xc) = x;
  *(float *)(in_ECX + 0x10) = y;
  *(float *)(in_ECX + 0x14) = z;
```

**ФАКТ (Diggles.exe): у объекта ДВА поля позиции — логическое (`+0xc/+0x10/+0x14`) и «мировое» (`+0x40/+0x44/+0x48`) — и оба заполняются СЫРЫМИ значениями из шаблона, без конвертации.** Значит конвертация `*0.5 + 7.0` — свойство потребителей, а не хранилища.

Evidence: `CTclGlobalMethods__New_00623ea0.c:396-397` — 0x623ea0 — сразу после создания объекта:
```c
    FUN_005cd7e0(&local_50);      // SetPos      -> +0xc/+0x10/+0x14
    FUN_005cd840(&local_5c);      // SetWorldPos -> +0x40/+0x44/+0x48
```
Evidence: `FUN_005cd840_005cd840.c:8-20` — 0x5cd840 — «SetWorldPos», копия **без преобразования** + кламп недопустимых значений:
```c
  fVar1 = *param_1;
  *(float *)(in_ECX + 0x40) = fVar1;
  *(float *)(in_ECX + 0x44) = param_1[1];
  *(float *)(in_ECX + 0x48) = param_1[2];
```

(Родственная `FUN_005cda60_005cda60.c:8-20`, 0x5cda60 — тот же setter без вызова `FUN_005ebc90`/`FUN_005eb470`.)

### Откуда взялся литерал в .tcl

**ФАКТ (Diggles.exe): собственный писатель шаблонов движка выгружает в `.tcl` СЫРОЕ значение поля `+0x14` (уровень), без вычитания базы. Значит литерал в шаблоне — это ровно то, что движок хранит и потом умножает на `*0.5 + 7.0`.**

Evidence: `FUN_004fb840_004fb840.c:47-50` — 0x4fb840:
```c

```
где x = `*(float*)(param_1+0xc)` минус `in_ECX+0x194`, y = `*(float*)(param_1+0x10)` минус `in_ECX+0x198`, а z = `*(float*)(param_1+0x14)` **как есть** (база не вычитается — потому что база и есть уровень 0, а не world-Z).

### Сколько дефектов остаётся после перевода

**ФАКТ (измерение, скрипт `z2_surface_check.py`, 2 168 объектов с клеткой и мешем):** правильная конвертация убирает основную массу «висящих» объектов.

**ФАКТ (Diggles.exe): ни одна из команд установки шаблона не вносит смещения по z — ни по величине, ни относительно поверхности.**

## З2.3 Движок не сажает объект на поверхность

**ФАКТ (Diggles.exe): автопривязки к поверхности нет. Единственный механизм посадки — явная команда `set_pos_bottom`, которая вызывается скриптом, а не движком при создании объекта.**

Evidence: `CTclObjMethods__SetPosBottom_00683050.c` (0x683050) → `FUN_005cb600_005cb600.c:32-37` (0x5cb600) — смещение считается от низа модели:
```c
  ... - *(float *)(iVar2 + 0x54) * 0.005 ...
```
(множитель 0.005 — модельный масштаб; в шаблонах главы эта команда не используется — grep по `data/Templates/*.tcl` не дал совпадений).

Evidence: `FUN_006bafe0_006bafe0.c` (0x6bafe0) — разбор позиции из Tcl — не обращается к карте и клетке вовсе.

Вывод: **объект в шаблоне стоит там, где автор его поставил, в абсолютных уровнях; «прилипания» к рельефу нет.**

## З2.5 Отрицательные z: надземный слой со своей системой отсчёта

**ФАКТ (данные + код): объекты с отрицательным литералом — это декор надземного слоя (Oberwelt), а не подземный декор; их z записан в чужой системе отсчёта и в главу не переносится.**

* Классы с целиком отрицательным z (выборка по всем `data/Templates/*.tcl`, 1 111 объектов из 33 325): `Dummy_Urw_sumpf` [−45.01…−37.01], `Dummy_Urw_baumriese_a/b/c`, `Dummy_Urw_baumstumpf_*`, `Dummy_Urw_bergwand_a`, `Dummy_Urw_riesenwurzel_*`, `Dummy_Urw_wurzel_l`, `Dummy_Urw_xwing` (−73.01), `Dummy_Lav_*`/`Dummy_Lava_sumpf` (−41.01…−53.01), `Dummy_Kris_*`, `Dummy_Met_*`, `Dummy_Swf_*`, `Dummy_Obw_*`, `Dummy_Brain_borg_*`.
* В шаблоне `data/Templates/urw_unq_einsiedler.tcl` это видно буквально: обычные объекты комнаты имеют z в шкале уровней (8.55999, 10.9, 1.89999, 3.14, 11.02, 13.2, 15.04 …), а «надземные» — отрицательные: `Dummy_Urw_sumpf` z = −39.01 и −41.01, `Dummy_Urw_baumriese_a` −29.01, `Dummy_Urw_bergwand_a` −53.01, `Dummy_Urw_xwing` −73.01. Причём их x/y — целые/половинные координаты **другой** сетки (22.5/11.5, 4.5/2.5, 37.5/24.5), т.е. координаты надземной сцены, а не главы.
* Уровень быть не может отрицательным: высота клетки — это байт-уровень (`sub-block+0x54 & 0xf`, диапазон 0…15). Отрицательное значение в шкале уровней невозможно ⇒ это **не** шкала уровней.
* То есть у надземного декора **своя система отсчёта**, и приведение её к уровням главы невозможно одним множителем. Движок такого преобразования не имеет: он переведёт −39.01 как `7.0 + 0.5·(−39.01) = −12.5`, то есть **в оригинале эти объекты тоже лежат ниже карты и не видны** — они остались от надземной сцены.

**ФАКТ (Diggles.exe): в движке существует отдельная система воды/жидкости, не связанная с объектами-декорами.** «Sumpf» (пруд/болото) и «Lava» в оригинале — это блоки-жидкости, а не обычные меши.

Evidence: `CFluid__Draw_00576c60.c:161` — 0x576c60 — «`wasser_env.tga`» (окружение воды).
Evidence: `CTclGlobalMethods__SetWater_006622b0.c` (0x6622b0), `CTclGlobalMethods__GetWaterHeight_00662010.c` (0x662010), `CTclGlobalMethods__IsUnderWater_00661da0.c` (0x661da0), `CTclGlobalMethods__WaterDBG_006624d0.c` (0x6624d0) — команды `set_water`, `get_waterheight`, `isunderwater`, `waterdbg`.
Evidence: `FUN_005716e0_005716e0.c:125-126` и `:584-585` — 0x5716e0 — блок-класс **`WaterBlock`**; `FUN_0056e320:73-87`, `FUN_0056fb00:49-50`, `FUN_0056f5e0:47-48`, `FUN_00570000:62-63,524-525` — **`WaterDBGBlock`**.
Evidence: `FUN_00618010_00618010.c:2814-2840` — 0x618010 — регистрация команд: `isunderwater`, `set_water`, `waterdbg`, `get_waterheight`.

Вывод для «голубой воды `urw_sumpf` в породе»: в оригинале это **не** объект-меш на поверхности, а (а) остаток надземной сцены, лежащий ниже карты по координате, и (б) по смыслу — поверхность жидкости, задаваемая блоком воды. Порту нечего «прилипать» к нему: его надо либо не выводить в главе, либо выводить как в оригинале — ниже карты (т.е. невидимо).

## Что это меняет для порта

1. **Главное правило: z объекта из шаблона — уровень, и порт обязан переводить его в world-Z той же формулой, что и высоты клеток: `z_world = 7.0 + 0.5 * z_level`.**

   **Как это выглядит в координатах порта (и почему там ошибаются).** В порте три пространства:
   * экспорт мешей/рельефа пишет z в **world-Z** (диапазон 7.0 … 14.5) — это и есть `7.0 + 0.5*уровень`;
   * сцена упаковывается один раз: `scene_root.scale.z = 0.5`, `scene_root.position.z = 7.0` (`native_campaign_first_level.gd:139-140`, константы `RENDER_DEPTH_SCALE = 0.5`, `RENDER_DEPTH_OFFSET = 7.0`), поэтому **пространство сцены = уровень**: `world = 0.5*уровень + 7.0`;
   * рельеф в сцену кладётся как `BDB_DEPTH_SCALE * export_z + BDB_DEPTH_OFFSET` = `2·export_z − 14` (`native_campaign_first_level.gd:208, 333, 427, 535`), что для export_z = world-Z даёт ровно уровень ⇒ тождественно. То же и в мультиплеерной сцене с её комментарием «BDB corners encode depth as (game_z + 14) / 2» (`multiplayer_test.gd:1711`).

   **Ошибка в объектах:** `native_campaign_first_level.gd:635-637` ставит объект в сцену как
   `BDB_DEPTH_SCALE * placement.z + BDB_DEPTH_OFFSET` = `2·z − 14`, то есть **считает литерал мировой высотой и упаковывает его как рельеф**. После упаковки сцены получается **world-Z = литерал**, а движок даёт **world-Z = 0.5·литерал + 7.0**. Расхождение `7.0 − 0.5·z` (на поверхности 0.6…1.0, внизу главы — до 5 единиц).
   **Исправление (одна строка):** в `instance_root.transform` подставлять z **без BDB-преобразования** — литерал уже является уровнем, а уровень и есть координата сцены:
   ```gdscript
   Vector3(float(placement["x"]), -float(placement["y"]), float(placement["z"]))
   ```
   (эквивалент: `BDB_DEPTH_SCALE * (0.5*z + 7.0) + BDB_DEPTH_OFFSET`).

   **Порт противоречит сам себе:** манифест моделей `godot/models/native_campaign_models.json` в поле `coordinate_transform` прямо документирует правило движка: *«Tcl logical position (x,y,z) -> Godot logical (x,-y,z), then render Z=7+z/2»* — но код рендера реализует `render Z = z`. То же в аудите `tools/audit_object_height.py:4-6, 37`: контрольная величина объявлена как «world-Z = 7.0 + 0.5 * level», а сравнивается с ней **сырой** литерал `z < 7.0` — то есть аудит тоже считает литерал мировой высотой. Оба места надо привести к формуле движка.
   **Почему именно так:** BDB-пространство порта определён так, что BDB = уровень (мир 14.5 → BDB 15, мир 7.0 → BDB 0), т.е. `BDB = 2·(world − 7)`. Для объекта `world = 0.5·литерал + 7` ⇒ `BDB = литерал`.
2. **Следствие — «висящий» декор.** 418 объектов главы, которые сейчас формально ниже низа породы (z < 7.0), после перевода оказываются на 36 (только надземный декор с отрицательным литералом). Именно это и есть артефакт «объекты висят/утоплены» из `docs/review/caves-audit-2026-11-21.md`.
3. **Проверка «террасы 12.5» в комментарии порта (`native_campaign_first_level.gd:624-634`) ошибочна.** Комментарий утверждает, что прежнее поведение (`z/2 + 7`) «подвешивало всё над землёй» и потому было «исправлено». На деле `z/2 + 7` — это ровно формула движка. Ошибка оценки состояла в том, что опорная «земля» бралась как **режим уровня** по всей главе (уровень 11 ⇒ 12.5, `native_campaign_walls.gd:608-614` `cliff_floor_level()`), тогда как дворфы стартовой площадки стоят на уступе уровня 13 (world-Z 13.5) внутри «шахты» блока 71. Исправлять комментарий нужно именно в эту сторону: вернуть `z/2 + 7`.
4. **Надземный декор (`Dummy_Urw_*`, `Dummy_Lav_*`, `Dummy_Obw_*`, `Dummy_Swf_*`, `Dummy_Kris_*`, `Dummy_Met_*`, `Dummy_Brain_borg_*`) не конвертировать общей формулой.** В оригинале он лежит ниже карты (world-Z < 7.0) и не виден; в порту он виден как «голубая вода в породе». Правило: объекты с литералом < 0 (или, точнее, с world-Z < 7.0 после перевода) либо не выводятся в главе, либо выводятся с тем же значением, что и в оригинале (ниже карты), т.е. фактически невидимы. Отдельно: по смыслу «вода/лава» — это блоки-жидкости (`WaterBlock`/`WaterDBGBlock`, `set_water`/`get_waterheight`), а не объекты-декоры; их надо рисовать как поверхность жидкости по данным блока, а не как меш `Dummy_Urw_sumpf`.
5. **Где править:**
   * `godot/scripts/native_campaign_first_level.gd:635-637` — конвертация z объекта (п. 1) + комментарий 624-634 (п. 3);
   * `tools/export_campaign_chapter.py:612` (`"z": entry["z"]`) — можно оставить как есть: экспорт должен хранить **уровень** (как в оригинале), конвертация — на этапе рендера;
   * `godot/scripts/native_campaign_ground.gd` — см. З3 (материал 2 и Z 14.5 вне главы);
   * фильтр надземного декора — рядом с `_build_objects()` (`native_campaign_first_level.gd:586`), где уже есть отсев по классу (`deleted_class`).

## Что осталось неизвестным

1. **В какой именно системе отсчёта записаны отрицательные z надземного декора.** Это не уровни (уровень не может быть отрицательным) и не world-Z главы. Виден только факт: значения «X.01» (−37.01, −39.01, −41.01, −45.01, −53.01, −73.01) и целочисленные шаги по 2/4/8 — следствие конвертации из координат старых карт оригинала. **Как проверить:** найти исходные (не сконвертированные) карты оригинала в `data/` (например, `data/Level*/`) и сопоставить координаты объектов с координатами сцен; либо breakpoint на `FUN_005cd8e0` и лог z объектов надземного слоя в оригинале.
2. **Как именно оригинал рисует поверхность «Sumpf».** Установлено, что в движке есть блоки-жидкости и команды `set_water`/`get_waterheight`, но не установлено, как поверхность воды в конкретной комнате (`urw_unq_einsiedler`) связывается с блоком. **Как проверить:** в оригинале поставить breakpoint на `CTclGlobalMethods__SetWater` (0x6622b0) и `CFluid::Draw` (0x576c60) и посмотреть, какая высота воды соответствует комнате einsiedler.
3. **Не разобран загрузчик `.pmp` (`FUN_005992b0`, 0x5992b0) целиком** — известны только записываемые поля (`cell+0x00, +0x07, +0x13, +0x18`). Возможны неучтённые поля (например, признак «клетка выкопана»). **Как проверить:** дизассемблировать 0x5992b0 целиком и разметить все записи в `map->0x14 + i*0x7c`.
4. **Не проверено, что `set_pos_bottom` (`0x683050`/`0x5cb600`) не вызывается из движка автоматически** для каких-то классов объектов (например, «жидкость» или «трава»). Поиск по декомпиляции не проводился. **Как проверить:** grep по call-графу `FUN_005cb600` и по `set_pos_bottom` в `data/Scripts/`.
5. **Не проверена точная поправка на «дно модели»** в `FUN_005cb600:32-37`: множитель `0.005` указывает на модельный масштаб, но какое поле означает «низ модели» и в какой системе оно задано — не разобрано.
