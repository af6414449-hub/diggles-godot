# З10–З11 — Семантика `cell+0x34…0x3b` (туман войны по игрокам) и `cell+0x3c…0x7b` (карта суб-клеток)

Дата: 2026-11-21. Инициатор: сессия `mvs_785ae066116d4a819552d6b624e53aef`.
Источник: декомпиляция `Diggles.exe` (`C:\diggles-ghidra\out\decomp`), разбор субагента Explore (read-only) + собственные сверки.

**Короткий ответ:** два поля клетки, которые в З8 были записаны как «не разобрано», разобраны:

* `cell+0x34…0x3b` — **не 4 байта «направлений выемки», а 8 байт уровней тумана войны, по одному на каждого из 8 игроков**. Их читает рендер: грань блока рисуется только если рельеф соседней клетки **известен данному игроку**.
* `cell+0x3c…0x7b` — **8×8 карта суб-клеток с битовой семантикой** (бит 0 — «земля», бит 1 — «ступенька/обрыв», биты 2–3 — «тень объекта»). Потребитель существует и он **игровой** (поиск опоры, выбор места, проходимость), а не рендерный.
* `FUN_005a5da0` — это **штамп теней объектов** в карту суб-клеток (биты 2–3), а не «штамп объектов». Это закрывает последний вопрос инициатора по З9 п. 4.

## З10. `cell+0x34 … cell+0x3b` — восемь байт тумана войны (по игрокам)

### ФАКТ (Diggles.exe)

**1. Поле — 8 байт, а не 4.** Все обращения проверяют индекс `if (idx < 8)`, максимальное смещение `0x3b`; `0x34 + 8 = 0x3c` — ровно начало карты суб-клеток, т. е. поле занимает весь остаток клетки до `cell+0x3c`.
Evidence: `FUN_005ab220_005ab220.c:22-68` (accessor: `cell+0x34+param_1`, `param_1 < 8`); `FUN_0057e120_0057e120.c:154` (`pbVar9 = pbVar11 + param_5` при `param_5 < 8`).

**2. Индекс — номер игрока (owner), 0..7.** В файлах сохранились строки-имена функций движка:
* `"void CFogOfWar::RemoveFog(const int iX2, const int iY2, int iRangeX, int iRangeY,const int iOwner)"` — `FUN_0057e120_0057e120.c:47-49`;
* `"void CFogOfWar::FadeBlocks(int iPlayer)"` — `FUN_0057e710_0057e710.c:36`;
* `"void CFogOfWar::NewVisibleBlock(int iX,int iY))"` — `FUN_0057dfc0_0057dfc0.c:19`;
* `"void CFogOfWar::UpdateFoW()"` — `FUN_0057f5c0_0057f5c0.c:47`.

Параметр `iOwner`/`iPlayer` используется как индекс в `cell+0x34`.

**3. Писатели:**

| функция | что делает | запись |
|---|---|---|
| `CFogOfWar::RemoveFog` (`FUN_0057e120:212-218`) | клетка открывается игроку | `*pbVar11 = 0xff` |
| `CFogOfWar::FadeBlocks` (`FUN_0057e710:86-118`) | затухание: значение убывает на 4 за тик; пока > 0x7F — рисуется тёмный «fade block» (цвет 0x50) | `pbVar7[param_1] = (byte)local_20` |
| `CFogOfWar::UpdateFoW` (`FUN_0057f5c0:259-270`) | полный сброс видимости всем 8 игрокам | `*puVar16 = 0xff` (8 байт) |
| `CMap::Init` (`CMap__Init_00594160.c:241-247`) | начальное состояние — memset всего массива клеток в 0 | `cell+0x34…0x3b = 0` |

Последовательность значений при затухании: `0xFF → 0xFB → 0xF7 → … → 0x7F → 0x7B → … → 0x03 → 0x01` (при ≤ 1 клетка убирается из списка).

**4. Семантика значения одного байта `cell+0x34[p]`:**

| значение | смысл |
|---|---|
| `0x00` | клетка игроку `p` **никогда не открывалась** (рельеф неизвестен) |
| `0x01…0x7F` | клетка **исследована** (рельеф известен и засвечен) |
| `0x80…0xFE` | **затухает**: убывает на 4/тик, поверх клетки рисуется тёмный quad |
| `0xFF` | клетка **сейчас видима** игроку `p` |

**5. Читатели (выборочно, полный список — в приложении субагента):**

* **Поиск пути — только по известным клеткам:** `FUN_005a0f00_005a0f00.c:110-118` (`MapPathFinder_Random.cpp`, строка-путь `:51`): `if (*pcVar4 != '\0') { … разрешить шаг … }`; второй поисковик — `FUN_005a1920_005a1920.c:110,181,251,322`; ещё два — `FUN_0059bf90_0059bf90.c:97-103`, `FUN_0059ca30_0059ca30.c:101,178,252,326`.
* **Метка DigMark: условие `cell+0x34[player] != 0` — это байт FoW игрока, и оно НЕ ограничивает постановку метки,** а лишь **включает** проверки материала и твёрдости породы: `FUN_005671a0_005671a0.c:19-27`, `FUN_005672d0_005672d0.c:35` — `if (*(char *)(iVar3 + 0x34) != '\0') { … }` (дизасм `FUN_005671a0` 0x56721C `cmp byte ptr [eax+0x34],0` / `je 0x567269` — при байте 0 метка пишется сразу). Для клетки, игроку **никогда не открытой** (байт = 0), метка ставится без проверок. Подробнее — З18 отчёта.
* **Может ли персонаж стоять:** `FUN_00420840_00420840.c:1984-1986` — `if (*(char *)(uVar3 + 0x34 + iVar8) != '\0')`, где `uVar3` — владелец персонажа (`*(uint *)(param_3 + 0x36c)`).
* **Рендер боковых граней блока:** `FUN_004c6b20_004c6b20.c:38-45, 47-54, 65-72, 74-81, 92-99, 101-108, 120-127, 129-136` — грань (W/S/N/E) рисуется **только если у соседней клетки `cell+0x34[player] != 0`**, то есть рельеф соседа этому игроку известен; дополнительно грань не рисуется, если блок соседа — «воздух» (`:36, 62, 89, 115, 143`). То же: `FUN_004c8220_004c8220.c:50,62,74,85`, `FUN_004c8480_004c8480.c:62,72,82,93,103`.
* **Яркость/затенение клетки:** `FUN_00485370_00485370.c:27-52, 61-86, 95-120, 129-154` — значение `0xFF` даёт самую тёмную яркость (`(255 − min(255, 2·slope))/255`), значения 1..0x7F — полностью светло.
* **Рендер моделей** (паттерн `pbVar = (byte *)(cell + 0x34)` сразу после `FUN_00592f10`) — 40+ функций: `FUN_0049e760:47`, `FUN_0049f790:47`, `FUN_004a07d0:29`, `FUN_004a66c0:34`, `FUN_004b47c0:24`, `FUN_004bfc30:19,29` и др.
* **Иконки на карте:** `CScapeIconMgr__Draw_004c0940.c:109,120,131,141`.

### Что это меняет для порта

* В оригинале **рендер граней блока зависит от тумана войны**: грань к соседней клетке, рельеф которой игроку не открыт, **не рисуется**. Порт рисует все грани всегда ⇒ в неисследованной области порт показывает больше геометрии, чем оригинал. Это отдельная тема (у порта, по-видимому, нет FoW для главы) — но правило зафиксировано.
* **ЗАКРЫТО (З14 отчёта):** `cell+0x08` — 8 ниблов **меток рытья (DigMark) по игрокам**, сдвиг `player*4`. Класс твёрдости: `FUN_00597430` (`v==0→15; v&8==0→11; v&8→(v&3)*4−1`). Гипотеза «известная игроку высота рельефа» — неверна.
* В экспорте порта (`native_campaign_chapter.json`) поля `cell+0x34…0x7b` **не выгружаются вообще** — ни FoW, ни карта суб-клеток. Для главы в исходном состоянии FoW = «видно всё», поэтому на скриншоте разницы не видно; при сравнении с кадром, где часть карты не исследована, разница будет.

### Что осталось неизвестным

* **ЗАКРЫТО (З14 отчёта):** `*(uint *)(param_2 + 0x36c)` — **номер игрока** (`FUN_00596b80:38-40`, `bVar10 = uVar1 * 4` — сдвиг нибла). Интерпретация «8 направлений» отброшена.
* Семантика старших битов байта суб-клетки (0x10…0x80) — прямых читателей не найдено, маска 0xf3 их сохраняет.
* Формула освещения в `FUN_00485370` (коэффициент 1.3) приведена как есть; что за конкретно цвет она даёт — не проверялось.
* Не найден явный писатель значения **0** в `cell+0x34`, кроме общего memset массива клеток (`CMap__Init:246`).

## З11. `cell+0x3c … cell+0x7b` — карта суб-клеток: биты «земля / ступенька / тень»

### ФАКТ (Diggles.exe)

**1. Это 8×8 байт на суб-клетки** (клетка хранится в 8× разрешении: `CMap__Init_00594160.c:169-170`, `*(int *)(in_ECX+0x7c) = param_3 * 8`). Accessor: `FUN_00407e70_00407e70.c:7-8` — `*(undefined1 *)(((param_2 & 7) << 3 | param_1 & 7) + 0x3c + cell)`.

**2. Биты байта суб-клетки:**

| биты | смысл | где |
|---|---|---|
| бит 0 (`0x01`) | **есть земля** (твёрдая проходимая поверхность) | `FUN_005a6350_005a6350.c:94-124` (`:113`), `FUN_00594e00:58,96,150,209,263` |
| бит 1 (`0x02`) | **ступенька / обрыв** (по этому признаку определяется, можно ли поставить гнома) | `FUN_005a6350:113-114`, `CTclObjMethods__GetGnomePosition_0068d8a0.c:86,89` (`if ((*(byte *)(iVar2 + 0x3c + uVar6) & 2) != 0) goto …` — гном не встаёт на обрыв) |
| биты 2–3 (`0x0C`) | **тень объекта** | `FUN_005a5da0_005a5da0.c:111,117,126,140,148` — маска `0xf3f3f3f3`: биты 2–3 заменяются значением тени, остальные сохраняются |
| биты 4–7 (`0xF0`) | не разобраны | маска 0xf3 их сохраняет |

Наблюдавшиеся ранее значения **{0, 1, 3}** этому согласуются: `0` = «нет земли», `1` = «земля», `3` = «земля + ступенька».

**3. Писатели (единственная функция, физически пишущая — `FUN_00596550`):**
* `FUN_00596550_00596550.c:62-101` — копирует 8×8 из плоского буфера суб-клеточного разрешения в `cell+0x3c..0x7b`;
* вызывается из **beautifier** `FUN_005a6b40_005a6b40.c:518`, из **загрузчика `.pmp`** `FUN_005992b0_005992b0.c:563` и из `FUN_005a5da0_005a5da0.c:148` (тени объектов, read-modify-write).

**4. Потребители — игровые (геометрия/коллизия), а не рендерные:**
* поиск точки опоры под объектом (спиральный поиск ближайшей суб-клетки с битом 0): `FUN_00594e00_00594e00.c:58,96,150,209,263,320` (бит 1 — «обрыв/непроходимо»);
* выбор позиции: `FUN_00595770_00595770.c:114,171,209`;
* поиск места: `CPlaceFinder__FindPlaceLongRange_005aa310.c:80,127` — `(... & 2) == 0`;
* команда `ground_pos`: `CTclGlobalMethods__GroundPos_00635c00.c:176,184,192` — маска `~((a & b & c) >> 1) & 1`;
* тест проходимости: `FUN_0040e1f0:38,40,42`, `FUN_0040e700:53`, `FUN_00410fa0:98`, `FUN_00412150:61`, `CTclGlobalMethods__TestD_00647d10.c:98`;
* позиция гнома: `CTclObjMethods__GetGnomePosition_0068d8a0.c:86,89`;
* обход всех 64 байт: `FUN_005a6350_005a6350.c:94-124`.

**5. В рендере потребителя НЕТ.** В диапазоне `0x004cxxxx` (весь рендер) обращений к `cell+0x3c…0x7b` нет: `CScapeRenderer::RenderScape` (0x4c4de0), `FUN_004c8480`, `FUN_004ca830`, `FUN_004c6b20`, `FUN_004cca20`, `FUN_004c5e20`, `FUN_004c6030` карту **не читают** — они читают `cell+0x34` (FoW) и BlockDB. Совпадения `0x3c` в `FUN_004c*.c` относятся к другим структурам; `pbVar16[0x3f]/[0x24]` в `FUN_004ca830:403-453` — это сетка высот **блока** (0x59 байт), а не клетки.

**6. Выемка породы карту суб-клеток НЕ читает.** `FUN_00596b80_00596b80.c` читает `cell+0x00` (ID блока), `cell+0x08` (ниблы), `cell+0x13` (флаги), `cell+0x18` (материал/вариация) — `cell+0x3c` не упоминается. `FUN_005968b0`, `FUN_005976b0` — тоже.

### Что это меняет для порта

* **`FUN_005a5da0` — это не «штамп объектов», а штамп ТЕНЕЙ объектов** в карту суб-клеток (биты 2–3). Ответ инициатору (З9, п. 4): ни `.pmp`-загрузчик (`FUN_005992b0`), ни `FUN_005a5da0` не меняют уровень объектов; они пишут в клетку совершенно другие вещи (материал/атрибут — `.pmp`; тень — `FUN_005a5da0`).
* Порт, если он моделирует расстановку объектов и их тени на земле, должен уметь считать «тень» как 2 бита на суб-клетку (по 8×8 сетке клетки) — сейчас в экспорте этого поля нет.
* Карта суб-клеток — это **единственный** носитель информации о «ступеньках» (бит 1). Порт, строящий откосы по разности высот соседей (З1/З3), решает ту же задачу, но по другому источнику. Стоит проверить, совпадает ли набор «ступенек» оригинала с набором уступов порта (162 грани границ + 1288 уступов + 106 плоских = 1556).

### Что осталось неизвестным

* Точная формула построения карты в beautifier `FUN_005a6b40` (файл ~600 строк): откуда берётся бит 1 («ступенька») — не воспроизведено.
* Семантика старших битов байта суб-клетки (0x10…0x80).
* `FUN_0060c590_0060c590.c:87` вызывает `FUN_005961c0(0, &local_18)` с NULL-буфером — по всей видимости сброс/очистка карты; смысл не раскрыт.
* Не проверен диапазон `0x0049xxxx…0x004bxxxx` на дополнительных потребителей `cell+0x3c` (там искались только `0x34`).

## Дополнение (2026-11-21): семантика параметра `value` команды `dig_mark` и уточнение про `cell+0x34`

Разобрано в отчёте (`report.md`, раздел З18). Кратко:

* Tcl-команда — **`dig_mark <игрок> <x> <y> <режим> [<value>]`** (`CTclGlobalMethods__DigMark_006586c0.c`; скрипты: `ai/std_ai.tcl:3036, 3038, 3054`, `sequences/Oberwelt/tourn_2100.tcl:266, 328`, `classes/story/Trigger_Schwefel.tcl:672, 702`, `Trigger_Crystal.tcl:645, 676`, `Trigger_Tutorial.tcl:1637`).
* **Режимы:** 0 — поставить метку с твёрдостью `value` (нибл = `value|8`); 1 — поставить метку с твёрдостью 3 (нибл = `3`, **без бита 3**); 2 — стереть метку игрока (`cell+0x08 &= ~(0xf << player*4)`).
* **`value` (0..3) = класс твёрдости/глубина породы**; нормализуется как `(value > 0) ? min(3, value) : 0`.
* **Структура нибла:** биты 0-1 = значение, бит 3 = «метка поставлена этим игроком»; класс твёрдости по `FUN_00597430`: 0→15, без бита 3→11, иначе `(nibble&3)*4−1` ⇒ 0/3/7/11.
* **Уточнение про `cell+0x34[player]`:** это байт **тумана войны** игрока, и условие `!= 0` **не запрещает** постановку метки —
  оно лишь **включает** дополнительные проверки материала (`cell+0x18 & 3` = 0 или 3 → отказ) и твёрдости породы
  (`FUN_005968b0` ≥ класса из нибла, иначе отказ). Для клетки, игроку **никогда не открытой** (байт = 0), метка ставится без проверок.
* **ID метки** (`cell+0x0c`) = `(*(uint *)(this + player*4 + 0xb4) & 0xf) << (player*4)`; `this` — синглтон `FUN_00566460()` (объект пещер, конструктор `FUN_005661c0` грузит `data/templates/cave0.tga`…`cave3.tga`).
