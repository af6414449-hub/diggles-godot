## З29.1. Вершинный формат движка — 8 вариантов, все расшифрованы

### ФАКТ (DigglesPort.dll)

1. **Порт разбирает вершинный формат, который присылает движок**, и сам собирает
   D3D11 input layout: `FUN_10009340` по коду формата возвращает **размер вершины в байтах**;
   неизвестный код ⇒ исключение `"unknown vertex format"` (строки `.rdata`:
   `POSITION`, `TEXCOORD`, `COLOR`).
   Evidence: `FUN_10009340_10009340.c:9-39`; `out_port/strings.tsv` (0x10044DC0…0x10044E98).
2. **Полная таблица «код формата → размер вершины»:**

   | код | размер | раскладка вершины | кому соответствует |
   |---:|---:|---|---|
   | `0x102` | 0x14 (20) | POSITION float3 + TEXCOORD float2 | `Straight.fx` |
   | `0x104` | 0x18 (24) | POSITION float4 + TEXCOORD float2 | — (вариант Straight) |
   | `0x1c2` | 0x1c (28) | POSITION float3 + COLOR0(dword) + COLOR1(dword) + TEXCOORD float2 | `UL1CS.fx` |
   | `0x1c4` | 0x20 (32) | POSITION float4 + COLOR0 + COLOR1 + TEXCOORD float2 | `TL1CS.fx` |
   | `0x202` | 0x20 (32) | вариант с 0x200 | — |
   | `0x204` | 0x20 (32) | вариант с 0x200 | — |
   | `0x2c2` | 0x24 (36) | POSITION float3 + COLOR0 + COLOR1 + TEXCOORD[2] | `UL2CS.fx` |
   | `0x2c4` | 0x28 (40) | POSITION float4 + COLOR0 + COLOR1 + TEXCOORD[2] | `TL2CS.fx` |

   Evidence: `FUN_10009340_10009340.c:9-39` (карта кодов);
   `FUN_100023e0_100023e0.c:49-85` (коды форматов при регистрации шейдеров:
   `0x1c2` → UL1CS, `0x2c2` → UL2CS, `0x1c4` → TL1CS, `0x2c4` → TL2CS, `0x102` → Straight);
   HLSL-структуры `VS_INPUT` в соответствующих `.fx`.
3. **Кодирование кода формата:** младшие биты `0x02`/`0x04` — разрядность позиции
   (float3 против float4), бит `0xC0` — наличие `COLOR0`+`COLOR1` (диффузный и зеркальный
   цвета), бит `0x100` — вторая текстурная стадия (два набора UV), бит `0x200` — отдельный
   вариант (точное назначение не установлено).
   ⇒ **Проверка согласованности с HLSL сходится байт в байт:** `UL1CS` объявляет
   `float3 crd : POSITION` (12) + 2×dword (8) + `float2 uv` (8) = 28 = 0x1C;
   `TL2CS` — `float4 crd` (16) + 8 + `float2 uv[2]` (16) = 40 = 0x28.
   Evidence: `UL1CS.fx`, `TL2CS.fx` (блоки `VS_INPUT`), таблица выше.

### Что это меняет для порта

* **Формат вершины оригинала известен точно**, в байтах: 20/24/28/32/36/40.
  Для Godot-порта это готовый контракт: вершина = позиция (3 или 4 float) +
  опционально два цвета (упакованный ARGB dword каждый) + один или два UV.
* **«Свет в вершине» — это два dword-цвета (COLOR0 diffuse, COLOR1 specular)**, а не
  отдельный float-материал. Это же объясняет, почему оригинальный шейдер обходится без
  нормалей: нормали света в цвете вершины.

## З29.2. Две пост-опции: Anti-Aliasing и Post Effect

### ФАКТ (DigglesPort.dll)

1. **`PostProcessOptionManager` управляет ровно двумя опциями**, индекс 0 и 1:
   * `param_1 == 0` ⇒ имя **«Anti-Aliasing»**;
   * `param_1 != 0` (т.е. 1) ⇒ имя **«Post Effect»**.
   Состояние каждой: `*(int *)(this + param_1*4) == 1` ⇒ «enabled», иначе «disabled».
   Evidence: `GetModeLine_100144f0.c:14-22`; строки `Anti-Aliasing` (0x1004387C),
   `Post Effect` (0x10043870), `enabled`/`disabled` (0x1004385C/64).
2. **Согласуется с exe:** `FUN_0047d4e0` вызывает `PostProcessOptionManager::Update(this,0)`
   и `Update(this,1)`, читает `GetModeSet(this,0)` (это Anti-Aliasing) и по нему зовёт
   `ScreenResolutionManager::EnableAntiAliasing(...)`; опция 1 (Post Effect = bloom)
   применяется в порту через цепочку `SceneBrightness → BloomBrightness → Blur → Composition`.
   Evidence: `FUN_0047d4e0_0047d4e0.c:45-46, 68-74, 93-94`; `FUN_0047d4e0` в отчёте (З25.4 п.4).
3. **Профили шейдеров:** `vs_4_0`, `ps_4_0` (SM 4.0) и `cs_5_0` (compute, только для
   `ResolveDepthBuffer.fx` — резолв MSAA-глубины).
   Evidence: `out_port/strings.tsv` (0x10044E74/80/8C).

### Что это меняет для порта

* **Набор «настроек графики» оригинала полон и мал:** разрешение, режим окна
  (Fullscreen / Windowed / Borderless), гамма, Anti-Aliasing, Post Effect (bloom).
  Godot-порт должен держать ровно эти пять — тогда поведение совпадёт.
* **AA в оригинале — не MSAA-сглаживание геометрии, а отдельная опция**, которая в порту
  влияет на создание ресурсов (`EnableAntiAliasing` ⇒ `DxResourcesRecreate`).
  Если в порту включать MSAA «по умолчанию», картинка разойдётся с оригиналом.

### ФАКТ (DigglesPort.dll)

   `C:\dev\wiggles\port\src\PortVideoPlayer.cpp`, `C:\dev\wiggles\port\src\RealDx.cpp`
   (движок — `C:\dev\wiggles\Wiggles\Wiggles\DxBase\Shader.cpp`, З27.1).
   ⇒ исходники движка и порта лежали рядом в одном дереве `C:\dev\wiggles`.
   Evidence: `out_port/strings.tsv` (0x10044F08, 0x100451B8).

   («Direct3D Adapter (bygpu) (%u): VID:%04X, PID:%04X - %ls», «Enumerated adapter %d : %ls»),
   выбор разрешения («Mode %d : (%d x %d) with %u Hz», «Sorted display mode : %d x %d, %u Hz, %s»),

3. **Достижения Steam:** константы `ACH_*` (ACH_WELCOME, ACH_THIEF_FIGHT, ACH_FINISH_TUTORIAL,
   ACH_END_OF_WORLD_1…4, ACH_COMPLETE_THE_CAMPAIGN, ACH_WATCH_END_CREDITS_UNTIL_THE_END,
   ACH_PLAY_X_HOURS, ACH_FINISH_ALL_QUESTS_MISSIONS) и `STAT_*`; триггеры `Trigger_Tutorial`,

   Evidence: `out_port/strings.tsv` (0x10043520…0x100437D8).

### Что это меняет для порта

* **Достижения и часть сюжетных триггеров — в портовом слое.** Значит, поведение
  «Trigger_Urw_006» / переходов между зонами надо сверять с порт-DLL, а не только с exe.
  Для Godot-порта это готовое задание: те же имена триггеров и тот же порядок.
* **Названия зон кампании (Urw / Met / Kris / Lava) и их переходы** видны прямо в порту —
  это ключ к сопоставлению с картой главы из З21/З24.
