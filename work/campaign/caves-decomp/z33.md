# З33. Исправление З30: `DAT_00773650` — это реестр **областей профилировщика**, а не «типы объектов»

*(2026-11-22; ревизия двух утверждений З28/З30 по результатам дизассемблирования)*

З32 ввёл метрику «по точкам принятия решений». При её наполнении пришлось
перепроверить Д24 и Д25, и проверка вскрыла **ошибку в З30**, которая
могла привести порт к постройке несуществующей подсистемы.

## 1. Где была ошибка

З30 утверждал:

* «существует глобальный **реестр типов объектов** — массив с шагом 0x40»
  (`DAT_00773650`), `+0x3C` — имя типа, счётчик — `DAT_00783650`;
* «**0x400 = 1024 тайла на тип объекта**», `DAT_00773680 + tile*0x10` — bbox тайла,
  `DAT_00783654 + (type*0x400 + tile)*4` — счётчик объектов в тайле;
* «**порядок/группировка отрисовки задаётся типом объекта** (реестр
  `DAT_00773650`)», отсечение — по 1024 тайлам на тип;
* «„группа“ из З28 — это и есть **тип объекта**».

## 2. ФАКТ (Diggles.exe): что на самом деле лежит в `DAT_00773650`

Проверено дизассемблером на трёх независимых местах.

### 2.1 Регистрация области (открытие)

Дизасм. `0x404E83–0x404EA9` (`C3DDB__Persist`):

```
mov  ecx, dword ptr [0x783650]                 ; счётчик областей
mov  eax, ecx
shl  eax, 6                                    ; index * 0x40
mov  dword ptr [0xc3ca20], ecx                 ; id этой области
mov  dword ptr [eax + 0x77368c], 0x71c7f4      ; имя области (+0x3C в записи)
mov  dword ptr [eax + 0x773650], ecx            ; id области (+0x00 в записи)
inc  dword ptr [0x783650]
```

### 2.2 Открытие области — инлайн в каждой функции

`CDisplay__Draw_004781b0.c:234-244` (то же в 647 файлах):

```
uVar1 = *(undefined4 *)(&DAT_00773650 + DAT_00c8ad84 * 0x40);   ; id области
iVar3 = FUN_0043fcc0();                                        ; TLS-стек
*(undefined4 *)(iVar3 + *(int *)(iVar3 + 0x8000) * 4) = uVar1;  ; push id области
*(int *)(iVar3 + 0x8000) = ... + 1;
... счётчик области +1, при первом входе — rdtsc-метка ...
FUN_00464180();     /* работа */
FUN_0043fd30();     /* закрытие */
```

### 2.3 Закрытие области (`FUN_0043fd30`)

Дизасм. `0x43FD8F–0x43FDD3`:

```
call 0x43fcc0
mov  ecx, dword ptr [eax + 0x8000]     ; глубина стека областей
add  ecx, -2
cmp  ecx, 0x1fff
ja   <нет родителя>
mov  eax, dword ptr [eax + ecx*4]      ; id РОДИТЕЛЬСКОЙ области
mov  dword ptr [esi + 0x38], eax       ; записать в запись области
cmp  eax, -1
je   <нет родителя>
shl  eax, 6
add  dword ptr [eax + 0x773680], edi   ; +0x30 записи РОДИТЕЛЯ: накопить время (низ)
adc  dword ptr [eax + 0x773684], ebx  ; +0x34: старшая часть
mov  eax, dword ptr [esi]             ; +0x00 записи области = её собственный id
shl  eax, 0xa                         ; id * 1024
add  eax, dword ptr [esi + 0x38]      ; + id родителя
inc  dword ptr [eax*4 + 0x783654]     ; счётчик связок «область → родитель»
```

`this` у `FUN_0043fd30` — **адрес записи области**, а не объект:
дизасм. `0x47838A–0x478399` (`CDisplay::Draw`):

```
mov  ecx, dword ptr [0xc8ad5c]     ; id области
shl  ecx, 6
add  ecx, 0x773650                 ; &запись_области
call 0x43fd30
```

### 2.4 Итоговая структура записи области (0x40 байт)

| смещение | содержимое |
|---|---|
| +0x00 | id области (равен индексу) |
| +0x04 | счётчик вхождений (сколько раз область открывали) |
| +0x08 | rdtsc-метка первого входа, младшие 32 бита |
| +0x0C | rdtsc-метка первого входа, старшие 32 бита |
| +0x30 | накопленное время (64 бита) — время внутри области |
| +0x38 | id родительской области |
| +0x3C | указатель на имя области |

И массив связок: `0x783654[(id_области * 1024) + id_родителя]` — счётчик.

## 3. Почему это профилировщик, а не «типы объектов»

1. **Имена областей — имена функций.** В реестре: `"CDisplay::Draw() 6"`,
   `"CDXExecBuf::Render() Per-Job"`, `"C3DDB::Persist(CUniArc& arc) Mapping"`,
   `"CTclGlobalMethods__fincr"`, `"CDisplay::DrawObjects() DummyRenderjobs"` —
   это **скоупы функций**, а не классы объектов. Всего таких регистраций
   в exe — 647 файлов (7853 обращения к символам).
2. **Открытие/закрытие строго парны** и вложены: `push id` в начале работы,
   `FUN_0043fd30` в конце, причём закрытие читает с вершины стела
   **родительскую** область.
3. **Считается время**, а не пространство: `rdtsc` на входе, разница на выходе,
   накопление в `+0x30` родителя. Для «типа объекта» время не накапливается.
4. **`0x783654` читает только `FUN_0043fd30`** — массив связок никто не читает
   в exe (поиск по `DAT_00783654` даёт ровно 3 совпадения, все в этой функции).
   Никакой геометрии по нему не строится.

## 4. Что именно было неверно (исправления)

| утверждение З28/З30 | статус | правильная формулировка |
|---|---|---|
| «реестр типов объектов `DAT_00773650`, шаг 0x40» | **ОПРОВЕРГНУТО** | реестр **областей (скоупов) профилировщика**, шаг 0x40 |
| «`+0x3C` — строковое имя типа» | **исправлено** | `+0x3C` — имя **области** (строки функций) |
| «0x400 = 1024 тайла на тип» | **ОПРОВЕРГНУТО** | 1024 — число возможных **родительских областей** на область (слоты счётчика связок), не тайлы |
| «`DAT_00773680 + tile*0x10` — bbox тайла» | **ОПРОВЕРГНУТО** | `0x773680` = `+0x30` **в записи области** — накопитель времени; шаг 0x40 (не 0x10) — это шаг записи области |
| «`DAT_00783654 + (type*0x400 + tile)*4` — счётчик объектов в тайле» | **исправлено** | счётчик связок «область → родительская область» |
| «порядок/группировка отрисовки задаётся **типом объекта**» | **ОПРОВЕРГНУТО** | порядок задаётся **ключом сортировки задач** в `FUN_00450850` (З31 п.3 ш.7); тип области к порядку отношения не имеет |
| «„группа“ из З28 — это и есть тип объекта» | **ОПРОВЕРГНУТО** | «группа» = **группа материалов** (`материалы +0x1058`, шаг 0x48, запись 0x48: 16 id техник + имя + родитель) — см. З31 п.2 |

**З31 не затронут**: там «группа» уже трактуется правильно — как группа
материалов с собственной 16-слотовной таблицей техник.

## 5. Что это меняет для порта

1. **Не строить тайловую сетку 1024×N.** Её в движке нет: ни бокса, ни
   счётчиков по тайлам, ни преобразования «мир → тайл». Любая такая сетка в
   порте — выдумка, а не воспроизведение оригинала.
2. **Не строить «реестр типов объектов» с таблицами техник на тип.**
   16-элементная таблица техник принадлежит **группе материала**
   (`default` / `additiveonly` / `modelnozwrite` + пользовательские), а не
   классу объекта. Это важное различие: в Godot это ресурс-материал
   с именем, а не свойство меша.
3. **Порядок отрисовки переносить из `FUN_00450850`**, а не из «типов»:
   ключ = (проход объекта, признак «есть настоящий шейдер», признак
   `+0x20 != 1`, `ROUND((fVar1+fVar2)*40)`), сортировка — `_qsort` с
   компаратором `RenderJob__Validate`.
4. **Профилировщик можно не портировать вообще** — на игру он не влияет
   (только тайминги и счётчики). Но если нужен отладочный оверлей
   с профилем, его устройство теперь известно полностью.

## 7. Что осталось неизвестным (и как проверить)

* **D25 (переформулированный) — есть ли отсечение по видимости.**
  Поиск по строкам `cull|frustum|ClipPlane` в exe даёт только 2 попадания
  (в парсере определений шейдеров) ⇒ поимённого отсечения нет. Но отсечение
  может быть встроенным в арифметику сортировки/глубины.
  **Как проверить:** поставить камеру так, чтобы значимая часть сцены была за
  спиной, и сравнить число вызовов отрисовки (счётчик в `DAT_0076a2f0`,
  `DAT_0076a338+0x281c/0x2820` — там движок сам считает объекты и кадры).
* **Компаратор `RenderJob__Validate`** (сортировка задач отрисовки) не разобран.
  **Как проверить:** прочитать `RenderJob__Validate` — он определяет старшинство
  двух ключей сортировки.
* **`FUN_0045e120(0)`** (вызывается в `CDXExecBuf__Render:101`) — по коду
  выглядит как сброс/инициализация записи шейдера (`FUN_004559a0(param_1 * 0x6c + base)`),
  но назначение не установлено.
  **Как проверить:** прочитать `FUN_0045e120` целиком.

## 8. Оговорка

Всё — статический анализ (Ghidra + дизассемблер + чтение PE). Сверка с живой
игрой не выполнялась. Структура профилировщика подтверждена **тремя**
независимыми дизассемблированными местами (`0x404E83`, `0x405AF0`, `0x43FD8F`,
`0x47838A`), что делает вывод устойчивым.
