## З24.7 — Уточнение спецификации `.pmp`: формула суб-клеток, потребители карты `cell+0x3c`, поправки

*(2026-11-22; дополнение к З8/З13/З16 — сам формат `.pmp` там уже восстановлен полностью; здесь только то, чего в отчёте не было)*

### ФАКТ (Diggles.exe + данные)

1. **RLE-секция `.pmp` — это плоская сетка (W·8)×(H·8) в row-major, а НЕ набор 8×8-плиток по клеткам.**
   Формула индекса суб-клетки подтверждена **двумя независимыми ветками** `FUN_00596550` (0x596550) — функцией, раскладывающей RLE-буфер по клеткам карты:

   * быстрый путь (копирование 8×8 целиком, `:64-102`):
     `idx = ((cy*8 − y0*8) + sy) * (w*8) − x0*8 + cx*8 + sx` → запись в `cell+0x3c + sy*8` (8 байт = две записи по 4 байта);
   * медленный путь (побайтово, когда блок выходит за границу шаблона, `:104-131`):
     `idx = ((cy*8 − y0*8) + sy) * (w*8) − x0*8 + cx*8 + sx` → запись в `cell+0x3c + sy*8 + sx`.

   Формулы в двух ветвях **идентичны**. Вызов из загрузчика `.pmp`: `FUN_005992b0:559-563` —
   `FUN_00596550(buf, {x0*8, y0*8, (x0+w)*8, (y0+h)*8})`.
   Evidence: `FUN_00596550_00596550.c:68-101` и `:111-124`; `FUN_005992b0_005992b0.c:559-563`.

   Раскладка **приёмника** в клетке карты: `cell+0x3c + subY*8 + subX` (8 строк по 8 байт; строка = Y, столбец = X) —
   это совпадает с З8 п.1/З11 п.1.

2. **Проверка на реальных данных (свой скрипт, своя зона).**
   `pmp_subcell_layout.py` → `pmp_subcell_layout.txt`: для `caves_1.pmp` (12×8), `hol_001.pmp` (20×8), `gng_001.pmp` (4×4)
   RLE-буфер имеет длину **ровно 64·W·H** во всех трёх случаях (совпадает с проверкой по всем 90 файлам из З8).
   При чтении как плоская сетка (W·8)×(H·8) картина связная: у `caves_1.pmp` — ступенчатый «карман»
   (субклетки клеток (4,3) и (5,3), граница идёт по диагонали) и сплошная полоса кода **3** высотой 2 субклетки
   по нижней грани шаблона; у `hol_001.pmp` — два «кармана» и та же нижняя полоса; у `gng_001.pmp` — полоса
   по нижней кромке с рваным верхним краем.
   При чтении как «плитки по клеткам» (cell-major) из той же формулы получается рваная каша, не согласующаяся
   с рисунком. ⇒ **формула плоской сетки верна.**

3. **Совпадает с реверсом инициатора.** `tools/audit_pmp_subcell.py:89` использует
   `(cy*8+sy)*(width*8)+cx*8+sx` — это та же формула (при `x0=y0=0`). **Расхождений нет.**

4. **УТОЧНЕНИЕ к З8 п.2 / З10–З11 п.3: у карты `cell+0x3c` есть явная БИТОВАЯ семантика, и найден конкретный формульный потребитель.**
   З8 п.2 был прав только про *рендер* («рендер `FUN_004ca830` карту `cell+0x3c` вообще не читает») — это остаётся верным;
   игровые потребители были описаны в З10–З11 п.5. Здесь уточнено:

   * **`CTclGlobalMethods__GroundPos_00635c00.c:172-192`** — читает **три байта подряд по строке субклеток**:
     `A = byte[(sx,sy)]`, `B = byte[(sx+1,sy)]`, `C = byte[(sx−1,sy)]`, и вычисляет
     `bVar9 = ~((C & B & A) >> 1) & 1`. Далее сканирование идёт вправо по X, пока `bVar9 != 0`
     (`:193-197`), т.е. **останавливается там, где ступенька идёт сплошной полосой из трёх субклеток**;
     после этого берётся **уровень блока** в найденной субклетке: `block+0x00..+0x3f` (сетка высот 8×8)
     (`:207-226`), и результат — высота «земли» под точкой.
   * `CPlaceFinder__FindPlaceLongRange_005aa310.c:78-80` — «здесь нет ступеньки?» =
     `(*(byte *)(subcell + 0x3c + cell) & 2) == 0`.

   ⇒ **бит 0 (значение 1) = «земля есть»; бит 1 (значение 2) = «ступенька / обрыв»;
   значение 3 = земля + ступенька; 0 = пусто** (подтверждает З10–З11 п.3 и набор {0,1,3} из З16).
   Evidence: `CTclGlobalMethods__GroundPos_00635c00.c:172-192, 207-226`;
   `CPlaceFinder__FindPlaceLongRange_005aa310.c:78-95`.
   ⇒ **НОВОЕ (не было в отчёте): формула выбора «где пол выработки» — «первая сплошная полоса
   ступеньки из трёх субклеток по X, и высота = уровень блока в этой субклетке».**


5. **ПОПРАВКА к З8 п.4: приоритет «диагонального распространения» — другой.**
   Точный порядок приоритета в第二个 проходе загрузчика `.pmp`:
   **своё → вниз → вправо → вниз-вправо** (а не «своё → диагональ → сосед»).
   Разбор: `local_1d` = сосед **снизу** (`(cy+1)*w + cx`), `bVar17` = сосед **справа** (`cy*w + cx+1`),
   `bVar20` = сосед **снизу-вправо** (`(cy+1)*w + cx+1`); выбор — `uVar3 = local_1d; if (current != 0) uVar3 = current;
   uVar21 = bVar17; if (uVar3 != 0) uVar21 = uVar3; local_1c = bVar20; if (uVar21 != 0) local_1c = uVar21;`.
   Evidence: `FUN_005992b0_005992b0.c:231-300` (в частности `:245` — индекс соседа снизу,
   `:262` — соседа справа, `:275` — соседа снизу-вправо; `:288-300` — выбор).

6. **Материал для shape-кода 1 = «материал самой клетки мира».**
   `(FUN_00592f10(x,y) → cell+0x18) & 3) + 1` — берутся 2 младших бита `cell+0x18` клетки мира, +1.
   Остальные коды (З8 п.3) не менялись: 2 ⇒ 3, 3 ⇒ 2, 4 ⇒ 1, 5 ⇒ 4; код 0 ⇒ пусто; бит 7 = флаг.
   Evidence: `FUN_005992b0_005992b0.c:124-125` (чтение `cell+0x18`), `:158-168` (подстановка).

7. **Новый факт: `cell+0x13 |= 1` проставляется по ВСЕМУ следу шаблона**, а не только при выемке.
   Загрузчик `.pmp` в финальном проходе (`:488-524`) помечает единицей бит 0 каждый блок карты в
   прямоугольнике `[max(mapX0,x0), min(mapW,x0+w)) × [max(mapY0,y0), min(mapH,y0+h))`.
   Плюс три «рамочные» операции над границей шаблона: `FUN_005a3dd0`/`FUN_005a3fd0` с масками
   **0x40000** (весь след), **0x400** (след + 8 клеток вокруг) и **8** (полоса справа) — `:566-603`.
   Evidence: `FUN_005992b0_005992b0.c:488-524, 566-603`.

8. **`cell+0x12` — ПРОИЗВОДНОЕ поле «где в клетке субклетка-пик» (уточнение по З24.12).**
   Младшие 3 бита = смещение по X, биты 3..5 = по Y (линейный индекс субклетки 0..63),
   **бит 6 = «в клетке есть субклетка с флагом поверхности 0x08»** (не «есть точная позиция» —
   точная позиция есть всегда). Писатель ровно один — `FUN_005a6350`; см. З24.12.
   Evidence: `CPlaceFinder__FindPlaceLongRange_005aa310.c:87-91`; `FUN_005a6350_005a6350.c:273, 281`.


9. **ПОПРАВКА: `DAT_0072b3d8` — это НЕ строка с именем camera-set.**
   По VA 0x72B3D8 в exe лежит байт `'s'` — это середина таблицы строковых литералов
   («stab» начинается с 0x72B3D0). Собственный скрипт зоны `str_at.py` (сканирование диапазона
   0x72B360-0x72B420) печатает: `0x0072B3D0 'stab'`, `0x0072B3DC 'beat'`, `0x0072B3E8 'unknown type'`.
   ⇒ Имя camera-set **не хранится строковым литералом exe**; оно приходит со стороны Tcl/скриптов.
   (Прежняя запись «строка DAT_0072b3d8 не извлечена» — следствие неверного предположения, что это строка.)

### Что это меняет для порта

* **RLE-секцию `.pmp` импортировать надо именно как плоскую сетку (W·8)×(H·8) в row-major**
  (а не как «плитки по клеткам»). Формула инициатора в `tools/audit_pmp_subcell.py:89` верна —
  менять её не нужно, но стоит зафиксировать в коде как инвариант (см. п.1–2).
* **Появился смысл, который нельзя упустить: карта `cell+0x3c` = «земля/ступенька», а не высоты.**
  Порт рисует рельеф по блокам BlockDB, поэтому визуально разница может не проявляться; но если порт
  когда-нибудь будет считать «где обрыв» (а он это делает — `native_walkmap.gd`, `native_terrain_state.gd`),
  то правильная семантика: **бит 1 = ступенька**, а не «высота 0.5».
* **«Голубая вода/висящий декор» и «ступеньки» (З19/З20) теперь объяснимы через одну карту:**
  `GroundPos` ищет *первую сплошную полосу ступеньки* и берёт по ней высоту блока — то есть
  **высота «пола» пещеры в оригинале = уровень блока в той субклетке, где кончается ровная земля**.
  Это конкретное, проверяемое правило, которое стоит перенести в порт при рисовании пола выработки.
* **`cell+0x12` — новый вход**: если порт когда-либо будет ставить объекты на землю «как оригинал»,
  позиция считается в субклетках (1/8 клетки) — шаг 0.125, а не в клетках.

### Что осталось неизвестным

* **Кто пишет `cell+0x12`** (полный список писателей и условий) — делегировано субагенту; на момент
  написания известен только читатель (`FindPlaceLongRange`).
* **Значение `cell+0x3c` = 2 (только ступенька, без земли)** в корпусе не встречается
  (З8 п.2: только 0, 1, 3) — неизвестно, может ли оно вообще появиться (beautifier пишет только {0,1,3}).
* **Точная геометрия «полосы ступенек»** — как именно `GroundPos` выбирает сторону обрыва
  (в `GroundPos` сканирование идёт только в +X; в `PlaceFinder` — только в +Y) — требует проверки
  на живой игре: возможно, выбор стороны зависит от положения камеры/игрока.
* **Семантика трёх «рамочных» операций** `FUN_005a3dd0`/`FUN_005a3fd0` (маски 0x40000/0x400/8) — не разобрана.
