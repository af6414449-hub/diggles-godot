# З26. Карта покрытия: сколько кода реально разобрано (и где лежит остальное)

Разобрано 2026-11-22. Скрипты зоны: `coverage_map3.py` (граф + атрибуция + тиры),
`coverage_by_size.py` (покрытие по объёму кода), `analyze_unattributed.py`,
`layout_probe.py`, `boundary_probe.py`.
Результаты: `coverage.tsv`, `coverage.md`, `next_targets.md`.

---

## З26.1. Методика

### ФАКТ (методика измерения)

1. **Корпус — два модуля, а не один:**
   * `C:\diggles-ghidra\out\decomp` — `Diggles.exe`, 11 373 записи;
   * `C:\diggles-ghidra\out_port\decomp` — `DigglesPort.dll`, 1 114 записей (декомпиляция
     порт-DLL уже была сделана, но в отчёте не использовалась ни разу).
2. **Каждая запись классифицируется:**
   * `pseudo` — псевдофункции раскрутки SEH (`Unwind_*`, `FID_conflict*`, `Catch_All_*`),
     созданные Ghidra из `.pdata`; **кода не содержат**;
   * `crt` — статически прилинкованный UCRT/MSVC-runtime. Признак: имя начинается с `_`
     (Ghidra так помечает все распознанные рантайм-функции: `_memset`, `__alloca_probe_16`,
     `___dcrt_*`, `__except_handler4`, `__security_init_cookie`) либо имя совпадает с
     известными шаблонами UCRT (`common_*`, `convert_decimal_*`, `parse_*`, `state_case_*`…);
   * `game` — всё остальное, то есть код игры.
3. **Покрытие измеряется по трём осям:** число функций, объём кода (байты из `index.tsv`),
   глубина разбора (тир). Тиры: `0` — не упомянута; `1` — упомянута один раз; `2` — 2 раза;
   `3` — цитируется со ссылкой вида `файл:строка` (то есть реально разобрана).
4. **Атрибуция анонимных функций** (`FUN_*`): BFS вверх по графу вызовов (до 6 уровней),
   CRT и SEH-узлы обходятся; подсистема берётся у ближайшей именованной функции,
   она же запоминается как «якорь» — по якорю видно, чей это код.
   Evidence: `coverage_map3.py`, функции `attribute()`/`class_of()`.

## З26.2. Числа

### ФАКТ (Diggles.exe + DigglesPort.dll)

1. **`Diggles.exe`: 11 373 записи = 6 105 псевдофункций SEH + 5 268 реальных функций,
   из них 654 — UCRT/MSVC-runtime и 4 614 — код игры.**
   Итого **реального игрового кода ≈ 2.96 МБ** (2 957 338 Б по `index.tsv`).
   Evidence: `coverage.md` (раздел `Diggles.exe`), `coverage_by_size.py`.
2. **`DigglesPort.dll`: 1 114 записей = 173 псевдофункции + 941 реальная функция,
   из них 87 — runtime и 854 — код порта (248 414 Б).**
   Evidence: `coverage.md` (раздел `DigglesPort.dll`).
3. **Покрытие отчётом (`report.md` + `z24.md`):**
   * по числу функций exe: **168 из 4 614 игровых = 3.6 %** (тир 3 — 154 функции = 3.3 %);
   * по объёму кода exe: **321 404 Б из 2 957 338 Б = 10.6 %** (тир 3 — 10.05 %);
   * порт: **0 из 854 функций = 0 %** (ни одна функция порт-DLL в отчёте не упомянута).
   Evidence: `coverage.tsv` (колонка `tier`), `coverage_by_size.py`.
4. **Почему разрыв между 3.6 % и 10.6 %:** разобранные функции — крупные (рендер рельефа,
   LG, загрузчики форматов), а неразобранная масса — мелкие обработчики Tcl-команд.
   Evidence: `coverage_by_size.py` (подсистемы по объёму).

### Что это меняет для порта

* **Корректный ответ на вопрос «какой процент кода exe понят» — 10.6 % по объёму
  (3.6 % по числу функций), причём по теме «пещеры главы» разобрано существенно больше,
  чем в среднем по движку.** Прежняя цифра «11 373 функции» в отчёте была завышена
  в 2.16 раза (псевдофункции SEH) — это надо учитывать при любой оценке.
* **Порт-DLL не исследована вообще — это самый большой нетронутый пласт** (248 КБ кода,
  где сосредоточены D3D11-шейдеры, пост-эффекты, разрешения, звук). Для «правильной картинки»
  это сейчас важнейший источник.

* **Рекордсмены по разобранности — ровно те подсистемы, которых касалась задача инициатора:**

  не разбирались вовсе — они и не входили в задачу.

  именованного вызывающего:** обработчики vtable/колбэки и статические методы, к которым
  Ghidra не восстановила имя. Они не классифицированы, но и не «не поняты» — они просто
  не адресованы по именам.
  Evidence: `analyze_unattributed.py` (все имена в этой корзине — `FUN_*` либо
  `_`-префиксные рантайм-функции).

### Что это меняет для порта

* **Для задачи «пещеры главы» максимальный прирост дают кластеры 3, 4, 5, 9, 14**
  (`CDisplay__DrawObjects`, `CGameThread__SrvDoThink`, `CGameThread__Draw`, `CDisplay__Draw`,
  `CFluid__Draw`) — это рендер и игровой тик, то есть ровно то, где принимаются решения
  «как выглядит пещера» и «когда пересчитывается её геометрия».
* **Кластер 7 (`CProdPlanner__MaintenanceTick`) — это то, чего в Godot-порте, вероятно, нет
  вообще**, а в оригинале он ежекадрово решает, что гномы делают. Если порт не моделирует
  производство, поведение NPC в пещерах будет отличаться.
* **Кластер 6 (`GameLoad`) — точка риска для порта:** загрузка главы из `.pmp`/`.3db`/`.l2m`
  идёт через Tcl-команды, поэтому любой порт, повторяющий формат, обязан поддерживать
  тот же набор команд.

## З26.5. Что осталось неизвестным

* **Функции `DigglesPort.dll` не классифицированы** (854 функции, 248 КБ): атрибуция по
  именам даёт «unattributed» 207 КБ, потому что имена классов порта не попадают в
  таблицу подсистем (`ScreenResolutionManager` и т. п. — это отдельные классы с
  одноимёнными методами, а не `Класс__Метод`). Чинится расширением таблицы.
* **Неизвестно, какая доля «unattributed» exe — реальный игровой код, а какая — служебные
  обёртки вокруг COM/SEH.** Нужен разбор выборки вручную.
* **Ни один процент покрытия не сверен с живой игрой** — все числа получены статически
  (граф вызовов + текст отчёта), а не по факту работы движка.
