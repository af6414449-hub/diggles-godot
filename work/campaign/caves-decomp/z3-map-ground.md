## З3.1 Есть ли отдельная сущность «земля всей карты»?

**ФАКТ (Diggles.exe): НЕТ. Отдельной сущности «земля всей карты» с собственным набором текстур в движке не существует.** Поверхность строится ровно одним путём — «один квад на клетку» — и этот путь работает по всему прямоугольнику карты, а не только по клеткам, затронутым шаблонами. «Камни» главы — не отдельная сущность, а то же самое per-cell разбиение: у клетки либо зарегистрирован 3D-блок (`cell[0x04] != 0xffff`) и тогда рисуется его меш, либо не зарегистрирован (`cell[0x04] == 0xffff`) и тогда рисуется квад земли.

## З3.2 Как карта-широкая земля стыкуется с блоками главы

**ФАКТ (Diggles.exe): стыковка неявная. Никакого правила шва, «кольца» на границе, растушёвки или отдельной обработки перехода «блок → земля» в движке нет.** Единый пофайловый (поклеточный) конвейер работает по всему прямоугольнику; решение «меш блока или квад земли» принимается для каждой клетки отдельно по признаку `cell[0x04]`.

Evidence:
- `FUN_004c8480_004c8480.c:245-274` — 0x4c8480: ветви `uVar17 == 0xffff` (квад земли) и `else` (меш блока) взаимно исключительны; переходных/смешанных случаев нет.
- `CScapeRenderer__RenderScape_004c4de0.c:559-576` — 0x4c4de0: обход прямоугольника карты единообразен, без ветвления по «внутри главы / вне главы».
- `FUN_004c6b20_004c6b20` (0x4c6b20) — построитель вертикальных стен — работает по owner-байтам соседей (`cell+0x34`), то есть по состоянию выемки, а не по границе главы; отдельного «шва» у него тоже нет.

Практический вывод: в оригинале «пустая» земля и камень главы — это один и тот же слой (квад на клетку), у которого в клетках главы вместо квада подставляется меш блока.

## З3.3 Какая команда что рисует

**ФАКТ (Diggles.exe): команду `map` разбирает `CTclGlobalMethods::Map` (0x6325f0); у неё три подкоманды — `create`, `move` и `getoffset`. Ни одна из них не строит квады земли: `create` только готовит данные, `move` двигает начало карты и красит кромку, `getoffset` возвращает начало.**

## З3.4 Что движок рисует в клетке без шаблона

**ФАКТ (Diggles.exe): клетка, на которую не лёг ни один шаблон, получает полноценный квад земли (не пустоту), материал 2 (копаемый) со случайным байтом вариации, и высоту дефолтного блока высот; Z = 7.0 + 0.5·уровень, для штатного BlockDB это уровень 15 ⇒ Z = 14.5 клетки.**

### 4.1 Клетка без шаблона = «нет блока» ⇒ квад земли

`CMap::Clear` (0x593ec0) инициализирует **каждую** клетку карты, а не только клетки шаблонов:

Evidence: `CMap__Clear_00593ec0.c:47-51` — 0x593ec0 — индекс дефолтного блока высот:

```c

  iVar6 = 0;
  if (iVar4 != -1) { iVar6 = iVar4; }
```

Evidence: `CMap__Clear_00593ec0.c:78-92` — 0x593ec0 — заполнение клетки:

```c
        *(undefined2 *)(local_14 + 4 + *piVar1) = 0xffff;   // cell[0x04] — нет 3D-блока
        *(undefined1 *)(local_14 + 6 + *piVar1) = 0xff;
        *(int *)(local_14 + *piVar1) = iVar6;               // cell[0x00] — блок высот
        *(undefined1 *)(local_14 + 7 + *piVar1) = 4;
```

Последний `memset` обнуляет, в частности, `cell[0x14]` (группа текстуры земли = 0 = группа A) и `cell[0x18]` (материал = 0).

`FUN_005992b0` (0x5992b0, загрузчик `.pmp`) **не трогает** клетки вне своего прямоугольника и **не пишет** `cell[0x04]`: он пишет только `cell[0x18]` (материал), `cell[0x00]` (индекс блока высот), `cell[0x07]` (атрибут) и `cell[0x13] |= 1` (`FUN_005992b0_005992b0.c:335-338, 373, 411, 449`). Значит, клетки вне шаблона сохраняют состояние `CMap::Clear`: `cell[0x04] = 0xffff`.

Итог: `FUN_004c8480` для такой клетки попадает в ветку `uVar17 == 0xffff` и строит квад земли через `FUN_004ca830` — то есть **вне главы земля рисуется тем же кодом, что и внутри**, и текстуры те же (`Gnd_<группа><NN>.tga` + `Msk_*.tga`).

Evidence: `FUN_00598f10_00598f10.c:23-26` и `:124-149` — 0x598f10 — «Map Mapgen» пишет материал **во все** клетки прямоугольника карты:

### 4.3 Высота (world-Z)

* `cell[0x00]` = индекс **дефолтного** блока высот (`BlockDB+0x24`, из заголовка `.BDB`), поэтому вся «пустая» карта плоская;
* Z угла (x,y) = `7.0 + 0.5 · (block[+0x54] & 0xf)`;
* Z угла (x+1,y+1) = `14.5` (клетка не выкопана) — тот же уровень 15, что и `get_hmap` за пределами карты (`CTclGlobalMethods__GetHMap_0062faf0.c:120-126` → `0xf` ⇒ 14.5);
* Z = 14.5 ⇒ «потолок» уровня 15 в шкале `7.0 + 0.5·level`.

Проверка согласованности: `FUN_004ca830_004ca830.c:333,341` — 0x4ca830 — уровень угла используется как порог «не рандомизировать вариант текстуры»:

```c
    local_64 = (float *)(float)(*(byte *)(iVar14 + 0x54) & 0xf);
    ...
    uVar5 = (uint)((float)local_64 < 11.0);
```

Для равнинной клетки (уровень 15) `uVar5 = 0`, т.е. вариант текстуры рандомизируется — что и делает mapgen, записывая случайный байт в `cell[0x18]>>8`.

### 4.4 Текстура

`cell[0x14]` (16 бит) = слово вида «земля»: биты 0–4 = индекс варианта внутри группы, биты 5–7 = **группа текстур** (0–7), биты 8–15 = четыре 2-битных угловых кода маски.

Evidence: `FUN_004c4c50_004c4c50.c:17,55` — 0x4c4c50:

```c
    uVar1 = param_1 >> ((char)iVar3 + 8U & 0x1f) & 3;   // угловые коды (байт 1)
    ...
    iVar3 = in_ECX + (param_1 >> 5 & 7) * 0x204 + 8;    // группа = биты 5–7, 8 групп
```

Для клетки вне главы `cell[0x14] = 0` ⇒ группа 0 (группа **A**, `Gnd_A01..A15.tga`), вариант 0, все угловые коды 0 ⇒ маска `Msk_AAAA01.tga`.

### 4.5 Контрольная проверка шкалы по UV экспорта

**ФАКТ (измерение по экспорту): вертикальная текстурная координата оригинала отсчитывается ОТ НИЗА ПОРОДЫ (world-Z = 7.0), а не от нуля модели: `v = z − 7.0`.** По всем 128 676 вершинам экспорта: 57 578 (44.6 %) удовлетворяют `v = z − 7.0` **точно**, остальные 71 098 (55.4 %) — локальные UV в [0,1] (собственные UV модели), иных значений нет.

Это независимая проверка шкалы `world-Z = 7.0 + 0.5*уровень`: если бы экспорт был в другой системе, равенство `v = z − 7.0` не выполнялось бы ровно. Одновременно это **правило для порта**: вертикальная координата текстуры породы/стен должна идти от world-Z 7.0.

> Замечание для порта: в `godot/scripts/native_campaign_ground.gd:32` задан `ROCK_BOTTOM = 0.25`, и в `godot/scripts/native_campaign_first_level.gd:578` V-координата тела породы считается как `corner.z - GROUND.ROCK_BOTTOM`, тогда как `corner.z` — это world-Z из экспорта (7.0…14.5). По оригиналу низ породы = **7.0**, то есть `up = corner.z - 7.0`. (Тело породы под свободными клетками — вообще изобретение порта: в оригинале свободная клетка = плоский квад земли на уровне 15 без тела под ним.)

## Что это меняет для порта

**Правило (одной строкой):** земля карты — это **один квад (2 треугольника) на каждую клетку прямоугольника карты `[0,W)×[0,H)`**; клетка, на которой зарегистрирован 3D-блок главы (`cell[0x04] != 0xffff`), рисуется мешем блока, и **только** она. Отдельной «плоскости земли во весь мир» нет, шва/кольца/растушёвки на границе главы нет.

**Точные параметры клетки вне главы (порту надо выставить ровно это):**

| параметр | значение | источник |
|---|---|---|
| Z всех углов | **14.5** клетки (уровень 15) | `FUN_004c8220:33,44,94` / asm 0x4c83f2 |
| материал (`cell[0x18] & 3`) | **2** (копаемый грунт) | `FUN_00598f10:149` |
| байт вариации (`cell[0x18] >> 8`) | **случайный 0…255** на клетку | `FUN_00598f10:149` |
| группа текстуры (`cell[0x14] >> 5 & 7`) | **0** ⇒ группа A | `CMap::Clear:92` (memset cell+8,0,0x74) |
| вариант текстуры внутри группы | по маске 4 углов + `cell[0x18]>>8` | `FUN_004c4ae0:49,71`, `FUN_004c4c50:55` |

**Что это ломает в текущем порту (проверено по `godot/scripts/native_campaign_ground.gd:10-18`):**
порт сейчас строит «поле земли» (`tools/build_ground_field.py`) с материалом, повторяющим распределение материалов главы (74 % камень / 13 % песок / 3 % земля), и комментирует это как «original draws the ground of the whole map with one texture and a colour variation over the map (Campaign.tcl:6 generate_color_variation)». По декомпиляции это неверно в двух пунктах:

1. **Материал свободной земли в оригинале — 2 (копаемый), а не смесь камня/песка/земли.**
   `map create` заливает материал 2 по всей карте (`FUN_00598f10:149`); камень (0) появляется только на кромке, которую красят `sm_draw_stone -border` / `-funnel` и `map move 0 …` (и в шаблонах главы).
2. **`generate_color_variation` в движке ничего не делает** (0x64cb30) — вариацию даёт генератор карты. Если порт звал эту команду как «источник вариации», это неверно; вариацию надо брать из `cell[0x18]>>8`.

**Где именно править в порте:**

* `godot/scripts/native_campaign_ground.gd` — функция, строящая «поле земли» для свободных клеток (файл целиком посвящён этой задаче; см. его шапку, строки 2–28): заменить «материал по распределению главы + непрерывная текстура» на
  «**каждая свободная клетка = свой квад, Z = 14.5, материал = 2, вариация = псевдослучайная из `cell[0x18]>>8`, текстура = группа A (`Gnd_A*.tga`) по маске углов**».
  Если порт держит «поле» из `tools/build_ground_field.py` (и `tools/build_seamless_ground.py` — то же место), то правило меняется там же: поле должно стать **поклеточным**, с разрывом по границам клеток, как в оригинале.
* `godot/scripts/native_campaign_first_level.gd:334-366` — там комментарий «original creates the map with map create 512 640 and draws the ground over all of it» — комментарий корректен по сути, но конкретику (Z = 14.5, материал 2) надо привести в соответствие.
* `godot/scripts/native_campaign_walls.gd:18-22` — если стены порта строятся по границе «свободные клетки ↔ клетки главы», правило «стык неявный» означает: стена ставится только там, где клетка главы **выкопана** (owner-байты / материал 3), а не на границе прямоугольника шаблона.

**Проверяемый тест:** после `map create 512 640` любая клетка вне шаблонов обязана иметь `material == 2`, `z == 14.5`, группу текстур A; любая клетка под шаблоном — `z` из её блока высот и `cell[0x04] != 0xffff`.

## Что осталось неизвестным

1. **Точный уровень дефолтного блока высот.** `CMap::Clear:47` берёт его из `BlockDB+0x24`, который загружается из заголовка `.BDB` (`FUN_00565ab0_00565ab0.c:70: *(undefined4 *)(in_ECX + 0x24) = puVar11[3];`). Файла `data/BlockDB0.BDB` в этом воркспейсе нет, поэтому проверить, что младший ниббл `+0x54` дефолтного блока равен 15 (Z = 14.5), декомпиляцией нельзя.
   **Как проверить:** прочитать 4-й dword заголовка `data/BlockDB0.BDB` → индекс блока → его байт `+0x54` → `Z = 7.0 + 0.5*(b & 0xf)`.
2. **Seed генератора `FUN_00598f10`** (xorshift `DAT_00767990` / `DAT_00768350`): откуда берётся начальное значение — в коде видно только пересев при `DAT_00768350 == 0x271`; воспроизводимость байтов вариации между запусками не проверена.
3. **Роль `map move` в кампании.** Подкоманда сдвигает начало карты на (dx,dy) и красит запад/восток при `dx == 0`; вызывается ли она в `Campaign.tcl` — по бинарю не видно.
   **Как проверить:** оригинальные скрипты (`data/Scripts/gameplay/Campaign.tcl`).
4. **Единицы измерения прямоугольников `FUN_005fc9d0`.** В коде они заданы числами (`0x20`, `scape->0x7c*4`), но перевод в клетки однозначно не установлен (в `FUN_005fc9d0` есть финальные вызовы `param_1*8-8 … param_3*8+8` ⇒ сетка 1/8-клетки, но тогда `scape->0x7c*4 = W` — это уже клетки). Требует отдельной сверки.
5. **Разделение «меш блока vs квад земли» внутри `FUN_004ca830` (0x4ca830).** Функция выбирает 3 угловых варианта текстуры (`FUN_004c4ae0` ×3, `FUN_004ca830:322-370`) и ищет перекрывающие клетку мезы через `FUN_004c7d80` («GetBlock»). Точный критерий, по которому в порту решается «рисовать квад земли или брать мез блока», декомпиляцией не выделен.
6. **`FUN_004c8220` как «сборщик вершин».** Функция объявлена `void`, но по дизасму (`0x4c8463: call 0x473300` → `ret 8` без записи EAX) её возвращаемое значение — это результат `FUN_00473300`, то есть **тест отсечения по пирамиде видимости**, а не добавление вершин. Прежний док (`answer-osveshchenie-surface`) описывал её как «строителя углов квада»; для З3 это не меняет вывода (высота углов оттуда же), но формулировку стоит уточнить.
7. **Соотношение «81 текстура × группы».** `FUN_004c4c50:55` даёт 8 групп (`(param_1>>5)&7`), на диске `Gnd_A/B/C` по 15 вариантов + `kris/lava/swf/urw` — как они мапятся на 8 групп, не разбиралось.
