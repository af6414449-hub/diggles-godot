**ПОПРАВКА к z5.** В `z5-dig-pipeline.md` и в разделе «конвейер выемки» отчёта было записано
«сетка образцов клетки = 32 байта по 4 бита в `cell+0x08..+0x27`». Это **неверно**:
образцы занимают **один uint32 в `cell+0x08`** (8 ниблов, сдвиг `local_1c` = 0,4,…,28) — это метки рытья по игрокам (З14 отчёта),
а не 32 байта. Основание: `FUN_00596b80_00596b80.c:133,149,276` — все три обращения
берут `*(uint *)(iVar5 + 8)` и маскируют `~(0xf << (local_1c & 0x1f))`.
Это важно, потому что `cell+0x14` (поле жидкости) иначе попадало бы внутрь «сетки образцов».

**A3. Код образца копания** (`FUN_00596b80_00596b80.c:134-145`): ниббл `n` ⇒ материал-запрос:
`n == 0` ⇒ `0xf`; `(n & 8) == 0` ⇒ `0xb`; иначе `0`, либо `(n & 3) * 4 - 1`.

**B2. Значения сетки блока — это УРОВНИ 0..15** (а не доли, не метры).
Эмпирически по `BlockDB0.BDB`: значения 0..15, распределение почти равномерное,
максимум 15 (64 710 вхождений на первых 4000 блоков), минимум 0.
Совпадает с уже установленной шкалой `world-Z = 7.0 + 0.5 * level`
(уровень 0 → 7.0 … уровень 15 → 14.5).

**B3. Рендер читает углы блока и центр.** `FUN_004ca830_004ca830.c:403-427` сравнивает
четыре угловые субклетки с центральной:

| субклетка | смещение | позиция |
|---|---|---|
| NW | `+0x00` | (0,0) |
| NE | `+0x07` | (0,7) |
| SW | `+0x38` | (7,0) |
| SE | `+0x3f` | (7,7) |
| центр | `+0x24` | (4,4) |

Порог: `|угол − центр| >= 4` ⇒ включается «дыра»/гребень (`FUN_004ca080`, вызов на `:420`),
`|Δ| <= 3` ⇒ обычная грань. Это и есть количественное правило «гребня» из З1.

**B4. Таблица конфигураций углов — 81 запись.** `FUN_004c4ae0_004c4ae0.c:49`:
`uVar2 = (((p5 & 3) * 3 + (p4 & 3)) * 3 + (p3 & 3)) * 3 + (p2 & 3)` ⇒ 4 угла × 3 состояния = 81,
таблица лежит по `in_ECX + 0x1194`, размер проверяется `uVar6 < 0x52` (`:53`).
То есть «диагональная» конфигурация — это **один из 81 случаев**, а не отдельное правило.

## C. Формат `.pmp` — ФАКТ, проверено на 100 % корпуса

Загрузчик: `FUN_005992b0` (0x5992b0). Вызывается из `CTclGlobalMethods__MapTemplate`
(0x63bca0, команда `map_template`, `:260,271`) и `FUN_004faa70` (`:88`).

### Формат (порядок чтения — `FUN_005992b0_005992b0.c:72,73,96,97,98,102,103`)

```
offset  тип        содержание
0       int32      W  (ширина шаблона в клетках)      local_18
4       int32      H  (высота шаблона в клетках)       local_30
8       uint8[W*H] сетка «форма/материал»              _DstBuf
8+WH    int32[W*H] ID блока (BlockDB) на клетку        _DstBuf_00
...     int32      N  — число RLE-записей              local_60
...     uint16[N]  RLE-поток высот                     _DstBuf_02
...     uint8[W*H] «extra» на клетку                    _DstBuf_01
```

**Эмпирическая проверка:** разобрано **90 файлов** `data/Templates/pmp/*.pmp`;
после последней секции **хвост = 0 байт у всех 90** ⇒ формат подтверждён полностью.

### Содержимое секций

**C1. Сетка «форма/материал»** (`_DstBuf`, W*H байт). Старший бит (0x80) — флаг;
младшие 7 бит — код 0..5. Наблюдаемые значения по корпусу: `0` (2206 шт.), `2` (6234),
`3` (334), `4` (5139), `5` (92), а также `0x82` (3888), `0x84` (330), `0x85` (17) —
то есть код + флаг 0x80.

Смысл кодов — `FUN_005992b0_005992b0.c:146-215` (первый проход по сетке):

| код | действие | итоговый материал клетки |
|---|---|---|
| 0 | ничего | клетка не меняется |
| 1 | взять материал самой клетки: `(cell->0x18 & 3) + 1` | 1..4 |
| 2 | `\| 3` | **3** (камень) |
| 3 | `\| 2` | 2 |
| 4 | `\| 1` | 1 |
| 5 | `\| 4` | 4 |

**C2. Сетка ID блоков** (`_DstBuf_00`, W*H × int32) → пишется в `cell+0x00` (`:409-411`).
Диапазон по корпусу: 0 … 33701, 3360 различных значений.

**C3. RLE-поток состояния поверхности** (`_DstBuf_02` → `iVar6`). Каждая запись — uint16:
`значение = code & 3`, `длина = code >> 2`, при `code >> 2 == 0` длина = 0x4000 (16384)
(`FUN_005992b0_005992b0.c:534-543`). Декодированный буфер передаётся в
`FUN_00596550` (`:563`) и раскладывается по клеткам в **8×8 сетку `cell+0x3c..0x7b`**.

> **Уточнение (дополнение З8).** Первая редакция называла этот поток «потоком высот».
> Это неверно: `cell+0x3c` — карта **состояния поверхности** со значениями {0, 1, 3},
> а не высоты. Доказательства: (а) по всему корпусу `.pmp` значения только {0, 1, 3} —
> значения 2 не встречается ни разу, и настоящая высота уровнем 2 не была бы редкой;
> (б) **рендер `FUN_004ca830` вообще не читает `cell+0x3c`** (grep по `0x3c` в файле
> не даёт ни одного совпадения) — геометрию он берёт из **блока** (`block+0x00..0x3f`);
> (в) тот же набор значений {0, 1, 3} пишет «beautifier» `FUN_005a6b40` (см. раздел G).

**Размер:** буфер = 64 × W × H байт (сетка 8×8 субклеток на каждую клетку) — проверено:
для всех файлов `len(decode) == 64*W*H` ровно.

**Значения по корпусу:** только **0, 1, 3** (0 → 1 118 704 байт, 1 → 33 774, 3 → 14 882);
значения 2 не встречается ни разу.

**C4. Секция «extra»** (`_DstBuf_01`) → `cell+0x07` (`:449`). Значения 0..8
(преобладает 4 — 15 150 вхождений).

### C5. Второй проход: «размазывание» материала по диагоналям

`FUN_005992b0_005992b0.c:222-456`. Для каждой клетки шаблона берутся четыре значения
(`:240-285`):

* своё (`local_48`),
* сосед по строке выше/ниже (`local_1d`),
* сосед справа (`bVar17`),
* диагональный сосед (`bVar20`).

Если ненулевое значение есть хотя бы в одном из четырёх — клетка получает материал
`:288-374`: приоритет «своё → диагональ → сосед» (`:288-300`), приоритетный код `4`
даёт материал 3 (камень) **без** случайной вариации (`:313-340`), остальные коды дают
материал `код − 1` и случайную вариацию 0..5 в старшем байте (`:343-373`).

**Это и есть единственный источник «диагонального» распространения материала в движке** —
никакого отдельного правила «диагональ → две вертикальные плоскости» нет
(см. З1); диагональ участвует только в выборе материала.

### C6. Что `.pmp` НЕ делает

* Не задаёт высоту клетки как таковую — высоты лежат в блоках BlockDB (раздел B).
  `.pmp` задаёт **какой блок** стоит в клетке, **материал** и **8×8 карту состояния поверхности**
  в `cell+0x3c`**.
* Не трогает существующий блок в клетке: `cell+0x00` перезаписывается только там,
  где сработал второй проход (`:375-411`).
* Не создаёт/не удаляет клетки — только заполняет существующие.

## D. Формат `.l2m` (magic `M2L`) — ФАКТ

**D1. Писатель — `FUN_004fb390` (0x4fb390).** Формат:

```
uint32  magic = 0x004C324D   ('M','2','L','\0')
uint32  w                     (ширина в клетках)
uint32  h                     (высота в клетках)
uint16  grid[w*h]             — из cell+0x14
```

`FUN_004fb390_004fb390.c:150-156` (magic и размеры), `:157-185` (цикл по клеткам,
`_fwrite((void *)(iVar5 + 0x14), 2, 1, pFVar2)`).

**D2. Читатель — `CFluid::Tick` (0x5987c0).** `CFluid__Tick_005987c0.c:22-46`:
читает magic (`:25` — сравнение `local_24 == 0x4c324d`), затем `w` (`:26`), `h` (`:27`),
и для каждой клетки `*(undefined2 *)(cell + 0x14) = value` (`:39`).
После загрузки инвалидируется прямоугольник карты (`:48-58`).

**D3. Эмпирика.** `data/Templates/l2m/*.l2m` — 800 файлов, все по 44 байта = 12 (заголовок) + 16×2.
Пример `lava_gng_012_a.l2m`:
`4d 32 4c 00 | 04 00 00 00 | 04 00 00 00 | 60 01 60 05 60 04 00 00 | 60 11 61 55 60 44 00 00 | 60 10 60 50 60 40 00 00 | 00 00 00 00 00 00`
— сетка 4×4, последняя строка и столбец нулевые, у ненулевых значений старший байт 0x60/0x61.

**D4. Семантика значения** `cell+0x14` как «тип жидкости» подтверждается косвенно:
поле читается/пишется только модулем жидкостей (`CFluid::Tick` — загрузка карты жидкостей,
`FUN_00565ab0`-соседняя подсистема). Конкретный код материала (0x60 = 96 и т.п.) не расшифрован.

## F. З4 (контрольная). Закон спада высоты на краю карты — ответ

### ФАКТ (Diggles.exe)

1. **Спада «по формуле» в движке нет.** Высота рельефа задаётся **данными**:
   8×8 сетка уровней внутри блока BlockDB (`block+0x00..+0x3f`) — это и есть высота;
   рядом в клетке лежит 8×8 **карта состояния поверхности** (`cell+0x3c..+0x7b`,
   значения {0,1,3}), которую `.pmp` и штампы объектов заливают (`FUN_00596550`).

   (`FUN_00596550`).
2. **Видимый «ступенчатый спад» — это буквально данные.** В примере блока 100 (E3) высота
   идёт 15 → 14 → 13 → 12/13/14 → 11, то есть **ступени по 1 уровню = 0.5 world-Z**.
   Движок этот переход не интерполирует, а берёт готовые уровни субклеток.
3. **Единственное вычисляемое правило перехода — порог «дыры»:** разница между угловой
   и центральной субклеткой блока. `|Δ| >= 4` уровня ⇒ «гребень/дыра»
   (`FUN_004ca080`), `|Δ| <= 3` ⇒ обычная грань (`FUN_004ca830:403-427`).
   Это же подтверждает З1: **диагональных вертикальных плоскостей движок не строит**.
4. **`sm_draw_stone` высоты не создаёт** (З4, ранее): он меняет только материал
   (`FUN_005fc9d0`); высоту круга/воронки на краю задаёт **BlockDB-блок**,
   записанный в клетку через `.pmp`.
5. **Сетка клетки (`cell+0x3c`) перезаписывается при штамповании объектов** —
   `FUN_005a5da0` (0x5a5da0) читает текущую сетку клеток (`FUN_005961c0`), накладывает
   маску объекта (8×8 масок-ниблов) и его уровень (`obj+0x268`) и пишет результат
   обратно (`FUN_00596550`, `FUN_005a5da0_005a5da0.c:111,148`). Маска — 4 бита на субклетку,
   уровень объекта — 1 байт; приоритет при наложении: `новый | старый` по младшим 2 битам
   (`:126,140`).

### Что это меняет для порта

* Порт, строящий рельеф по «гладкому» правилу, получит **не тот** профиль края:
  оригинал квантует перепад по **0.5 world-Z на ступень** и берёт высоты из таблицы блоков,
  а не из формулы «спада».
* Порту, который рисует свободную землю, нужна **та же сетка уровней 0..15**,
  а world-Z = `7.0 + 0.5·level` (уровень 15 → 14.5 = поверхность главы,
  уровень 15 → 14.5 = поверхность главы и плоскость земли вне острова (копланарны), см. З7).
* Правило «дыры»: если разница высот угла и центра клетки ≥ 4 уровней — движок строит
  вертикальную грань/проём; ≤ 3 — не строит. Порт, рисующий «510 открытых рёбер»
  (решение З1), должен считать **уровни по субклеткам блока**, а не по углам клетки.
* `cell+0x08` — это **8 ниблов**, а не 32-байтная сетка; любая правка порта, опирающаяся
  на прежнюю формулировку, неверна.

### Что осталось неизвестным

* **Семантика `cell+0x34[dir]`** (4 байта) — что за «направления» и кто их пишет.
  Проверка: grep по `+ 0x34` в функциях, работающих с `idx*0x7c + map->0x14`;
  запись — по всем местам, где пишут `cell+0x30..0x3b`.
* **Что означает «extra» (`cell+0x07`)**: значения 0..8, корреляция с материалом не установлена.
* **Коды материала 4** (в `.pmp` код 5 ⇒ материал 4) — как такой материал рисуется;
  в `FUN_005fc9d0` красятся только материалы 1 и 2.
* **Семантика старшего байта `cell+0x18`** (вариация 0..5) — как она выбирает текстуру.
* **Значения `cell+0x14`**: 0x60/0x61 — что это за идентификаторы жидкости/материала.
* **Формат `.3db`** (43 пакета, включая `hinterlegung.3db`/`oberwelt.3db`) не разобран.
* **Таблица 81 конфигурации углов** (`in_ECX+0x1194`) — не восстановлена, поэтому
  нельзя описать *внешний вид* грани для конкретной комбинации, хотя правило выбора
  («дыра / обычная грань») уже известно.
* **`FUN_005a6b40`** разобран (раздел G) — но не выяснено, что именно означают значения
  0/1/3 в карте состояния поверхности (материал? тип обрыва? уровень?).

## G. «Beautifier» `FUN_005a6b40` (0x5a6b40) — пересчёт карты состояния поверхности

### ФАКТ (Diggles.exe)

**G1. Назначение.** Функция вызывается из `FUN_005a46d0` (рядом с `FUN_005a5da0`) и делает
следующее:

1. Ограничивает прямоугольник по границам карты в субклетках:
   `map->0x94..0xa0` (это `0x7c/0x80/0x9c/0xa0`), с отступами `+0x18 / +0x10 / -0x18 / -0x18`
   клеток (`FUN_005a6b40_005a6b40.c:50-74`).
2. Читает **сетки высот блоков** в расширенный прямоугольник:
   `FUN_00595e40(pbVar6, &local_4c)` (`:78`) — по байту на субклетку.
3. Для каждой субклетки проверяет **16+ соседей** в этой высоте-сетке; если у всех
   `*pbVar15 < 0xe` (14) — `local_b8 = 1` (`:120-414`).
4. Дополнительно: если центральная высота более чем на **2 уровня** ниже соседней
   (`*pbVar15 + 2 < (uint)*pbVar14`, `:434`, `:452`, `:461`, `:466`) — `local_b8 = 3`.
5. Записывает результат `*puVar16 = local_b8` (`:512`) в новый буфер и **перезаписывает
   им 8×8 карты состояния поверхности клеток**: `FUN_00596550(puVar7, &local_20)` (`:518`).

**G2. Значения — те же {0, 1, 3}, что и в RLE `.pmp`.** Совпадение наборов значений
подтверждает, что `cell+0x3c..+0x7b` — одна и та же карта состояния, а не две разные сущности.

**G3. Проверка «клетка свободна».** Перед обработкой проверяется флаг клетки:
`local_c1 = ~(*(byte *)(iVar9 + 0x18) >> 7) & 1` (`:105`) — бит 7 байта `cell+0x18`
(тот же флаг, что ставит загрузчик `.pmp`) означает «клетка помечена», и такие клетки
beautifier не трогает.

**G4. Смысл значений (предположение, не факт).** 0 — «по умолчанию, оставить как есть»,
1 — «клетка окружена соседями ниже уровня 14 (край карты / вне острова)»,
3 — «то же, но с уступом более 2 уровней». Что именно означает каждый код в рендере —
не установлено: **рендер `FUN_004ca830` карту `cell+0x3c` не читает вообще.**

### Что это меняет для порта

* Порт, моделирующий край карты «красивым» сглаживанием, должен учитывать: оригинал
  **не сглаживает** высоты, а переключает состояние поверхности целой клетки
  (0 → 1 → 3) по правилу «все 16 соседей ниже уровня 14» и «уклон более 2 уровней».
* Уровень 14 = world-Z 14.0 (уровень 15 = 14.5 = поверхность главы). То есть «край карты»
  в оригинале — это места, где вокруг клетки **строго ниже 14.0** (т.е. ≤ 13.5) — как минимум на 1.0 world-Z ниже поверхности главы.
* Правило «уровень 14» согласуется с З7: плоскость земли вне острова лежит на 14.5
  (уровень 15) — копланарно с островом; уровень 14 (14.0) — это «ниже острова,
  но ещё не дно».

### Что осталось неизвестным

* Что означают 0/1/3 семантически (материал? признак обрыва? уровень?) — нужно найти
  потребителя карты `cell+0x3c`; рендер её не читает, читают `FUN_005961c0` (штампы)
  и `FUN_00596550` (запись).
* Кто вызывает `FUN_005a46d0` и в каком порядке с загрузкой `.pmp` (beautifier затирает
  то, что залил `.pmp`, — значит порядок существенен).
* Не проверено, что именно лежит в глобальном массиве, к которому обращается
  `FUN_0041fad0` (база `in_ECX[0]`, размер `in_ECX[1]`) — карта высот всей карты
  в разрезе 1/8 клетки.

## З8.1 Дочерние блоки и материалы квадрантов: что означают `block+0x40…0x4c` и `block+0x50…0x53`

*(уточнение З8: там эти поля были записаны как «4 дочерних блока (−1 = нет)» и «material-id», без семантики)*

### ФАКТ (Diggles.exe)

1. **Блок клетки состоит из четырёх квадрантов.** У каждого квадранта — свой **материал** (`block+0x50`, `+0x51`, `+0x52`, `+0x53`) и свой **дочерний блок** (`block+0x40`, `+0x44`, `+0x48`, `+0x4c`; −1 = нет). Это подтверждается выемкой: движок обходит четыре квадранта и для каждого сравнивает материал квадранта с вынимаемым материалом.
   Evidence: `FUN_00596b80_00596b80.c` (0x596b80) — `:56-113`: для каждого из четырёх квадрантов берётся `*(int *)(iVar5 + 0x4c | 0x48 | 0x44 | 0x40)` (ID дочернего блока) и проверяется `*(byte *)(iVar7 + 0x53 | 0x52 | 0x51 | 0x50) == uVar12` (материал квадранта против `uVar12 = FUN_005968b0()` — материала вынимаемого). Порядок квадрантов по смещению: `+0x40/+0x50`, `+0x44/+0x51`, `+0x48/+0x52`, `+0x4c/+0x53`.
2. **При выемке движок подставляет дочерний блок в клетку.** `FUN_00596b80:114-130`: `*piVar6 = local_20 / local_2c / local_30 / local_18` (новый ID блока) в клетку (`cell+0x00`) и `*(byte *)(iVar5 + 0x13) |= 1`; при совпадении материала вместо исходного блока клетки берётся дочерний блок соответствующего квадранта. Затем `:131-152` затирает **метки рытья** в `cell+0x08` (8 ниблов, шаг 4 — по игрокам; см. З14 отчёта) и `:173-174` ставит `cell+0x13 |= 2`.
3. **Сетка высот дочернего блока — это профиль клетки ПОСЛЕ выемки.** Пример из `BlockDB0.BDB`: блок 81 — родительская сетка 8×8 = строки 0-3 «11», строки 4-7 «15»; его квадрант 0 → блок 34526 с сеткой 7/10/11/15 (то есть в выемленной части уровень ниже), квадрант 1 → 34527 (7/9/11), квадранты 2 и 3 → 288 и 211 (11). То есть дочерние блоки — это **предрассчитанные варианты меша и высот для выемленного состояния**, а не «детализация» невыкопанной клетки.
4. **Карта высот в разрезе 1/8 клетки читает только родительский блок.** `FUN_004093f0_004093f0.c:10-21` — `*((param_2 & 7) << 3 | param_1 & 7)` из сетки блока, полученного из `cell+0x00`; `FUN_00595e40_00595e40.c:56-72` — тот же принцип (берётся блок клетки, `iVar11 * 0x59 + map->0x10`).

### Что это меняет для порта

* **В исходном (невыкопанном) состоянии главы экспорт блоков корректен:** порт читает `cell+0x00` → ID блока → меш из BlockDB (`tools/export_campaign_chapter.py:560-573`), и движок в том же состоянии рисует именно этот меш. Правки не требуется.
* **При выемке движок меняет меш клетки на дочерний блок** (предрассчитанный, с готовыми гранями откоса). Порт же рисует откосы, вычисляя их из разности высот (`native_campaign_walls.gd`) — это аппроксимация, а не точная копия. Для главы в исходном состоянии расхождения нет; для сценария с выемкой — есть (это зона сессии стен).
* **Материалы квадрантов (`block+0x50…0x53`)** — четыре байта, по одному на квадрант. В экспорте порта хранится только материал клетки (`cell+0x18`), материалы квадрантов не выгружаются; если порт когда-нибудь будет моделировать выемку, ему понадобятся эти четыре байта из блока.

### Что осталось неизвестным

* Какой именно квадрант (NW/NE/SW/SE) соответствует каждому из четырёх смещений `+0x40…+0x4c` — по выемке порядок известен, но пространственная ориентация не проверена (нужен разбор функции построения меша клетки).
* **ПОПРАВКА (З14 отчёта):** семантика `cell+0x08` установлена — это 8 ниблов **меток рытья (DigMark) по игрокам**, а не «прочность по направлениям»: сдвиг нибла = `player*4`; класс твёрдости через `FUN_00597430` (`v==0→15; v&8==0→11; v&8→(v&3)*4−1`); строки движка `Map\DigMark.cpp`, Tcl-команды `DigMark`/`IsDigMarked`; `cell+0x0c…0x0f` — ID метки по игрокам.
