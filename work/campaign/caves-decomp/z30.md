# З30. Реестр типов объектов, тайловое разбиение и порядок отрисовки

> `FUN_00450850`, а не «типом объекта»; «группа» из З28 — это **группа материалов**,
> а не тип объекта. Полный разбор и ссылки: **З33**, п. 2–4.

## З30.1. Реестр типов объектов

### ФАКТ (Diggles.exe)

1. **Существует глобальный реестр типов объектов** — массив с шагом **0x40 = 64 байта**:
   * `+0x00` — идентификатор типа (`iVar3`);
   * `+0x3C` — **строковое имя типа** (указатель на строку);
   * счётчик зарегистрированных типов — `DAT_00783650`.
   Имена типов в коде — например:
   `"C3DDB::Persist(CUniArc& arc)"`, `"C3DDB::Persist(CUniArc& arc) Mapping"`,
   `"… Header"`, `"… Materials"`, `"… Meshes"`, `"… Objects"`, `"… Anims"`.
   Evidence: `C3DDB__Persist_00402ff0.c:51-56, 75-81, 123-129, 185-191, 233-239, 316-322, 473-479`;
   `&DAT_0077368c + iVar9` при `iVar9 = DAT_00783650 * 0x40` ⇒ смещение имени = +0x3C.
2. **Регистрация типа идёт через `FUN_006cebaa(&<имя>)`** (7 вызовов в `C3DDB__Persist`).
   Evidence: `C3DDB__Persist_00402ff0.c:56, 80, 128, 190, 238, 321, 478`.
3. **«Группа» из З28 — это и есть тип объекта.** Резолвер `FUN_004860c0` берёт
   `in_ECX` = индекс группы, адресует `*(int *)(iVar1 + 0x1058) + in_ECX * 0x48`
   ⇒ **у каждого типа объекта своя таблица из 16 техник** (по «режиму» 0…15).
   Evidence: `FUN_004860c0_004860c0.c:12, 20-23`.

### Что это меняет для порта

* **Порядок и группировка отрисовки задаются типом объекта, а не только координатой.**
  Для Godot-порта нужен тот же реестр типов (или хотя бы тот же порядок проходов),
  иначе прозрачные объекты разных типов будут перекрываться иначе, чем в оригинале.

## З30.2. Тайловое разбиение: 1024 тайла на тип

### ФАКТ (Diggles.exe)

1. **Отрисовываемые объекты раскладываются по тайлам (пространственным ячейкам):**
   * `DAT_00773680 + tile * 0x10` — bbox тайла (4 dword на тайл);
   * `DAT_00783654 + (type * 0x400 + tile) * 4` — счётчик объектов в тайле;
   * **0x400 = 1024 тайла на тип объекта.**
   Evidence: `FUN_0043fd30_0043fd30.c:49-55`.
2. **Постановка объекта в отрисовку — `FUN_00405af0(param_1)`:**
   `*in_ECX = param_1` (сам объект); значение `DAT_00773650 + type*0x40`
   кладётся в **стек кадра** (`FUN_0043fcc0()`, указатель растёт через `+0x8000`);
   ведётся счётчик `DAT_00773654 + type*0x10`.
   Evidence: `FUN_00405af0_00405af0.c:11-24`.
3. **Снятие объекта — `FUN_0043fd30()`:** уменьшает счётчик ссылок; при обнулении
   распределяет объект по тайлам, обновляет bbox тайла и счётчики.
   Evidence: `FUN_0043fd30_0043fd30.c:14-59`.
4. **Тот же механизм стеков используется в сериализации `.3db`:** `puVar6[puVar6[0x2000]] =
   *(uint *)(&DAT_00773650 + type)` — в стек кладётся **id типа**.
   Evidence: `C3DDB__Persist_00402ff0.c:336-342, 493-499`.
5. **Пул слотов с ожиданием — `FUN_006cebf4(param_1)`:**
   при `*param_1 == 0` слот помечается `-1` (занят), при `*param_1 == -1` — ожидание
   (`__Init_thread_wait(100)`), иначе в TLS пишется `DAT_00767000`.
   ⇒ **рендер многопоточный**, объекты разводятся по потокам.
   Evidence: `FUN_006cebf4_006cebf4.c:5-19`; вызывается 7 раз из `CDisplay__DrawObjects`.

### Что это меняет для порта

* **Оригинал отсекает объекты по тайлам** (1024 на тип) — значит, «невидимые» объекты
  вообще не отправляются на отрисовку. Godot-порт может использовать свой culling,
  но обязан вести ту же **последовательность типов**, иначе изменится порядок наложения.
* **Многопоточность рендера в оригинале есть** — при воспроизведении результата
  (скриншот «как в оригинале») порядок вывода может зависеть от порядка завершения
  потоков; это стоит учитывать при сверке кадров.

## З30.3. Окно рендера, JPEG и таймер

### ФАКТ (Diggles.exe)

1. **`FUN_0044d010()` — ленивый создатель окна рендера** (`DAT_0076a2c0`):
   создаёт объект с `CSdlWindow` (**класс из порт-DLL**, З25.3), критическую секцию
   (`+0x22bc`), инициализирует счётчики (`+0x80…+0xbc`, `+0x223`), вызывает `FUN_0044f510`,
   `FUN_00449eb0`, и **загружает `ijl10.dll`** (Intel JPEG Library), запрашивая
   `ijlInit`, `ijlFree`, `ijlWrite`.
   Evidence: `FUN_0044d010_0044d010.c:15-54`.
2. **Отдельная функция `FUN_006ae200` пишет JPEG** тем же `ijl10.dll`
   (состояние JPEG — 0x4E40 байт на стеке) ⇒ **движок умеет сохранять кадры в JPEG**.
   Evidence: `FUN_006ae200_006ae200.c:33-40`.
3. **`FUN_006bd180()` — чтение счётчика тактов CPU (`rdtsc`)** (с `cpuid` перед чтением).
   В `FUN_0043fd30` его результат разбирается на две 32-битные половины, которые
   накапливаются в полях `[6]/[7]` и сравниваются с экстремумами `[8]…[0xb]`.
   Evidence: `FUN_006bd180_006bd180.c:10-16`; `FUN_0043fd30_0043fd30.c:22-37`.
4. **`FUN_00566460` (геттер cave-объекта) вызывается прямо из `CDisplay__DrawObjects`** ⇒
   объекты-скины пещер (З24.2) рисуются в общем проходе отрисовки, а не отдельным слоем.
   Evidence: `CDisplay__DrawObjects_00473cc0.c:973`.

### Что это меняет для порта

* **Скриншоты в JPEG — штатная функция оригинала.** Если Godot-порт должен давать
  «такие же» кадры (для сверки), формат вывода — JPEG через IJL (то есть кадр 8×8
  блоками, базовая линия JPEG, 4:2:0/4:4:4 по настройкам IJL).
* **Cave-объекты — часть общего прохода отрисовки**, а значит, их видимость зависит
  от общей системы тайлов и типов; отдельно их «включать» в порту нельзя.

### Что осталось неизвестным

* **Смысл полей `[2]…[0xb]` в `FUN_0043fd30`**: похоже на измерение времени
  (основа — `rdtsc`), но в коде эти же поля используются как экстремумы по двум осям.
  Проверка: посмотреть, кто пишет `[2]/[3]` (базу) — вероятно, это последний
  отсчёт времени, а сравнения — сравнения времени, а не координат.
* **Как объект выбирает технику при отрисовке**: где читается id техники из объекта
  (вероятно, поле типа + таблица 16 техник, З28) — не прослежено до конца.
* **Размер и смысл тайловой сетки** (1024 тайла на тип, но как они отображаются
  в мировые координаты) не установлены.
* **Полный список типов объектов** (в реестре `DAT_00773650`) не снят — сняты только
  имена, упомянутые в `C3DDB__Persist`.
* **Ни один вывод не сверен с живой игрой.**
