## З37. D25 — отсечение по видимости: как оригинал решает, что рисовать

*(закрывает D25 из З32 («есть ли отсечение по видимости») и уточняет поля объекта отрисовки из З34)*

---

### 1. Отсечения камерой в обычном смысле нет

**ФАКТ (Diggles.exe):** поиск по строкам `cull|frustum|ClipPlane|SetClipPlane` в exe даёт **только** два попадания — оба в парсере определений техник (`cullmode` в `FUN_0045c970`, `FUN_0045b000`). Ни `SetClipPlane`, ни `GetClipPlane`, ни имён вида «frustum» в бинарнике нет.

**ФАКТ (Diggles.exe):** вместо отсечения по пирамиде видимости движок **проецирует камеру на плоскость земли z = 0** и получает **полигон**, который затем превращается в **список горизонтальных отрезков клеток** («runs»).

Цепочка (на примере земли):

| шаг | функция | что делает |
|---|---|---|
| 1 | `FUN_00445dd0` | создаёт объект `CPolyFill` (`*DAT_0076a2a0`) — контейнер полигона и результата |
| 2 | `FUN_00445e40` | **вычисляет отрезки клеток** по полигону |
| 3 | `CScapeRenderer__RenderScape_004c4de0.c:559-611` | обходит отрезки и рисует клетки |

**ФАКТ (Diggles.exe):** полигон строится в **плоскости z = 0**:
`FUN_0050ab10_0050ab10.c:540-542` — `local_4c[idx*3 + 0] = X; local_4c[idx*3 + 1] = Y; local_4c[idx*3 + 2] = 0;` ⇒ вершины полигона лежат на z = 0; X/Y берутся из состояния камеры (`in_ECX + 0x58 / 0x5C / 0x60`).

**ФАКТ (Diggles.exe):** результат `FUN_00445e40` — массив записей по **3 int** = `(x0, y0, countX)`:
- `FUN_00445e40.c:182-194` — при вырожденном случае пишет `{x, y, 1}`;
- `CScapeRenderer__RenderScape.c:559` — `x0 = *(int *)(local_34 + 0)`; `:564` — `y0 = *(int *)(local_34 + 4)`; `:572` — `countX = *(int *)(local_34 + 8)`, и по нему идёт внутренний цикл по X;
- `FUN_0050ab10.c:574` — та же запись используется как `x0 + countX` (граница по X).

**ФАКТ (Diggles.exe):** каждый отрезок = **одна строка клеток** (y фиксирован, X идёт от `x0` до `x0 + countX`), а список отрезков покрывает видимую область построчно.

**ФАКТ (Diggles.exe):** отрезки, подходящие слишком близко к краю карты, **отбрасываются** — нужен запас в 2 клетки:
- `CScapeRenderer__RenderScape.c:565-566` — по Y: `map->0x88 + 2 < y0` и `y0 < map->0x90 − 2`;
- `:573-574` — по X: `map->0x84 + 2 < x0` и `x0 < map->0x8C − 2`.

**ФАКТ (Diggles.exe):** список отрезков используют **четыре** подсистемы:
- `CScapeRenderer__RenderScape_004c4de0.c:536` — **земля**;
- `FUN_0056af90_0056af90.c:464` — **поверхности/стены** (по каждой клетке вызывается `FUN_0056ae30`);
- `CFluid__Draw_00576c60.c:530` — **жидкости** (вода/лава);
- `FUN_0050ab10_0050ab10.c:546` — **высоты ландшафта** (по отрезкам читается массив высот).

**ФАКТ (Diggles.exe):** обычные объекты (деревья, камни, персонажи) **не отсекаются этой механикой**: `CDisplay__DrawObjects_00473cc0` (1028 строк) не обращается ни к списку отрезков, ни к камере для проверки попадания; в нём нет ни `sqrt`, ни сравнений с расстоянием. Объекты попадают в кадр по списку сцены; их отсекают только `ZFuncMode`/`CullMode` (см. З36) и отсечение задних граней.

**⇒ ОТВЕТ НА D25:** отсечения по пирамиде видимости в оригинале **нет**. Вместо него — **проекция камеры на плоскость z = 0 → полигон → список отрезков клеток**, по которому идёт построчный обход. Применяется к земле, стенам/поверхностям, жидкостям и выбору высот; **обычные объекты не отсекаются вообще**. Плюс запас в 2 клетки от края карты (компенсация того, что проекция на z = 0 неточна: рельеф лежит на z = 7…14.5).

### 2. Уточнение полей объекта отрисовки (рендер-задачи)

**ФАКТ (Diggles.exe):** структура задачи отрисовки (то, что сортируется в `FUN_00450850`):

| смещение | что | где подтверждено |
|---|---|---|
| +0x08 | **категория/«проход» сортировки** — целое, из которого делаются старшие биты ключа (`×2`) | `FUN_00450850.c:78-88`; в пути `DestrucionMesh` = 0x14 (20), см. `FUN_00483d80.c:234` |
| +0x0C | константа 4 | `FUN_00483d80.c:233` |
| +0x10 | **id техники** | `FUN_00483d80.c:252-277` (`local_14[4] = iVar5`) |
| +0x14 | **порог приоритета** — сравнивается с 0xFA (250) | `FUN_00450850.c:60,68`; значение приходит из 5-го поля источника задачи (`FUN_00483d80.c:235`, `local_14[5] = local_30[4]`) |
| +0x18, +0x1C, +0x20 | floats (bbox/центр) | `FUN_00450850.c:55-57` |
| +0x3C, +0x40 | **два уровня освещения** (сумма = вторичный ключ) | `FUN_00450850.c:89`; заполняются `CTclObjMethods__ChangeLight_00614990.c:186,203` |
| +0x48 | **первичный ключ сортировки** | `FUN_00450850.c:86-88` |
| +0x4C | **вторичный ключ сортировки** | `FUN_00450850.c:89` |

**ФАКТ (Diggles.exe):** полный смысл ветвления в сортировщике:
`FUN_00450850.c:65-77` —
1. если у техники `+0x0C` (AlphaEnable) = 0 ⇒ объект непрозрачный (`bVar12 = false`);
2. иначе, если `задача + 0x14 < 0xFA` ⇒ объект считается прозрачным (`bVar12 = true`) **независимо от режима смешивания**;
3. иначе ⇒ прозрачность определяется `DestBlendMode (+0x20) != 1 (ZERO)`.

**ФАКТ (Diggles.exe):** при прозрачном объекте (`bVar12 = true`) в ключ идёт `проход` без вычитания и **неинвертированный** байт высоты; при непрозрачном — `проход − 1` и **инвертированный** байт высоты (`FUN_00450850.c:78-88`). Это ровно то, что описано в З34, но теперь с указанием **причины**: непрозрачное рисуется раньше (проход на 1 меньше) и «дальше» по высоте (инверсия байта).

**ФАКТ (Diggles.exe):** подстановки техник (при выборе id из слота группы): `FUN_00483d80.c:265-276` — `7 → 6`, `18 (0x12) → 19 (0x13)`, `33 (0x21) → 7`, иначе без изменений.

### 3. Что это меняет для порта

1. **Отсечение надо делать по прямоугольникам клеток, а не по пирамиде.** Простейший эквивалент оригинала: взять 4 угла экрана/камеры, спроецировать на z = 0, получить полигон, разложить на отрезки строк клеток. Для Godot это можно сделать один раз на кадр — список прямоугольников, а не проверка на каждый объект.
2. **Обычные объекты отсекать не нужно** (в оригинале не отсекаются) — это упрощение, а не ошибка. Сцена небольшая (уровень), объектов мало.
3. **Запас 2 клетки от края карты** — обязателен, иначе у края карты будут дыры в земле (проекция на z = 0 не совпадает с рельефом).
4. **Порядок прозрачного/непрозрачного** — из двух полей: `AlphaEnable` у техники и порог задачи 250. В порте это надо задать явно, иначе прозрачные объекты (вода, огонь, эффекты) переставят накладываться правильно.
5. **Категория/«проход» (задача +0x08) — это не «номер прохода рендера»**, а число, из которого получаются старшие биты ключа сортировки. В порте это должно быть **поле сортировки**, а не «pass index» в смысле RenderPipelinePass.
6. **Подстановки 7→6, 18→19, 33→7** надо воспроизвести буквально, если порт использует те же id техник.

### 4. Что осталось неизвестным (и как проверить)

1. **Что именно записано в «задача + 0x14»** (источник — `local_30[4]`, 5-е поле описания задачи) и кто его ставит. **Проверка:** найти писателя `+ 0x14` у задачи отрисовки в общем (не в `DestrucionMesh`) пути.
2. **Точная геометрия проекции камеры**: как из состояния камеры (`+0x58/+0x5C/+0x60`) получаются вершины полигона, и есть ли учёт высоты рельефа. **Проверка:** поставить камеру на известную позицию и посмотреть полученные отрезки.
3. **Отсекаются ли объекты как-то ещё** (например, по «видимости для игрока» — `CFogOfWar::Visible`, `CTclObjMethods__GetVisibility`): эти функции относятся к игровой логике, а не к рендеру, но их можно перепутать. **Проверка:** сравнить список рисуемых объектов с игровым флагом видимости.
4. **Что делает `FUN_00489f0` / `FUN_004089d0`** (выборка X/Y камеры при построении полигона).
5. **Ни одно утверждение не сверено с живой игрой** — всё статическое.
