## 1. Структура блока: 89 байт, из них первые 64 — карта 8×8

| смещение | размер | что |
|---|---|---|
| `+0x00 … +0x3f` | 64 | **карта 8×8 по 1 байту на суб-клетку** = высота верхней грани колонки, в уровнях |
| `+0x40 … +0x4f` | 16 | 4 дочерних блока (З8.1) |
| `+0x50 … +0x53` | 4 | 4 материала квадрантов (З8.1) |
| `+0x54` | 1 | материал/вариант блока (`& 0xf`) |
| `+0x55 … +0x58` | 4 | не разобрано |

* **Размер блока = 0x59 = 89 байт** — `FUN_004093b0_004093b0.c:8` (`param_1 * 0x59 + *in_ECX`), `FUN_004093f0_004093f0.c:18`, `FUN_00595e40_00595e40.c:71`.
* **Точечное чтение высоты суб-клетки** — `FUN_004093f0(x, y)` (`FUN_004093f0_004093f0.c:10,21`):
  клетка = `FUN_00592f10(x>>3, y>>3)`, блок = `cell[0]*0x59 + base`, байт = `block[((y&7)<<3) | (x&7)]`.
  ⇒ индекс построчный: строка = y, столбец = x; **индекс 0 = (x0,y0), 7 = (x7,y0), 56 = (x0,y7), 63 = (x7,y7), 36 = (x4,y4) = центр клетки**.
* **Bulk-заполнение сетки** — `FUN_00595e40(grid, rect)` (выровненная ветка `:81-110` — 16 dword'ов = 64 байта на клетку; невыровненная `:112-129` — по байту на суб-клетку).

### Единица значения — уровень, world-Z = 7.0 + 0.5·v (проверено на данных)

Прогон `work/campaign/caves-decomp/bdb_map.py` по BlockDB0-2.BDB (118 688 блоков в каждом), значение v в карте 8×8 vs фактический Z меша блока:

| v | z меша | | v | z меша | | v | z меша |
|---|---|---|---|---|---|---|---|
| 0 | 7.0 | | 5 | 9.5 | | 10 | 12.0 |
| 1 | 7.5 | | 6 | 10.0 | | 11 | 12.5 |
| 2 | 8.0 | | 7 | 10.5 | | 12 | 13.0 |

| 4 | 9.0 | | 9 | 11.5 | | 14 | 13.5–14.0 |
| | | | | | | 15 | 14.5 |

⇒ **v = уровень, world-Z = 7.0 + 0.5·v.** Это в точности действующее в проекте правило «world-Z = 7.0 + 0.5·level» — теперь оно подтверждено по самим данным оригинала.

Контрольные блоки главы:
* **блок 0** — карта вся 15 → меш `z[14.5..14.5]` ⇒ свободная клетка = квад на 14.5 (З3 ✓);

Значение — **верхняя грань** колонки, а не низ: у блока 81 половина карты 11 даёт верх на 12.5, и меш блока действительно начинается с 12.5.

## 2. Рендер блока: углы против центра, порог «дыры» |Δ| ≥ 4

`FUN_004ca830_004ca830.c:396` — `pbVar16 = block + blockId*0x59`; далее:

* `:403-404` `abs(pbVar16[0x3f] - pbVar16[0x24])`; `:412` `if (3 < iVar13) goto LAB_004cb1bf` ⇒ **если разница > 3 (т.е. ≥ 4) — полная 81-конфигурация** (`FUN_004ca080`, `:420`), иначе упрощённая (`:429` `LAB_004cb110`);
* `:446-464` — то же для `pbVar16[7]` (NE), `pbVar16[0x38]` (SW), `*pbVar16` (NW) против `pbVar16[0x24]` (центр);
* `:424-427` — «центр против центра» для случая, когда все углы = 3.

Итог:
* **порог |Δ| ≥ 4 подтверждён независимо** (раньше он был выведен из данных BlockDB в З4);
* сравниваются **4 угла клетки с центром клетки** ⇒ углы клетки = (0,0), (7,0), (0,7), (7,7), центр = (4,4);
* «81 конфигурация» = 3^4 ⇒ **каждый угол клетки имеет 3 состояния**.

## 3. Beautifier `FUN_005a6b40` — формула (установлена)

Вход: прямоугольник валидатора в суб-клеточных координатах.

1. `:71-78` — сетка высот по расширенному прямоугольнику: `local_4c = x0-8`, `local_44 = x1+8`, `local_48 = y0-16`, `local_40 = y1+2`; заполняется `FUN_00595e40` ⇒ **значения = уровни (0..15)**.
2. `:104` — клетка суб-клетки: `FUN_00592f10((x+4)>>3, (y+4)>>3)`.
3. **Первый фильтр — бит 7 байта `cell+0x18`.** Дизасм:
   ```
   0x5A6D9E: mov  al, byte ptr [eax + 0x18]
   0x5A6DA1: shr  al, 7
   0x5A6DA4: not  al
   0x5A6DA6: and  al, 1
   0x5A6DC3: mov  byte ptr [esp + 0x28], 0      ; состояние = 0
   0x5A6DC8: je   0x5a76eb                       ; если бит7 установлен -> записать 0
   ```
   ⇒ **если бит 7 `cell+0x18` = 1, состояние суб-клетки = 0** (в декомпиляции это `local_c1`, `:105`).
4. **Цепочка проверок соседей — 31 блок** вида:
   ```
   0x5A6E0A: cmp  byte ptr [eax], 0xe
   0x5A6E0D: jae  0x5a76eb
   ```
   (аналогично 0x5A6E59, 0x5A6E93, 0x5A6ECC, 0x5A6F10, 0x5A6F4A, 0x5A6F7D, 0x5A6FC5, 0x5A7005, 0x5A7051, 0x5A7087, 0x5A70DA, 0x5A7116, 0x5A7154, 0x5A718B, 0x5A71C7, 0x5A7202, 0x5A723E, 0x5A7271, 0x5A72B9, 0x5A72ED, 0x5A733E, 0x5A7374, 0x5A73C1, 0x5A73FD, 0x5A7441, 0x5A7481, 0x5A74BB, 0x5A74F5, 0x5A7539, 0x5A7575).
   ⇒ **если хоть один из 31 проверенного соседа имеет уровень ≥ 14 (world-Z ≥ 14.0) — состояние = 0.**
   **Смещения (Δстрока, Δстолбец) в суб-клетках, восстановлены построчно из дизасма (исправлено 2026-11-21):**
   `(−1,0)`, `(−2,±2)`, `(−3,±4)`, `(−4,0)`, `(−5,0)`, `(−5,±5)`, `(−5,±7)`, `(−6,±2)`,
   `(−8,0)`, `(−8,±4)`, `(−8,±7)`, `(−10,±2)`, `(−11,±5)`, `(−12,0)`, `(−12,±7)`,
   `(−13,±3)`, `(−15,0)`, `(−15,±4)`, `(−15,±7)`.
   Все смещения — в сторону меньшего Y (окрестность радиусом ≈ 2 клетки, верхняя половина).
5. **Если все проверки пройдены — `local_b8 = 1` (`:414`), т.е. бит 0 = «земля».**
   Смысл: над суб-клеткой и вокруг неё нет породы верхнего уровня (≥ 14) ⇒ место открытое, пол есть.
6. **Бит 1 = «ступенька».** Сравнения `:434`, `:452`, `:461`, `:466` вида `h_a + 2 < h_b` ⇒ разница **≥ 3 уровней (1.5 world-Z)** ⇒ `local_b8 = 3`.
   Правило состоит из **двух ветвей** (исправлено 2026-11-21):
   * `h[r−1][c] + 2 < h[r][c]` **И** `h[r−8][c] + 2 < h[r][c]` → состояние 3 (`:434`, `:452`);
   * иначе `h[r][c] + 2 < h[r+1][c]` **И** `h[r−15][c] + 2 < h[r+1][c]` → состояние 3 (`:461`, `:466`).
   Четыре вызова `FUN_0041fad0` (`:458,460,462,464`) читают **ту же сетку высот** `pbVar6`, переданную через стек (`0x5A7669: lea ecx,[esp+0x88]` — там лежит указатель на сетку) ⇒ это **не** вторая сетка, а границы проверяемого массива.
   Потребители: `CTclObjMethods__GetGnomePosition_0068d8a0.c:86,89,91` — при бите 1 гном не встаёт; `FUN_005a6350_005a6350.c:102-114` — бит 0 даёт высоту пола `4 - row`, бит 1 поднимает её на 0x80.
7. Запись: `:503-512` — 1 байт на суб-клетку; `:518` — `FUN_00596550(puVar7, &local_20)` в `cell+0x3c`.

**Итоговая формула состояния суб-клетки:**
```
если (cell+0x18) & 0x80            -> 0
иначе если хоть один из 31 проверенного соседа имеет уровень >= 14 -> 0
иначе если (h[r-1]+2 < h[r] и h[r-8]+2 < h[r]) -> 3
иначе если (h[r]+2 < h[r+1] и h[r-15]+2 < h[r+1]) -> 3
иначе -> 1
```

**Рабочая область** (`:50-74`): `x ∈ [max(x0, mapX0+24), min(x1, mapX1−24))`, `y ∈ [max(y0, mapY0+16), min(y1, mapY1−24))` — в суб-клетках.

**Проверка формулы на данных (2026-11-21):** прогон по 37 шаблонам главы — **99.99 %** совпадения с RLE-картами `.pmp` (1 268 736 суб-клеток); `caves_1.pmp` — 100.00 %. См. З16.

## 4. `.pmp` содержит РЕЗУЛЬТАТ работы beautifier'а

Формат `.pmp` (загрузчик `FUN_005992b0`, `:72-103`):

```
int32 W
int32 H
byte  material[W*H]
int32 block_id[W*H]
int32 rle_words
uint16 rle[rle_words]          ; 2 байта на слово
byte  extra[W*H]
```

RLE (`FUN_005992b0:534-546`): слово `v` → **длина `v>>2`** (0 → 0x4000), **значение `v & 3`** ⇒ 0/1/2/3.

**Проверка на данных** (`work/campaign/caves-decomp/pmp_subcell.py`):

| файл | W×H | слов RLE | декодировано | ожидалось 64·W·H | значения |
|---|---|---|---|---|---|
| caves_1.pmp | 12×8 | 53 | 6144 | 6144 ✓ | 0:5232, 1:792, 3:120 |
| caves_2.pmp | 16×8 | 53 | 8192 | 8192 ✓ | 0:6448, 1:1560, 3:184 |
| caves_3.pmp | 20×12 | 117 | 15360 | 15360 ✓ | 0:9528, 1:5584, 3:248 |

Во всех трёх файлах после последнего массива остаётся **0 байт** — формат подтверждён целиком.

⇒ **RLE-секция `.pmp` — это карта 8×8 суб-клеток на клетку, сжатая RLE, и значения в ней ровно те же {0,1,3}, что производит beautifier.**

**ВАЖНО — раскладка (исправлено 2026-11-21):** RLE декодируется в **плоское изображение (W·8)×(H·8) суб-клеток**, а **не** как 64 байта подряд на клетку: индекс суб-клетки = `y*(W*8) + x`. Evidence: `FUN_00596550_00596550.c:70, 121-124` (источник читается как `((row8 − y0)*(x1 − x0)) + (col8 − x0)`). В `cell+0x3c` 64 байта клетки идут **подряд** — это другая раскладка.

## Что это меняет для порта

* **Порт может взять готовую карту «земля / ступенька» прямо из `.pmp`** — это снимает необходимость восстанавливать уступы из разности высот. Нужен ридер RLE-секции `.pmp` (16 байт заголовка + W·H + 4·W·H + 4 + 2·N + W·H).
* **Единицы высот в карте блока = уровни, world-Z = 7.0 + 0.5·v.** Шкала порта **корректна** (исправлено 2026-11-21 по замечанию инициатора): `BDB_DEPTH_SCALE = 2.0` / `BDB_DEPTH_OFFSET = -14.0` (`godot/scripts/native_campaign_first_level.gd:31-32`) применяются к **z вершины меша BDB**, а z вершины BDB — это уже world-Z (`7.0 + 0.5·уровень`); упаковка сцены `scene_root.scale.z = 0.5`, `scene_root.position.z = 7.0` (`:205-206`, `RENDER_DEPTH_SCALE/OFFSET` `:33-34`) даёт `0.5·(2·world-Z − 14) + 7 = world-Z` — тождественно. Карта 8×8 для высот в порту не используется вообще.
* **Порог «дыры» |Δ| ≥ 4 подтверждён из кода рендера.** ⇒ портовые правила откосов должны срабатывать при разнице уровней ≥ 4 (world-Z ≥ 2.0), а сравнивать надо **углы клетки с центром**, а не только соседей.
* **Уступки в оригинале — это бит 1 карты суб-клеток, а не отдельная геометрия.** Значит «ступенька» и «земля» приходят одним файлом, и порт может воспроизвести их точно, а не приблизительно. При этом **геометрия уступов в порту уже есть**: меши блоков берутся из BDB дословно (`tools/export_campaign_chapter.py:563`), а порог откоса `CLIFF_HEIGHT = 2.0` (`godot/scripts/native_campaign_walls.gd:122`) равен |Δ| ≥ 4 уровней — то есть совпадает с порогом оригинала. **Чего порту не хватает — только навигационных байтов `C+0x3C`** (карта «земля/ступенька»), а не геометрии.
