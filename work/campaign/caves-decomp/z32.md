# З32. Метрика покрытия по «точкам принятия решений» + проверка реестра типов объектов

*(2026-11-22; новая метрика готовности порта и ревизия одного вывода З30)*

## 1. Зачем метрика не по байтам

Процент декомпилированного кода не отвечает на вопрос «можно ли делать порт без
догадок». Порт угадывает не код, а **решения**: какой материал, какая техника,
какой шейдер, какой формат вершин, в каком порядке, что отсечь. Поэтому
покрытие считается по **точкам принятия решений**: каждый пункт — это место,
где движок выбирает, и для него нужно либо точное правило, либо точная таблица.

Правило статусов:

* **ЗАКРЫТО** — значение/правило извлечено и проверено (адрес + строка в отчёте);
* **ЧАСТИЧНО** — правило известно, но не покрывает все случаи;
* **ОТКРЫТО** — не установлено.

## 2. Уточнение по З30: реестр типов объектов подтверждён дизассемблером

З30 утверждал: «реестр типов объектов — массив с шагом 0x40, `+0x00` — id типа,
`+0x3C` — имя типа, счётчик — `DAT_00783650`». При попытке прочитать эти
адреса прямо из образа файла получился мусор, и это выглядело как опровержение.
**Опровержения нет — мусор объясняется устройством PE.**

ФАКТ (Diggles.exe): секция `.data` имеет `VirtualSize = 0x549754`, но
`SizeOfRawData = 0x2800` при `PointerToRawData = 0x365200`.
Адреса `0x773650` (реестр типов) и `0x783650` (счётчик) лежат за пределами
raw-части `.data` ⇒ это **неинициализированная (BSS-подобная) область**:
в файле её нет, в памяти она заполняется загрузчиком (релокации vtable) и
кодом регистрации типов. Поэтому читать эти структуры из образа **бессмысленно** —
нужен дизассемблер.

ФАКТ (Diggles.exe): регистрация типа (дизасм. `0x404E83–0x404EA9`):

```
mov  ecx, dword ptr [0x783650]                 ; счётчик зарегистрированных типов
mov  eax, ecx
shl  eax, 6                                    ; index * 0x40
mov  dword ptr [0xc3ca20], ecx                 ; id типа этого класса
mov  dword ptr [eax + 0x77368c], 0x71c7f4      ; имя типа (+0x3C в записи)
mov  dword ptr [eax + 0x773650], ecx            ; id типа (+0x00 в записи)
inc  dword ptr [0x783650]                      ; счётчик++
```

ФАКТ (Diggles.exe): VA `0x71c7f4` в `.rdata` = строка
`"C3DDB::Persist(CUniArc& arc)"` — совпадает с указателем в инструкции.

ФАКТ (Diggles.exe): использование записи типа (дизасм. `0x454B8A–0x454BD6`,
`CDXSound__CreateSimpleBufferFromFile`):

```
mov  edi, dword ptr [0xc86be4]     ; id типа этого класса (кеш)
shl  edi, 6
mov  esi, dword ptr [edi + 0x773650]   ; +0x00 — id типа (кладётся в стек сериализации)
mov  eax, dword ptr [edi + 0x773654]   ; +0x04 — счётчик объектов этого типа
...
call 0x6bd180                          ; rdtsc
mov  dword ptr [edi + 0x773658], eax   ; +0x08 — метка времени (низ)
mov  dword ptr [edi + 0x77365c], edx   ; +0x0C — метка времени (старшая часть)
inc  eax
mov  dword ptr [edi + 0x773654], eax   ; счётчик++
```

⇒ **Структура записи типа (0x40 байт):**

| смещение | содержимое |
|---|---|
| +0x00 | id типа (равен своему индексу) |
| +0x04 | счётчик объектов этого типа |
| +0x08 | rdtsc-метка, младшие 32 бита |
| +0x0C | rdtsc-метка, старшие 32 бита |
| +0x3C | указатель на имя типа (строка в `.rdata`) |

Побочный вывод: поле «время» пишется **только при первом появлении типа**
(если счётчик был нулём) — это замер времени первой отрисовки типа, т.е.
профилировочная метка, а не игровое время.

Имена типов (все 15 зарегистрированных в `C3DDB__Persist`, VA из `.rdata`):
`C3DDB::Persist(CUniArc& arc)` (0x71C7F4), `… Mapping` (0x71C814),
`… Header` (0x71C854), `… Materials` (0x71C8A4), `… Meshes` (0x71C8EC),
`… Objects` (0x71C92C), `… Anims` (0x71C970), `… Shadows` (0x71C9AC),
`… CMaps` (0x71C9F0), `… Lst Count&Init` (0x71CA2C), `… IdxLst map` (0x71CA58),
`… UVLst map` (0x71CA80), `… VLst map` (0x71CAA8), `… NLst map` (0x71CAD0),
`… FollowMesh` (0x71CAF8).

## 4. Что это меняет для порта

1. **Порт может быть построен без догадок по 20 из 30 решений.** Все закрытые
   пункты — это либо таблицы (импортируемые дословно), либо форматы
   (побайтно разобранные), либо исходники шейдеров (поставляются игрой).
2. **Оставшиеся 10 пунктов — не «сложный код», а конкретные вопросы.**
   Их можно закрыть точечно: каждый в отчёте имеет «как проверить».
3. **Открытые пункты не блокируют начало порта.** D24 (тайл → мировые
   координаты) и D25 (отсечение) — единственные, которые бьют по геометрии
   и по «объекты не там на экране» ⇒ их надо закрыть первыми.
4. **Метрика проверяема:** по ней видно, что именно мешает, и её можно
   показывать инициатору как список задач, а не как процент.

## 5. Что осталось неизвестным (и как проверить)

* **D24 — тайл → мировые координаты.** Известно, что `DAT_00773680 + tile*0x10`
  хранит bbox тайла и что тайлов 1024 на тип. Не известно, как индекс тайла
  переводится в мировые координаты и какой у тайла физический размер.
  **Как проверить:** поставить объект в известную позицию через Tcl и посмотреть
  его bbox в `FUN_0043fd30`; либо сопоставить с `CMap` (шаг блока известен из З13).
* **D25 — отсечение. ЗАКРЫТО в З37.** Поиск по строкам `cull|frustum|ClipPlane` в exe дал
  только два попадания (в парсере шейдеров) ⇒ отдельного отсечения камерой нет.
  Разбиение по 1024 тайлам на тип — ложный следствие (З33).
  **Как на самом деле:** видимая область = проекция камеры на плоскость z = 0 →
  полигон → список отрезков клеток `(x0, y0, countX)`; по нему рисуются земля,
  стены/поверхности, жидкости и выбираются высоты; отступ 2 клетки от края карты;
  обычные объекты не отсекаются вовсе (З37).
  **Как проверить:** поставить камеру так, чтобы часть карты была за спиной,
  и посмотреть, рисуется ли она (счётчик объектов в тайле покажет, что
  отсечения не было).
* **D26 — `water_mt0/1`, `lava_mt0/1`, `sulfur_m/mt1`.** В реестре 37 техник их
  нет ⇒ это другая таблица (вероятно, варианты материала жидкости).
  **Как проверить:** найти их употребление — искать в коде чтение строки,
  где она сравнивается с именем материала.
* **D29 — `[2]…[0xb]` в `FUN_0043fd30`.** Похоже на измерение времени
  (используется `rdtsc` — `FUN_006bd180`), но значения применяются как
  экстремумы по двум осям.
  **Как проверить:** посмотреть, кто читает эти поля дальше.
* **D27 — код формата 0x202/0x204 (бит 0x200).** Для какой раскладки вершин —
  не установлено. **Как проверить:** найти в порту ветку, где 0x200 иной раз
  отличается от обычных `vs_4_0/ps_4_0`.

## 6. Оговорка

Ни один вывод не сверен с живой игрой — всё получено статическим анализом
(Ghidra + дизассемблер + чтение PE). Для D24/D25/D29 проверка «вживую»
обязательна, остальное можно подтвердить сверкой с данными игры
(`.3db`, `.pmp`, `data/Shaders/`).
