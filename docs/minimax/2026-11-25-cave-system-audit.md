## 2. Что уже реализовано корректно

1. **Защита гранита.** `can_dig()` (`native_campaign_dig_test.gd:158`) отказывает клетке, у которой
   `profile.cell_material()` не равен 1 или 2. Гранит (0) не вскопается, поэтому гранитный барьер
   вокруг скриптованных пещер сохраняется. Проверено тестом `granite_protected=1`.
2. **Открытые клетки не размечаются повторно.** `can_dig()` сравнивает `heights[0]` блока с целевой
   высотой: у уже открытой клетки `heights[0] <= 11`, и она отбрасывается. Это же проверяет
   `RULES.target_height()` из ниблов оригинала, а не «максимум углов» (см. п. 5.1).
3. **Разметка туннеля идёт по оригинальной геометрии штриха.** `native_corridor_stroke.gd` +
   `native_corridor_selection.gd` дают ровно ту растеризацию, что описана в `docs/review/caves-audit-2026-11-21.md`
   (§14, §15.5): coarse-чётность по индексам, сетка 4 клетки, отбраковка «по времени» ячеек.
4. **Переходы BDB.** `_next_height()` и `_native_strike()` используют таблицу `next` из экспорта
   BlockDB2.BDB, включая асимметрию «поддержка = `heights[0]`» (не `max(corners)`).
5. **Пещера привязана к туннелю.** `_touches_tunnel()` требует, чтобы контур пещеры касался уже
   открытой клетки или отмеченного коридорного хода. Пещера в воздухе не ставится.
6. **Стирание по группе.** `_erase()` снимает всю группу пещеры целиком, коридорные метки — по
   одной клетке. Стирание трогает только `marks`, выкопанное пространство не затрагивает.
7. **ПКМ снимает инструмент.** `handle_input()` на правой кнопке вызывает `_choose(false, tool)`.
8. **Иконки оригинальные.** `BuddelnG`, `BuddelnH0..H3`, `BuddelnUndo`, `Spitzhacke` — 40×40 TGA
   из `res://textures/gui/`, без перерисовки. Лишних кнопок и панелей нет.
9. **Один BDB-переход = один шаг.** `advance()` бьёт по 4 клетки за шаг с шагом 0.025 с, `newly_open`
   обнуляется на каждом шаге — обработка объектов привязана к конкретному шагу.

## 3. Где стоит эвристика

### 3.1 Модель состояния — эвристика (нарушение п. 2 задания)

`marks: Dictionary` хранит **и** коридорные метки (`nibble = 3, group = 0`), **и** метки пещер
(`nibble = 8 | depth, group = N`). Разметка и фактическая вскопка лежат в одной структуре, а
принадлежность к пещере после вскопки восстанавливается только из `block_overrides` плюс флаг
`excavated_cave_cells`, который ставится **в момент удара**, а не по завершении пещеры.

Следствия:
- клетка пещеры, которая была уже открыта до разметки, вообще не попадает в `marked_cave_cells`
  и никогда не получает признак «пещерная» — она выглядит как обычный коридор;
- частично выкопанная пещера (часть клеток не достигла целевой глубины) оставляет свои клетки
  в `excavated_cells` без признака пещеры, и коридорные опоры попадают внутрь неё.

### 3.2 Опоры туннеля — эвристика

`_decorate_new_passages()` (`native_campaign_dig_test.gd:476`):
- ставит опору в каждой клетке, удовлетворяющей набору геометрических условий, но **не чаще чем раз
  в 8 клеток** (`x - last_support < 8`) — это фиксированный шаг, не зависящий от геометрии;
- пропускает только клетки с признаком «пещера», который, как показано в 3.1, неполон;
- расстояние до оригинальной опоры — 2.0 клетки (`_near_original_support`), поэтому рядом с
  оригинальной опорой может встать вторая, почти параллельная опора;
- проверка «сверху открыто» есть только на момент постановки: если верхний туннель вскопают
  **позже**, уже поставленная опора остаётся под открытым пространством и не удаляется;
- верхняя часть опоры не проверяется на пересечение с открытым пространством отдельно.

Подтверждение из исходных шаблонов: `docs/reverse-engineering/agent-result-campaign-dig-tools-2026-11-25.md:7`
— «`Dummy_Multi_Holzstuetze_*` и `Dummy_Holzwand_*` не образуют равномерную сетку. Опоры
сохраняются для обычных вскопанных туннелей, но ставятся редко и только там, где над ходом
остаётся порода».

### 3.3 Рамка пещеры — не реализована вовсе

В `scripts/native_campaign_dig_test.gd` нет ни загрузки `urw_caves_*`, ни понятия «завершённая
пещера», ни спавна рамки. Механизм есть только в мультиплеере:

| multiplayer_test.gd | Назначение |
|---|---|
| `_load_cave_skin_resources()` :400 | `res://models/cave_skins/urw_caves_%d_a_a.json` → `cave_skin_resources[size]` |
| `_build_cave_skin_meshes()` :421 | Точки/UV/треугольники → `ArrayMesh`, текстура из `res://assets/textures/`, `OBJECT_WORLD_SCALE = 0.005` |
| `_spawn_cave_skin_visual()` :461 | `Node3D` с мешами, печать `NATIVE_CAVE_SKIN_PREVIEW` |
| `native_select_cave_skin()` :753 | `urw_caves_<brush 1..4>_a_<detail c/b/a>` |
| `native_finish_completed_caves()` :761 | Для завершённых пещер: центр записи + спавн скина |
| `_native_cave_record_center()` :783 | Центр = середина bbox кисти по курсору |

Параметры скинов подтверждены оригиналом (`docs/review/caves-audit-2026-11-21.md:1215-1220`,
`data/Scripts/init/animinit.tcl:382-415`, `SetCaveSkinClasses`):
**Set** = Met→1 / Kris→2 / Golden→3, **Size** = 2→0 / 3→1 / 4→2, **Detail** = a→2 / b→1 / c→0.
В порту лежат только комбинации `urw_caves_{1..4}_a_a` (Set=a, Detail=a).

### 3.4 Падение объектов — эвристика, построенная на неверной оси

`_settle_objects()` (`native_campaign_dig_test.gd:430`) ищет твёрдый уровень **по строкам карты**
(`while solid < 638 and _is_open(Vector2i(x, solid))`), то есть модель «вид сбоку». Карта кампании —
**вид сверху**: клетка (x, y) — это квадрат 1×1 поверхности, а `z` — высота. Это следует из:
- `MAP_GROUND_LEVEL = 14.5` — «уровень, на который движок ставит объект»
  (`native_campaign_ground.gd:65`, комментарий `FUN_00568410`/`FUN_00420840`);
- свободная земля рисуется как плоскость на уровне 14.5 (`native_campaign_first_level.gd:648-676`);
- блок BDB хражит 4 высоты углов и 4 перехода `next` — это карта высот.

Следствия текущего кода:
- триггером падения служит клетка **впереди** объекта (`under`), а не собственная клетка объекта:
  объект над своей собственной вскопанной клеткой остаётся висеть;
- «ближайший твёрдый уровень» ищется в строках, а не по высоте;
- если твёрдого уровня не найдено (`solid >= 638`), объект **не** попадает в `falling_objects` и
  просто остаётся в воздухе — нарушение п. 5.4 задания;
- `_settle_objects()` опирается на `block_overrides`, который накапливается, поэтому один и тот же
  объект re-обрабатывается на каждом шаге — нарушение п. 5.5 задания.

### 3.5 Стыки и стирание

- `_mark_corridor()` отказывает клетке, если `marks.has(cell)`, иначе пещера и туннель могли бы
  пересечься. Проверка «пещера пересекает незавершённую разметку» есть.
- Лишней полоски разметки на открытом краю нет: клетка с `heights[0] <= 11` отбрасывается в
  `can_dig()`.
- **ПКМ не снимает нажатое состояние кнопки.** `_choose(false, tool)` чистит `tool`, но кнопка
  остаётся `button_pressed = true` (у `ButtonGroup` выставлен `allow_unpress = true`, и
  `toggled` при ручном сбросе не приходит). В интерфейсе кнопка выглядит нажатой, хотя инструмент
  снят.
- `next_group` не переиспользуется, `groups` не чистится при завершении пещеры.

## 4. Что из мультиплеера переиспользуемо

1. `_build_cave_skin_meshes()` — построение `ArrayMesh` из JSON-скина, масштаб `OBJECT_WORLD_SCALE = 0.005`,
   `cull_mode = CULL_DISABLED`, `roughness = 0.95`, текстура `res://assets/textures/<имя>.tga`.
   Текстуры на месте: `Holz_Standard_a_256.tga`, `trollh_4_wand_d.tga`.
2. `native_select_cave_skin(record, detail = 2)` — имя скина по номеру кисти и детали.
3. `_native_cave_record_center()` — идея «центр по bbox», но в кампании центр должен считаться по
   **фактически выкопанным** клеткам пещеры, а не по bbox кисти.
4. Идея «пещера завершена → появляется скин» (`native_finish_completed_caves`), но с явной
   привязкой к завершённой пещере кампании.

Переносить multiplayer-сцену целиком и менять её публичное поведение — нельзя (жёсткое
ограничение задания). Нужен **минимальный адаптер**: отдельный модуль скинов, который читает те же
JSON и строит те же меши.

## 5. Что нельзя утверждать без дополнительного референса

1. **Точное правило расстановки опор в оригинале.** В исходниках движка правило авто-постановки
   `Holzstuetze` при рытье не найдено; найдено только, что в оригинальных шаблонах опоры не
   образуют равномерную сетку. По заданию (п. 3) в этом случае нужна **консервативная** реализация
   с явной пометкой в отчёте, а не изобретение сложной генерации.
2. **Параметр `Set` скина (Met / Kris / Golden).** В порту есть только `Set = a`. Как выбирается
   Set по «уровню материала» — из имеющихся файлов не следует.
3. **Высота рамки пещеры.** Оригинальная пещера — объёмная комната; в порту нет подтверждения,
   на каком именно уровне (по высоте) ставится скин: в мультиплеере это `BDB_DEPTH_SCALE * 15 + BDB_DEPTH_OFFSET`,
   в кампании своя шкала.
4. **Семантика `cave_skin add/rem` в Tcl** (`FUN_0066a9a0`, `FUN_0058eb30`, `FUN_0058fb10`,
   `FUN_0058f2a0`) — прямо помечена как неизвестная в аудите от 21.11.2026.
5. **Роль масок `cave0..3.tga`** — в движке потребитель не найден.
6. **Модель «зеркальной» оригинальной главы.** Оригинал ставит пещеру по LG-якорю (метка
   режима 1 рядом) или скриптом (`Trigger_Schwefel.tcl`, центр между двумя гномами). Кампания
   использует собственную кисть игрока — расхождение зафиксировано в аудите (§15.3) и в этом
   задании не исправляется.

## 6. Итог аудита

- Правила, которые можно считать выполненными: защита гранита, отбраковка открытых клеток при
  разметке, оригинальная геометрия штриха и переходов BDB, привязка пещеры к туннелю, стирание по
  группе, ПКМ снимает инструмент (внутри), оригинальные иконки.
- Места эвристики: модель состояния, шаг опор, отсутствие рамки пещеры, ось падения объектов,
  повторная обработка объектов, нажатое состояние кнопки после ПКМ.
- Готовый к переиспользованию код мультиплеера: загрузка и построение мешей скина, выбор имени
  скина по кисти, идея «завершённая пещера → спавн».
- Решения, которые нельзя выдавать за правило оригинала без референса: точное правило
  расстановки опор, параметр `Set` скина, высота рамки, семантика `cave_skin` в Tcl.
