## 1. Опции `sm_draw_stone` — ровно четыре, все без аргументов

Сравнение опций идёт полным строковым сравнением с константами в `.rdata`:

| Адрес | Строка | Ветка в `CTclGlobalMethods::SMDrawStone` (0x65e090) |
|---|---|---|
| 0x731060 | `-border` | стр. 898 → 922-939 |
| 0x731068 | `-funnel` | стр. 185 → 209-235 |
| 0x731088 | `-exlimit` | стр. 246 → 270-395 |
| 0x73109c | `-matlist` | стр. 512 (литерал), принимает значение |

**`-utmat` в бинаре отсутствует.** В строковой таблице `Diggles.exe` нет ни
`utmat`, ни `-utmat` (проверена вся таблица `strings.tsv`). То есть
`sm_draw_stone -utmat` (`data\Scripts\classes\story\story.tcl:228`) — это
**неизвестная опция в самом оригинале**, т.е. мёртвый вызов: цикл опций
сравнивает строку целиком и просто переходит к следующему аргументу
(ветка `LAB_0065e367` → `local_18 = pbVar7 + 1`), ошибки не возникает.

**`-exlimit` — тоже флаг без значения**: он не читает число, а работает с
записями зон (шаг 100 байт, поля `+0x30/0x34/0x40/0x44/0x48/0x4c/0x5c`).
`-matlist` — единственная, у которой есть аргумент (`16 16 $nexttemp`).

Полный набор опций `sm_add_temp` из строковой таблицы (0x730fd0-0x731010) —
`-events`, `-digconnect`, `-connect`, `-exclusive`, `-nonrelevant`, `-middist`,
`-mindist`, `-zoneborder`, `-stoneidx`, `-checkalign` — совпадает с твоим.

## 2. Закон кромки: где и как движок рисует край

Кромка рисуется **в двух местах**, оба — через один и тот же примитив
`FUN_005fc9d0` (0x5fc9d0) «красить прямоугольник с опадающей вероятностью».

### 2.1 `map create W H` — южная сторона

`CTclGlobalMethods::Map` (0x6325f0, стр. 236-243):

```c
iVar11 = FUN_005f8080();                                  // объект карты
iVar12 = *(int *)(DAT_0077241c + 0x90) - iVar6;           // map->0x90 (y1) - H
local_20 = (int *)(*(int *)(DAT_0077241c + 0x90) + 4);
FUN_005fa640(0, (int)(iVar6 + (iVar6 >> 0x1f & 3U)) >> 2);  // ceil(H/4)
FUN_005fc9d0(0, iVar12, 0x20, local_20, 4, 0, 0x3f800000, 0,0,0,0);      // запад
iVar6 = *(int *)(iVar11 + 0x7c) * 4;
FUN_005fc9d0(iVar6 + -0x20, iVar12, iVar6, local_20, 8, 0, 0x3f800000, 0,0,0,0); // восток
```

### 2.2 `sm_draw_stone -border` — северная, западная и восточная стороны

`CTclGlobalMethods::SMDrawStone` (0x65e090, стр. 922-939):

```c
FUN_005fc9d0(0, 0, *(int *)(iVar2 + 0x7c) << 2, 0x20, 1, 0, 0x40200000, 0,0,0,0);          // СЕВЕР
FUN_005fc9d0(0, 0, 0x20, *(int *)(iVar2 + 0x80) * 4 + 4, 4, 0, 0x3f800000, 0,0,0,0);     // ЗАПАД
FUN_005fc9d0(iVar8 + -0x20, 0, iVar8, *(int *)(iVar2 + 0x80) * 4 + 4, 8, 0, 0x3f800000, 0,0,0,0); // ВОСТОК
FUN_005fa510(0, 0, *(undefined4 *)(iVar2 + 0x7c), 9);
```

Итого: **север/запад/восток** рисует `-border`, **юг** — `map create`.
Южной полосы в `-border` нет, северной — в `map create` нет.

Масштабы: север — `0x40200000` = **2.5**, запад/восток — `0x3f800000` = **1.0**,
юг (в `map create`) — **1.0**. Целевой материал везде `0` (порода), флаг
направления падения: север `1`, запад `4`, восток `8`.

### 2.3 `sm_draw_stone -funnel` — зеркальная лестница

0x65e090, стр. 209-235: цикл полосами **6 клеток высотой**, шаг **4 клетки вниз**
и **8 клеток внутрь** с каждой стороны; материал → 0, масштаб 1.0:

```c

local_14 = *(int *)(iVar2 + 0x7c) * 2 + -0x14;     // ширина полосы
do {

    pbVar3 = local_20 + 6;
```

## 3. Закон спада и случайности — `FUN_005fc9d0` (0x5fc9d0)

Это и есть «сила спада + случайность», которую ты просил. Функция целиком:

```
region = [x1,x2) × [y1,y2), предварительно обрезанный по границам карты
         (map->0x84 / 0x88 / 0x8c / 0x90)
dx = x2-x1,  dy = y2-y1,  d = min(dx,dy)
divisor = s / (d * 0.2)                       // s = «сила» (масштаб): 2.5 / 1.0 / ...
centre_x = x1 + dx/2,   centre_y = y1 + dy/2
target = param_6;  if (target==1) target=2; else if (target==2) target=1;   // 1<->2

для каждой клетки:
    p = 1.0
    if (flags&4) && centre_x <  x:  p -= ((centre_x-x)/dx)^2 / divisor   // восточная половина
    if (flags&8) && x < centre_x:  p -= ((x-centre_x)/dx)^2 / divisor   // западная половина
    if (flags&1) && centre_y <  y:  p -= ((centre_y-y)/dy)^2 / divisor   // южная половина
    if (flags&2) && y < centre_y:  p -= ((y-centre_y)/dy)^2 / divisor   // северная половина
    m = cell[0x18] & 3
    if (m != 0 && m != 3):                       // ТОЛЬКО копаемый материал (1 или 2)
        if ((rand() & 0x7fff) <= p * 32768.0):
            cell[0x18] = (cell[0x18] & 0xfffc) | target
```

Ключевые следствия:

- **Флаг = на какой половине прямоугольника гаснет вероятность.** Биты:
  `1` = «y > центра» (южная половина), `2` = «y < центра» (северная),
  `4` = «x > центра» (восточная), `8` = «x < центра» (западная).
- Для кромки выбран именно **внутренний** флаг: север `1` (y > центра),
  запад `4` (x > центра), восток `8` (x < центра). Значит **у самого края
  вероятность = 1.0 (камень ставится гарантированно), а внутрь полосы она
  гаснет квадратично**.
- **Материал 0 и 3 никогда не перекрашиваются** — правило действует только на
  копаемый материал (1 или 2). Иначе край был бы целиком породой.
- Случайность — «мягкая»: сравнение `rand() & 0x7fff <= p * 32768.0`, т.е.
  при p = 1.0 всегда истина (32767 ≤ 32768), при p = 0.5 — примерно половина.
- Параметр `s` (2.5 для севера, 1.0 для запада/востока/юга) входит через
  `divisor = s / (min(dx,dy) * 0.2)`: чем больше `s`, тем **круче** спад
  (меньше делитель → вычитание больше → p быстрее падает).
- `target` для кромки/воронки = **0** (порода); подстановка 1↔2 на входе 0 не
  трогает. Т.е. кромка — это «заливка породой» поверх того, что было.

## 4. ВЫСОТЫ кромки движок НЕ генерирует — они из шаблона

Это ответ на твой пункт 2 и часть твоего пункта 3.

`FUN_005fc9d0` пишет **только** `cell[0x18]` (материал). Ни одного
присваивания высоты в ней нет. То же и в `-funnel`, и в `-border`, и в
`map create`: там меняется только материал (+ вызывается `FUN_005a3dd0` /
`FUN_005a3fd0` / `FUN_005fa510` — перестроение меша и сеток по изменённой области).

Высота клетки в движке берётся из **шаблона**:
- `.pmp` шаблона даёт на каждую клетку идентификатор блока (у тебя:
  `refs[index] -> block_id`, `flags -> материал`, `attributes -> байт атрибута);
- загрузчик карты `FUN_005992b0` кладёт в клетку `cell[0x00]` = индекс
  **под-блока высот** из блока высот (шаг 0x59 байт), а в `cell[0x3C]` — копию
  сетки высот 8×8 этой клетки;
- видимая геометрия пещеры — меш блока из базы `.3db` (то, о чём ты говоришь).

**Итог: твоя реконструкция верна.** Видимая геометрия выработок — это 3D-блоки
из `.pmp`/`.3db`, а сетка высот 8×8 — параллельная (коллизионно-навигационная)
модель в тех же данных. Ступени 14.5 → 12.5 → 7.0 по 0.5 на северном краю
стартового шаблона (x=211..214, y=0..12) — это **данные оригинала в шаблоне**,
а не результат `-border`/`-funnel`.

Поэтому «точный закон высот кромки для -border/-funnel» в движке такой:
**движок высоты кромки не создаёт вообще**; его вклад — только материал
(см. §2-§3). Всю геометрию кромки порт должен взять из шаблона, как ты и делаешь.

## 5. Кратность сеток: 4× — это сетка кромки, а высота — 8×

Отвечаю на твой вопрос 4. В движке **две** разные сетки, и их нельзя смешивать:

| Сетка | Шаг | Где подтверждено |
|---|---|---|
| **Клетки карты** | 1 клетка движка = 1 клетка Tcl | `FUN_00592f10(x,y)`; границы `map->0x84..0x90`; `dig_mark`/`dig_next` передают Tcl-координаты напрямую |
| **Высота** | **8 единиц на клетку** (сетка 8×8 на клетку, 1 байт на единицу) | `GetHMap`: `ROUND(x*8.0)`; `FUN_004093f0`: `x>>3`, `&7`; `cell+0x3C` = 64 байта; `FUN_005fc9d0` финальные вызовы: `param_1*8-8 … param_3*8+8` |
| **Кромка / рёбра выемки** | **4 единицы на клетку** | `FUN_005fa510`: смещение `-ceil(W/4)`, вызовы `>>2`; `FUN_005fd060`: `>>2` |

Итого по твоим числам «512×640 → 2048×2560»:
- **2048×2560 = 4× — это сетка рёбер/кромки**, а не высота;
- **высота сэмплится 8×8 на клетку** ⇒ для 512×640 это **4096×5120** отсчётов;
  твои «0.25 клетки» = ровно **2** отсчёта высоты.

И ещё важное про размеры карты: объект карты хранит
`map->0x74 = W`, `map->0x78 = H`, `map->0x7c = W*8`, `map->0x80 = H*8`,
а **границы клеток** `map->0x84/0x8c = 0 / 2W`, `map->0x88/0x90 = 0 / 2H`
(`CMap::Init`, 0x594160:167-201). То есть игровое поле — квадрат W×H, а объект
карты вдвое больше по каждой оси: вторая половина — это как раз «внешняя»
область, где живут кромка и воронка. Плюс отдельные границы в единицах 1/8
клетки: `map->0x94/0x98/0x9c/0xa0 = W*8 / H*8 / 2W*8 / 2H*8`.

## 6. Что осталось открытым

- Точный смысл байтовой сетки `FUN_005fa510` (stride `this->0x7c` = W*8) —
  что в ней лежит (похоже, «рёбра/направления выемки», но не доказано).
- Семантика `-exlimit`: читает список зон шаблона, но как выбирается зона —
  не разобрано.
- Генерация геометрии меша из блоков `.3db` (FUN_0058a8b0, FUN_00590040) —
  чтение высот разобрано, сама генерация вершин нет.
- Шкала Z: высота — целый байт; соотношение с портовыми 12.5 / 14.5 требует
  одной сверки `get_hmap` с оригиналом.
