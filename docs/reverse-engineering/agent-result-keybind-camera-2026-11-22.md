# Diggles: WASD-камера и x8 скорость — результаты реверса (2026-11-22)

Тема: точки расширения Tcl в оригинальной игре, нативная команда `keybind`,
чтение/запись камеры, снятие потолка скорости времени.

Маркировка: **факт** — проверено в запущенной игре или в декомпиляции;
**адаптер** — правдоподобное объяснение, требует подтверждения;
**неизвестно** — не установлено.

---

## 1. Tcl в игре — версия 8.3 (факт)

`info patchlevel` в игровом интерпретаторе → **8.3.2**.
Отсюда — в игровых `.tcl` **не существуют** `eq`/`ne`/`in`/`ni` (8.4+),
`file normalize` (8.4+), `file join` (8.5+), `lassign`/`try` (8.5/8.6+).

**Критично:** Tcl компилирует файл целиком. Одна несовместимая конструкция →
всё выражение не компилируется → **не выполняется НИЧЕГО**, включая команды,
идущие до неё. Это причина «пустых логов» в ранних прогонах.

Отчёт об ошибках движок пишет в `tclerrors.txt` в корне игры; надёжный канал
для отчёта — намеренный `error "текст"`.

## 2. Точки расширения (факт)

| Файл | Когда грузится | Примечание |
|---|---|---|
| `data/userinit.tcl` | `CGameThread::Init() TclInit2 user` (строка 0x735d50) | **рабочая точка**: выполняется до `systeminit.tcl` |
| `data/systeminit.tcl` | `TclInit2 system` (0x735d90) | штатный файл игры |
| `data/userstartup.tcl` | вызывается из `systeminit.tcl` | **ловушка**, см. ниже |

**Ловушка `userstartup.tcl`** (факт, `data/systeminit.tcl:69`): если файл
существует, движок пропускает **весь** блок создания меню —
`call data/templates/unq_menue.tcl`, `MapTemplateSet`, `set_view`, `FogRemover`,
`Trigger_StartScreen`, `gui_new_game`. Игра стартует без главного меню.
Для своих скриптов использовать только `data/userinit.tcl`.

## 3. `keybind` — нативная команда (факт)

Ранее в `docs/research/Diggles_modding-2026-11-22.md` §9 было записано, что
`keybind` отсутствует — **это неверно**, исправлено здесь.

Обработчик: `CTclGlobalMethods::KeyBind`, VA **0x00640FC0**
(`work/campaign/ref/ghidra-out/decomp/CTclGlobalMethods__KeyBind_00640fc0.c`).
Подкоманды:

- `keybind keynames` — список имён клавиш движка (`Esc 1..0 - = Backspace Tab
  Q W E R T Y U I O P ... Enter Ctrl A S D F G H J K L ... Shift \ Z X C V B N M
  ... Alt Space {Caps Lock} F1..F24`, плюс кириллические раскладки);
- `keybind current` — список активных привязок: `{KEY {скрипт}}`;
- `keybind set <KEY> [shift] [ctrl] [alt] [down] <скрипт>` — установка.

Подтверждено в живой игре:

```
keybind set W {dig_cam_north}   ->  принято
keybind current                 ->  {W dig_cam_north} {A dig_cam_west} ...
```

Модификаторы — битовые флаги записи; `down` выставляет байт «вниз» в записи
(в `keybind current` для таких привязок печатается суффикс ` down`).
Имя ключа проверяется через `FUN_004e4d90`, при ошибке — `invalid key code`.

**Особенность (факт):** `keybind set F1 {...}` команда принимается, но
привязка **не создаётся** — движок разбирает токен вида `F<цифра>` как
модификатор. Рабочие имена: `W A S D P O` и прочие из `keynames`.
`set_time_factor`/`F1` в этой сборке для хоткеев не годятся.

## 4. Камера: `get_view` / `set_view` и источник краша (факт)

- `get_view` / `get_view 1` / `get_view 0` — возвращают **5 чисел**.
- `set_view` — минимум 4 аргумента; сама игра использует 5:
  `set_view 32.368 40.858 1.38 -0.355 0.165` (`data/systeminit.tcl:84`)
  и 3: `set_view 160 78 1`.
- Собственный идиом игры для относительного изменения камеры —
  `set_view [lreplace [get_view] 2 2 1.5]`
  (`data/Scripts/classes/story/Trigger_Tutorial.tcl:238`).

**Источник краша (факт, воспроизведён):** пока камера не «двигалась»,
`get_view` отдаёт **неинициализированную память**, например

```
get_view   -> 5 values: 1.02796901161e-38 5.39705214103e+33 1.20000004768 0.0 0.0
get_view 1 -> те же значения
```

Значения x/y — мусор (1e-38 и 5.4e+33). Если скрипт скормить их в `set_view`,
камера уезжает в координату 5e+33 и **движок падает** (проверено: игра
вылетала после загрузки). Поэтому перед `set_view` значения обязательно
проверяются на диапазон и числовой тип; при мусоре нажатие игнорируется.

**Неизвестно:** возвращает ли `get_view` корректные значения в геймплее
(в момент старта камеры ещё нет — это ожидаемо).

## 5. Скорость времени (факт)

- `gametime factor <x>` — команда, которую используют игровые скрипты
  (`data/Scripts/sequences/*`). **Не клампится**: проверены 8, 16, 32.
  Чтение — `gametime factor` (возвращает, например, `8.0`).
  Сброс: `gametime factor 1.0` при старте уровня (кампанийные скрипты).
- `set_time_factor <x>` — **другой** глобальный множитель
  (`DAT_00b836d0`), на `gametime factor` не влияет (проверено:
  `set_time_factor 8` → `gametime factor` остался `1.0`).
- Потолок кнопок `+`/`-` живёт в реестре (факт — значения и строки описаний
  в бинарнике: `Misc\MaxGametimeFactor` 0x7298a0, `Misc\NoGamespeedLock`
  0x72985c, описания `MaxGameTimeFactor [value] (4.0)=%f` 0x729af0,
  `NoGameSpeedLock [true|false] (false)=%s` 0x729b84):

  ```
  HKCU\Software\SekOst\Diggles\Misc\MaxGametimeFactor  (REG_SZ "4")
  HKCU\Software\SekOst\Diggles\Misc\NoGamespeedLock    (REG_SZ "0")
  ```

  **адаптер:** поднятие `MaxGametimeFactor` до `"8"` (и `NoGamespeedLock`
  в `"1"`) должно поднять предел кнопок `+`/`-` до x8. Проверяется только
  вручную в GUI — программно прочитать этот предел не удалось.
  Tcl-команда `option set` в реестр не пишет (проверено: реестр не изменился).

## 6. Правила безопасности скриптов (факт)

- Нативные команды Tcl при **неверном числе аргументов** роняют движок
  (`RaiseException(0xc000008c)` → APPCRASH), а не возвращают ошибку Tcl.
  Пример: `set_camerafollow` без аргументов. `catch` такой вызов **не спасает**.
  Всегда сверять argc по декомпиляции.
- Файл `userinit.tcl` читается не сразу: до фазы Tcl «user» игра грузится
  **от 15 секунд до 4 минут**. Отсутствие лога через 30 с — не признак
  того, что скрипт не выполнился.

> **Статус:** рецепт на `keybind` **не работает** (§9) и не используется.
> Рабочий вариант — реестр (§8, команды ниже) плюс Tcl-скрипт для тумана

`data/userinit.tcl` рядом с `Diggles.exe`. Содержит:

- `keybind set P` → `gametime factor 8`, `keybind set O` → `gametime factor 1`;

> `NoGamespeedLock` должен быть **`0`**: при `"1"` пропадала надпись скорости
> на экране даже на x2/x4. Текущие рабочие значения — `MaxGametimeFactor = 8`,
> `NoGamespeedLock = 0`, `Input\SimpleControl = 1`.

## 9. `keybind` — команда есть, диспетчера нет (факт)

Привязка регистрируется (`keybind current` её показывает), но **по нажатию клавиши
скрипт не вызывается ни разу**: проверено в меню и в геймплее, с обычной привязкой
и с флагом `down`, при `Input\SimpleControl` = 1 и 0. В логе нет ни одной строки
от привязанной процедуры.

Поиск по бинарнику: `Tcl_EvalObjEx` (единственный импорт `tcl83.dll`) вызывается
**ровно в одном месте** — VA `0x006BC3E3`; отдельного «диспетчера привязок»,
читающего таблицу `DAT_00772400 + 0x148/+0x14C`, в коде не найдено.
Вывод (адаптер): механизм `keybind` в этой сборке **не подключён** к вводу —
наследие от另一 версии/редакции игры. Через Tcl WASD не прикрутить.

## 10. Коды клавиш движка — Windows VK (факт)

`FUN_004E4CF0` (код → имя) вызывает `GetKeyNameTextA`: внутренние коды движка —
это Windows virtual-key codes.

| клавиша | VK |
|---|---|
| W / A / S / D | `0x57` / `0x41` / `0x53` / `0x44` |
| стрелки ← ↑ → ↓ | `0x25` / `0x26` / `0x27` / `0x28` |

WASD в игре не используются вообще → подменять их стрелками безопасно.

## 11. Найденный обработчик (факт) — это НЕ камера

VA `0x0054E65D` (`work/thirdparty/DigglesModManager/arrow-handler.asm`):

```
0x0054E65D  cmp ecx, 0x100          ; WM_KEYDOWN
0x0054E663  jne 0x54E824
0x0054E669  cmp ebx, 0x25            ; VK_LEFT
0x0054E6AD  cmp ebx, 0x27            ; VK_RIGHT
0x0054E6B7  cmp ebx, 0x26            ; VK_UP
0x0054E733  cmp ebx, 0x28            ; VK_DOWN
```

Коды клавиш движка — Windows VK: получаются из поля события `[ecx+0x10]`
через `MapVirtualKey`-подобный вызов `[0x715038]`.

**адаптер:** функция обрабатывает клавиши в окне редактора/консоли GUI
(сдвиг курсора по строке), а не прокрутку камеры: патч подстановки
W/A/S/D → стрелок (изменено 65 байт, проверено побайтно, `patch-wasd.py`)
не дал эффекта — камера не двигалась. **Патч откачен**, `Diggles.exe`
возвращён к оригиналу (SHA256 `58A01D3D…0ED74`).

Настоящий обработчик прокрутки камеры в наборе декомпиляции не найден
(в `index.tsv` нет ни camera-scroll функций, кроме `CameraSets`).

## 12. Внешний перехватчик клавиш — самотест зелёный, но в игре не проверен (факт)

> **Статус:** подход не дал эффекта, перехватчик перенесён в `archive/`, не используется.
> Окончательный вердикт по всем подходам — §15.

`work/thirdparty/DigglesModManager/DigglesWasdCamera.cs` → `DigglesWasdCamera.exe`
(сборка `csc /platform:x64`, .NET Framework 4.x) + `WASD camera.cmd` в папке игры.

Логика: опрос `GetAsyncKeyState` для W/A/S/D; если окно Diggles в фокусе —
инъекция стрелки (`VK_UP/LEFT/DOWN/RIGHT`) через `SendInput`.

**Две важные детали (обе найдены через самотест `--selftest`):**

1. **Размер структуры `INPUT` должен быть ровно 40 байт на x64.**
   Объединение обязано включать `MOUSEINPUT` (32 байта), иначе `INPUT`
   получается 32 байта и `SendInput` молча падает с ошибкой 87
   (`ERROR_INVALID_PARAMETER`) — ключи просто не инъектируются.
2. **Стрелку надо удерживать, а не «тапать».** Движок может опрашивать
   состояние клавиши, а не реагировать на одиночный `WM_KEYDOWN`, поэтому
   реализация шлёт `KEYDOWN` при нажатии WASD, повторяет его каждые 80 мс
   (движок получает события) и шлёт `KEYUP` при отпускании.

Самотест `--selftest` создаёт окно, инъектирует `VK_LEFT` и проверяет,
что окно получило `WM_KEYDOWN` с `wParam = 0x25`. Проверка зелёная —
инъекция доходит до адресата.

## 14. WASD-камера: найден реальный конвейер ввода, патч в `DigglesPort.dll` (НЕ ДАЛО ЭФФЕКТА — см. §15)

### 14.1 Как на самом деле устроен ввод (факт)

1. `Diggles.exe` (32 бит, PE32, base `0x400000`) импортирует из `SDL2.dll` **только `SDL_PollEvent`**;
   весь ввод с клавиатуры идёт через собственный обработчик событий движка.
2. Обработчик — `FUN_0054e470` (VA `0x0054E470`, 1008 байт). Он вызывается из `0x006B5A37`
   (`lea ecx, [ecx+0x368]; call 0x54e470`, где `ecx = *DAT_00772400` — глобальный объект игры).
3. Обработчик работает со **структурой `SDL_Event`**:
   `type` по смещению `0x00` (`0x300` = SDL_KEYDOWN, `0x301` = SDL_KEYUP),
   `keysym.scancode` по смещению `0x10` (тип `SDL_KeyboardEvent`).
4. **Ключевая точка:** `keysym.scancode` передаётся в импортированную из `DigglesPort.dll`
   функцию `?GetVKScanCode@@YAGG@Z` (IAT `0x00715038`), и результат — **Windows VK-код** —
   сравнивается с константами `0x25/0x26/0x27/0x28` (VK_LEFT/UP/RIGHT/DOWN) в VA `0x54E669…0x54E740`.
   То есть движок оперирует **VK-кодами**, а не SDL-символами.
5. Реестр подтверждает, что это именно камера: `HKCU\Software\SekOst\Diggles\Input\KeyScroll = 1`
   (рядом `MouseScroll`, `BorderScroll`).

### 14.2 Таблица scancode → VK (факт)

`GetVKScanCode` (`DigglesPort.dll`, RVA `0x11650`, 1141 байт) строит `std::map<uint16,uint16>`:
* **ключ** = SDL-сканкод (младшие 16 бит константы),
* **значение** = Windows VK-код (старшие 16 бит константы),
* константы упакованы как `(vk << 16) | scancode` и лежат как **непосредственные значения
  (`mov dword ptr [ebp-0xNN], imm32`) внутри самой функции** — то есть таблицы в `.data` нет,
  она собирается на стеке при первом вызове.

Найденные записи (файл-офсеты в `DigglesPort.dll`):

| сканкод | клавиша | было | стало | офсет |
|---|---|---|---|---|
| 4  | A | `0x00410004` (VK_A=0x41)   | `0x00250004` (VK_LEFT=0x25)  | `0x010CB6` |
| 7  | D | `0x00440007` (VK_D=0x44)   | `0x00270007` (VK_RIGHT=0x27) | `0x010CD4` |
| 22 | S | `0x00530016` (VK_S=0x53)   | `0x00280016` (VK_DOWN=0x28)  | `0x010D6A` |
| 26 | W | `0x0057001A` (VK_W=0x57)   | `0x0026001A` (VK_UP=0x26)    | `0x010D92` |

Стрелки (сканкоды 79/80/81/82 → 0x27/0x25/0x28/0x26) и остальные клавиши не тронуты.
Побочный эффект: A/S/D/W больше не приходят в движок как буквы (текстовых полей ввода в игре нет —
в `Diggles.exe` нет ни одного `EditField`/`TextField`).

### 14.3 Проверка (факт, автотест)

`work/thirdparty/DigglesModManager/WasdVerify.cs` грузит DLL через `LoadLibrary` и вызывает
`GetVKScanCode` по mangled-имени `?GetVKScanCode@@YAGG@Z`:

```
оригинал:  scancode 4 (A) -> VK 0x41      scancode 80 (Left) -> VK 0x25
после:     scancode 4 (A) -> VK 0x25      scancode 80 (Left) -> VK 0x25
            scancode 7 (D) -> VK 0x27      scancode 26 (W)    -> VK 0x26
            scancode 22(S) -> VK 0x28      scancode 30 (1)    -> VK 0x31 (без изменений)
```

| файл | назначение |
|---|---|
| `DigglesPort.dll` | пропатченная (SHA256 `358B12A6…FC7BF`) |

### 14.5 Почему не сработали прежние подходы (факт)

* **Патч `Diggles.exe`** (code cave в INT3-padding'е, VA `0x401F23`) — хук цеплялся к
  обработчику клавиш **текстового поля** (`GetKeyState(VK_SHIFT)` + `MapVirtualKeyA` по пути `0x54E5C9`),
  а не к обработчику камеры. Реальная точка сравнения VK-кодов — `0x54E669`, но она
  сравнивает уже **преобразованный** движком код, а не «сырое» нажатие.
* **Внешний перехватчик (`SendInput`)** — в принципе не нужен: сценарий «WASD → стрелка»
  делается нативно, без подмены ввода. Перехватчик оставлен в `work/thirdparty/DigglesModManager/archive/`.
* **`keybind`** — по-прежнему мёртвый код (§9), Tcl-путь закрыт.

### 14.6 Уточнение после первого теста пользователя (факт)

Пользователь подтвердил: **в игровом уровне стрелки двигают камеру**, но WASD после патча — нет.

Полный разбор конвейера ввода показал, что **других путей ввода клавиш в движке нет**:

| что | где | вывод |
|---|---|---|
| порт (`DigglesPort.dll`) | не импортирует ни `SDL_PollEvent`, ни `SDL_GetKeyboardState` | порт клавиатурой не занимается вообще |
| `Diggles.exe` | импортирует из SDL2 только `SDL_PollEvent` | события читает сам движок |
| exe | `GetKeyState`/`GetAsyncKeyState` вызываются **только с `VK_SHIFT` (0x10)** | опроса клавиш вне SDL нет |
| exe | `SetWindowsHookExA(idHook=13, lpfn=0x440E00)` | low-level хук только блокирует Alt+Tab/Win (код `0x440E00`), камеры не касается |
| exe | чтения `keysym.scancode` есть всего в 3 местах (`0x503489`, `0x5035a8`, `0x54e49d`/`0x54e4af`) и **везде** сразу конвертируются через `GetVKScanCode` | «сырого» сканкода в игре нигде не сравнивают |

То есть путь единственный:
`SDL_KEYDOWN/UP -> keysym.scancode -> GetVKScanCode() -> Windows VK -> GUI/виджет`.

Отдельно: обработчик в `FUN_0054e470` (`0x54E669`), где сравниваются `0x25/0x26/0x27/0x28`, — это **не камера**,
а редактор текста: `dec [app+0x370]` + `strlen(строка по app+0x37C)` — индекс курсора в строке,
и `app+0x390` — позиция скроллбара, зажатая в `[0, app+0x398]`.

**Вывод:** патч `GetVKScanCode` попадает ровно в тот путь, которым идут стрелки, поэтому WASD должен
вести себя как стрелки. Наиболее вероятная причина неудачного теста — **игра была запущена до патча**
(DLL уже загружен в память процесса). Поэтому `WASD camera.cmd` теперь:
1. проверяет, что `Diggles.exe` **не запущен** (иначе ругается и выходит);
2. переустанавливает патч (идемпотентно);
3. **печатает в окно проверку** вызовом `GetVKScanCode` из загруженной DLL
   (ожидается A=0x25, D=0x27, S=0x28, W=0x26) и пишет её в `%TEMP%\diggles-wasd-patch.log`;
4. только потом запускает игру.

### 15.2 Что установлено и почему не помогло (факт)

Конвейер ввода в движке **один**, и патч стоял ровно на нём:

```
SDL_KEYDOWN/UP -> keysym.scancode -> GetVKScanCode() -> Windows VK -> GUI/виджет
```

* `Diggles.exe` импортирует из SDL2 только `SDL_PollEvent`; порт `DigglesPort.dll`
  клавиатурой не занимается вообще.
* `GetKeyState`/`GetAsyncKeyState` вызываются **только с `VK_SHIFT`** — опроса клавиш вне SDL нет.
* Low-level хук `SetWindowsHookExA(13, 0x440E00)` только блокирует Alt+Tab/Win.
* «Сырой» сканкод в exe нигде не сравнивается — везде сразу конвертируется в VK.

Сравнение `0x25/0x26/0x27/0x28` в `FUN_0054e470` (`0x54E669`) — это **не камера**, а редактор
текста (индекс курсора `app+0x370`, длина строки `app+0x37C`, скроллбар `app+0x390`).

**Недоказанное (честно):** эмпирически не подтверждено, что именно помешало. Статика
показывает единственный путь ввода, и патч стоит именно на нём, но результат отрицательный.
Гипотеза «игра была запущена до патча, DLL уже в памяти процесса» осталась недоказанной —
пользователь отказался от дальнейших тестов. Патчить `Diggles.exe` code-cave'ом дальше
не планируется: хук цеплялся не туда.
