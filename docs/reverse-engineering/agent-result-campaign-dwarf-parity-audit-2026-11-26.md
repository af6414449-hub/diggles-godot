## 1. Итог

Боковой бег — **не** проблема маршрута, скорости или клипа анимации. Это
расхождение в том, **откуда берётся направление корпуса**.

- Эталон мультиплеера выводит поворот корпуса **непрерывно из вектора
  движения** в плоскости, в которой корпус умеет поворачиваться:
  `atan2(direction.x, direction.z * render_depth_scale)`
  (`godot/scripts/multiplayer_test.gd:3461`, `:3865`). Там перед корпусом
  всегда лежит направление движения, расхождение равно 0°.
- Первая глава выбирает фас корпуса **снапом в четыре фиксированных
  направления** из *проекции* направления движения:
  `native_campaign_dwarf.gd:966-978` (`_heading_of_direction` →
  `_front_of_direction`). Проекция отбрасывает тот компонент движения,
  который корпус не может показать разворотом, и никогда не содержит
  глубину маршрута.

Измеренный результат (`godot/tools/native_campaign_dwarf_heading_test.gd`):
угол между отрендеренным движением гнома и отрендеренным передком корпуса.

| Маршрут | Движение (рендер) | Передок корпуса | Угол | Итог |
|---|---|---|---|---|
| доска +X | (1, 0, 0) | (1, 0, 0) | 0° | совпадает |
| доска −X | (−1, 0, 0) | (−1, 0, 0) | 0° | совпадает |
| доска вниз по экрану | (0, −1, 0) | (0, 0, 1) | **90°** | боковой бег |
| доска вверх по экрану | (0, 1, 0) | (0, 0, −1) | **90°** | боковой бег |
| доска по диагонали | (0.707, 0.707, 0) | (1, 0, 0) | **45°** | боковой бег |
| поверхность, смена глубины на 2 | (0.125, 0, −1) | (1, 0, 0) | **82.9°** | боковой бег |
| площадка, только глубина | (0, 0, −1) | (0, 0, −1) | 0° | совпадает |
| площадка, диагональ глубины | (0.707, 0, −0.707) | (0, 0, −1) | **45°** | боковой бег |

То есть гном бежит боком **везде, где маршрут не лежит вдоль строки доски**,
и особенно там, где маршрут уходит в глубину: глубина в главу вообще не
попадает в направление корпуса.

Второй, независимый дефект в том же месте: `_heading_of`
(`native_campaign_dwarf.gd:981-983`) читает базис гнома **после**
предмножения на упаковку глубины, поэтому угол, записанный в гнома, и угол,
прочитанный обратно, расходятся на 18.4° (0.322 рад) для любого
неосевого угла. Сегодня это скрыто, потому что снап даёт только четыре
осевых угла. Как только направление станет непрерывным (план исправлений,
блок 1), расхождение проявится в логике поворота (пороги 1.4/0.2 в
`:699-705`) — поэтому блок 1 и блок 2 должны идти вместе.

## 3. Геометрия: почему оси расходятся и что именно адаптер

| | Сцена мультиплеера | Первая глава |
|---|---|---|
| Плоскость пола/грунта | XZ, высота — Y | XY (линия грунта доски), глубина — Z |
| Упаковка глубины корнем | 0.5 (`multiplayer_test.gd:9`) | 0.5 (`native_campaign_first_level.gd:35`) |
| Поворот корпуса | вокруг Y, передок = колонка Z базиса | то же самое |
| Формула базиса | `render_to_logical * Basis(UP, heading)` (`:3512-3519`) | то же самое (`native_campaign_dwarf.gd:986-995`) |
| Угол поворота | непрерывно из движения, глубина × 0.5 | снап в 4 фаса из проекции движения |

Камера главы стоит на нормали доски (`native_campaign_first_level.gd:1497-1501`),
доска лежит в XY, уровень клетки — это глубина по Z, и root упаковывает её
вдвое. **ADAPTER:** экрановная вертикаль главы (строка доски, ось Y) не
является осью поворота корпуса: корпус всегда стоит вертикально и
разворачивается вокруг мировой Y. Поэтому вертикальный маршрут нельзя
показать разворотом корпуса — нативный скрипт решает это ровно так же,
см. §5.

## 5. Нативные FACT, на которых стоит решение

Исходный скрипт главы `data/Scripts/classes/zwerg/z_dignwalk.tcl`:

1. **Четыре фиксированных фаса.** `rotate_tofront` = 0, `rotate_toleft` =
   1.57, `rotate_toback` = 3.14, `rotate_toright` = 4.71
   (`z_dignwalk.tcl:1052-1055`).
2. **Поворот к цели — непрерывный.** `rotate_towards_pos` =
   `action this rotate [expr 1.57+[vector_angle [get_pos this] $pos]]`
   (`:1096-1100`). Вектор угла берётся в плоскости карты, поэтому передок
   корпуса равен `(dx, 0, −dy)/|d|`: вертикаль экрана доски уходит в ось
   глубины корпуса.
3. **Снап `_front_of_direction` воспроизводит нативную конвенцию** для всех
   четырёх осевых направлений: +X → `rot = 1.57`, −X → `4.71`,
   вверх по экрану → `3.14` (в стену), вниз по экрану → `0` (к камере).
   Расхождение нативного и главы есть только на диагоналях.
4. **Удар по стене — фиксированный фас «назад»** (`digclimb` → roty 3.14,
   `:643-645`), то есть PI, как в мультиплеере (`:3316`).
5. **Бродячий гном возвращается фасом к камере** (`adjust_gnome_rotation`,
   `:1143-1148`).
6. **Направление удара в нативе считается в плоскости XZ**
   (`get_anglexz`, `:311-325`), а не в плоскости карты, как в главе.

## 7. План исправлений в порядке риска

### Блок 1. Направление корпуса из вектора движения (минимальная причина)

Риск: низкий. Меняется только выбор угла; маршрут, скорость, клипы и
пороги поворота не трогаются.

- `native_campaign_dwarf.gd:966-978`: заменить `_heading_of_direction` /
  `_front_of_direction` на непрерывный угол из движения.
  - Плоскость доски (XY): `heading = atan2(dx, −dy)` — нативная
    конвенция `rotate_towards_pos`, вертикаль экрана уходит в глубину
    корпуса; четыре осевых фаса сохраняются без изменений.
  - Плоскость глубины (XZ, маршрут площадки):
    `heading = atan2(dx, dz * RENDER_DEPTH_SCALE)` — формула эталона
    дословно (`multiplayer_test.gd:3865`).
- Оставить принудительный PI там, где натив его требует: лазание по
  стене (`:903`, `:928`) и удар по стене (`:1303-1304`).
- Проверка: `native_campaign_dwarf_heading_test.gd` должен дать 0° на
  осевых маршрутах и на диагонали доски угол 45° вместо 45°-снапа с
  промежуточным фасом; новый golden-значение — передок диагонали
  `(0.707, 0, −0.707)`, а не `(1, 0, 0)`.

### Блок 2. Чтение угла корпуса (`_heading_of`)

Риск: низкий; обязателен вместе с блоком 1.

- `native_campaign_dwarf.gd:981-983`: передок читать из базиса без
  упаковки (`basis.z.z * RENDER_DEPTH_SCALE`) либо брать записанный угол из
  `dwarf_headings`. Сегодня расхождение 18.4° на диагональных углах;
  после блока 1 это попадёт в логику поворота.
- Проверка: golden — `heading 2.356 → stored 2.356` (сейчас 2.678).

### Блок 3. Удар киркой (PI по стене + непрерывный угол)

Риск: низкий.

- `native_campaign_dwarf.gd:1303-1304`: для удара по стене (клип
  `kletter_*`) ставить PI, как в эталоне (`multiplayer_test.gd:3316`) и
  как нативно (`z_dignwalk.tcl:643-645`); для остальных — непрерывный
  угол из блока 1.

### Блок 4. Глубина в маршруте по поверхности (требует решения владельца)

Риск: средний; здесь нужен выбор, а не правка.

- Измеренный случай: маршрут, уходящий в толщу грунта (глубина
  меняется), даёт 82.9° расхождения, потому что `_step_surface_walk`
  (`:931-932`) берёт угол только из (dx, dy) и глубину отбрасывает.
- Вариант A (нативная конвенция): глубину не учитывать — глубина это
  толщина грунта, а не направление линии грунта; тогда гном на участке
  изменения толщины всё равно идёт боком, и это надо принять как
  ADAPTER и описать.
- Вариант B (паритет с эталоном): считать угол из (dx, dz·0.5), как в
  мультиплеере; тогда гном доворачивает корпус при изменении толщины
  грунта, но уходит от нативной конвенции карты.
- Нативного подтверждения ни одному варианту нет (§8), поэтому выбор
  фиксирует владелец, а не аудит.

### Блок 5. Idle: возврат фаса к камере

Риск: низкий, но влияет на вид карты.

- Нативно `adjust_gnome_rotation` (`z_dignwalk.tcl:1143-1148`) возвращает
  гнома фасом к камере, если |roty| > 1.2. В главе гном после ходьбы
  остаётся в последнем фасе. Перенос требует проверки, чтоidle-клип
  главы это допускает.
