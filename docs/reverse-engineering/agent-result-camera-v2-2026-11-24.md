## 1. Почему игра падала (разбор дампов) — факт

Свежие дампы: `C:\Users\frant\AppData\Local\CrashDumps\Diggles.exe.4964.dmp`
и `…\Diggles.exe.6624.dmp` (24.11, 13:30 и 13:31).

Разбор `ExceptionStream` (тип 6) обоих дампов:

| поле | значение |
|---|---|
| ExceptionCode | `0xC0000005` (ACCESS_VIOLATION) |
| ExceptionInformation[0] | `8` — **выполнение** кода по невалидному адресу |
| ExceptionInformation[1] / ExceptionAddress | `0x01E3493A` |
| база образа `Diggles.exe` | `0x00F90000` (delta = `0x00B90000`) |

`0x01E3493A` **вне** образа exe (`.text` кончается на `base+0x31493A`).
Проверено по полному списку модулей из дампа (112 модулей в `6624.dmp`,
110 в `4964.dmp`): **адрес падения не принадлежит ни одному загруженному
модулю** — это «выстрел в молоко», т.е. переход по испорченному адресу,
а не ошибка в коде DLL.
Арифметика сходится до бита с такой моделью:

```
next   = base + 0x2B6A7A            = 0x01246A7A      (следующая инструкция после call)
rel32  = 0x0005DEC0                 (поле rel32 моего call в файле)
rel32' = rel32 + delta             = 0x00BEDEC0       (загрузчик ПРИБАВИЛ delta)
target = next + rel32'             = 0x01E3493A   ✓ = адрес падения
```

**Причина (факт):** у exe включён ASLR (`DllCharacteristics=0x8140`,
`ImageBase=0x00400000`), а в `.reloc` есть HIGHLOW-запись на RVA
`0x002B6A76` — это DWORD-операнд старой инструкции
`mov eax, [0x77241c]` (`VA 0x006B6A75`), которую я заменил на
`call rel32`. Поле `rel32` моего `call` оказалось ровно на месте
операнда, загрузчик прибавил к нему delta, и вызов ушёл в мусор.
Пещера (`code cave`) при этом **не выполнялась ни разу** — падение
происходило на самом первом кадре отрисовки.

Дополнительно (почему абсолютные адреса в самодельном коде нельзя):
даже без релокации `mov edi, [0x77241c]` в пещере читает по адресу
`0x0077241c`, которого в загруженном образе нет (образ по `0x00F90000`).

**Вывод:** любой самодельный код в exe должен быть position-independent,
а вставлять `call rel32` поверх инструкции с абсолютным операндом нельзя
(если только не гасить запись в `.reloc`).

## 2. Новая схема: используем штатную ветку движка (code cave не нужен)

В движке есть готовая ветка «показать всю карту» —
`CFogOfWar::UpdateFoW` (`FUN_0057F5C0`, `VA 0x0057F5C0`):

```
0x0057fac2  mov      edx, [ebp-0x10]        ; this (CFogOfWar*)
0x0057fac5  cmp      byte ptr [edx+8], 0     ; флаг "раскрыть всю карту"
0x0057fac9  je       0x57fcb5
0x0057facf  mov      ecx, [0x77241c]         ; map
0x0057fad5  test     ecx, ecx
0x0057fad7  je       0x57fc64
0x0057fadd  cmp      byte ptr [ecx+0x29], 0  ; map->mapFlags
0x0057fae1  je       0x57fc64
0x0057faed  mov      byte ptr [edx+8], 0     ; сбросить флаг
0x0057faf1  xor      edx, edx
0x0057faf6  xor      edi, edi
0x0057faf8  nop (8 байт)                    ; <-- P3
0x0057fb00  add      eax, 0xa328            ; &rect[owner]
...
0x0057fb2a  movups   xmm0, [ecx+0x84]       ; ПОЛНЫЕ границы карты (16 байт)
0x0057fb38  movups   [eax], xmm0            ; rect[owner] = границы карты
0x0057fb3b  mov      eax, [0x772400]        ; app
0x0057fb40  cmp      edi, 0x80              ; 8 владельцев * 0x10
0x0057fb46  jl       0x57fb00
0x0057fb48  ... цикл раскрытия тумана (0xff по всем 8 владельцам) ...
0x0057fb5a  jge      0x57fc64               ; <-- P4
```

Она делает ровно то, что нужно: копирует `map+0x84` (полные границы карты)
в `app+0xa328` (прямоугольники камеры) для всех 8 владельцев.
Прямоугольник камеры потом клампит камеру в `FUN_00529570` и в
winroot-tick: `camX ∈ [rect.x0-1, rect.x1+1]`.

Функция вызывается **каждый игровой тик**:
`CGameThread::SrvDoThink()` → «FOW» → `FUN_0057f5c0()`
(условие вызова: `map != NULL && map->mapFlags != 0`).

### Правки (6 штук, все — относительные переходы/immediate, ASLR-безопасно)

| # | VA | было | стало | смысл |
|---|---|---|---|---|
| P1 | `0x0057FABD` | `E9 B0 01 00 00` (jmp `0x57fc72`) | `E9 00 00 00 00` (jmp `0x57fac2`) | после штатной обработки тумана зайти в ветку «вся карта» |
| P2 | `0x0057FAC9` | `0F 84 E6 01 00 00` (je) | `90 90 90 90 90 90` | не проверять флаг «раскрыть всю карту» (он всё равно сбрасывается) |
| P3 | `0x0057FAF8` | `0F 1F 84 00 00 00 00` (nop ×8) | `E9 3E 00 00 00 90 90 90` (jmp `0x57fb3b`) | войти в цикл копирования с `eax = [0x772400] = app` (иначе eax был бы мусором) |
| P4 | `0x0057FB5A` | `0F 8D 04 01 00 00` (jge) | `E9 05 01 00 00 90` (jmp `0x57fc64`) | пропустить цикл раскрытия тумана — копируем только границы камеры, туман ИИ не трогаем |
| P5 | `0x006B6968` | `F3 0F 10 35 38 71 73 00` (константа 1.0) | без изменений | **нижняя** граница зума = 1.0 (предел ПРИБЛИЖЕНИЯ) — не трогаем |
| P6 | `0x006B6973` | `F3 0F 10 2D D8 73 73 00` (константа 2.5) | `F3 0F 10 2D 6C 75 73 00` (константа **16.0**) | **верхняя** граница зума 2.5 → **16.0** (предел ОТДАЛЕНИЯ) |
| P7 | `0x00452BF9` | `F3 0F 10 0D D8 73 73 00` (константа 2.5) | `F3 0F 10 0D 6C 75 73 00` (константа **16.0**) | **тот же кламп в рендерере** (`CDXExecBuf::Render`) — иначе движок рисует эффекты по старому зуму 2.5 и экран закрашивается чёрным |

Проверка релокаций (`.reloc`): на RVA `0x17FABE / 0x17FAC9 / 0x17FAF8 /
0x17FB5B` записей HIGHLOW **нет** → загрузчик их не чинит ✓.
Абсолютные адреса есть в операндах P5 (`0x737138`), P6 (`0x7374e0`/`0x73756c`)
и P7 (`0x7373d8`/`0x73756c`); на RVA `0x2B696C`, `0x2B6977` и `0x052BFD`
записи HIGHLOW **есть** (тип 3) ⇒ загрузчик пересчитает их правильно под
реальный базовый адрес образа.

### Зум: как он устроен на самом деле (факт, исправление прошлых выводов)

`CGameThread::Draw` (`0x006b6968…0x006b6997`) клампит зум в ветке
«обычная игра» (`app+0x598 == 0`):

```
0x006b6968  movss xmm6, [0x737138]   ; 1.0  - нижняя граница
0x006b6973  movss xmm5, [0x7373d8]   ; 2.5  - верхняя граница  (стало 6.0)
0x006b697e  maxss xmm0, xmm1
0x006b6997  minss xmm5, xmm0         ; zoom = min(upper, max(lower, zoom))
0x006b69b5  movss [edi+0x15c], xmm5  ; app+0x15c = итоговый зум
```

**zoom — обратная величина.** Размер объекта на экране = `300.0 / zoom`
(`CDisplay::DrawObjects`, `0x00473cc0:314`), то есть:

| zoom | размер объекта | что это |
|---|---|---|
| 1.0 | 300 px | сильное приближение |
| 2.5 (штатный максимум) | 120 px | штатное отдаление |
| 6.0 | 50 px | отдаление ×2.4 от штатного |
| **16.0 (текущий патч)** | **19 px** | **отдаление ×6.4 от штатного** |

Граница настраивается без правки байтов: `python patch-camera.py --zoom-max=8.0`
(доступны 2.5 / 4.0 / 6.0 / 8.0 / 10.0 / 12.0 / 16.0 / 50.0 — все эти
float-константы уже лежат в `.rdata` exe; 50.0 — экстремум, обзор шире
карты ценой ~6 px на объект).

⇒ **больший zoom = дальше отдаление**, верхняя граница ограничивает
ОТДАЛЕНИЕ, нижняя — ПРИБЛИЖЕНИЕ.

**Ошибка прошлой версии патча (исправлено):** P5 раньше менял нижнюю
границу 1.0 → 0.1. Это усилило **приближение** (300/0.1 = 3000 px на объект),
а не отдаление — игрок это сразу заметил («теперь я могу очень сильно
приближать, а не отдалять»). Теперь P5 возвращён к 1.0, а отдаление
расширяется через P6 (верхняя граница 2.5 → 6.0).

Побочный эффект, о котором стоит знать: в той же ветке считается
`scale = 0.7 / max(lower, zoom² − 2)` (`0x006b69b1…0x006b69d1`,
`0.7` = `0x7370b0`, `2.0` = `0x737330`); она ограничивает угол наклона
камеры при большом зуме (камера «выпрямляется»). Значения
`0.7 (zoom≤1.73) → 0.165 (zoom=2.5) → 0.021 (zoom=6)`. Если при
максимальном отдалении камера поведёт себя странно — правка рядом:
заменить `maxss xmm6, xmm0` (`0x006b69c5`) на `movss xmm6, [0x737138]`,
тогда `scale` всегда 0.7.

Других клампов зума в движке нет: ввод (`winroot-tick`, `0x0052c138`)
просто умножает зум на множитель, клампит только `CGameThread::Draw`
(`0x006b6968`), а построитель вида (`FUN_00475EE0`) зум не трогает вовсе.
Штатная «кинематографическая» ветка (`app+0x598 != 0`) имеет свой диапазон
`[0.5 … 6.0]` (`0x006b68b6`, `0x006b68c7`) — оттуда и взят 6.0.

### Чёрный экран на предельном отдалении (24.11.2026)

Симптом: на максимальном отдалении (zoom 16) очередной щелчок колеса
закрашивает весь экран в чёрный.

**Это не накопление.** Зум жёстко зажимается **каждый кадр** в
`CGameThread::Draw` и значение записывается обратно:

```
0x006b697e  maxss  xmm0, xmm1          ; max(1.0, zoom)
0x006b6997  minss  xmm5, xmm0          ; min(16.0, ...)
0x006b69b5  movss  [edi + 0x15c], xmm5  ; app+0x15c = зум (запись обратно)
```

Значит после 16-го щелчка зум уже равен 16.0 и 17-й/18-й щелчок его
изменить не могут — «перелёт» через порог невозможен.

Причина — **жёстко зашитые в движок допущения «зум ≤ 2.5»**, которые мы
подняли только в одном месте, а движок их дублирует:

| где | VA | что делает |
|---|---|---|
| `CGameThread::Draw` | `0x006B6968…6973` | кламп зума в рендере (P6) |
| `CDXExecBuf::Render` | `0x00452BF9` | второй кламп `min(2.5, max(1.0, zoom))`, значение уходит в **пост-эффект** (P7) |
| освещение/рельеф | `0x00480796`, `0x00480FA1`, `0x004811BD`, `0x0046F068` | `±2.5` в формулах света/тумана, настроены под зум ≤ 2.5 |
| `SetCameraFollow` | `0x006987C8` | `minps` с 2.5 при записи зума (Tcl-команда) |
| угол камеры | `0x00427F03`, `0x00427F12` | кламп **угла** ±2.5 рад (не зум) |

Геометрия камеры (факт, `FUN_00475EE0`): высота камеры над картой =
`14 + cos(dir.y)·cos(dir.x)·(zoom·16 − 10)`, т.е. при zoom 16 камера
висит на 260 единицах над героем (при штатном 2.5 — на 44). Видимая
область растёт примерно в 6 раз, поэтому у краёв карты неизбежно
появляется «пустота» (вне карты) — это нормально. **Полностью** чёрный
экран — уже баг движка, и P7 его устраняет (пост-эффект получает
настоящий зум вместо 2.5 и перестаёт закрашивать кадр).

Если после P7 чёрный экран сохранится — следующие кандидаты:
1. опустить предел (`python patch-camera.py --zoom-max=8.0`) — быстрый
   способ понять, где именно ломается;
2. пересчитать константы `±2.5` в формулах освещения под новый зум.

Инструменты для этой задачи: `refscan.py` (все ссылки на float-константу
в .text exe), `disasmwin.py` (точная дизассемблировка окна по VA, когда
линейная разъезжается).

### Множитель панорамирования — править не нужно (исправление прошлых выводов)

Множитель панорамы: `fVar12 = (zoom-1) * app[0x198] * 0.2 + 1.0`
(`FUN_00529570` VA `0x00529611` и winroot-tick VA `0x0052bc7d`).

Раньше `app+0x198` был ошибочно идентифицирован как опция `Screen\Brightness`
(=50) ⇒ якобы при `zoom<0.9` множитель уходит в минус.
**Факт:** по дизасму `CGameThread::Init` (`0x006afcd4…0x006afd3b`) в
`app+0x198` пишется опция **`Input\ZoomSpeedFactor`**, а не Brightness:

```
0x006afcdd  push 0x735a84     ; "ZoomSpeedFactor"
...
0x006afd3b  movss [eax+0x198], xmm0
```

В реестре `HKCU\Software\SekOst\Diggles\Input\ZoomSpeedFactor = 0` ⇒
`fVar12 ≡ 1.0` при любом зуме ⇒ инверсии панорамы нет, дополнительных
правок не требуется. (Заодно снят вопрос про «изменение скорости панорамы
при зуме ≥ 1.0» — её не будет.)

## 4. Что проверяет пользователь

1. Игра запускается без падения (старая версия падала сразу на первом кадре).
2. **Камера**: увести её за пределы вскопанной/исследованной области —
   должна ехать (раньше отскакивала к центру). За пределы *карты* камера
   по-прежнему не уедет (это ограничение `FUN_00475EE0`).
3. **Зум**: колесо мыши вниз (отдаление) теперь доводится до 16.0 вместо
   штатных 2.5 — объект на экране ~19 px вместо 120 px (обзор примерно
   в 6.4 раза шире штатного). Приближение осталось как в оригинале
   (zoom ≥ 1.0). Если нужно больше или меньше — одна команда:
   `python patch-camera.py --zoom-max=10.0`
   (2.5 / 4 / 6 / 8 / 10 / 12 / 16 / 50).
4. Скорость панорамирования не должна измениться (множитель = 1.0, как и раньше).

**Грабли (dumpinfo.py, 24.11.2026):**
- список модулей — это поток **типа 4** (`ModuleListStream`), а не 3
  (`ThreadListStream`); при чтении не из того потока `nameRva` указывает
  в мусор;
- имя модуля читается по структуре `MINIDUMP_STRING` (4-байтовая длина +
  UTF-16LE), **не** поиском `00 00` до конца файла: на EOF `read(2)`
  возвращает пустой байт и цикл «чтение до нуля» зависает навсегда
  (та задача висела час до срабатывания watchdog);
- контекст потока в этих дампах недоступен (заполнен `0xAAAAAAAA`) — EIP
  брать из `ExceptionStream`, а стек не читать; иначе `struct.error`
  и код выхода 1;
- `ExceptionInformation[0]`: 0=READ, 1=WRITE, **8=EXECUTE** (а не «WRITE»).

**Грабли:** `.reloc`-записи типа **3** (HIGHLOW), а не 10 — при разборе
таблицы релокаций это легко перепутать и решить, что релокаций нет вовсе.
