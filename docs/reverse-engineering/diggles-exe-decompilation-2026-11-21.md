хватило, чтобы восстановить **API движка** — то есть слой «C2», который и

### 2.4 Реестр нативных Tcl-команд (`exe_map.py`)

Команды регистрируются через `Tcl_CreateObjCommand` (tcl83.dll). В бинаре
**49 мест регистрации**; подтверждённое соответствие «имя команды → адрес
обработчика» восстановлено для 23 (`ai_*`-группа, 0x429E..–0x42A5..),
остальные требуют разрешения xref — этим занят Ghidra.

Шаблон вызова (MSVC cdecl), восстановленный дизассемблированием:

```asm
push 0              ; deleteProc = NULL
push edi            ; clientData
push 0x0042BE80     ; proc  -> обработчик в .text
lea  eax,[esi+0xC]  ; objName -> буфер std::string
push eax
push ecx            ; interp
call dword ptr [0x715570]   ; Tcl_CreateObjCommand
```

### 2.5 Словарь команд игровых скриптов (`tcl_commands_from_scripts.py`)

## 3. Пайплайн Ghidra (полный экспорт)

Установлено: **Ghidra 11.4.3** (`C:\ghidra\ghidra_11.4.3_PUBLIC`), Java —
системный OpenJDK 21 (`JAVA_HOME` уже задан), `MAXMEM=3G` в
`support\analyzeHeadless.bat` (машина: 8 логических ядер, 6.9 ГБ RAM,
15 ГБ свободного диска).

Скрипты: `work\campaign\ref\ghidra\ExportDiggles.java` (headless post-script) и
`work\campaign\ref\ghidra\run_ghidra.ps1` (обёртка).

Что делает `ExportDiggles.java`:

1. переименовывает функции по таблице `tcl_commands.tsv` → `TclCmd_<имя>`;
2. декомпилирует **каждую функцию** и пишет `decomp/<функция>_<адрес>.c`;
3. пишет `index.tsv` (имя, адрес, размер, число строк C, файл, статус);
4. выгружает `strings.tsv` и `classes.txt`.

Запуск:

```powershell
& C:\ghidra\ghidra_11.4.3_PUBLIC\support\analyzeHeadless.bat `
    C:\diggles-ghidra\project Diggles `
    -import C:\diggles-ghidra\Diggles.exe `
    -analysisTimeoutPerFile 3600 `
    -scriptPath <путь>\work\campaign\ref\ghidra `
    -postScript ExportDiggles.java C:\diggles-ghidra\out <путь>\tcl_commands.tsv `
    -max-cores 3
```

Проект Ghidra и выгрузка лежат **вне OneDrive** (`C:\diggles-ghidra`) — иначе
синхронизация мешает и съедает место.

### Ограничения (важно для ожиданий)

- **PDB в бинаре нет** → имена функций восстанавливаются только из RTTI,
  assert-строк и экспортов `DigglesPort.dll`; остальные — `FUN_xxxxxxxx`,
  но с корректной структурой и типами.
- Полный экспорт всех функций — процесс на часы; индекс и выгрузка
  инкрементальны, поэтому результат полезен уже во время прогона.
- 6.9 ГБ RAM: декомпилятор и анализатор в одном JVM, отсюда `-max-cores 3`
  и `MAXMEM=3G`.

### 6.0 Типизированный проход (21.11, `ApplyStructs.java`)

Отдельный headless-проход по тому же проекту (`C:\diggles-ghidra\project2`),
который **материализует выведенные раскладки классов как настоящие структуры
Ghidra**, проставляет их в указатель `this` (`__thiscall`) и передекомпилирует
затронутые функции.

| Что | Результат |
|---|---|
| Структур создано | **77** (из `ghidra_structs.tsv`, 666 полей) |
| Функций типизировано | **319** (из 935 известных; 615 — класс без выведенной раскладки, 1 — нет функции по адресу) |
| Ошибок типизации | **0** |
| Выгружено типизированного C | **319 файлов**, 31 296 строк |
| Обращений `this->поле` | **2 381** |

Результат — `work\campaign\ref\ghidra-out\typed\` (индекс — `index_typed.tsv`).
Пример: `bool __thiscall CAct_Lore__GetPosRotSpeed(CAct_Lore *this)` и
`iVar5 = this->i_0c;` вместо `*(int *)(in_ECX + 0xc)`.

**Грабли, на которые ушло время (зафиксировано в скрипте):**
- `Function.insertParameter(0, …)` на функции с авто-параметром `this`
  (`__thiscall`) падает с `InvalidInputException: Parameter may not be inserted
  before auto-parameter` — **все 319 функций молча пропускались**. Лечится
  пере-типизацией существующего параметра (`Parameter.setDataType`), а при
  отказе — пересборкой списка параметров.
- Ghidra-скрипт падает целиком («class could not be found»), если в рабочем
  каталоге скриптов лежит хотя бы один некомпилируемый `.java`: рабочий каталог
  — `C:\diggles-ghidra\scripts2`, исходники — в репозитории.

### 7.1 Имена ~3 764 функций (65% кода) — невосстановимы принципиально

### 7.4 Геометрия карты и клетки

Разобрано по запросу параллельной сессии «Освещение» (стены выработок);
уточнено 21.11 после разбора системы выемки. Полный разбор с адресами —
`docs/reverse-engineering/answer-osveshchenie-2026-11-21.md`.

**Запись клетки — 0x7C (124) байта**, доступ `idx * 0x7c + *(int *)(map + 0x14)`:

| Смещение | Тип | Содержимое |
|---|---|---|
| +0x00 | int32 | индекс **под-блока высот** (под-блок = 0x59 байт) |
| +0x04 | ushort | индекс объекта в клетке (0xFFFF = нет) |
| +0x08 | uint32 | 8 нибблов, индекс = **owner (клан)**: код грани/выемки |
| +0x0C | uint32 | 8 нибблов, индекс = **owner**: тип грани (4 бита) |
| +0x13 | uint8 | бит0 = «высота изменилась», бит1 = «выкопано», бит2 = «просмотрено» |
| +0x18 | ushort | биты 0-1 = **материал**, биты 2-15 = флаги |
| +0x34 | uint8[8] | индекс = **owner**: второй байт на слот |
| +0x3C | uint8[64] | **флаги** на 64 отсчёта, индекс = (y&7)<<3\|(x&7) — **НЕ высоты** (поправка 21.11 вечер, см. §7.9) |

**ВАЖНАЯ ПОПРАВКА (21.11).** Раньше здесь было написано «+0x08 / +0x0C / +0x34 —
по 4 бита на 8 *направлений*». Это неверно: индекс слота 0..7 — это **owner id
(id клана)**, а не направление. Доказательства:

- `CTclGlobalMethods::IsDigMarked` (0x650a50:240) — индекс ниббла = owner игрока
  (`*(DAT_00772400 + 100)`);
- `FUN_00596b80` (выемка) — сдвиг ниббла = owner гнома (`gnome+0x36c`, поле
  пишет `SetOwner`, читает `GetOwner`);
- `dig_mark` — первый Tcl-аргумент = owner id (в скриптах ИИ туда кладут id
  клана: `std_ai.tcl:3036`).

Следствие: **направлений в записи клетки нет вообще** — они вычисляются из
сетки высот. «8 направлений» — артефакт моей прежней интерпретации.

**Материал (младшие 2 бита +0x18)** — код материала, не «ground/wall/ladder»:
`get_material` и `ground_pos` — один обработчик `CTclGlobalMethods::GroundPos`,
возвращающий `*(ushort *)(cell + 0x18) & 3`; игровой ИИ трактует его как
`if {$m==0||$m==3} { set rock 1 }` (`data/Scripts/ai/std_ai.tcl:2991`).
**0 и 3 — порода (не копается), 1 и 2 — копаемо.** Это совпадает с данными
выгрузки главы (материал 3 — базовый слой, материал 2 — и на поверхности,
и на полу выработки), т.е. материал **не** кодирует выемку.

Код материала ставится: создание клетки — `| 3` (порода, `FUN_005992b0:338`),
генератор уровня — `FUN_005fc9d0:110` (рандомизация 1↔2 с градиентом по
расстоянию, только для клеток, уже имеющих материал 1 или 2), `| 2` — земля
(`FUN_00598f10:149`). Код 1 (песок) приходит из данных шаблонов.

**Высота (поправка 21.11 вечер).** В первых 0x18 байтах высоты нет. `cell+0x00` = индекс
под-блока высот; **сетка высот 8×8 живёт в под-блоке** (0x59 байт, байты `+0x00..+0x3F`),
а `cell+0x3C` — **параллельный массив флагов** на те же 64 отсчёта, а не копия высот
(`CTclGlobalMethods__TestD_00647d10.c:98-104`, `FUN_00407e70_00407e70.c:7-8`).
Чтение: `FUN_004093f0(engine_x, engine_y)` → `x>>3`, `y>>3` → клетка;
`base = cell[0x00]*0x59 + block->0x10`; байт по индексу `((y&7)<<3) | (x&7)`
(+x — младший индекс, +y — старший).
**Шкала:** байт — это **уровень**, world-Z = **`7.0 + 0.5*v` клетки**
(`FUN_004c8220_004c8220.c:33,44`), диапазон 7.0…14.5, верхняя плоскость (туман, верх
стен) = 15.0. Горизонталь — адресация 1/8 клетки (`GetHMap`: `ROUND(x*8.0)`), т.е. высота
сэмплится в 64 точках на клетку; **вершины геометрии — в клетках**.

**Выемка.** Признака «выкопано» в материале нет; выемка = понижение пола:
`FUN_00596b80` меняет `cell[0x00]` у выкопанной клетки и 3 соседей и ставит
`cell+0x13 |= 0x01` (dirty, читается в 4 местах) и `cell+0x13 |= 0x02`
(«выкопано»; в exe **не читается** — служебная метка). **Стены в движке
выводятся из перепада высот** — значит портовый подход «стены = перепад
высот» является реконструкцией оригинала, а не адаптером.

**Объект карты (CMap):**

| Смещение | Содержимое |
|---|---|
| +0x14 | база массива клеток |
| +0x18 | число клеток |
| +0x24 | дескриптор блока высот (+0x10 = база под-блоков, +0x14 = их число) |
| +0x44 | шаг сетки |
| +0x4C | модуль индекса (ширина мира) |
| +0x84 / +0x88 / +0x8C / +0x90 | границы карты (x0, y0, x1, y1) |

Индекс клетки: `(y * stride + x) % modulus`. Доступ по координатам —
`FUN_00592f10(x, y)` (клампит в границы и возвращает запись клетки).

### 7.4.1 Система выемки (по владельцам)

| Tcl-команда | C-обработчик | Смысл |
|---|---|---|
| `dig_mark <owner> <x> <y> <mode> [value]` | `CTclGlobalMethods::DigMark` (0x6586c0) | mode 0 — записать `(value|8)` в ниббл +0x08 и тип грани в +0x0C; mode 1 — «метка ребра» (ниббл = 3); mode 2 — снять заявку |
| `dig_next <pos> <gnome> [try]` | `CTclGlobalMethods::DigNext` (0x634b50) → `FUN_00597b20` | поиск точки копания: сканирует клетки, у которых ниббл **своего** owner удовлетворяет маске `0xB` и материал = 1 или 2 |
| `dig_apply <point> <gnome>` | `CTclGlobalMethods::DigApply` (0x6347a0) → `FUN_00596b80` | собственно выемка: понижение пола, чистка слишком твёрдых нибблов |
| `is_dig_marked <x1> <y1> <x2> <y2>` | `CTclGlobalMethods::IsDigMarked` (0x650a50) | есть ли заявка у **игрока** |
| `get_digedge`, `get_digid`, `dig_resetid` | — | обслуживание заявок |

Ниббл +0x08 (индекс = owner): бит 3 — «грань существует», бит 2 — «метка
точки копания», биты 0-1 — класс копаемости (требуемая сила гнома 0/3/7/11).
Ниббл +0x0C — **тип грани** (0..15, из какой породы сделана грань): гном
копает только грани своего типа (`FUN_00597b20` сравнивает его с
`gnome+0x250`) — это ограничение спец-инструмента «Кристаллstrahl».

**«Стена»** по `CMapBeautifier::ScanAtPos` (0x58b130:178): клетка — стена для
owner, если ниббл ≠ 0 и бит 3 сброшен. Пер-дерегрессии коды пишутся **при
загрузке карты из блоков** (`FUN_00567cb0` → `FUN_005671a0`), а не при выемке;
выемка их, наоборот, чистит.

`0x28B0 + 0x17388 = 0x19C38` — начало полей `CDisplay`.

**5. Таблица масок и выбор текстуры.** Группа = `(param_1 >> 5) & 7`;
база группы = `this + group * 0x204 + 8`; 2 варианта по 0x100, 16 слотов по 0x10,
слот = {указатель на массив номеров текстур, количество};
`base + 0x200` — дефолтная текстура группы. `param_1`: биты 0..4 — случайность
(`(param_1 & 0x1F) % count`), 5..7 — группа, 8..15 — уровни углов
(байт `CHeightBlock + 0x54`).
Выбор текстуры: `idx = (((p5&3)*3+(p4&3))*3+(p3&3))*3+(p2&3)` (0..80 = 3^4),
`tex = textures[textureIndex[idx] + ((idx | rand8) >> 8) % variants[idx]]`.

**6. Поправлены ошибочные назначения классов CMap** — по дизассемблированию и по типизированному выводу `0x00427610`,
`0x00427e30`, `0x005763e0`, `0x005e9700` **не являются** методами CMap: они зовут
аксессор с **глобальной** картой (`FUN_00592f10(PTR_0077241c)`), а не со своим
`this`; либо читают `0x20` как байты; либо уходят за 0x200 (чужой объект).
Подтверждённые методы CMap (9): `0x004093f0` (геттер высоты), `0x00424cc0`,
`0x00590410`, `0x00592f10` (аксессор клетки), `0x005939b0`, `0x00595770`
(читает `this->x0_8/x1_8/y0_8/y1_8` и зовёт `FUN_00592f10(this)`),
`0x00593ec0`, `0x00594160` (Init), `0x005948b0` (Shut).

**7. Проход снимает устаревший тип `this`.** Четыре функции, ошибочно отнесённые
к CMap в прошлом проходе, переведены в класс `CUnassigned`; скрипт снимает с них
прежний тип `this` и перевыгружает заново (в проходе, который их снял: `this reset: 5`;
далее — 0, тип уже снят). Без этого в выгрузке остались бы файлы с неверной
сигнатурой.

**8. Проход чистит выходную папку.** После экспорта удаляются `.c`-файлы, не
попавшие в текущий индекс (`stale removed: 577`), — иначе в выгрузке копились бы
файлы прошлых прогонов с устаревшими типами.
