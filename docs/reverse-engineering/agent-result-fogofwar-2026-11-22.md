# Diggles: чёрный туман войны — разбор механизма и снятие (2026-11-22)

**Задача:** убрать **чёрный** туман (области, которые ещё не разведаны).
Обычная дымка, лежащая на карте там, где сейчас нет гнома или постройки, **не трогается** —
это разные слои и у них разные команды.

**Итог:** сделано **только Tcl-скриптом**, без патчей бинаря.
`data/userinit.tcl` → `work/thirdparty/DigglesModManager/userinit-nofog.tcl`.

---

## 1. Два слоя тумана — разные команды (факт)

Данные тумана в движке — **один байт на (владельца × ячейку карты)**, ячейка = 8×8
мировых единиц. Значения байта:

| значение | смысл | вид на карте |
|---|---|---|
| `0x00` | ячейка **не разведана** | **чёрный** туман |
| `0x01` | разведана, но не освещена | тёмная «дымка» |
| `0x02 … 0xFE` | градация освещения | дымка |
| `0xFF` | полностью освещена | ярко |

Байт лежит в ячейке карты по смещению `+0x34 + owner`
(`FUN_0066AEC0`: `lea esi, [eax+0x34]` … `add esi, edi`).

Проверка шкалы: `get_max_fow <obj> [<owner>]` (обработчик `0x0067BEB0` →
`FUN_00580EA0`) возвращает **байт состояния** ячейки, на которой стоит объект
(без второго аргумента — максимум по всем 8 владельцам; `0xFF`, если объект вне карты
или без владельца).

Подтверждение шкалы из `CFogOfWar::FadeBlocks(iPlayer)` (`FUN_0057E710`) — это
покадровое гашение:

```
local_20 = byte - 4;                 ; гасим на 4 за кадр
if (local_20 < 0xe3) {
    if (local_20 < 2) {              ; дошли до дна
        local_20 = 1;                ; ← дно = 1
        FUN_00581090(...)            ; блок убирается из списка видимых
    }
    ...
}
byte = local_20;
```

Значит:

* `0` — «область не разведана» (чёрный туман);
* `1` — «разведана, но максимально темно» — **дно дымки**, сюда и гаснут освещённые
  блоки; то есть обычный вид разведанной, но неосвещённой земли;
* `0xFF` — «видно сейчас».

Это же объясняет пороги в AI: `get_max_fow this < 10` → «ячейка слишком тёмная,
объект ничего не видит» (`w_procs.tcl:138`, `raupe.tcl:68`), `> 100` → «ярко»
(`infoobjs.tcl:100`).

**Следствие:** `remove_black_fog` (0 → 1) даёт ровно требуемую картинку — вся карта
становится разведанной, но остаётся в дымке; чёрных областей нет.

Движок: `CFogOfWar` — `RemoveFog`, `RemoveFogLine`, `RemoveFogBoxNoCollision`,
`FadeBlocks(iPlayer)`, `ShowBlocks`, `UpdateFoW`, `Visible`, `NewVisibleBlock`.

Отсюда два **разных** механизма:

| слой | команда | что делает с байтом | эффект |
|---|---|---|---|
| **чёрный** (не разведано) | `remove_black_fog <owner> <x0> <y0> <x1> <y1>` | `0 → 1` | **убирает чёрный туман, дымка остаётся** |
| чёрный + освещение | `set_fow_begin <y> [owner]` | `0 → 0xFF` | убирает чёрный туман **и** дымку |
| **дымка** (исследовано, но не видно) | `set_fogofwar <obj> <w> <h>` | `→ 0xFF` | убирает дымку (объект «накрывает» туман) |

**Вывод для задачи:** нужен `remove_black_fog` — он меняет `0 → 1`, то есть оставляет
дымку на месте. `set_fow_begin` для этой задачи не подходит: он ставит `0xFF`
(полностью освещено) — то есть убирал бы и дымку тоже.

## 2. `remove_black_fog` — основной механизм (факт)

Обработчик: `CTclGlobalMethods` → **`0x0066AEC0`** (найден через `find-tcl-handler.py`).

Разбор дизасма (`work/thirdparty/DigglesModManager/rmblack_full.asm`):

```
0x0066af0c: cmp esi, 6            ; ждём ровно 5 аргументов (+ имя команды)
0x0066af11: push 5                ; иначе ошибка "wrong # args"
...
0x0066b2ac: mov esi, [ebp-0x14]   ; x1
0x0066b2af: mov esi, [esi+0x14]   ; массив ячеек
0x0066b2b2: mov edi, [ebp-0x18]   ; owner
0x0066b2b5: cmp edi, 7            ; owner < 8
0x0066b2ba: add esi, edi          ; esi = &cell->byte[owner]
0x0066b2cf: cmp byte ptr [esi+0x34], 0   ; ячейка чёрная?
0x0066b2d3: jne 0x0066b306        ; нет — пропускаем (дымку не трогаем)
0x0066b2e1: call 0x592f10         ; FUN_00592f10(x,y) — доступ к ячейке
0x0066b303: mov byte ptr [esi], 1 ; *** 0 -> 1 : «разведано, но не освещено» ***
```

* Координаты — **ячейки карты** (`FUN_00592f10` клампит x/y по границам карты),
  поэтому прямоугольник можно задавать с запасом — он обрежется по карте.
* Ячейки с байтом `1 … 0xFF` **не трогаются** → дымка сохраняется.
* Если `owner` совпадает с владельцем локального игрока (`app + 0x64`), дополнительно
  обновляется прямоугольник «видимой области» (`FUN_005a3dd0` / `FUN_005a3fd0`,
  координаты × 8) — то есть камера может скроллить всю карту.
* Команда **идемпотентна**: повторный вызов чинит только то, что снова стало чёрным.

Использование в игре: `data/Scripts/classes/story/Trigger_Urwald.tcl:319`

```tcl
remove_black_fog 1 $xn $firey $xp $myy
```

## 3. `set_fow_begin` — что он на самом деле делает (факт)

Обработчик `CTclGlobalMethods::SetFoWBegin` (`0x0064B380`) → `FUN_00580610(y, owner)`
(`work/campaign/ref/ghidra-out/typed2/FUN_00580610_00580610.c`):

1. `fowBegin[owner] = min(y, cellY1 - 2)` — фронт разведки (массив `int[8]` по `+0x0C`).
2. Цикл по `y` от `cellY0 + 5` до `fowBegin - 1` и по всем `x`:
   * если байт ячейки **== 0** → `FUN_0057dfc0(...)` (регистрация «вновь открытого» блока);
   * байт → **`0xFF`** (всем ячейкам в диапазоне, безусловно).

Где это использует сама игра: `story.tcl:589` (`set_fow_begin [expr $ofsy + 150]`),
`Trigger_Lava.tcl:55` (`set_fow_begin 2000`).

**Обновлённый вердикт (v9/v10).** Раньше вывод был «`set_fow_begin` не годится, он
ставит `0xFF`». Теперь известно, что `set_fow_begin` делает **две** вещи, и вторая
важнее первой:

* `FUN_0057dfc0` (`CFogOfWar::NewVisibleBlock`) — **регистрирует** ячейку как видимую
  (дизасм: `work/thirdparty/DigglesModManager/newvisible.asm`);
* запись `0xFF` в байт ячейки — «полностью освещено».

`remove_black_fog` не делает НИЧЕГО из этого — он меняет только байт (`0`→`1`),
и поэтому земля остаётся чёрной. Значит рабочий инструмент — `set_fow_begin`,
а «пересвет» (`0xFF` вместо `1`) — это его побочный эффект, который лечится
патчем байта в `FUN_00580610` (см. §4.5).

## 4. Реализация: `data/userinit.tcl` (адаптер)

Файл: `work/thirdparty/DigglesModManager/userinit-nofog.tcl`
(ASCII, Tcl 8.3 — без `eq/ne`, `{*}`, `lassign`, `try`).

### 4.0 Что поменялось после первой версии

Первая версия скрипта (SHA256 `E1DD724A…`) использовала `set_fow_begin 999999 0`.
Разбор дизасма показал, что это **неправильный инструмент** для этой задачи:

* `set_fow_begin` → `FUN_00580610` ставит ячейкам значение **`0xFF`**, то есть
  «полностью освещено» — такой вызов убирает **и чёрный туман, и дымку**;
* `remove_black_fog` → `FUN_0066AEC0` ставит ячейкам значение **`1`**, то есть
  «разведано, но темно» — **чёрный туман исчезает, дымка остаётся** (то, что нужно).

Кроме того, первая версия снимала туман только сразу после `map create`, а уровень
собирается уже после этого (шаблоны грузятся через `call`), и состояние тумана могло
пересоздаваться позже. Поэтому снятие повторяется в нескольких точках.

### 4.1 Текущая версия (v8) — где на самом деле создаётся карта уровня

**Главная находка:** карта **уровня** создаётся НЕ через `map create`, а через
`sm_create_map` (Story Manager):

| что | команда | где |
|---|---|---|
| карта меню | `map create 64 64 { }` | `systeminit.tcl:64` |
| **карта уровня** | **`sm_create_map 512 640`** | **`CampaignInit.tcl:34`** |
| уровень грузится | `call_method $sm load_level Campaign` | `GameScripts/single_CampaignX.tcl:5` → `story.tcl:1139` |

Уровень запускается так: `single_CampaignX.tcl` создаёт объект `StoryMgr` и вызывает
`call_method $sm load_level Campaign`; `story.tcl:1139` выполняет
`call "scripts/gameplay/CampaignInit.tcl"` (там и создаётся карта) и
`call "scripts/gameplay/Campaign.tcl"`.

Из-за того, что в предыдущих версиях хук стоял только на `map create`, **карта
уровня не обрабатывалась вообще** — в логе пользовательской сессии было всего две
записи, обе на карте меню. Теперь стоит хук и на `sm_create_map`.

| хук | зачем |
|---|---|
| `map create` | карта меню и обычные карты (`Scripts/gameplay/Campaign.tcl:2` и др.) |
| `sm_create_map` | **карта уровня** (`CampaignInit.tcl:34`) |
| `show_loading` | конец скрипта кампании (`Campaign.tcl:212`), сюжетные переходы (`story.tcl:908/928/1053/1090/1094`) |
| `reset_map` | сброс карты в сюжетных переходах (`story.tcl:585/916`) |
| `gameload` | загрузка сохранения |
| `obj_query`, `call_method`, `sm_get_event`, … | «пульс»: снятие тумана повторяется, пока идёт уровень (см. ниже) |

Про размер прямоугольника: движок **сам обрезает** прямоугольник по карте
(`start = max(mapCellX0, x0)`, `end = min(mapCellX1, x1)`, дизасм `rmblack_full.asm`),
поэтому передаётся заведомо большой прямоугольник `0 0 100000 100000` — он всегда
покрывает всю карту независимо от её размера и начала координат.

Размер карты для лога берётся из `get_map_width` / `get_map_height`
(`0x00630830` / `0x006309F0`) — они возвращают `map->x1 - map->x0`, то есть
**число ячеек**. Замер: после `map create 64 64` движок отдаёт `512x512` — то есть
сетка ячеек карты всегда 512×512, а `map create W H` задаёт логический размер
в мировых единицах.

Каждый хук после исходной команды вызывает

```tcl
remove_black_fog 0 0 0 100000 100000
```

(owner 0 — игрок; остальные владельцы не трогаем, чтобы не менять поведение ИИ).

Особенности обёрток:

* перехватываются только команды, которые **не вычисляют игровые скрипты** —
  это обязательное условие, см. §4.2;
* обёртка **процедуры** (или команды, вызывающей метод, как `call_method`) безопасна:
  у процедуры своя рамка вызова в любом случае, переменные скрипта не затрагиваются
  (проверено по декомпиляции `CTclGlobalMethods__CallMethod_00626970.c`: скрипт
  не вычисляется, только ищется и вызывается метод);
* аргументы передаются оригиналу списком (`eval` по списку), а не склейкой
  строки, поэтому экранирование не ломается;
* для `map` (у него подкоманда `getoffset` с **двумя** значениями) результат
  оригинала возвращается напрямую, без `catch`/`return $res`, — иначе
  `[lindex [map getoffset] 1]` в `story.tcl:907` сломался бы.

### 4.2 Почему хук `call` ломал игру (факт)

Версии 2–5 дополнительно перехватывали команду `call` («уровень собирается
скриптами»). **Именно этот хук ронял игру**, и вот почему:

Нативная команда `call` (`0x006313A0`) вычисляет загружаемый скрипт **в области
видимости вызывающей команды**. Когда `call` переименовывается и заменяется
процедурой-обёрткой, «вызывающей» становится тело моей процедуры, и весь
загружаемый скрипт выполняется **внутри неё**. Всё, что скрипт задаёт через
`set` на верхнем уровне, попадает в локальную переменную обёртки вместо
глобальной.

Доказательство — `tclerrors.txt` прогона v5 (54 КБ ошибок), все они одного класса:

```
Error(5830): can't read "noidiobjclassescnt": no such variable
    (reading value of variable to increment)
    invoked from within
"incr noidiobjclassescnt"
    (procedure "SetDummyClassesAll" line 96)
    invoked from within
"SetDummyClassesAll {noidiobj noviewinfog} {...}":
call scripts/init/animinit.tcl
```

* `animinit.tcl:258` — `if {![info exists noidiobjclassescnt]} {set noidiobjclassescnt 0}`
  → переменная создалась в области обёртки;
* `SetDummyClassesAll` — глобальная процедура, `incr noidiobjclassescnt` ищет
  переменную в **глобальной** области → «no such variable»;
* из этого же класса ошибки `can't read "tttmaterial__Offen"` и `unknown class:` —
  сломан реестр классов анимаций;
* следствие — падение (AV `0xC0000005`).

Тот же хук в v4/v5 дополнительно создавал игровые объекты внутри хука
`map create` — это тоже роняло движок (AV в `atidxx32.dll`, 23.11 01:57),
поэтому пробный объект и хук `obj_query` убраны.

**Вывод:** хуки можно ставить только на команды, которые **не вычисляют
игровые скрипты**. `map`, `sm_create_map`, `show_loading`, `reset_map`,
`gameload` — безопасны; `call` — нет.

### 4.3 Загрузка сохранения (факт)

**Главный механизм движка:** у него **ровно одна точка входа в Tcl** —
`FUN_006BC2C0` → `Tcl_EvalObjEx(interp, obj, flags = 0)`.

```
0x006BC3DC: push 0                    ; flags = 0  (НЕ TCL_EVAL_GLOBAL)
0x006BC3DE: push dword ptr [edi]       ; Tcl_Obj*
0x006BC3E0: push dword ptr [ebx]       ; interp
0x006BC3E2: call dword ptr [0x715530]  ; Tcl_EvalObjEx
```

Два следствия:

1. Движок **никогда не вызывает Tcl-команду по имени** — он только вычисляет
   текст скрипта, и делает это **в текущей рамке вызова**. Значит любая
   процедура-обёртка становится этой рамкой, и всё, что вычисляется через
   `Tcl_EvalObjEx` внутри неё, получает неверную область видимости.
   → **оборачивать можно только те команды, которые не достигают
   `FUN_006BC2C0`**.
2. Собственные Tcl-команды движка (`obj_query`, `call_method`, …) вызываются
   **только из игровых скриптов**, а не из C++: полный скан `.text` не даёт
   ни одного нативного вызова для `obj_query`, `call_method`, `gametime`,
   `gettime`, `show_loading`, `load_done`, `load_info`, `gameload` и др.
   Имена команд встречаются только в функции регистрации `FUN_00618010`.

**Классификация команд** (проверено транзитивным обходом графа вызовов до
`FUN_006BC2C0`, инструмент `work/tmp_re/reach.py`):

| статус | команды |
|---|---|
| **нельзя оборачивать** | `call` (0x006313A0), `call_method` (0x00626970), `call_method_static` (0x00627940), `update_objdetail` (0x006647D0), `gameload` (0x006310F0), `gamesave` (0x00630EB0), `sm_add_temp` (0x0065CBA0), `sm_get_level_info` (0x00661340) |
| **можно** | `map`, `sm_create_map`, `show_loading`, `reset_map`, `obj_query`, `gettime`, `gametime`, `load_info`, `load_done`, `set_ingame_loading`, `particle_processing`, `gameisloading`, `newsticker`, `obj_list`, `playerinfo`, `get_local_player`, `send_trigger`, `autoloadlevel`, `gui_new_game`, `template_set`, `show_maped`, семейство `sm_*` (кроме двух перечисленных выше) |

**Загрузка сохранения.** Загрузчик сейвов — `FUN_00556570`
(= `TCL:CTclGlobalMethods::GameLoad()`, обработчик `0x006310F0`). Кто его
вызывает (сканер прямых вызовов `work/thirdparty/DigglesModManager/callxref.py`):

```
call at 0x0053F27D   <- GUI (меню, «загрузить игру»)
call at 0x005418B5   <- GUI
call at 0x00631272   <- Tcl-команда gameload
```

То есть **GUI грузит сейв напрямую из C++**, а Tcl-команда `gameload` не имеет
ни одного вызова (ни из C++, ни из поставляемых скриптов) → это мёртвый код.
Сам загрузчик и его обработчики чанков (`FUN_006C6DA0`, `FUN_006C76B0`) не
вычисляют скрипты и не вызывают Tcl-команд — это чистый C++.

Значит **после загрузки сейва никакая Tcl-команда не выполняется**: карта и
состояние тумана восстанавливаются молча. Единственный способ поймать этот
момент — команда, которую движок вызывает регулярно во время игры («пульс»).
В v8 обёрнуто около 30 безопасных команд (`obj_query`, `sm_get_event`,
`sm_map_set`, `timer_event`, `gettime`, …), и в лог пишется **первый** вызов
каждой — это и есть диагностика того, что реально вызывается на уровне.

### 4.4 Особенности Tcl 8.3.2 в этой игре (факт)

В игре `tcl83.dll` → **Tcl 8.3.2**. Чего нет (и из-за чего уже ломался скрипт):

| нет | чем заменить |
|---|---|
| `eq`, `ne` | `==`, `!=` |
| `info body` | (в 8.3.2 этой подкоманды **нет** — проверено в игре: `info body` → ERROR) |
| `{*}`-раскрытие | `eval [concat [list $cmd] $args]` |
| `lassign`, `try`, `dict`, `file join` | — |

Осторожно с генерацией кода: если тело процедуры собирается строкой, каждый `[`
надо экранировать как `\[`, иначе Tcl выполнит его как подстановку **на этапе
сборки** (в версии v8 из-за этого скрипт вообще не загрузился).

**Стенд для проверки без запуска игры:** `work/thirdparty/DigglesModManager/tclcheck.py`
поднимает чистый Tcl (через tkinter), создаёт заглушки всех нужных команд,
подгружает скрипт и проверяет: синтаксис, установку хуков, вызов
`remove_black_fog` из `map create` / `sm_create_map` / `reset_map`, сохранение
многозначного результата (`map getoffset`) и прямоугольник `0 0 100000 100000`.
Проверка занимает секунды вместо 2,5-минутного запуска игры.

Установка (Write-инструмент в `C:\Program Files (x86)\…` заблокирован политикой,
поэтому копирование через PowerShell):

```powershell
Copy-Item 'work\thirdparty\DigglesModManager\userinit-nofog.tcl' `
          'C:\Program Files (x86)\Steam\steamapps\common\Diggles The Myth of Fenris\data\userinit.tcl' -Force
```

### 4.5 Новые факты о внутренностях тумана (v9 → v10, факт)

**Раскладка ячейки** (аксессор `FUN_00592F10(map, x, y)` → `CMapCell*`):

| смещение | что |
|---|---|
| `cell + 0x08` | dword, **4 бита на владельца** (8 владельцев = 32 бита) — «уровень/высота объёма тумана» |
| `cell + 0x18` | word с флагами ячейки |
| `cell + 0x34 + owner` | байт состояния: `0` = неразведано (чёрный туман), `1` = разведано и максимально темно (дно дымки), `0xFF` = освещено |

**`CFogOfWar::NewVisibleBlock(&cell, x, y, owner)` = `0x0057DFC0`** (полный дизасм:
`work/thirdparty/DigglesModManager/newvisible.asm`):

* ячейку ни в какой список **не** добавляет;
* работает **только** с 4-битным полем `cell+8`: сбрасывает его (если сработали флаги
  в `cell+0x18`) и сравнивает результат с `FUN_00597460(x, y)` — по смыслу это высота
  рельефа (0..15); в итоге в поле попадает `0` либо `1..14`;
* вывод: «видимость» ячейки хранится **не** в байте `cell+0x34+owner`, а в 4-битном поле.

**`CFogOfWar::UpdateFoW()` = `0x0057F5C0`**:

* обычный путь (`*(char*)(app+0x590) == 0` **и** `*(char*)(app+0x8E) != 0`) → `FadeBlocks`
  для владельцев 0..7 + «ShowBlocks»: для движущихся объектов вызывается `RemoveFog` /
  `RemoveFogLine` / `RemoveFogBoxNoCollision` — это «фонарь», которым гномы открывают
  туман вокруг себя;
* иначе, если `*(char*)(this+2) != 0` → **каждый кадр ВСЕ ячейки ВСЕХ владельцев ставятся
  в `0xFF`** — встроенный в движок режим «показать всю карту»;
* в конце вызываются `FUN_0057fde0` и `FUN_00581150(0, list[count-1])` — снятие одного
  «зажжённого» блока из списка владельца.

**`CFogOfWar::FadeBlocks(owner)` = `0x0057E710`** — перебирает список владельца
`this+0x2C + owner*8` (записи по 8 байт: x,y), уменьшает байт `cell+0x34+owner` на 4;
когда байт < 6 → ставит `1` и убирает запись из списка (swap-remove `FUN_00581090`).
Значит `1` — это штатное «разведано и темно», в которое система сама переводит потухшие
участки. `FUN_00581090` = удаление элемента по индексу (последний элемент переносится
в освободившееся место).

**`show_fogofwar <bool>` = `0x0062AF80`** пишет `*(bool*)(app+0x59C)` и вызывает
`FUN_00464CC0`. Читателей флага в выгрузке Ghidra нет (проверяется сканером .text).

**Гипотеза (требует проверки в игре):** чёрный туман определяется 4-битным полем
`cell+8`, а байт `cell+0x34+owner` задаёт яркость/дымку. Тогда `set_fow_begin` снимает
чёрный туман (через `NewVisibleBlock`), но пересвечивает карту (`0xFF`), а требуемое
состояние «разведано и темно» = байт `1`. Практический вывод: патч **одной** инструкции
в `FUN_00580610` (`mov byte ptr [..], 0xFF` → `0x01`) даёт ровно требуемый результат.
Точное смещение в `Diggles.exe` ищется отдельным проходом по .text.

### 4.7 Патч байта тумана в `Diggles.exe` (применён)

**Гипотеза (проверяется):** чёрный туман — это не байт `cell+0x34+owner`, а **объём тумана**
в 4-битном поле `cell+8`; байт задаёт только **яркость** (0 = неразведано,
1 = «разведано и максимально темно», 255 = освещено).

Отсюда объясняется, почему `remove_black_fog` ничего не менял: он правит байт,
но не снимает объём тумана → земля остаётся чёрной.

`set_fow_begin` снимает объём тумана (`NewVisibleBlock`), но ставит байт `0xFF` —
то есть **пересвечивает** карту (пропадает и дымка). Чтобы получить ровно требуемое
состояние («вся карта разведана, но тёмная»), в `FUN_00580610` меняется одна
инструкция:

| | |
|---|---|
| VA | `0x005807B2` — `mov byte ptr [edi], 0xff` (`C6 07 FF`) |
| файловое смещение в `Diggles.exe` | **`0x0017FBB2`** |
| замена | `C6 07 FF` → **`C6 07 01`** (`mov byte ptr [edi], 0x01`) |

Контекст (проверено дизасмом):

```
0x00580777  cmp      byte ptr [eax], 0        ; байт == 0 ?
0x0058077a  jne      0x58078f
0x0058078a  call     0x57dfc0                 ; NewVisibleBlock - ячейка видима
0x005807b2  mov      byte ptr [edi], 0xff     ; <-- ПАТЧ: 0xff -> 0x01
```

Скрипт: `work/thirdparty/DigglesModManager/patch-fogbyte.py`
(`apply` / `--revert` / `--check`). Бэкап оригинала:
`Diggles.exe.fogbyte.orig` рядом с exe (SHA256 `58A01D3D…ED74`).
Патченый exe: SHA256 `13288FA51B7EE8BC6B85E42E8564D036268A10B0112F42B9CD280BE3E0EE9233`.

**Побочный эффект:** собственные вызовы `set_fow_begin` в игре
(`story.tcl:589` — фронт разведки сюжета, `Trigger_Lava.tcl:55`) теперь раскрывают
область «тускло» (байт 1), а не «ярко» (255). Свечение вокруг гномов сохраняется —
оно идёт через `RemoveFog`/`FadeBlocks`, а не через `set_fow_begin`.

**Откат:** `python patch-fogbyte.py --revert`.

### 4.8 Почему хуки не видели карту уровня (факт, 23.11)

Прогон v11 показал: игра не вылетела, ошибок Tcl нет, но чёрный туман остался.
Лог:

```
map create: set_fow_begin ok  n=1  map=512x512     <- карта МЕНЮ (64x64 ячеек)
HOOK gui_new_game: {}
show_loading: probe: min fow(owner 0)=0            <- байт всё ещё 0
show_loading (black fog back): set_fow_begin ok  n=2  map=512x512
HOOK gametime: start
load_done (save loaded): set_fow_begin ok  n=3  map=512x512
```

**`sm_create_map` не вызвался ни разу** — значит карта уровня создавалась не здесь.
Разбор игровых скриптов:

| файл | строка | команда |
|---|---|---|
| `data/systeminit.tcl` | 64 | `map create 64 64 { }` — карта **меню** |
| `data/systeminit.tcl` | 103–108 | `gui_new_game` / `show_loading no` / `gametime start` / `load_done` — весь этот след в логе отсюда |
| `data/Scripts/gameplay/CampaignInit.tcl` | 34 | `sm_create_map 512 640` — карта **уровня** |
| `data/Scripts/gameplay/Campaign.tcl` | 2 | `map create 512 640` — карта **уровня** |
| `data/GameScripts/single_CampaignX.tcl` | 3–4 | `set sm [new StoryMgr]` + `call_method $sm load_level Campaign` |
| `data/Scripts/classes/story/story.tcl` | 1139–1143 | `method load_level {level}` → `call "scripts/gameplay/CampaignInit.tcl"`, `call "scripts/gameplay/$level.tcl"` |

Вывод: **уровень грузится в интерпретаторе объекта StoryMgr, а `data/userinit.tcl`
загружается только в главный интерпретатор** (`CGameThread::Init` — единственное
место, где движок грузит `data/userinit.tcl`, VA `0x006B10E7`/`0x006B1103`).
Поэтому хуки главного интерпретатора не видят ни `sm_create_map`, ни `map create`
уровня, а главный интерпретатор во время уровня практически молчит.

**Решение:** вставить раскрытие прямо в игровой скрипт уровня — в
`data/Scripts/classes/story/story.tcl`, методы `load_level` и `load_sandbox`:

```tcl
catch {set_fow_begin 999999 0} nofog_err
log "nofog: set_fow_begin -> $nofog_err"
```

Это выполняется в том же интерпретаторе, где карта уровня создаётся и
заполняется, то есть ровно в нужный момент. Скрипт патча:
`work/thirdparty/DigglesModManager/patch-story.py` (`--revert` / `--check`).
Бэкап оригинала: `work/thirdparty/DigglesModManager/story.tcl.orig`
(SHA256 `655BC0F70DC5E67B63693403F1FB04C2D9EF4572BF3365FC99C9FBD99720C844`).
Пропатченный файл: SHA256 `9B1A5E7885956ACCC9BD66AE56598A495D6C41A0FB52BE3AF31590B11F9F9DAF`.
Файл в кодировке CP1252 с CRLF — правится на уровне байтов, кириллица не трогается.

**Случай загрузки сохранения остаётся нерешённым**: загрузчик сейвов работает в C++
(`FUN_00556570`, вызывается из GUI `0x0053F27D`/`0x005418B5`), и после него ни одна
Tcl-команда не выполняется — хук `load_done` на этот путь не попадает.

## 5. Что НЕ работает / бесполезно (факт)

* **`show_fogofwar`** — команда есть (`CTclGlobalMethods::ShowFogOfWar`, `0x0062AF80`),
  ставит флаг `*(bool*)(app + 0x59C)`, но **этот флаг никем не читается** → команда мёртвая.
* **`set_fogofwar obj -1 -1`** — это НЕ «снять весь туман», а **выключить** раскрытие
  объекта (`CTclObjMethods::SetFogOfWar`, `0x0068A980`: при `w == -1` или `h == -1`
  пишется `*(obj+0x364) = -1`, `*(obj+0x368) = -1`). Так делает `genericprod.tcl:187`,
  когда машина перестаёт «накрывать» туман.
* **`FogRemover` (`data/Scripts/classes/items/infoobjs.tcl:954`)** — класс
  `fog_remove {owner xrange yrange}` → `set_fogofwar this $xrange $yrange`.
  Это инструмент для **дымки**, а не для чёрного тумана. Плюс `obj_init` ставит
  `set_fogofwar this -1 -1`, то есть по умолчанию объект ничего не раскрывает.
* **Отрицательные радиусы** (`fog_remove 0 -70 -70` в `Trigger_Tournament.tcl:632`,
  `set_fogofwar this -50 -50` в `GameObserver.tcl:111`) — относятся к механизму дымки
  и на чёрный туман не влияют.
* **`set_fow_begin`** — снимает и чёрный туман, и дымку (ставит `0xFF`), см. §3.

## 6. Известные побочные эффекты

* `get_max_fow <obj>` возвращает уровень тумана в точке объекта и используется в AI:
  `w_procs.tcl:138` и `raupe.tcl:68` (`< 10` → «объект в глубоком тумане, не действовать»),
  `infoobjs.tcl:100` (`> 100` → удалить точку появления троллей).
  После снятия чёрного тумана значения меняются — это может повлиять на поведение AI
  (например, на появление троллей). **Не проверено в игре** (адаптер, не факт).
* Снятие чёрного тумана означает, что карта целиком считается разведанной: скроллить
  и строить можно везде. Сюжетные «открытия» тумана при этом остаются в силе —
  это отдельные `FogRemover`/триггеры, они не отключаются.

### 7.2 Почему упал v10 (мой баг) и что исправлено в v11

Пользовательский прогон v10: игра вылетела. Разбор:

1. **Настоящая причина ошибки — мой баг в скрипте** (не краш как таковой).
   В `tclerrors.txt` записано:

   ```
   Error(2628):invalid arg count (2 expected)
       while executing
   "__nofog_orig_obj_query {Типы готовы}"
       ("eval" body line 1)
       invoked from within
       "eval [concat [list $nofog_orig_name] $args]"
       (procedure "load_info" line 4)
   ```

   Все обёртки хранили имя исходной команды в **общей глобальной переменной**
   `nofog_orig_name`. Пока `load_info` выполнялся, из него вызывался
   `obj_query` (пробник тумана) — вложенная обёртка перезаписала глобал, и
   внешняя обёртка `load_info` вызвала `__nofog_orig_obj_query {Типы готовы}`
   вместо `__nofog_orig_load_info`. Ошибка оборвала скрипт игры прямо в
   `systeminit` («Classes done»), т.е. инициализация осталась незавершённой.
2. **Сам краш** — AV `0xC0000005` в `atidxx32.dll` (драйвер видеокарты),
   сигнатура ровно та же, что и у фоновых крашей 23.11 01:57 / 02:01 / 02:26
   и 22.11 20:16 (до всей работы с туманом). Но спровоцировать его могла как
   раз незавершённая инициализация, поэтому изолировать их в одном прогоне
   нельзя.
3. В этом прогоне раскрытие тумана **не выполнялось**: в логе нет ни одной
   строки `set_fow_begin ok` — до уровня дело не дошло. То есть патч exe
   (см. §4.7) в этом прогоне **не был проверен**.

**Исправления в v11:**

* имя исходной команды пишется **в тело обёртки литералом**, общей
  глобальной переменной больше нет → вложенные вызовы не могут сломать друг
