# Ответ сессии «Освещение»: рендер поверхности, сетка высот 8×8 и порог на перепад

Дата: 2026-11-21. Источник: декомпиляция `Diggles.exe` (Ghidra, 11 373 функции),
данные `data/BlockDB0-2.BDB`, скрипты `data/Scripts`, `data/GameScripts`.

---

## 0. Короткий ответ на два вопроса

**В1. Рисует ли движок поверх меша блока ещё и сетку высот 8×8?**

**Нет.** Геометрии по сетке высот 8×8 в движке нет вообще. Видимая поверхность
земли строится **один квад на клетку** (4 угловые вершины в углах клетки),
текстура квада подбирается по 4 уровням углов из 81 пре-вычисленной текстуры.
Сетка высот 8×8 — это **логическая** карта (освещение, поиск пути, позиция
гномов, решение «нужна ли яма»), а не геометрия.

**В2. Есть ли порог на перепад (нужна ли стенка на перепадах меньше 2.0)?**

**Да, порог есть, и он ровно 2.0 клетки.** Геометрия «ямы/ребра» создаётся,
когда перепад высот **внутри клетки** (центральный отсчёт против углового)
**≥ 4 уровней = 2.0 клетки**. Меньше — никакой стенки, поверхность остаётся
простым квадом.

⚠️ Важное уточнение: порог применяется **не между соседними клетками**, а
**внутри одной клетки** — сравнивается центральный отсчёт (индекс 36) с
угловыми (0, 7, 56, 63) одной и той же сетки 8×8. Вертикальные стенки между
клетками — это **не** результат сравнения высот: они строятся из состояния
выемки (owner-байты), см. §5.

**Сетка высот 8×8 живёт в под-блоке**, а не в клетке:

```
под-блок (шаг 0x59):
  +0x00..+0x3F  64 байта = сетка высот 8×8, индекс = (y8&7)<<3 | (x8&7)

  +0x54        byte — **два 4-битных уровня углов** клетки: младший ниббл и старший
  +0x55..+0x58  хвост
```

Подтверждено эмпирически: в `BlockDB0.BDB` найдено 3244 таких под-блока,
значения сетки лежат в диапазоне **3…15** (мода 15 и 11), `+0x54` — 0…15.

## 2. Шкала высот (главное расхождение с вашим портом)

**Движок:** значение `v` (байт) — это **уровень**, а world-Z = **`7.0 + 0.5 * v` клетки**.

```c
// FUN_004c8220_004c8220.c:33,44  — два угла клетки из одного байта +0x54
local_c = (float)(*(byte *)(iVar4 + 0x54) & 0xf) * 0.5 + 7.0;   // младший ниббл
local_8 = (float)(*(byte *)(iVar4 + 0x54) >> 4)  * 0.5 + 7.0;   // старший ниббл
```

* диапазон world-Z: **7.0 … 14.5 клетки** (шаг 0.5), плоскость тумана/верх стен — **15.0**
  (`FUN_004cca20_004cca20.c:49` = `0x41680000` = 15.0f);
* за пределами карты `get_hmap` отдаёт `0xf` = 15 → Z = 14.5 (`CTclGlobalMethods__GetHMap_0062faf0.c:120-126`);
* **ваши значения z = 14.5 / 12.5 / 7.0 — это ровно уровни 15 / 11 / 0.**
  Значит ваши «116 / 100 / 56» — это `z*8`, ваша собственная шкала 1/8 клетки.
  **Оригинал грубее: шаг 0.5 клетки.** Уровней 16 на диапазон, а не 256.
* Проверка по скриптам оригинала: `get_hmap` сравнивается с `10`, `12`, `12.5`
  (`brut.tcl:465`, `Trigger_Tournament.tcl:303`, `Trigger_Tutorial.tcl:1462`) и
  используется как `+1.5` (`z_spare_procs.tcl:515`) — дробные величины в тех же
  единицах, что и уровень.

Горизонталь: адресация в **1/8 клетки**, `x8 = ROUND(x_cell * 8)`,
индекс отсчёта `(y8&7)<<3 | (x8&7)` (`FUN_004093f0_004093f0.c:21`).
Вершины геометрии, наоборот, в **координатах клеток** (`FUN_004c8220:99-102`,
`FUN_004c6b20:193-241`).

Разделение сеток (подтверждено): **8× — выборка высоты/уровня, 4× — рёбра**,
смешивать нельзя.

## 3. Как именно рисуется поверхность (ответ на В1)

### 3.1 Один квад на клетку

`FUN_004c8220(param_1, param_2)` — вызывается на каждую клетку:

```c
// FUN_004c8220_004c8220.c:99-104
local_24 = (float)param_1 + 1.0;    // x+1
local_30 = (float)param_1 + 0.0;    // x
local_20 = (float)param_2 + 1.0;    // y+1
local_2c = (float)param_2 + 0.0;    // y
local_28 = local_c;                 // Z угла (x,y)
FUN_00473300(&local_30, &local_24); // → (x, y, Z1) и (x+1, y+1, Z2)
```

Каждая клетка отдаёт **диагональную пару углов**: `(x, y)` с Z из младшего
ниббла `+0x54` и `(x+1, y+1)` с Z из старшего ниббла. Соседние клетки дают
остальные два угла — сетка получается непрерывной, а на клетку приходится
**2 треугольника**, а не 8×8 квадов.

Если все 4 соседа по owner непусты (участок выкопан), второй угол берётся
как `14.5` (`FUN_004c8220:94`).

### 3.2 Текстура — 81 пре-вычисленная, по маске углов

`GroundRenderer` (строки исходника в бинаре: `GroundRenderer.cpp`,
`GroundRenderer2`, `WallRenderer.cpp`):

* `FUN_004cde30_004cde30.c:59-112` — пре-компьют **81** текстуру: 4 уровня по
  3 значениям (0,1,2) = 3⁴ комбинаций;
* `FUN_004cd020_004cd020.c:40,146-147` — имя маски `ground/Msk_%c%c%c%c01.tga`
  (4 символа A/B по углам) и тайлов `ground/Gnd_%c%c%c.tga`;
* `FUN_004cd020:219-241` — **в рантайме смешиваются две текстуры** 64×64
  (4096 пикселей) по маске: `dst = mask*A + (255-mask)*B`;
* `FUN_004c4ae0_004c4ae0.c:49` — индекс текстуры:
  `((v5&3)*3 + (v4&3))*3 + (v3&3))*3 + (v2&3)`, плюс случайный выбор варианта
  из счётчика по индексу;
* `FUN_004c4c50_004c4c50.c:17,29,55` — 2-битный уровень каждого угла
  (`значение & 3`) → 4-битная маска → 16 масок на группу, 8 групп (A/B/C/kris/lava/…).

Файлы на диске это подтверждают: `data/Ground/Gnd_A01..C15.tga` (по 15 на группу),
`Msk_AAAB01..BBAB01.tga` (16 масок), `kris2_*/lava2_*/swf2_*/urw2_*` (16 вариантов
с 4-битными именами `0000..1111`).

**Итог: сетка 8×8 не превращается в вершины. Вершины — только в углах клеток.**

## 4. Порог на перепад — точное место и константа

`FUN_004ca830_004ca830.c:399-427` (зеркальные проверки — `:446-475`):

```c
uVar5 = (int)((uint)pbVar16[0x3f] - (uint)pbVar16[0x24]) >> 0x1f;   // |h(7,7) - h(4,4)|
iVar13 = ((uint)pbVar16[0x3f] - (uint)pbVar16[0x24] ^ uVar5) - uVar5;
joined_r0x004cb050:
  if (3 < iVar13) goto LAB_004cb1bf;              // |Δ| >= 4  → создать «яму»
...
if (((local_68 != 3) || (local_58 != 3)) ||
    (uVar5 = abs(pbVar16[7] - pbVar16[0x24]), abs < 4)) goto LAB_004cb110;
LAB_004cb1bf:
  FUN_004ca080(local_40, local_48, ...);          // "GetBlockHole" — геометрия ямы
```

* **Константа: 4** уровня (`3 < Δ` ⇔ `Δ ≥ 4`; `Δ < 4` → пропуск).
* Сравниваются: **центральный** отсчёт клетки (индекс `0x24` = 36 = (4,4)) и её
  **угловые** отсчёты (`0x00` = (0,0), `0x07` = (0,7), `0x38` = (7,0), `0x3F` = (7,7)).
* Единица — уровень (0.5 клетки) ⇒ **порог = 4 × 0.5 = 2.0 клетки**.
* Второе, не связанное с этим число: `FUN_004ca830:341` — `local_64 < 11.0`
  (уровень угла < 11 → не рандомизировать вариант текстуры).

**Ответ на ваш вопрос: ваша гипотеза «нужна стенка на перепадах ≥ 2.0»
подтверждается численно — но стенка/яма возникает при перепаде ≥ 2.0 клетки
внутри клетки, а не между соседними клетками.**

## 5. Вертикальные стенки: не от высот, а от выемки

`FUN_004c6b20_004c6b20.c` (построитель стен, буфер `in_ECX+0x1368/0x1370`,
тип отрисовки 10 — `FUN_004c6030_004c6030.c:32`):

* вершины в **координатах клеток**: `(x, y)`, `(x+1, y+1)` и т. п. (`:193-241`);
* **низ** стенки: `local_14 = (float)(*(byte *)(iVar10 + 0x54) & 0xf) * 0.5 + 7.0` (`:173`);
* **верх** стенки: `0x41680000` = **15.0** (`:202,214,228,241`);
* условие появления стенки — **owner-байты** соседей (`cell+0x34[owner]`) и
  различие индексов под-блока у соседей (`:37-145`), т. е. **выкопан ли участок**;
* если все 4 соседние клетки имеют материал 3 (порода) — низ стенки
  опускается в `-14.0` (`:175-182`), чтобы стенка не выглядела вырезанной.

Т. е. «стены = перепад высот» в оригинале **неверно**: вертикальные поверхности
строятся из состояния выемки/материала, а высоты лишь задают, где стоят углы.

## 6. Влияние на ваш порт (Godot)

1. **Шаг высоты — 0.5 клетки, а не 1/8.** Если в вашем порте Z хранится как
   `z*8`, у вас в 4 раза больше градаций, чем в оригинале. Можно оставить
   (визуально гладче), но при сравнении с оригиналом помните: оригинальный
   уровень = `round((z_cells - 7.0) * 2)`, диапазон 0…15.
   ⇒ 14.5 клетки = уровень 15, 12.5 = 11, 7.0 = 0.
2. **Меш поверхности — 1 квад (2 треугольника) на клетку**, вершины в углах
   клеток, Z = `7.0 + 0.5*уровень`. Ваша «сетка высот 8×8» как геометрия —
   это **лишнее**; оставьте её как логическую карту (именно её использует ИИ,
   свет и расчёт опоры).
3. **Порог 2.0 клетки** применять к разнице «центр клетки vs угол клетки» —
   не между клетками. В Годоте это проверка на *внутриклеточном* перепаде.
4. **Текстура земли** в оригинале — рантайм-блендинг двух тайлов по 4-угольной
   маске (`Msk_XXXX01.tga`), 64×64. У вас в порту, если вы рисуете «текстуру
   по 3D-блокам», этого блендинга, вероятно, нет — и в этом разница с оригиналом.
5. Текстуры земли в оригинале: `data/Ground/Gnd_<группа><NN>.tga` (A/B/C × 15),
   `Msk_XXXX01.tga` (16 масок) — это то, чем сейчас пользуется оригинальный
   рендер; если вы их не используете, стыки будут выглядеть иначе.

## 7. Что осталось неизвестным (честно)

1. **Не доведена цепочка «уровень байта → world-Z»** в логических функциях:
   `FUN_00424120_00424120.c:57,71,89,107` сравнивает байт с world-Z запроса
   напрямую и возвращает байт как Z (`in_ECX[2] = (float)bVar6`), тогда как
   рендер использует `7.0 + 0.5*v`. То есть внутри движка есть два соглашения,
   и в каких единицах отдаёт Z наружу `ground_pos`/`get_hmap` — не проверено
   до конца (скрипты используют и целые, и дробные пороги).
   ⇒ **Проверяемый тест:** взять любую карту, распечатать `get_hmap` и сравнить
   с `ground_pos` в той же точке.
2. Точный смысл 2-битного «уровня» (`значение & 3`) в маске текстуры: он
   используется как A/B-сторона маски (`FUN_004cd020:121-134`), но порядок
   «выше/ниже» по нему явно не монотонен.
3. Семантика выбора зоны в `sm_draw_stone -exlimit` не разобрана.
4. Генерация геометрии меша из блоков `.3db` (`FUN_0058a8b0`, `FUN_00590040`)
   разобрана частично: `FUN_0058a8b0` — это **выбор варианта блока** по
   прямоугольнику материальной сетки (не построитель меша), `FUN_00590040` —
   resize-хелпер `DSFastArray`.
5. Текстуры `GroundRenderer`/`GroundRenderer2` (`FUN_0047f440`, `FUN_00480720`)
   строят 9×9-меши с анимированными волнами — **не рендер карты** (не ссылаются
   на `DAT_0077241c`).
