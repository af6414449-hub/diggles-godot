## 0. ПОПРАВКА к моему прежнему ответу (важно, меняет ответы на вопросы 1 и 2)

Я раньше написал: «`cell+0x08` = uint, 4 бита × 8 направлений; `cell+0x34` = char[8], декор на направление».
**Это неверно.** Индекс слота 0..7 — это **owner id (id клана)**, а не направление.

Три независимых доказательства:

1. `CTclGlobalMethods::IsDigMarked` (0x650a50, стр. 240):
   ```c
   local_28 = *(undefined4 *)(DAT_00772400 + 100);            // owner игрока
   ...
   if ((*(uint *)(iVar4 + 8) >> ((char)local_28 * '\x04' & 0x1fU) & 0xf) != 0) { uVar8 = 1; }
   ```
   `is_dig_marked` проверяет ниббл с индексом = **owner игрока**.
2. `CTclGlobalMethods::DigApply` (0x6347a0) → `FUN_00596b80`:
   ```c
   uVar1 = *(undefined4 *)(param_2 + 0x36c);   // owner гнома
   bVar10 = (char)uVar1 * '\x04';              // сдвиг ниббла
   ```
   Поле `+0x36c` — это owner: его пишет `CTclObjMethods::SetOwner`
   (`*(int *)(iVar4 + 0x36c) = iVar7;`) и читает `CTclObjMethods::GetOwner`.
3. `dig_mark`: первый Tcl-аргумент — owner id, и движок использует его именно как индекс слота.
   В скриптах ИИ туда кладут id клана: `std_ai.tcl:3036`
   `dig_mark $owner [lindex $point 0] [lindex $point 1] 1`, где `$owner` — параметр
   `proc analyze_world {center xdim ydim owner placeneed igcount}`.
   В оригинале owner совмещён с индексом слота (DigMark отбрасывает индекс > 6).

**Следствие:** в записи клетки нет **никаких** «8 направлений». Направление в движке как сущность
не хранится — оно вычисляется из сетки высот.

## 1. Актуальная раскладка записи клетки

Размер записи **0x7C = 124 байта**, доступ через `idx * 0x7c + *(int *)(map + 0x14)`.

| Смещение | Тип | Содержимое |
|---|---|---|
| +0x00 | int32 | индекс ПОД-БЛОКА ВЫСОТ (в таблице под-блоков карты) |
| +0x04 | uint16 | индекс объекта в клетке (0xFFFF = нет) |
| +0x07 | uint8 | служебный байт заголовка |
| +0x08 | uint32 | 8 нибблов, индекс = **OWNER** 0..7: код грани/выемки для клана |
| +0x0C | uint32 | 8 нибблов, индекс = **OWNER** 0..7: ТИП грани (4 бита) |
| +0x13 | uint8 | флаги: бит0 (0x01) = «высота изменилась» (dirty), бит1 (0x02) = «выкопано», бит2 (0x04) = «просмотрено» |
| +0x18 | uint16 | биты 0-1 = МАТЕРИАЛ, биты 2-15 = прочие флаги |
| +0x34 | uint8[8] | индекс = **OWNER**: ещё один байт на слот (смысл не разобран) |
| +0x3C | uint8[64] | **СЕТКА ВЫСОТ 8×8 клетки** (1 байт на 1/8 клетки) |

Проверка размера: `0x3C + 64 = 0x7C` — ровно конец записи.

## 2. Вопрос 2 — что кодируют 4 бита на слот в +0x08 и +0x0C

### +0x08 — «код грани/выемки» для клана

Запись (FUN_005671a0, режим `dig_mark` mode 0):
```c
cell[8] = (value | 8) << (slot * 4) | cell[8] & ~(0xF << (slot * 4));
```
`value` клампится в 0..3.

Разбор ниббла (индекс = owner):

| Бит | Значение | Смысл | Где ставится |
|---|---|---|---|
| 3 (0x08) | всегда 1 | «грань существует / граница клана активна» | FUN_005671a0, загрузчик блоков FUN_00567cb0 |
| 2 (0x04) | метка | «здесь назначена точка копания» | FUN_005981d0: `cell[8] |= 4 << (slot*4)` |
| 1..0 | 0..3 | класс копаемости → требуемая сила гнома 0 / 3 / 7 / 11 | FUN_00596b80: `cost = (nibble & 3) * 4 - 1` (класс 0 → 0) |

Особые случаи в FUN_00596b80: ниббл == 0 → cost 15 (копать нечего); бит 3 сброшен → cost 11.

**«Стена» для рендера** — `CMapBeautifier::ScanAtPos` (0x58b130, стр. 178):
```c
uVar7 = *(uint *)(cell + 8) >> (owner * 4);
if (((uVar7 & 8) == 0) && ((uVar7 & 0xf) != 0)) { /* клетка = СТЕНА для owner */ }
```
То есть бит 3 = 1 → «грань пробита/открыта», бит 3 = 0 и ниббл ≠ 0 → «стена».

### +0x0C — «тип грани» (из какой породы/минерала)

```c
cell[0xC] = ((this->0xb4 & 0xF) << (slot * 4)) | (cell[0xC] & ~mask);
```
Значение берётся из поля `+0xb4` объекта-«менеджера выемки» (`DAT_0077240c`) и пишется в слот того же owner.

Смысл доказан в FUN_00597b20 (реализация `dig_next`):
```c
uVar3 = *(uint *)(cell + 0xc) >> (owner * 4) & 0xf;
if ((param_5 == 0) || (uVar3 == local_30)) { ... }   // local_30 = *(uint *)(gnome + 0x250)
```
т.е. **тип грани должен совпасть с «типом цели» гнома** (`gnome+0x250`, записывается в FUN_00596b80).
Тип 0..15 = из какой породы/минерала сделана грань; гном копает только грани своего типа
(это ограничение спец-инструмента «Кристаллstrahl»).

### dig_mark — точный контракт (0x6586c0; порядок аргументов — по дизассемблеру, Ghidra тут путает слоты)

- argv[1] = **OWNER** (индекс слота), argv[2] = x, argv[3] = y, argv[4] = mode, argv[5] = value.
- **mode 0** → записать `(value|8)` в `+0x08[owner]` и `(manager->0xb4 & 0xF)` в `+0x0C[owner]`; value клампится 0..3.
- **mode 1** → записать `3` в `+0x08[owner]` (FUN_005672d0), только если FUN_00566870 подтверждает «край».
- **mode 2** → **очистить** ниббл `+0x08[owner]` (снять заявку).
- Индекс слота ограничен 0..6 (`cmp eax,6; ja`).

### Важное уточнение к твоему выводу

Ты написал: «per-direction коды граней из выгрузки не берутся в принципе, их пишет рантайм при выемке».
Верно, что их нет в выгрузке, но причина другая:
- per-direction кодов в движке **нет вообще** (есть per-owner коды заявок на выемку);
- эти коды пишутся **при загрузке карты из блоков**, а не при выемке: `FUN_00567cb0` читает байт из
  таблицы блока и вызывает `FUN_005671a0(x, y, code, slot)` для всех клеток блока (код 4 пропускается);
- выемка их, наоборот, **чистит**: после копки снимаются все нибблы, для которых требуемая сила выше силы гнома.

## 3. Вопрос 3 — признак выемки

**Отдельного «кода материала выемки» в движке нет. И в +0x18 отдельного бита выемки нет.**

- **Материал (+0x18) при выемке НЕ меняется.** Единственный писатель битов 0-1 в +0x18 —
  `FUN_005fc9d0` (генератор уровня / SM):
  ```c
  uVar1 = *(ushort *)(iVar2 + 0x18) & 3;
  if ((uVar1 != 3) && (uVar1 != 0)) {
      uVar3 = FUN_0049c670();                       // rand()
      if ((float)(uVar3 & 0x7fff) <= local_40 * 32768.0) {
          *(ushort *)(iVar2 + 0x18) = *(ushort *)(iVar2 + 0x18) & 0xfffc | (ushort)param_6;
      }
  }
  ```
  Функция в начале делает `param_6 = 1 ↔ 2` (swap). То есть это **рандомизация «грунт vs камень» с
  градиентом по расстоянию** и только для клеток, у которых материал **уже** 1 или 2.
  Материалы 0 и 3 не трогаются никогда.
- Это согласуется с ИИ оригинала: `std_ai.tcl:2991` → `if {$m==0||$m==3} {set rock 1}` —
  0 и 3 = порода (не копается), 1 и 2 = копаемо. Ровно то, что ты нашёл в данных главы.
- **Признак выемки есть, но в другом поле — байт флагов `cell + 0x13`:**
  - бит 0 (0x01) = «высота изменилась» → dirty, перестроение меша. Ставится в FUN_00596b80,
    `CTclGlobalMethods::LGMarkArea`, FUN_005992b0; **читается в 4 местах**
    (FUN_00583c60, FUN_005848b0, FUN_0058a510, FUN_006475d0).
  - бит 1 (0x02) = «выкопано». Ставится в FUN_00596b80 сразу после успешной выемки:
    `*(byte *)(iVar5 + 0x13) = *(byte *)(iVar5 + 0x13) | 2;`
    В exe **нигде не читается** (проверены все чтения `0x13 & ...`) — служебная метка.
  - бит 2 (0x04) = «просмотрено» (FUN_005791a0 — сборщик перестраиваемых клеток; сброс: FUN_0057c6e0 `& 0xFB`).
- **Сама выемка = понижение пола.** `FUN_00596b80` меняет `cell[0x00]` (индекс под-блока высот)
  у выкопанной клетки и 3 соседей, попутно ставя `cell[0x13] |= 1`.

**Итог:** выемку несёт **высота** (понижение пола) + служебные биты в `cell+0x13`.
Твой вывод верен, и его стоит записать в отчёт как **факт, а не адаптер**:
«портовый подход "стены = перепад высот" совпадает с оригиналом».
Две поправки к формулировке:
  (а) движок держит высоту с разрешением **8×8 на клетку**, а не одной высотой на клетку;
  (б) «стена» в движке — не флаг, а сам перепад (вертикальная плоскость между соседями с разной высотой).

## 4. Вопрос 1 — диагональные рёбра

**Самостоятельных 45-граней в модели движка нет.**

- Направление нигде не хранится (см. §0). Геометрия строится из сетки высот.
- Стены — вертикальные плоскости между клетками/суб-единицами с разной высотой.
  Меш собирается из сетки высот: `FUN_005906a0` читает байты высоты 4 соседних клеток по углам
  (`bVar1 = *(byte *)(((uVar18 & 7) << 3 | uVar15 + 2 & 7) + subblock)`) и строит стенки;
  `FUN_0046b450` сравнивает 4 угловые высоты ячейки (равенство всех четырёх → плоский квад).
- Сглаживание углов — в `CTclGlobalMethods::GroundPos` (0x635c00): при поиске точки опоры
  сравниваются высоты **диагональных** соседей,
  `bVar9 = ~((local_55 & local_86) >> 1) & 1` — «не гладкий угол», поиск идёт дальше.
  То есть диагонали учитываются как **соседи при сглаживании опоры**, но отдельной 45°-грани нет.
- То, что я раньше назвал «декором на направление» (`cell+0x34[8]`), на самом деле индексируется
  **owner-ом**: `FUN_005671a0` читает `cell[0x34 + slot]`, где slot — тот же owner-индекс.
  Это второй байт на слот клана, а не на направление. Точный смысл не разобран — помечаю как открытое.

**Про твои 40 уступов с диагональным нижним ребром:** движок не рисует на них 45-грань.
В его модели стена стоит там, где есть перепад высот между соседними отсчётами сетки 8×8;
диагональный скос уступа — это просто перепад, разложенный на вертикальные плоскости по сетке.

## 5. Вопрос 4 — где лежит высота и кратность сетки

### Где

Высоты нет в первых 0x18 байтах. Точнее:

- `cell + 0x00` = **int32 индекс под-блока высот**. Под-блок = **0x59 байт**, лежит в блоке высот
  карты (`map + 0x24` → дескриптор, `+0x10` = база, `+0x14` = число под-блоков).
  Первые 64 байта под-блока = та же сетка высот 8×8 (1 байт на 1/8 клетки).
  `+0x40/+0x44/+0x48/+0x4C` = индексы под-блоков-соседей для 4 «типов углов» (выбираются при копке,
  FUN_00596b80); хвост до 0x59 — остальное.
- `cell + 0x3C` = **копия** этой же сетки 8×8 в самой записи клетки (`0x3C+64 = 0x7C`).
  Её читает `GroundPos`: `uVar12 = (x&7) | ((y&7)<<3); local_56 = *(byte *)(uVar12 + 0x3c + cell);`
- Чтение высоты: `FUN_004093f0(engine_x, engine_y)`:
  ```
  x>>3, y>>3                -> клетка
  sub = cell[0x00]
  base = sub*0x59 + block->0x10
  byte = base[ ((y&7)<<3) | (x&7) ]
  ```
  **Знак оси: +x = младший индекс (0..7), +y = старший (0..7)** — подтверждено и GroundPos:
  `local_84 = (y&7)<<3; uVar12 = (x&7) | local_84;`

### Кратность сетки

**8 единиц движка на клетку, а не 4.** `CTclGlobalMethods::GetHMap` (0x62faf0) переводит координаты Tcl:
`ROUND(x*8.0)` / `ROUND(y*8.0)` → единицы движка, затем `FUN_004093f0`.
Высота отсчитывается на каждой из 8×8 = 64 позиций внутри клетки.

Отсюда по твоему вопросу про 512×640 → 2048×2560:
- движок мельче не в 4 раза, а **в 8 раз** по X/Y (8 суб-отсчётов на клетку), и высота сэмплится в этих
  64 точках на клетку;
- твоя модель с 4× — в 2 раза грубее движковой.

**По статусу твоей правки (адаптер vs реконструкция):**
- твой переход 14.5 → 12.5 за 0.25 клетки = **2 движковых суб-отсчёта** (0.25 = 2/8), т.е. он попадает
  ровно на границу между отсчётами сетки 8×8 → вертикальная грань встаёт туда же, куда движок ставит
  свою стену;
- **но** есть предостережение по шкале Z: высота в движке — **один байт, целое число** в тех же единицах,
  что и мировые координаты (`get_hmap` возвращает этот байт, и скрипты используют его прямо как z:
  `lrep sp 2 $sh`, `get_hmap $x $y > $checkpoint`, где `checkpoint = z + bboxz - 1.0`; типичные значения
  грунта в скриптах 10..15). Значит **полуцелых высот 12.5 / 14.5 в движке быть не может** — они
  соответствуют целым 12/13 и 14/15 (или, если твоя единица z вдвое мельче движковой, то 25/29 —
  это одна эмпирическая проверка: взять любую свою клетку 14.5 и сравнить с `get_hmap` в оригинале).
- вывод: **приведение стен к высотам — реконструкция, а не адаптер**, при условии что шкала z совпадает;
  и при условии, что стены у тебя выводятся из перепада высот **по той же сетке 8×8**, а не по своему
  4× (иначе разъезд на уступах будет).

## 6. Что осталось неизвестным

- Точный смысл байта `cell+0x34[owner]` (второй байт на слот).
- Четыре «типа углов» в под-блоке высот (`+0x40..+0x4C`) — как выбираются при копке.
- Точная шкала Z (целое в байте; соотношение с твоими 14.5/12.5 — требует одной проверки).
- Как именно сетка 8×8 превращается в меш (FUN_0058a8b0, FUN_00590040, FUN_005906a0) — разобрано
  чтение высот, не генерация геометрии.
