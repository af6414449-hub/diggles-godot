# Diggles / Wiggles (2001–2002): техническое исследование рендеринга и производительности

**Дата исследования:** 19 ноября 2026 г.  
**Цель:** доказательная база для самостоятельной реализации игры на Godot 4, в том числе для слабых ПК и мобильных устройств.  
**Ограничения:** использованы только открытые публикации, документация, архивные материалы и сообщения авторов инструментов. Исполняемый файл игры, игровые ресурсы и проект порта не исследовались, профилирование игры не выполнялось.

## Render architecture evidence

### 1. Краткое резюме

Предпосылку о том, что Wiggles стабильно и плавно работала на типичном компьютере 2001 года, необходимо скорректировать. Технические тесты того времени сообщают о серьёзных требованиях к процессору, памяти и диску, рывках при прокрутке и анимации. Оригинальный движок всё же содержал целый набор конкретных оптимизаций, позволявших ему обслуживать большую изменяемую карту и тысячи игровых объектов: разделение активной и пассивной логики, кэширование байткода, управление частотой обработки объектов, отложенная загрузка текстур, регулируемая детализация и инструменты профилирования.

**Шкала надёжности:**

- **A — высокая:** непосредственное описание разработчика либо публичный технический интерфейс движка (для интерфейса подтверждается наличие команды, но не её внутренний алгоритм).
- **B — хорошая:** измерение или наблюдение очевидца эпохи релиза, либо официальный материал переиздания. Не переносится автоматически на другие версии.
- **C — средняя/низкая:** опыт моддера или пользователя, ретроспективные данные, регистрационные ключи без эксперимента. Нужна перепроверка на оригинальном билде.
- **H — гипотеза:** инженерная интерпретация или предлагаемая реализация, не исторический факт.

### 4. Самые сильные доказательства: оптимизация симуляции

Источник всего подраздела — собственный технический доклад разработчика [Carsten Orthbandt, Game Scripting with Tcl, 7–8 июня 2001 года, с. 117–126](https://www.eurotcl.eu/presentations/EuroTcl2001-AllPresentations.pdf#page=117). Доклад предшествует релизу; он раскрывает архитектуру разрабатываемой игры, но не доказывает неизменность каждого параметра в релизном EXE.

| ID | Что подтверждено | Точное место в докладе | Применение / надёжность |
|---|---|---|---|
| R11 | Для объекта хранились позиция, ориентация, скорость и состояние анимации. В C++ реализованы простые действия, Tcl формирует сложное поведение. | §3.1, Wiggles game objects | **A.** Хранить состояние отдельно от визуального представления; actions как короткие операции native API/систем. |
| R12 | Активный экземпляр создавал независимый Tcl-интерпретатор. Накладные расходы составляли примерно 35 КБ на интерпретатор, при тысячах объектов это стало проблемой. **Это не число видимых на экране объектов.** | §3.4.1, §3.4.3, Performance considerations | **A.** Плотные структуры данных для массовых предметов и декораций; не создавать дорогой runtime для каждого камня. 1000×35 КБ ≈35 МБ — оценочный порядок расходов, не измеренная суммарная память. |
| R13 | Классы без обработчиков/методов автоматически создавались без индивидуального интерпретатора, с установленными в классе значениями по умолчанию. Разработчик называет их «dumb» objects. Другие активные объекты могли с ними взаимодействовать. | §3.4.3 | **A.** Пассивный предмет остаётся адресуемым ID и участвует в подборе/коллизии, но не выполняет свою логику каждый кадр. |
| R14 | Чтение/компиляция сценариев при каждом создании объекта приводили к падению производительности. Добавлен кэш предварительно обработанного и скомпилированного Tcl; более 250 файлов классов. Доля попаданий выше 80% на старте и выше 99% спустя несколько минут. | §3.2.2, Bytecode cache; фрагмент «>99% after a few minutes» | **A.** Кэш класса, общих Mesh/Material/AnimationLibrary/Resource. Не загружать и не разбирать ресурсы при каждом спавне. |
| R15 | Событие запускает действие, обработку текущего состояния можно выключить до завершения. C++ выполняет анимацию, ходьбу, простое ожидание. Есть отдельные обработчики нормального и ошибочного завершения. | §3.4.1, Class properties | **A.** Событийная FSM: выполнение команды не требует переоценивать весь план на каждом кадре. |
| R16 | Счётчики времени выполнения встроенных команд, обработчиков состояний, событий и методов собирались и выгружались в текстовый файл после завершения. В debug-сборке использован макрос `TCLTRACE()`; сложные обработчики переносили в процедуры ради оптимизации байткода. | §3.4.2–3.4.3 | **A.** Ввести собственные счётчики стоимости систем с агрегатами *count / total / max* и запись CSV; оптимизировать измеренные горячие участки. |
| R17 | Интерфейс игры написан на C++, а не Tcl. Имелись встроенная командная оболочка и веб-сервер для удалённой диагностики. | §3.6, §4.3 | **A.** Встроенная debug-панель для Godot; UI обновляет данные по уведомлениям, без обхода всей колонии при каждом кадре. |

Доклад не является описанием GPU-конвейера. Его ценность — прямое объяснение того, как разработчики боролись с нагрузкой со стороны объектов и игровой логики.

### 5. Архив интерфейса движка: земля, свет, частицы, загрузка

Архив [Wiggles Tcl Commands](https://wiggles.ruka.at/tipstricks/wiggles_tcl.html) — особенно ценный технический материал. Его можно искать по приведённым далее именам. Доклад Ортбандта (§3.4.2) независимо сообщает об утилите разработчиков, генерировавшей HTML-документацию встроенных Tcl-команд из комментариев C++. Архив по структуре соответствует этому классу документации; точный билд и происхождение копии не установлены. Это свидетельство о доступном API, а не листинг реализации renderer-а.

## Concrete Godot optimizations

Это проектные решения для Godot 4, а не требования к исторической точности внутренней реализации.

### 1. Архитектура минимального прототипа

```text
WorldData (материалы/глубина/вода/свет/видимость, данные объектов)
  -> simulation scheduler (AI, события, задачи, экономика)
  -> dirty chunk queue (земля, локальные коллизии, навигация)
  -> render proxies (сцены/меши только там, где нужны)
  -> Camera3D + UI (самостоятельные FPS и масштабирование)
```

**P0 — обязательные решения первого прототипа**

1. Мир: плоское логическое представление X/Y с глубиной для визуального 3D. Хранить редактируемую землю компактными массивами, отдельно материал, проходимость, освещение и разведанность. Не создавать Node3D для каждой клетки.
2. Чанки геометрии: тестировать 16×16, 32×32, 64×64 логических клеток; стартовый кандидат 32×32. Копание помечает грязным затронутый chunk и соседей, если затронута общая граница. Перестройка только этих мешей с отложенным обновлением коллизий и навигационного графа. Это современные параметры эксперимента.
3. Пассивные предметы: запись в WorldData + id, тип, позиция, количество, flags; отдельная активная сцена лишь там, где требуется физика или сложная анимация. Взаимодействие — через запрос к реестру. Помнить, что предмет за границей экрана может быть целью работы.
4. Диспетчер: один центральный планировщик, несколько очередей задач по сроку и приоритету. Ближайшие/работающие AI обновляются чаще, дальние косметические состояния — реже. Критические сроки еды, сна, производства и нападения продолжают работать вне камеры.
5. Камера: 3D-рендер с боковым обзором, управляемый зум/наклон. Дальние декорации без навигации/физики. Вычислять ограниченную видимую область с запасом; рендер и симуляция имеют разные критерии активности.
6. Освещение: базовая темнота + локальное поле RGB в данных мира, обновляемое после изменения источника или стены. Для художественной проверки добавить ограниченное количество OmniLight3D без теней на весь экран; источник может мерцать изменением яркости/эмиссии. Тени сначала точечные, только у важных объектов, либо дешёвые контактные пятна. Туман войны хранить отдельно.
7. Рендерер: начать с Compatibility для слабых ПК/широкой совместимости, сравнить с Mobile на подходящем устройстве; не требовать Forward+ и глобальное освещение в минимальном профиле. Подбирать renderer исходя из измерений и особенностей целевых устройств.
8. Плавность: фиксированный шаг симуляции и физики, визуальная интерполяция. Маркеры удара киркой/подбора синхронизировать с временем действия, а не с количеством отрисованных кадров. Само действие не должно выполняться дважды при низком FPS.

| Система | Реализация | Критерий проверки |
|---|---|---|

### 2. Начальные бюджеты для прототипа (не исторические!)

Это стартовые значения для проверки, а не обещания быстродействия. Размер карты в клетках и аппаратные пределы ещё предстоит выбрать. Не смешивать условную карту 4×4 областей с историческим размером карты Diggles.

| Метрика | Начальная цель |
|---|---|
| Render FPS | 60 на среднем устройстве, устойчивые 30 на минимальном |
| Frame time | 16,67 мс при 60 FPS; 33,33 мс при 30 FPS |
| 3D internal render scale | 1,0 / 0,75 / 0,5 (при сохранении разрешения UI) |
| Фиксированный основной simulation step | 20 Гц как первый эксперимент, движения визуально интерполируются; коллизия по отдельному шагу при необходимости |
| Частота дорогих вторичных AI-проверок | 2–5 Гц в фоне, 5–10 Гц рядом; отдельные события немедленно |
| Тестируемые чанки | 16² / 32² / 64² клеток |
| Перестройка мешей | Не более 1–2 небольших чанков за кадр в первом тесте; лимит заменить временем (например 2 мс), если профилирование выявит пики |
| Пассивные объекты | 1 000, 5 000, 10 000 записей в данных |
| Активные персонажи | Стресс-сцены 16, 64, 128; проверить реальные целевые числа отдельно |
| Свет и FX | По крайней мере три уровневых теста плотности; не ухудшать читаемость при отключении косметики |

### 3. План профилирования

Каждый сценарий проводить на одинаковом seed, маршруте камеры, пресете, длительности, отдельно на минимальном и среднем устройстве. Собирать p50/p95/p99 времени кадра (не только средний FPS), максимальный кадр, CPU/GPU frame time, draw calls, rendered objects, primitives, используемую память, число активных AI, длину очередей перестройки чанков и запросов пути.

| Сценарий | Что изменить при повторе | Диагностический вывод |
|---|---|---|
| пустая карта / много пассивного декора | обычные nodes vs data-only + MultiMesh | Стоимость экземпляров и draw calls |
| плотная колония в пределах одного экрана | число персонажей и rate AI | CPU, skeleton animation, сценарная логика |
| панорама по карте | внутреннее разрешение, LOD, range | GPU, overdraw, появление ресурсов |
| одновременное копание | размер чанка, лимит dirty queue | Пики геометрии, коллизий и pathfinding |
| множество костров/факелов/частиц | тени off/on, число источников, FX scale | Light/shadow passes и прозрачность |
| переход в необследованную область | cold vs warm, eager vs lazy loading | Стоимость IO, инстанцирования, распаковки |
| закрытые туманом и видимые поселения | частота фоновых AI, рендер | Независимые расходы симуляции и графики |
| сохранение/загрузка большого мира | число объектов и размеры карты | Время сериализации, рост памяти, stalls |

Правило интерпретации: ускорение при снижении внутреннего разрешения — аргумент в пользу GPU/fill-rate bottleneck, но проверить CPU/GPU профили. Плохая частота кадров при почти неизменном GPU времени и росте активных объектов — повод проверять AI/навигацию/анимацию. Редкие длинные кадры при движении камеры — повод отдельно проверить загрузку ресурсов и обновление геометрии. Ни один признак сам по себе не доказывает причину.

## Unsupported assumptions

Следующие утверждения не удалось доказать по доступным открытым материалам.

| Вопрос | Что известно | Не утверждать без дополнительных данных |
|---|---|---|
| Конкретная версия Direct3D оригинала | DirectX 8.0 в опубликованных требованиях, отдельно ретроспективная запись о D3D7 | Что рендерер оригинала использовал именно DX8 API или исключительно D3D7 |
| Фактический FPS на минимальном ПК | Качественные категории GameStar, сообщения о рывках | 30/40/60 FPS, точный встроенный cap, гарантированная плавность |
| Количество объектов | Доклад говорит о тысячах игровых объектов в целом; есть счётчики | Лимит на активные/видимые объекты, число гномов, максимальные полигоны/кадр |
| Полигональный бюджет моделей | Известны сторонние парсеры 3DB | Число полигонов одного гнома, число костей, нормали всех типов моделей |
| Динамический LOD | Параметр детализации и режимы качества | Наличие расстояний переключения LOD, автоматической редукции полигонов |
| Устройство карты | Координатные области, материалы, слой текстур, генерация шаблонами | Фиксированные render chunks, их ширина, структура quadtree, voxel mesh, алгоритм marching squares |
| Culling | Видимость и туман управляются отдельно, API поиска видимых объектов | Какой-либо конкретный frustum/portal/PVS/occlusion алгоритм оригинала |
| Свет | Координатное поле яркости/цвета, объектные источники и настройка теней | Световые карты GPU, конкретная сетка lmap, stencil shadows, shadow maps, CPU vertex lighting или GI |
| Частицы | Число/дальность/видимость и временные источники на уровне API | GPU/CPU реализация, точные лимиты для всех типов и состав particle batching |
| Вода | Источники воды и влияние препятствий | Реальные отражения, физический solver, фиксированная частота обновления, алгоритм волн |
| Загрузка | Lazy texture loading и буфер объектов | Background streaming, отдельный IO thread, LRU, размер текстурного кэша, порядок освобождения |

| Патчи оригинала | Известны номера и адреса release notes | Конкретные исправления FPS, памяти или света в 1.0.707/814/844 без текста |

### Приоритет дальнейшей проверки без доступа к проекту

1. Получить читаемые архивные release notes с Developer-копии, не устанавливая игру.
2. Найти исходный HTML-архив встроенных команд с датой/версией генерации и описание карты света.
3. Проверить исходники парсеров .3db: структуру вершин, индексов, материалов, кадров/костей, вариантов объектов; отдельно статус лицензии. Без разрешённых моделей не сообщать реальные статистики.
4. Найти скриншоты встроенной Performance-панели и оригинальные логи PerfStats/AnimStats, привязанные к версии и аппаратуре.
5. При будущем доступе к законной оригинальной копии — снять DX API trace и измерить FPS при изменении настроек, количество объектов/полигонов, память, свет и пики загрузки. Сейчас эти измерения не выполнены.

**Вывод для порта:** наиболее надёжно воспроизводить не предполагаемый рендер-конвейер 2001 года, а доказанные принципы работы: дешёвые пассивные объекты, общие ресурсы, событийная логика, управляемая частота обработки, локальные операции над картой, ограниченные эффекты и измеряемая производительность. Архитектуру GPU/чанков проектировать под Godot и проверять экспериментально, не выдавая её за реализацию оригинала.
