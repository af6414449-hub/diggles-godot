# Diggles / Wiggles: сетевой режим и мультиплеер

Дата исследования: 19 ноября 2026 г. Объект: оригинальные Wiggles (2001) / Diggles: The Myth of Fenris (2002), остатки сетевого режима и позднейшие эксперименты. Исследование только публичных материалов; оригинальные файлы, исполняемый код, сетевой трафик и проект Godot не исследовались.

**Главный вывод:** сетевой режим существовал в разработке, но официально выпущенная игра была одиночной. Доклад руководителя разработки от июня 2001 подтверждает возможность превращения методов игровых объектов в удалённые вызовы. Документация команд дополнительно подтверждает предусмотренную отправку карты клиентам и расчёт сетевых стартовых позиций. Полноценная спецификация сетевого протокола и функционирующий оригинальный матч не обнаружены. Фанатский мод 2024–2025 — отдельная реконструкция, а не доказательство протокола SEK.

Шкала: **высокая** — прямое техническое свидетельство или независимые тесты релиза; **средняя** — опубликованный эксперимент, пересказ или задокументированная возможность без проверки исполнения; **низкая** — косвенное воспоминание; **неизвестно** — достаточного подтверждения нет. Наличие API не означает доступности функции в релизном интерфейсе.

#### Фанатский Wiggles Multiplayer Mod v0.1 (phantom)

Первичный источник: [пост v0.1, 02.03.2024](https://wiggles.ruka.at/forum/viewtopic.php?p=4208). Автор описывает TCP между двумя копиями игры, настройку через `setupmpconnection.tcl`, отправку событий Tcl и изменённую библиотеку Tcl. Приём проверялся с интервалом 200 мс. Это интервал опроса мода, **не частота сетевого тика оригинала**. Автор предупреждает, что полноценная игра на этом этапе невозможна.

Порядок экспериментального запуска по автору: установить файлы мода рядом с Wiggles.exe, прописать IP второй копии в setupmpconnection.tcl, для одного клиента включить задержку старта 20 секунд и запустить его заранее, затем одновременно загрузить одинаковое сохранение на обеих машинах. Это историческая процедура альфы, не гарантированная инструкция для текущего переиздания. Не проверена совместимость версий.

Автор приводит два вспомогательных Java-проекта: [WigglesTestServer](https://github.com/itsme12345678910/WigglesTestServer) (принимает и журналирует команды, для локального теста указан 127.0.0.1:5591), [WigglesTestClient](https://github.com/itsme12345678910/WigglesTestClient) (посылает Tcl-команды в тестовую игру). Не подтверждено, что это общедоступный игровой сервер или матчмейкинг. Эти прямые ссылки опубликованы автором, однако открыть содержимое репозиториев не удалось. Ссылка на главный репозиторий в доступной индексированной копии форума усечена; точный URL не угадываю. Лицензия и актуальное состояние исходников не проверены.

**Развитие, 08–10.01.2025:** [обсуждение автора](https://wiggles.ruka.at/forum/viewtopic.php?t=2374), [отчёт о проблемах 10.01.2025](https://wiggles.ruka.at/forum/viewtopic.php?p=4218). Сетевая связь вынесена во внешние Java-компоненты, команды второй копии попадают в файл `remoteCommands`, который модифицированная Tcl-библиотека читает при вызовах `Tcl_EvalEx`. Ранний вариант с Tcl и потоками приводил к сбоям. Непереданные действия постепенно расходят состояния. Автор выделяет три препятствия:

1. Рисуемые мышью зелёные области копания не перехватывались выбранным Tcl-хуком.
2. Микродвижения, потягивания, рисование на стене также обходили перехват, вызывая расхождения.
3. Не удалось свободно менять `playerid`, что затрудняет PvP по разным кланам.

Уверенность высокая для отчёта автора о собственном моде, средняя для причины на уровне оригинального EXE. Автор поздней версии сообщает о видео в Discord, но публичный постоянный URL и таймкод не найдены. Успешный завершённый матч, работающий публичный сервер или надёжный современный MP-патч не подтверждены.

Для безопасной проверки этого мода — изолированная копия игры, локальный/доверенный тест, не открывать экспериментальный сетевой порт внешнему интернету: приём произвольных Tcl-команд несовместим с современной моделью недоверенных клиентов.

## Likely simulation model

### 1. Самое сильное первичное свидетельство: технический доклад SEK-Ost

Carsten Orthbandt, директор разработки SEK-Ost, **Game Scripting with Tcl**, Second European Tcl/Tk Users Meeting, Hamburg, 7–8 июня 2001. [Полные материалы конференции, PDF](https://www.eurotcl.eu/presentations/EuroTcl2001-AllPresentations.pdf), разделы 3.1, 3.4.1, 3.4.2 (с. 124 материалов для ключевого фрагмента); [дата конференции](https://wiki.tcl-lang.org/page/Second%2BEuropean%2BTcl%2BTk%2BUsers%2BMeeting).

> When running a networked game, method calls may transform into remote procedure calls on some other computer.

Это прямое подтверждение того, что объектные методы проектировались с возможностью удалённого исполнения (RPC). Доклад описывает исходную архитектуру: классы задают поведение, объекты имеют атрибуты, события, состояния и методы; действия низкого уровня реализует C++ (ходьба, сон, анимация), а окончание или ошибка действия могут запускать разные обработчики. Ссылки на объекты используют идентификатор либо `this`. Уверенность высокая для проектной архитектуры на момент выступления. Доклад предшествует релизу; не указывает, какие конкретные вызовы дошли до рабочего сетевого матча. Он также описывает отдельные интерпретаторы активных объектов, что не следует механически отождествлять с единственным контекстом, упомянутым автором мода 2025, без анализа сборок.

В публичном [каталоге Tcl-команд](https://wiggles.ruka.at/tipstricks/wiggles_tcl.html) дополнительно документированы средства AI по игрокам, идентификаторы владельцев, `map send`, `net version`, `get_mpstartpos`, игровое время и туман войны по владельцу. Дата и точная сборка HTML не указаны. Доклад 2001 (§3.4.2) говорит об автоматическом создании документации команд из C++-комментариев, но идентичность конкретного HTML этой сборке не доказана.

### 2. Как интерпретировать эти свидетельства

| Модель | Основание | Вывод |
|---|---|---|
| Объектные RPC / передача методов | Доклад Orthbandt, 2001, §3.4.1 | Подтверждённая предусмотренная возможность; точная маршрутизация и авторитет неизвестны |
| Сервер передаёт карту клиентам | Tcl `map send` | Документированная возможность. Вероятна хоть какая-то передача состояния карты, поэтому нельзя безоговорочно утверждать, что пересылался только seed |
| Отдельные команды владельцев / рас | `get_local_player`, `get_objownertype`, `set_owner`, `set_ownerrace` | Сильное основание для модели владельцев сущностей; не установлен сетевой контроль прав |
| Сервер-авторитет / client-server | `-server`, `map send`, RPC | Возможная, но не доказанная топология; можно также представить хост-авторитет или распределённую ответственность |
| Детерминированный lockstep | Нет опубликованных данных о тиках, порядке команд, RNG или хешах | Не доказан. Объектные RPC совместимы с разными архитектурами |
| Зеркалирование Tcl-команд двух локальных симуляций | phantom, 2024–2025 | Документированная фанатская модель, которая демонстрирует проблему пропущенных изменений, но не является исходной архитектурой |

Уверенность высокая в наличии перечисленных подсистем/API, неизвестная в конкретном сетевом поведении, если оно не подтверждено отдельно. Указанные имена команд служат поисковыми локаторами, а не гарантией, что команда сетевой режим активирует.

## Godot replication implications

Следующее — **проектная рекомендация**, не реконструкция протокола SEK. Предпочтительный начальный вариант: единый авторитетный хост (в перспективе headless dedicated server) с репликацией событий и версионированных изменений состояния. Это проще проверить, чем детерминированную симуляцию на каждом клиенте, особенно при сложных ИИ, динамических пещерах, физике и разных версиях платформ.

### 1. Структура

- `SessionConfig`: mode, seed, map_id, map_revision, ruleset/content_hash, список слотов с player_id, clan_id, team_id, human/AI и состоянием ready. Отдельно `account/session peer ID`, `player ID`, `owner ID`, `entity ID`; сетевой ID подключения нельзя использовать как постоянный ID мира.
- `WorldState`: сетка логических материалов/копания, пещеры, владельцы, инвентари, очереди задач, атрибуты и состояния всех сущностей, авторитетный игровой tick, состояние RNG, прогресс производства и цели сценария.
- `CommandBus`: одинаковый формат для ввода человека и ИИ, проверка владельца и допустимости; запрос → серверное решение → событие/изменение. Не исполнять полученные от клиента произвольные скрипты.
- `Simulation`: фиксированный логический шаг, например 10–20 Гц как экспериментальный параметр (не историческое значение); визуальная анимация и камера свободны по FPS. До измерений 2 человека, одна малая карта, затем увеличение масштаба.

### 2. Практическая матрица

| Действие | Запрос игрока (пример) | Авторитетное событие/state | Сетевой приоритет |
|---|---|---|---|
| Маркировка копания / ластик | DigMark(cells, owner), DigErase(cells) | Принятые метки и версии чанков | P0, reliable |
| Реальная выемка породы | Серверный этап задачи гнома | TerrainDelta(chunk_id, revision, cells), перестройка навигации | P0, reliable |
| Приказ, отмена, очередь | IssueOrder / CancelOrder | TaskAccepted/Rejected, очередь и статус | P0, reliable с порядковыми номерами |
| Движение | Цель и ID гнома | Позиция, скорость, action/state, tick; интерполяция | P0; периодический unreliable_ordered, коррекция reliable при необходимости |
| Подбор, выброс, передача | Pickup / Drop(item_id, entity_id, slot) | Атомарный InventoryDelta и владение предметом | P0, reliable, без дубликатов |
| Строительство | PlaceBlueprint / Pack / Unpack | Spawn/Despawn, стадия, ресурсы, прогресс | P0, reliable |
| ИИ, сон, еда, бой, рождение | Серверные задачи и события | Изменение потребностей, HP, action, spawn, смерть | P0/P1; значимые переходы надёжно, состояния по версии |
| Смена времени/пауза | Запрос хосту | TickClock, PauseState, speed_factor | P0, reliable для переходов |
| Кланы, команды и FOW | Выбор слота и серверные правила | owner/team/clan, видимые области по клиенту | P0/P1, надёжные изменения, фильтрация скрытых данных |
| Микропозы, пыль, звуки, частицы | Визуальный триггер | Только событие, если влияет на логику; остальное локальное | P2, loss-tolerant |

Базовый уровень — Godot 4 `ENetMultiplayerPeer`, RPC с разделёнными каналами надёжной игровой логики, ненадёжных частых обновлений и чата; `MultiplayerSpawner` и `MultiplayerSynchronizer` для подходящих сущностей, собственные компактные структуры для земли и инвентарей. Документация: [High-level multiplayer, Godot 4.4](https://docs.godotengine.org/en/4.4/tutorials/networking/high_level_multiplayer.html), [ENetMultiplayerPeer](https://docs.godotengine.org/en/stable/classes/class_enetmultiplayerpeer.html), [MultiplayerSynchronizer](https://docs.godotengine.org/en/stable/classes/class_multiplayersynchronizer.html). Важное ограничение: локальные instance ID/RID непригодны как универсальные идентификаторы объектов.

### 3. Этапы разработки и проверки

1. **P0.** Host + client, одна battle-карта; хост передаёт стартовый snapshot и дельты, локально рисуются лишь предварительные ghost/рамки. Кампания остаётся отдельным ruleset. Один сценарий: оба игрока копают, меняют задачу и конкурируют за один предмет.
2. **P0.** Изменение земли, навигация, инвентарь и строительство проверяются атомарно на сервере. Карта передаётся версиями чанков; seed используется только при идентичной версии генератора и подтверждении hash. Клиент после снапшота применяет события с более новыми revision/tick.
3. **P1.** Ввести логический hash мира, журнал первичных команд и результат каждого server tick. При несовпадении — диагностика секции/чанка и восстановление snapshot. Проверять серверный и клиентский хеши только по общедоступному данному клиенту подмножеству, без раскрытия скрытого мира.
4. **P1.** Разрыв сети, возвращение с прежним player_id, сохранение сервером на границе tick; загрузка требует совпадающий content_hash. Это новые функции порта. Пауза — согласованный серверный флаг, не независимая остановка SceneTree каждого клиента. Сначала не обещать миграцию хоста.
5. **P2.** После проверки стабильности — публичное лобби, наблюдатели, настройки команд, собственные правила Deathmatch/CTF/Counter-Wiggles только после исследования, иначе пометить как авторские режимы. LAN discovery и интернет-подключение могут делить один игровой протокол; NAT, relay и discovery относятся к новому транспорту.

Минимальные тесты принятия: двойной подбор одного ID (ровно один владелец), одновременное копание одного чанка, непроходимая цель после изменения породы, постройка в занятой клетке, рассинхронизация вследствие пропуска обновления и последующая коррекция, смерть гнома с инвентарём, пауза с незавершённой задачей, перезапуск хоста из сохранения, отключение клиента на 30 секунд и повторный вход. Тестировать искусственные задержки, потерю и переупорядочивание пакетов. Числа — предлагаемые тестовые настройки, не параметры оригинала.

| Открытый вопрос | Что могло бы его закрыть |
|---|---|

| Условия Deathmatch/CTF/Counter-Wiggles, отличия размеров и шаблонов battle-карт | Архив оригинальных init/map/rules scripts, руководство тестовой сборки |
| Протокол/сокеты, порты, TCP/UDP/DirectPlay, discovery, формат пакетов, хостинг | Публичная техдокументация, независимый трассировочный отчёт оригинальной сборки; не данные мода 2024 |
| Авторитет, порядок команд, тик, RNG, контроль расхождений, репликация позиций/анимаций и физики | Оригинальная сетевая техническая документация или воспроизводимая диагностика двух экземпляров |
| Совместные сохранения, reconnect, spectators, pause, resume, co-op кампании | Демонстрация двух соединённых клиентов и журнал поведения, включая вход/выход |
| Точная Config-Option, вызовы multiplayer.tcl/mpinit, способы включения в немецкой и английской версиях | Сохранённая инструкция SEK-Ost или старого форума, проверка нескольких версий |
| Действительная причина отключения MP | Современное интервью с разработчиками или архив баг-трекера; имеющееся свидетельство сообщает только о нестабильности |
| Состояние исходников фанатского мода и наличие новых исправлений | Доступный GitHub с неизменяемым commit URL, лицензией, релизами и проверкой двух клиентов |
| Точные версии и содержимое официальных release notes 707/814/844 | Чтение архивных текстов в исходной кодировке; контрольный поиск MP-исправлений и их отсутствия |

**Граница достоверности:** старые форумы Wiggles доступны через индексированные полные фрагменты поисковой выдачи, но прямой просмотр нескольких страниц возвращал HTTP 403; отдельные GitHub URL также не открылись. Поэтому утверждения о моде обозначены как отчёты автора, а не результат анализа его кода. Аутентичного общедоступного технического видео о сетевом матче 2001–2002 не найдено; таймкоды не выдуманы. Получить руководство полностью не удалось: [MogelPower](https://www.mogelpower.de/cheats/Wiggles_PC_21653.html) указывает на немецко-английское руководство, но документ не прочитан. Сведения о DLL и Java относятся к позднему моду, а не к историческому протоколу.

Главная рекомендация для порта: соблюдать наблюдаемые правила одиночной игры, но проектировать надёжную современную сеть отдельно, сохраняя семантические команды, ID объектов, общий порядок изменений карты, состояния и часы на сервере. Именно документированный объектный API — самая полезная историческая зацепка.
